# 检索增强进阶：压缩与多查询

第 11 章的 `VectorStoreRetriever` 把命中的整块文档塞进提示词。但整块里常含无关句子，既浪费 Token 又干扰模型。本章介绍两种「检索增强」手段。

## 1. ContextualCompressionRetriever：压缩检索结果

思路：先正常检索，再用一个 LLM 把每块「与问题相关」的句子抽出来，无关内容丢弃：

```ts
import { ContextualCompressionRetriever } from "langchain/retrievers/contextual_compression";
import { LLMChainExtractor } from "langchain/retrievers/document_compressors/chain_extract";
import { ChatOpenAI } from "@langchain/openai";

const compressor = new ContextualCompressionRetriever({
  baseCompressor: LLMChainExtractor.fromLLM(
    new ChatOpenAI({ model: "gpt-4o-mini" })
  ),
  baseRetriever: vectorStore.asRetriever({ k: 6 }),
});

const docs = await compressor.getRelevantDocuments("退款流程是什么？");
```

<Callout type="info" title="压缩=再省一次调用">
压缩器会对每块文档额外调用一次 LLM 做抽取，用少量成本换回更干净、更短的上下文，长文档场景收益明显。
</Callout>

## 2. MultiQueryRetriever：一个提问，多路检索

用户问题往往表述单一，召回不足。多查询检索器用 LLM 把原问题改写成多个不同角度的问法，分别检索后合并去重：

```ts
import { MultiQueryRetriever } from "langchain/retrievers/multi_query";

const multiRetriever = MultiQueryRetriever.fromLLM(
  new ChatOpenAI({ model: "gpt-4o-mini" }),
  vectorStore.asRetriever({ k: 3 })
);

const docs = await multiRetriever.getRelevantDocuments("怎么重置密码？");
// 内部可能改写为「找回密码」「密码丢失怎么办」等再检索
```

## 3. 组合使用

压缩与多查询可叠加：先用多查询扩大召回，再用压缩提纯，最后喂给模型：

```ts
const retriever = new ContextualCompressionRetriever({
  baseCompressor: LLMChainExtractor.fromLLM(model),
  baseRetriever: MultiQueryRetriever.fromLLM(model, baseRetriever),
});
```

<Callout type="tip" title="何时上增强">
单块命中已够准 → 不必增强；召回不足或上下文太长 → 先试 MultiQuery，仍噪声大再上压缩。两者都增加 LLM 调用，按语料规模权衡。
</Callout>

<Callout type="warn" title="别无限叠加">
每加一层增强都多一次模型调用与延迟。先用 LangSmith（第 14 章）对比「加前/加后」的回答质量，确认收益再保留。
</Callout>

**完整对比脚本**

```ts
// compare-multiquery.ts
import "dotenv/config";
import { MemoryVectorStore } from "langchain/vectorstores/memory";
import { OpenAIEmbeddings, ChatOpenAI } from "@langchain/openai";
import { RecursiveCharacterTextSplitter } from "@langchain/textsplitters";
import { TextLoader } from "langchain/document_loaders/fs/text";
import { MultiQueryRetriever } from "langchain/retrievers/multi_query";
import { ChatPromptTemplate } from "@langchain/core/prompts";
import { StringOutputParser } from "@langchain/core/output_parsers";
import type { Document } from "@langchain/core/documents";

const raw = await new TextLoader("./docs/handbook.md").load();
const splits = await new RecursiveCharacterTextSplitter({
  chunkSize: 400,
  chunkOverlap: 40,
}).splitDocuments(raw);

const store = await MemoryVectorStore.fromDocuments(splits, new OpenAIEmbeddings());
const llm = new ChatOpenAI({ model: "gpt-4o-mini", temperature: 0 });

// ---------- A：基础检索器 ----------
const base = store.asRetriever({ k: 3 });

// ---------- B：多查询检索器 ----------
const multi = MultiQueryRetriever.fromLLM({
  llm,
  retriever: store.asRetriever({ k: 3 }),
  verbose: true,        // 打开后能看到 LLM 改写出的几个问法
  queryCount: 3,        // 改写成 3 个变体
});

// 选一个「表述与文档用词不一致」的问题，最能体现差异
const question = "密码忘了怎么办？";

const baseDocs = await base.invoke(question);
const multiDocs = await multi.invoke(question);

// ---------- 量化对比 ----------
function key(d: Document) {
  return d.pageContent.slice(0, 80);
}

const baseKeys = new Set(baseDocs.map(key));
const newOnes = multiDocs.filter((d) => !baseKeys.has(key(d)));

console.log("=== 命中块数 ===");
console.log("基础检索：", baseDocs.length);
console.log("多查询检索：", multiDocs.length, `（其中 ${newOnes.length} 块是基础检索没找到的）`);

console.log("\n=== 多查询新增的内容 ===");
newOnes.forEach((d, i) =>
  console.log(`[新增 ${i + 1}] ${d.pageContent.slice(0, 70).replace(/\n/g, " ")}…`)
);

console.log("\n=== 上下文总长度 ===");
console.log("基础：", baseDocs.reduce((s, d) => s + d.pageContent.length, 0), "字符");
console.log("多查询：", multiDocs.reduce((s, d) => s + d.pageContent.length, 0), "字符");
```

**接上生成，对比回答完整性**

```ts
const prompt = ChatPromptTemplate.fromTemplate(
  "只根据下面的上下文回答，若没写就说不知道。\n上下文：\n{context}\n\n问题：{question}"
);

async function answer(docs: Document[]) {
  return prompt
    .pipe(llm)
    .pipe(new StringOutputParser())
    .invoke({
      context: docs.map((d) => d.pageContent).join("\n---\n"),
      question,
    });
}

console.log("\n【基础检索的回答】\n" + (await answer(baseDocs)));
console.log("\n【多查询检索的回答】\n" + (await answer(multiDocs)));
```

**典型结果**

`verbose: true` 会先打印出 LLM 生成的改写：

```
生成的查询变体：
1. 如何重置账户密码？
2. 登录密码丢失的找回流程是什么？
3. 忘记密码后怎样恢复账号访问权限？
```

然后：

| 指标 | 基础检索 | 多查询检索 |
|---|---|---|
| 命中块数 | 3 | 6（去重后） |
| 上下文长度 | 约 1200 字符 | 约 2400 字符 |
| 检索耗时 | 约 300 ms | 约 1800 ms（含一次改写 LLM 调用 + 3 次并行检索） |
| 回答内容 | 只说了「在登录页点『忘记密码』」 | 完整覆盖了自助重置、绑定手机验证、以及**联系管理员人工重置**这条基础检索漏掉的路径 |

**差异从何而来？** 文档里那段讲人工重置的内容用的措辞是「**账号无法访问时的人工恢复**」，和用户说的「密码忘了」字面差距很大，单一查询的向量相似度不够高，排在第 5 名进不了 top-3。而改写出的第 3 个变体「恢复账号访问权限」几乎是原文用词，一下就命中了。

**这也说明了 MultiQuery 的适用边界：**

| 什么时候有效 | 什么时候是浪费 |
|---|---|
| 用户口语表述 vs 文档书面语差异大 | 用户问法和文档用词高度一致 |
| 问题涉及多个方面（「怎么用，有什么坑」） | 单点事实型问题（「端口号是多少」） |
| 语料规模大、同一主题分散在多处 | 语料就几十个块，`k` 调大即可 |
| 召回不足（答案明显不完整） | 已经召回充分，只是噪声多 → 该上压缩而非多查询 |

**成本必须算清楚**

多查询的开销是**一次改写 LLM 调用 + N 倍的向量检索 + N 倍的上下文 Token**。上面的例子里延迟涨了 6 倍、生成阶段的输入 Token 翻倍。所以课文才强调「先实测收益再保留」。

**判断收益的实用方法**：准备 10–20 个真实问题，人工标注每题的「标准答案应覆盖哪几个要点」，然后统计两种检索下的**要点覆盖率**：

```ts
const cases = [
  { q: "密码忘了怎么办？", points: ["自助重置", "手机验证", "联系管理员"] },
  // …更多用例
];

for (const c of cases) {
  const ans = await answer(await multi.invoke(c.q));
  const hit = c.points.filter((p) => ans.includes(p)).length;
  console.log(`${c.q}  覆盖 ${hit}/${c.points.length}`);
}
```

覆盖率提升明显才值得为它付出延迟和成本。这套用例集稍加整理，就是第 24 章 LangSmith 数据集评估的雏形。

**组合技**：如果多查询让上下文变得又长又杂，可以在它外面再套一层 `ContextualCompressionRetriever`——先扩大召回，再提纯压缩，两者互补（见课文第 3 节）。

## 小结

- `ContextualCompressionRetriever` 用 LLM 抽取相关句，压缩上下文
- `MultiQueryRetriever` 改写多视角问法，提升召回
- 两者可组合：多查询扩召回 + 压缩提纯
- 增强以额外调用为代价，需实测收益
