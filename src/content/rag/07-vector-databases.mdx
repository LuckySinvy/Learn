# 向量数据库概览

向量数据库专门解决「从百万级向量里快速找出最相似的 K 个」这个问题。它们用 **ANN（近似最近邻）索引** 把暴力检索的 O(N) 降到亚线性，支撑生产级规模。

## 1. 为什么不能直接用 SQL LIKE

- `LIKE` 是字符匹配，不懂语义（"车" 匹配不到 "汽车"）
- 百万向量暴力算余弦，每次查询都要扫全库，延迟爆炸
- 缺少面向向量的索引结构（HNSW、IVF 等）

<Callout type="info" title="向量库做的是 ANN 搜索">
精确最近邻（Exact NN）太慢，工程上接受「近似但够快」的结果，即 ANN。常用算法：HNSW（图）、IVF（倒排）、PQ（量化压缩）。
</Callout>

## 2. 主流方案对比

| 方案 | 形态 | 部署 | 适用规模 | 特点 |
|---|---|---|---|---|
| **FAISS** | 库（CPU/GPU） | 嵌入进程 | 单机百万级 | 极快、轻量、无服务化 |
| **Milvus** | 独立服务 | 容器/K8s | 十亿级 | 分布式、功能全、运维重 |
| **Qdrant** | 独立服务 | 容器 | 百万~亿级 | Rust、易用、过滤强 |
| **Pinecone** | 全托管 SaaS | 云端 | 弹性 | 免运维、按量付费、数据出网 |
| **PGVector** | Postgres 插件 | 已有 PG | 百万级 | 复用现有 DB、事务一致 |

## 3. 各自的取舍

```text
FAISS      → 原型 / 单机 / 不想起服务，但需自己管持久化与并发
Milvus     → 超大规模、需要分布式与多租户，能接受较重运维
Qdrant     → 想要独立服务又怕运维重，过滤与元数据支持好
Pinecone   → 不想碰基础设施，接受 SaaS 成本与数据出网
PGVector   → 已经用 Postgres，希望事务+向量一把梭，规模不大
```

<Callout type="warn" title="规模决定选型">
个人项目或百万以内：FAISS / PGVector 足够。千万到十亿级、要水平扩展：Milvus / Qdrant 集群。别为小项目上重武器，也别用单机方案硬扛海量数据。
</Callout>

## 4. FAISS 最小示例

```python
import faiss
import numpy as np

dim = 768
index = faiss.IndexFlatL2(dim)        # 精确 L2；生产用 IndexHNSWFlat
xb = np.random.rand(10000, dim).astype("float32")
index.add(xb)

xq = np.random.rand(5, dim).astype("float32")
D, I = index.search(xq, k=4)          # 最近 4 个的 距离D 与 下标I
```

## 5. PGVector 最小示例

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE docs (id serial, content text, emb vector(768));

INSERT INTO docs (content, emb)
VALUES ('退款政策', '[0.1,0.2,...,0.3]');

SELECT id, content, emb <-> '[0.1,0.2,...,0.3]' AS dist
FROM docs ORDER BY emb <-> '[0.1,0.2,...,0.3]' LIMIT 5;
```

<Callout type="tip" title="元数据过滤很关键">
真实系统常需「只在技术文档里搜」「只搜 2024 年后的」。Qdrant、Milvus、PGVector 都支持在向量检索的同时按元数据过滤，选型时确认过滤能力是否满足。
</Callout>

**参考答案：**

**第一步：算出向量总数与内存占用**

```python
docs = 5000                 # 文档数
pages_per_doc = 20          # 平均页数
chars_per_page = 1200       # 每页字数
chunk_size = 500
overlap_factor = 1.2        # overlap 会让 chunk 数比理论值多 ~20%

chunks_per_doc = pages_per_doc * chars_per_page / chunk_size * overlap_factor
total_vectors = int(docs * chunks_per_doc)

dim = 1024                  # bge-large-zh
bytes_per_vec = dim * 4     # float32
raw_gb = total_vectors * bytes_per_vec / 1024**3

print(f"向量总数 ≈ {total_vectors:,}")
print(f"裸向量   ≈ {raw_gb:.2f} GB")
print(f"HNSW 索引 ≈ {raw_gb * 1.5:.2f} GB（含图结构开销）")
print(f"加原文与元数据 ≈ {raw_gb * 2.5:.2f} GB（整机内存预算）")
```

输出：

```text
向量总数 ≈ 288,000
裸向量   ≈ 1.10 GB
HNSW 索引 ≈ 1.65 GB
加原文与元数据 ≈ 2.75 GB（整机内存预算）
```

**估算时的三个经验系数**（很多人只算裸向量，结果上线内存爆掉）：

- **overlap 系数 1.2**：15% overlap 大约让 chunk 数多两成。
- **HNSW 系数 1.5**：图索引的邻居链表本身要占约 50% 额外空间。
- **原文系数**：原文和 metadata 通常与向量同量级，别忘了算。

**第二步：按规模对号入座**

| 向量总数 | 首选 | 理由 |
|---|---|---|
| 小于 10 万 | **FAISS** 或 **PGVector** | 单机内存装得下，不值得起独立服务 |
| 10 万 – 1000 万 | **Qdrant** 或 **PGVector** | 需要过滤与持久化，但单节点仍够用 |
| 1000 万 – 10 亿 | **Milvus** / Qdrant 集群 | 必须分片、副本，接受较重运维 |
| 任意规模但不想运维 | **Pinecone** | 前提是数据允许出网 |

上面算出的 28.8 万落在第二档，**首选 Qdrant**。

**第三步：用规模之外的三个因素做终选**

规模只是入场券，真正决定选型的往往是另外三条：

1. **合规是一票否决项**。只要数据不许出域，Pinecone 直接出局，无论它多省事。这个判断要**放在最前面**，别等选完了才发现过不了安全评审。
2. **有没有现成的 Postgres？** 如果团队已经在跑 PG、且规模在百万以内，PGVector 的性价比无人能敌——不用新增组件、不用学新运维、事务和向量在同一个库里保证一致，备份复用现有方案。为一个百万级知识库单独引入 Milvus 集群，是典型的过度设计。
3. **元数据过滤能力够不够？** 如果业务需要「按部门 + 按密级 + 按时间范围」组合过滤，FAISS 就很吃力（它本身不管元数据，得自己在外层维护映射），这时 Qdrant 的 payload 过滤会省掉大量自研代码。

**一条实用建议**：不确定时**先用 FAISS 或 PGVector 把链路跑通**，因为向量库在 RAG 里是最容易替换的一环——接口无非「加向量、查 top-k」。先把切分、Embedding、Prompt 这些真正影响效果的环节调好，等规模真的顶不住了再迁移，迁移成本远低于一开始就上重武器的成本。
</Answer>
</Callout>

## 小结

- 向量库用 ANN 索引做快速相似搜索，LIKE 做不到语义检索
- FAISS 轻量单机；Milvus 海量分布式；Qdrant 易用；Pinecone 免运维；PGVector 复用 PG
- 选型由规模、运维成本、合规共同决定
