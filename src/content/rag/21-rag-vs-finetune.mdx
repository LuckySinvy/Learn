# RAG 与微调如何取舍

第 1 章提到 RAG 与微调互补，本章给出可落地的**决策框架**，帮你判断该上哪一个、还是两个都要。

## 1. 先问四个问题

| 维度 | 倾向 RAG | 倾向微调 |
|---|---|---|
| 知识是否频繁更新 | 是，改库即生效 | 否，知识相对稳定 |
| 答案需引用原文溯源 | 是，必须可追溯 | 否，重在表达 |
| 目标是改「知识」还是改「行为/风格」 | 知识 → RAG | 风格/格式 → 微调 |
| 标注数据是否充足 | 不需要，有文档即可 | 需大量高质量样本 |

<Callout type="info" title="一句话判据">
要「接上最新、可溯源的事实」用 RAG；要「让模型学会一种说话/做事方式」用微调。
</Callout>

## 2. 典型决策树

```text
问题需要引用最新内部文档吗？ ─是→ RAG
   │否
要改变输出格式/语气/任务行为吗？ ─是→ 微调
   │否
数据会每周变吗？ ─是→ RAG
   │否
两者都不强烈 → 先用 RAG（更快更稳）
```

## 3. 组合使用更常见

很多成熟系统**RAG + 轻量微调**双管齐下：

```python
# RAG 负责「事实」，微调负责「格式」
answer = rag_generate(question)        # 基于检索原文作答（事实准）
# 模型已微调为固定输出结构：先给结论，再列引用
```

## 4. 成本与风险对比

| 项 | RAG | 微调 |
|---|---|---|
| 上线速度 | 快，接知识库即可 | 慢，需准备数据 + 训练 |
| 迭代成本 | 低，改文档 | 高，重新训练 |
| 幻觉风险 | 低（有原文） | 中（知识固化权重） |
| 数据门槛 | 极低 | 需标注样本 |

<Callout type="warn" title="别用微调解决知识更新">
若你的真实诉求是「让模型知道最新政策」，微调是错误解法——训练完政策又变了，且无法给出处。这种情况 RAG 才是正解。
</Callout>

<Callout type="tip" title="默认从 RAG 起步">
不确定时先上 RAG：它成本低、可溯源、易迭代。当评测发现「风格/格式总不对」且数据充足时，再补一道微调。
</Callout>

<Answer>
**参考答案：**

**三个示范需求走一遍决策树**

**需求 1：「客服要能准确回答最新的退换货政策」**

```text
需要引用最新内部文档吗？ ─是→ RAG ✅
```

政策每季度都在改，且客服说的话可能成为纠纷证据，必须能指到原文。**结论：RAG**，且必须开引用溯源（第 12 章）。

**需求 2：「所有回复都要按『先致歉→给方案→留联系方式』的固定结构」**

```text
需要引用最新内部文档吗？ ─否
要改变输出格式/语气/任务行为吗？ ─是→ 微调 ✅
```

但先别急着训——**这个需求 90% 的情况下 Prompt 就能解决**。只有当你发现「Prompt 写得再详细，模型在长对话里还是会跑偏」，且已积累上千条人工标注的优质回复，微调才划算。**结论：先试 Prompt，不行再微调**。

**需求 3：「用公司内部术语，按标准格式，回答关于最新产品的问题」**

```text
需要引用最新内部文档吗？ ─是→ RAG（管事实）
同时要改变输出格式？    ─是→ 微调（管格式）
```

**结论：两者组合**。RAG 保证产品参数是最新的、可溯源的；微调保证输出结构统一。分工清晰，互不干扰。

**重点自查：三个最常见的误判**

**误判一：「模型不认识我们的产品名/内部黑话，得微调让它学会」**

❌ 错。这是**知识缺失**，不是能力缺失。把产品手册、术语表放进知识库即可，成本是微调的百分之一，而且明天出新产品，改文档就生效，不用重训。

真正需要微调的信号是：**资料已经给足了，Prompt 也写清楚了，模型依然做不对这个任务**。如果你还没试过「把资料喂给它」，就没资格判断需不需要微调。

**误判二：「知识库文档太多，模型记不住，微调进权重里就记住了」**

❌ 错，而且是危险的错。微调**不是**一种可靠的知识注入方式：

- 训练完的知识是模糊的、不可溯源的，你无法让它说出「这条规定在手册第几页」
- 知识一变就得重训，一次训练的成本够跑几十万次检索
- 更糟的是，微调注入的知识会与模型原有知识混在一起，出错时**无法定位、无法修复**，只能重训碰运气

文档多是**检索问题**（该优化切分、加重排、做元数据过滤），不是模型记忆容量问题。

**误判三：「微调后模型更懂我们领域，幻觉会减少」**

❌ 恰恰相反，常常更严重。微调让模型对该领域**更自信**，而自信 + 没有原文约束 = **更流畅、更像真的、更难被发现的幻觉**。RAG 的原文约束才是抑制幻觉的正解。

**一张自查表**

拿你的每个需求过一遍，勾中任意一条「RAG 信号」就别考虑微调：

| RAG 信号 | 微调信号 |
|---|---|
| 答案会随时间变化 | 输出结构/语气始终固定 |
| 用户可能追问「依据是什么」 | 没人关心出处，只看表达 |
| 有文档但没有标注数据 | 有上千条高质量输入输出对 |
| 内容按部门/密级需要权限隔离 | 全员通用，无权限区分 |
| 需要快速上线、频繁迭代 | 可接受数周训练周期 |

**最后一条实践原则**

**默认从 RAG 起步，把微调当作「RAG 已经做到极致后的补充」。** 因为 RAG 的失败是可诊断的——检索日志能告诉你哪一步出了问题；而微调的失败往往只能得到一个「效果不太行」的模糊结论，调试成本高一个数量级。

顺序应该是：Prompt 工程 → RAG → RAG 调优（切分/重排/改写）→ 仍不满足特定行为要求 → 才轮到微调。绝大多数团队在前三步就能解决问题。
</Answer>
</Callout>

## 小结

- 判据：知识时效与溯源 → RAG；风格行为 → 微调
- 决策树：先问是否需引用最新文档、是否改行为、数据变不变
- 常见组合 RAG + 轻量微调，各管事实与格式
- 不确定时默认 RAG 起步，再按需补微调
