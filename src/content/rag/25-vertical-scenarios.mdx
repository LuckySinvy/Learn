# 垂直场景：代码与法律

通用 RAG 套路在垂直领域常水土不服。本章以**代码**与**法律**两个高频场景为例，讲适配要点。

## 1. 代码检索 RAG

代码不是散文，切分时不能破坏语法结构：

```python
# 按「函数 / 类」为粒度切分，而非固定字数
def chunk_by_symbol(code):
    return [extract_function(fn) for fn in parse_ast(code)]

# 用代码专用 Embedding（如针对代码的向量模型）效果更好
vec = code_embedding(chunk)
```

<Callout type="info" title="代码要保留结构上下文">
光给一个函数往往不够——调用方、所属模块、依赖才决定含义。父子文档（第 14 章）在此特别有用：检索命中函数，返回其所在文件上下文。
</Callout>

要点：
- 优先按 AST/符号切分，避免截断语句
- 用代码专用嵌入模型，而非通用文本模型
- 检索时附上文件路径、导入关系，帮模型定位

## 2. 法律合同 RAG

法律文本长、条款相互引用、措辞严谨，错一字意思全变：

```python
# 保留条款编号层级，检索结果带出处条款号
hits = retrieve(question, k=5)
for h in hits:
    print(h["clause_no"], h["text"])   # 如「第 8.2 条」
```

要点：
- **切分保留条款边界**，别把「8.2 条」拆成两半
- 答案必须**精确引用条款号**，便于律师核验
- 长合同用父子文档：命中小条款，返回整章上下文防断章取义

<Callout type="warn" title="法律场景严禁编造条款">
幻觉在医疗/法律下后果严重。务必开第 20 章的 Self-RAG 反思校验，且生成时强制「每条结论附条款号」，无出处即拒答。
</Callout>

## 3. 两场景对比

| 维度 | 代码 RAG | 法律 RAG |
|---|---|---|
| 切分粒度 | 函数 / 类（AST） | 条款（保留编号） |
| 嵌入模型 | 代码专用 | 通用或更细粒度 |
| 核心风险 | 结构丢失、缺上下文 | 断章取义、幻觉条款 |
| 必做校验 | 父子文档补全上下文 | 强制引用 + 反思校验 |

<Callout type="tip" title="垂直领域先改切分与嵌入">
多数垂直 RAG 的失败不在模型，而在「切分破坏了领域结构」。先按领域结构切分、选对嵌入模型，再用指标验证。
</Callout>

**两种切分的实现**

```python
import ast
from langchain_text_splitters import RecursiveCharacterTextSplitter

source = open("payment.py", encoding="utf-8").read()

# ---------- 方式 A：固定 200 字硬切 ----------
def split_fixed(code, size=200, overlap=30):
    sp = RecursiveCharacterTextSplitter(chunk_size=size, chunk_overlap=overlap)
    return [{"text": t, "meta": {"type": "fixed"}} for t in sp.split_text(code)]

# ---------- 方式 B：按 AST 符号切分 ----------
def split_by_symbol(code, filename="payment.py"):
    tree = ast.parse(code)
    lines = code.splitlines()
    chunks = []

    # 模块级 import 单独成块，作为所有函数的公共上下文
    imports = [l for l in lines
               if l.startswith(("import ", "from ")) and l.strip()]
    header = "\n".join(imports)

    for node in ast.walk(tree):
        if not isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef, ast.ClassDef)):
            continue
        body = "\n".join(lines[node.lineno - 1: node.end_lineno])
        # 关键：给每个符号块补上「它是谁、在哪、依赖什么」
        signature = f"# 文件: {filename}\n# 符号: {node.name}\n{header}\n\n"
        chunks.append({
            "text": signature + body,
            "meta": {"type": "symbol", "name": node.name,
                     "file": filename, "lineno": node.lineno,
                     "calls": [n.func.id for n in ast.walk(node)
                               if isinstance(n, ast.Call)
                               and isinstance(n.func, ast.Name)]},
        })
    return chunks
```

注意方式 B 里的两个加工：**补上 import 头** 和 **记录调用关系（`calls`）**。这是代码 RAG 与普通文本 RAG 最大的区别——代码片段的含义高度依赖它的外部环境，光有函数体本身信息量不够。

**观察结论**

1. **固定切分产生的是「语法残骸」。** `fee = _apply_fee(` 这种从括号中间断开的片段，人看不懂，模型更看不懂。而且这些残片的向量质量极差——一段语法不完整的代码，Embedding 模型也编码不出有意义的语义。

2. **符号切分让两个相关函数**都完整地**进了上下文。** 模型能清楚看到 `calculate_refund` 调用了 `_apply_fee`，从而准确回答「手续费在计算总额后、返回前扣除，且有 1 元下限」。

3. **块数从 47 降到 9。** 更少但更完整的块，意味着 `top_k=3` 就能覆盖足够信息，token 效率反而更高。

**再进一步：用调用图补全上下文**

符号切分解决了「片段完整」，但还有一个问题：如果只召回了 `calculate_refund`，没召回 `_apply_fee`，模型仍然不知道手续费怎么算。这时用第 14 章的父子文档思路，配合前面记录的 `calls` 元数据自动补齐：

```python
def retrieve_code(question, k=3, expand=True):
    hits = rerank(question, retrieve(embed(question), top_k=15))[:k]
    if not expand:
        return hits

    picked = {h["meta"]["name"] for h in hits}
    extra = []
    for h in hits:
        for callee in h["meta"].get("calls", []):
            if callee not in picked and callee in symbol_index:
                extra.append(symbol_index[callee])   # 把被调用的函数一并带上
                picked.add(callee)
    return hits + extra[:3]        # 限制扩展数量，避免撑爆预算
```

这一步让「跨函数理解」从碰运气变成确定性的——**只要命中了入口函数，它的依赖会被自动拉进来**。这其实就是第 19 章图检索思想在代码场景的轻量应用：调用关系天然就是一张图。

**代码 RAG 的四条要点**

1. **AST 解析失败要有降级。** 代码文件可能语法错误、可能是 Jinja 模板、可能是你不支持的语言。`ast.parse` 抛异常时要 fallback 到「按空行 + 缩进」的启发式切分，不能让整个文件被跳过。

2. **超长函数仍要二次切分。** 有些遗留代码里一个函数几百行，超过 Embedding 上限。这时按「函数内的逻辑块 + 保留函数签名作为每块的头部」再切，确保每块都知道自己属于谁。

3. **用代码专用 Embedding。** 通用中文模型对 `def`、`return`、驼峰命名的理解很弱。代码检索场景要选在代码语料上训练过的模型，差距通常在 10 个点以上。

4. **元数据要包含文件路径和行号。** 这样引用溯源能精确到 `payment.py:42`，用户可以直接跳转——这在代码场景比「来自某文件」有用得多。

**法律场景的同构解法**

法律 RAG 的坑与代码几乎一模一样，只是把「函数」换成「条款」：

```python
CLAUSE = re.compile(r"^第\s*([\d一二三四五六七八九十]+(?:\.\d+)*)\s*[条款]")

def split_by_clause(text):
    chunks, cur, no = [], [], None
    for line in text.splitlines():
        m = CLAUSE.match(line.strip())
        if m:
            if cur:
                chunks.append({"text": "\n".join(cur),
                               "meta": {"clause_no": no}})
            cur, no = [line], m.group(1)
        else:
            cur.append(line)
    if cur:
        chunks.append({"text": "\n".join(cur), "meta": {"clause_no": no}})
    return chunks
```

「第 8.2 条被从中间切断」造成的后果和「函数被截断」一样严重——甚至更糟，因为法律文本里一个「但书」条款被切掉，意思可能完全反转。所以课文那句「垂直 RAG 的失败多数不在模型，而在切分破坏了领域结构」，在这两个场景里得到了同样的印证。

## 小结

- 代码 RAG：按 AST/符号切分 + 代码专用嵌入 + 父子文档补上下文
- 法律 RAG：保留条款边界、强制引用条款号、开反思校验防幻觉
- 两类场景失败多在「切分破坏结构」，先改切分与嵌入
