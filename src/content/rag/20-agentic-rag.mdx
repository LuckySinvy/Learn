# Agentic RAG 与 Self-RAG

基础 RAG 是「**一问一检索**」：无论问题难易，永远先召回再生成。Agentic RAG 与 Self-RAG 把控制权交给模型——它自己判断**要不要检索、检索几次、答案够不够好**。

## 1. 固定流程的局限

```text
固定 RAG:  提问 → 检索(top5) → 生成
问题: 简单问候「你好」也被迫检索；复杂问题只检索一次可能不够
```

真正的难点是「检索」本身也该是**自适应**的。

## 2. Agentic RAG：模型调度检索

把检索封装成工具，由 Agent 决定是否调用、调用几次：

```python
from langchain_core.tools import tool

@tool
def retrieve(query: str) -> str:
    """当回答需要外部知识时，用此工具检索知识库。"""
    return rag_search(query)

# Agent 自主决定：先答一部分 → 发现缺知识 → 调 retrieve → 再续答
agent.run("对比我们三款产品的退款政策，并指出差异")
```

适合需要**多步、跨来源**检索的场景，检索次数随问题动态变化。

## 3. Self-RAG：带自反思的生成

Self-RAG 引入特殊的**反思标记（reflection tokens）**，让模型在生成中自我校验：

```text
[检索?] 需要 → 调检索 → [相关性?] 高 → 引用片段作答
                                  → [是否支持?] 否 → 重新检索或声明不知
```

核心四问：**要不要检索 / 检索到的相关吗 / 内容支持论断吗 / 整体没问题吗**。任一环节不过关就重试或拒答。

<Callout type="info" title="Agentic 管「何时检」，Self-RAG 管「检得对不对」">
两者可叠加：Agent 决定检索策略，Self-RAG 的反思机制保证每一步质量。共同目标都是「减少无效检索、抑制幻觉」。
</Callout>

## 4. 实现要点

```python
# Self-RAG 思路（示意）：生成中插入校验
for step in generate(question):
    if step.needs_retrieval and not step.supported_by(context):
        context = retrieve(step.clarify())   # 带反思地补充检索
    if not step.faithful(context):
        step = regenerate(context)            # 重写使其忠于原文
```

<Callout type="warn" title="反思越多越慢越贵">
每加一轮反思就多一次 LLM 调用。给「最大检索/生成轮数」设上限，避免为了完美而无限循环。
</Callout>

## 5. 何时用

- 问题简单、答案稳定 → 普通 RAG 足够，别上 Agent 增加延迟
- 多源、需推理、易幻觉 → Agentic + Self-RAG 显著提升质量

<Callout type="tip" title="用指标决定是否值得">
对照第 13 章的忠实度指标：若基础 RAG 幻觉率高，再引入 Self-RAG 的反思校验，用分数变化验证收益。
</Callout>

**参考答案：**

这本质上是在实现 **Self-RAG 四问中的第二问——「检索到的相关吗」**，并在不相关时触发自我修正。

**实现：带反思重试的检索工具**

```python
import logging
from langchain_core.tools import tool

log = logging.getLogger(__name__)

RELEVANCE_THRESHOLD = 0.5      # 重排分阈值，需在自己语料上标定
MAX_REWRITE = 2                # 最多改写 2 次，防无限循环


def judge_relevance(question, chunks):
    """
    两级判断：先用重排分（快且便宜），分数在灰区时才用 LLM 复核（准但贵）
    返回 (是否相关, 判断依据)
    """
    if not chunks:
        return False, "no_hits"

    top_score = chunks[0]["rerank_score"]
    if top_score >= 0.7:
        return True, f"high_score={top_score:.2f}"
    if top_score < 0.3:
        return False, f"low_score={top_score:.2f}"

    # 0.3–0.7 灰区：交给 LLM 判断
    verdict = llm(f"""判断下面的资料能否回答该问题。只回答「能」或「不能」。
问题：{question}
资料：{chunks[0]['text'][:500]}""").strip()
    ok = verdict.startswith("能")
    return ok, f"llm_judge={verdict}"


def rewrite_query(question, failed_query, chunks):
    """带失败反馈的改写——告诉模型上次为什么没检索到"""
    sample = chunks[0]["text"][:200] if chunks else "（无结果）"
    return llm(f"""上一次检索没有找到能回答问题的资料。
原问题：{question}
上次检索词：{failed_query}
召回的无关内容示例：{sample}

请给出一个更可能命中的检索词。可以：
- 替换成文档中更可能出现的正式术语
- 拆解成更聚焦的子问题
- 补全省略的实体

只输出新的检索词，不要解释。""").strip()


@tool
def search_knowledge(query: str) -> str:
    """检索企业知识库。会自动判断结果相关性，不相关时改写查询重试。"""
    trace = []
    current_q, chunks = query, []

    for attempt in range(MAX_REWRITE + 1):
        chunks = rerank(current_q, retrieve(embed(current_q), top_k=20))[:5]
        ok, why = judge_relevance(current_q, chunks)

        trace.append({
            "attempt": attempt,
            "query": current_q,
            "top_score": chunks[0]["rerank_score"] if chunks else 0.0,
            "relevant": ok,
            "why": why,
        })

        if ok:
            break
        if attempt < MAX_REWRITE:
            current_q = rewrite_query(query, current_q, chunks)
            log.info("改写查询: %s -> %s", trace[-1]["query"], current_q)

    log.info("retrieval trace: %s", trace)

    # 关键：反思后仍不相关，要如实说明，不能把噪声塞给 Agent
    if not trace[-1]["relevant"]:
        return ("知识库中未找到能回答该问题的资料。"
                "请勿基于以下内容作答，如需帮助请考虑转人工。")

    return "\n".join(f"[{i+1}] {c['text']}" for i, c in enumerate(chunks))
```

**典型结果**

```text
无反思:  context_precision=0.48  context_recall=0.55
带反思:  context_precision=0.73  context_recall=0.81
平均检索次数: 1.0 → 1.6    平均延迟: 0.9s → 2.3s
```

**结果解读：收益真实，但代价也真实**

精度涨了 25 个点，代价是延迟涨了 1.5 倍。这正是本章反复强调的权衡——**反思不是免费的**。所以关键设计是「只在需要时才反思」：上面代码里，分数高于 0.7 直接放行，根本不调 LLM 判断，因此**大部分请求（简单问题）的延迟完全不受影响**，只有真正检索失败的那部分才会走重试路径。这也是为什么统计出来的平均检索次数是 1.6 而不是 3。

**四个设计要点**

1. **两级判断是成本控制的关键。** 每次都用 LLM 判相关性太贵（每次检索多一次调用）。用重排分做粗筛，只在灰区（0.3–0.7）调 LLM，能砍掉 80% 以上的判断开销。阈值要用第 13 章的评测集在自己语料上标定，不要照抄。

2. **改写时必须带上失败反馈。** 只说「换个说法」效果很差；把「上次用了什么词、召回了什么无关内容」告诉模型，它才知道该往哪个方向改。这和第 12 章「重试时把错误明确回传给模型」是同一个道理。

3. **重试次数必须有硬上限，且失败要如实上报。** `MAX_REWRITE=2` 是防死循环的保险丝。更重要的是最后那个分支：**反思后仍找不到，就明确返回「未找到」，而不是把低分噪声当结果返回**。如果把噪声塞给 Agent，它大概率会硬着头皮编一个答案——那还不如不做反思。这是整个练习最容易被忽略、但对抑制幻觉最关键的一步。

4. **trace 一定要记录并可观测。** 上线后要监控三个数：**改写触发率**（突然升高 = 知识库有缺口或用户问法变了）、**改写成功率**（长期偏低说明改写 prompt 需要优化）、**最终失败率**（这些问题就是知识库该补充的内容清单）。这个 trace 本身就是一份免费的知识库改进建议书。

**与第 18 章 Agent 的衔接**

把这个增强版 `search_knowledge` 换进第 18 章的客服 Agent 后，还有一个额外好处：它返回的「未找到相关资料」是**明确信号**，正好可以喂给 `create_ticket` 的守门逻辑——检索反思后仍失败，就是建工单的合法依据。两章的设计在这里自然咬合。

## 小结

- 基础 RAG 一问一检索；Agentic RAG 让模型自主调度检索次数与时机
- Self-RAG 用反思标记校验「是否该检、检得相关吗、内容支持吗」
- 两者叠加可减无效检索、抑幻觉，但增加延迟与成本
- 先测基础 RAG 指标，确有需要再升级
