# 长上下文模型 vs RAG

如今模型上下文窗口已达百万 token（能塞进一整本书）。一个自然的问题：**既然能全文喂给模型，还要 RAG 干嘛？** 答案是——仍要看场景。

## 1. 长上下文能做什么

直接把全部文档放进上下文，让模型「一口气读完全文」再答：

```python
context = "\n".join(all_docs)        # 整库塞进 prompt
answer = llm.chat(f"基于以下资料回答问题：\n{context}\n\n问题：{question}")
```

优点：实现极简，无需切分、建索引、调检索。

## 2. 但长上下文有三道坎

| 问题 | 说明 |
|---|---|
| **成本** | token 按量计费，每次问答都重发全库，贵且随库增长线性膨胀 |
| **延迟** | 输入越长，首字延迟越高，交互体验差 |
| **注意力稀释** | 研究（如「Lost in the Middle」）表明：关键信息若在长文本中部，模型易忽略，准确率反而下降 |

<Callout type="info" title="「能装下」不等于「读得准」">
窗口再大，模型对超长输入中部内容的利用率会下降。RAG 通过检索把「最相关的小段」前置，反而提升命中率。
</Callout>

## 3. 二者并非对立

更优解是**长上下文 + RAG 协同**：

```python
top_k = retrieve(question, k=20)        # RAG 先精确定位
context = "\n".join(top_k)              # 只把相关片段喂给长上下文模型
answer = llm_long.chat(build_prompt(question, context))
```

RAG 负责「缩小范围、降成本」，长上下文负责「在相关片段内做深层推理」。

## 4. 决策速查

| 场景 | 建议 |
|---|---|
| 库小（小于几万 token）、偶尔问 | 直接长上下文，免建索引 |
| 库大、高频问答、要溯源 | RAG 为主 |
| 需跨多段深度推理 | RAG 召回 + 长上下文生成 |

<Callout type="warn" title="别迷信窗口长度">
窗口标称 100 万 token，不等于模型真用好了 100 万。上线前用第 13 章指标实测：长上下文直喂 vs RAG 召回，对比忠实度与相关性。
</Callout>

<Callout type="tip" title="组合性价比最高">
对大多数生产系统，RAG 召回 Top-K + 长上下文模型生成，比「全库直喂」更准、更省、更可追溯。
</Callout>

模型明明「看到」了那段文字，为什么答不出来？这就是「Lost in the Middle」现象——模型对超长输入的注意力分布是**U 形**的：开头和结尾记得清楚，中间大段内容的利用率显著下降。而细节答案恰恰常常就埋在中间。

**做一个位置验证实验，把这个现象亲眼看清楚**

这是本练习最值得做的一步：把同一段「答案原文」插到文档的不同位置，看准确率怎么变。

```python
answer_snippet = "第三阶段验收需满足：P99 延迟 < 200ms、可用性 ≥ 99.9%、并发 ≥ 5000 QPS。"
base = full_text.replace(answer_snippet, "")      # 先移除原位置

for label, pos in [("开头", 0.0), ("四分之一", 0.25),
                   ("正中间", 0.5), ("四分之三", 0.75), ("结尾", 1.0)]:
    idx = int(len(base) * pos)
    doc = base[:idx] + "\n" + answer_snippet + "\n" + base[idx:]
    out = llm(f"基于以下资料回答：\n{doc}\n\n问题：{question}")
    hit = "200ms" in out and "99.9" in out
    print(f"答案位于{label:6s}: {'命中' if hit else '未命中'}")
```

典型结果：

```text

答案位于四分之三: 未命中
```

**结论：「能装下」确实不等于「读得准」。** 窗口标称 100 万 token，不代表第 50 万个 token 处的信息能被可靠使用。

**那什么时候可以直接用长上下文？**

不要因为上面的结果就全盘否定长上下文，它在这些场景下反而更好：

| 场景 | 推荐 | 原因 |
|---|---|---|
| 一次性分析单份合同/论文 | **长上下文** | 建索引的成本还不如直接读；且需要全局理解 |
| 需要「通读全文才能答」的问题（总结、找矛盾） | **长上下文** | RAG 只召回片段，天然看不到全局 |
| 高频问答、库大、要溯源 | **RAG** | 成本和延迟差 25 倍，且能给出处 |
| 细节精确查找 | **RAG** | 避开 U 形注意力谷底 |

注意第二行——**RAG 有个结构性短板：它永远只看到片段**。问「这份 50 页报告里有没有前后矛盾的地方」，RAG 召回的 10 段里可能恰好只包含矛盾的一边，根本发现不了。这类问题要么用长上下文，要么用第 19 章的 GraphRAG 社区摘要。

**最优解仍是组合**

```python
def hybrid(question, k=20):
    chunks = rerank(question, retrieve(embed(question), top_k=50))[:k]
    # 召回数可以放宽到 20，因为长上下文模型吃得下
    ctx = "\n\n".join(f"[{i+1}] {c['text']}" for i, c in enumerate(chunks))
    return llm_long(f"仅依据资料回答，句末标 [n]：\n{ctx}\n\n问题：{question}")
```

长上下文模型的真正价值，不是让你能「全库直喂」，而是**让 RAG 的 `top_k` 可以放得更宽**——从 5 段放到 20 段，召回率大幅提升，同时仍然远远避开注意力稀释的临界点。这是两者协同的正确姿势：**RAG 负责把范围从 8 万 token 缩到 5 千，长上下文负责在这 5 千里做深度推理。**

## 小结

- 长上下文简化实现，但受成本、延迟、注意力稀释三道坎限制
- 「能装下」不等于「读得准」，长文本中部信息易被忽略
- 协同最优：RAG 精确定位 + 长上下文深度推理
- 先测指标再选型，多数场景 RAG 为主、长上下文为辅
