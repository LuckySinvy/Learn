# 图谱检索 GraphRAG

向量检索擅长「语义相似」，但不擅长回答「A 和 B 是什么关系」「谁影响了谁」这类需要**多跳推理**的问题。GraphRAG 把知识组织成图，弥补这一盲区。

## 1. 向量检索的盲区

```text
问题: "导致项目延期的关键风险有哪些？它们如何相互关联？"
向量检索: 召回零散的几段描述，但拼不出「风险 A → 引发 → 风险 B」的链路
图谱检索: 沿实体关系游走，还原完整的因果链
```

当答案依赖实体间的**结构关系**而非文本相似度时，纯向量检索会力不从心。

## 2. 什么是 GraphRAG

GraphRAG（微软提出）分两步：

1. **建图**：用 LLM 从文档抽取「实体—关系—实体」三元组，聚合成知识图谱。
2. **检索**：沿图游走做局部查询，或对整图做社区摘要做全局查询。

<Callout type="info" title="图与向量的分工">
向量负责「找语义相近的片段」，图负责「理清实体间的关系」。两者常组合：先用图定位相关实体，再取回原文喂给 LLM。
</Callout>

## 3. 抽取与索引

```python
# 用 LLM 从一段文本抽取三元组（示意）
prompt = f"""
从下面文本抽取实体关系，输出 JSON 列表，每项含 subject/relation/object：
{chunk}
"""
triples = llm.json(prompt)   # [{"subject":"项目X","relation":"依赖","object":"服务Y"}, ...]

# 写入图数据库（Neo4j / Nebula 等）
for t in triples:
    graph.merge_entity(t["subject"])
    graph.merge_entity(t["object"])
    graph.add_edge(t["subject"], t["object"], t["relation"])
```

## 4. 两种查询模式

| 模式 | 适合 | 做法 |
|---|---|---|
| **局部查询** | 具体实体问答 | 从相关节点沿边游走，取邻域子图 + 原文 |
| **全局查询** | 整体总结（「这套文档的主题是什么」） | 对图做社区检测，逐层摘要再汇总 |

<Callout type="warn" title="建图有额外成本">
抽取三元组依赖 LLM，文档量大时耗时且烧钱；图质量高度依赖抽取 prompt。小语料、浅关系场景，普通 RAG 已够用，别为了用图而用图。
</Callout>

## 5. 适用场景

- 科研文献的「方法 A 引用了谁、被谁改进」
- 企业内部的「谁负责什么、向谁汇报」组织问答
- 运维领域的「服务依赖与故障传播链」

<Callout type="tip" title="先用向量，不够再上图">
经验法则：先跑通向量 RAG 并用第 13 章指标评估。只有当「多跳关系 / 全局总结」类问题持续答不好时，再引入 GraphRAG。
</Callout>

**哪些问题向量答不出、图能答出**

| 问题 | 向量检索 | 图检索 | 为什么 |
|---|---|---|---|

| 「哪个服务是整条链路的单点风险？」 | ❌ **答不出** | ✅ 能答 | 需要计算节点的**入度/中心性**，这是图算法，不是文本检索 |

**核心洞察：分水岭是「答案在不在某一段文字里」**

- 向量检索的本质是**「找到那段话」**。只要答案完整地写在某个 chunk 里，向量就能搞定。
- 图检索的本质是**「把散落各处的关系拼起来」**。第 3、4、5 个问题的答案，**原文里任何一段都没有直接写**，它必须由多条独立的事实**推导**出来。

这就是为什么单纯把 `chunk_size` 调大也救不了第 3 个问题——就算把整段话都放进一个 chunk，模型仍要自己完成三跳推理，而它很容易在中间断链；而图检索是先用确定性的图遍历把 `订单→支付→风控→画像库` 这条路径找出来，再交给 LLM 表述，可靠性高得多。

**另一类图擅长的问题：全局总结**

「这套文档整体在讲什么」——向量检索必然失败，因为它只会返回 5 段局部内容，无法代表全局。GraphRAG 的做法是对图做社区检测（Leiden 算法），把节点聚成若干主题社区，逐个社区生成摘要，再把摘要汇总成全局答案。

**抽三元组时的四条实操经验**

1. **消歧比抽取更重要。** 「画像库」「用户画像库」「user-profile-db」如果不归一成同一个节点，图就断了，多跳游走走到一半就走不下去。实际工程里，实体对齐（entity resolution）的工作量往往超过抽取本身。
2. **关系类型要预先定义好，不能让 LLM 自由发挥。** 否则会抽出「依赖」「调用」「使用」「需要」四种表达同一含义的关系，查询时要写四遍条件。给 prompt 一个封闭的关系枚举列表，效果会稳定很多。
3. **给三元组带上出处。** 每条边都要记录它来自哪个 chunk，这样图检索命中后能回带原文给 LLM——**图负责找到相关实体，原文才是回答的依据**，不能只拿三元组去生成，那样信息太贫瘠。
4. **别急着上图。** 上面 5 个问题里，前 2 个用普通 RAG 完全够用。只有当你发现「多跳关系类问题持续答不好」，且这类问题在业务中占比不低时，建图的成本才划算。抽三元组要对全量文档跑一遍 LLM，成本和延迟都不低。

## 小结

- 向量检索弱在多跳关系与全局总结，GraphRAG 用知识图谱补位
- 流程：LLM 抽三元组建图 → 局部游走 / 全局社区摘要
- 图与向量互补，常组合使用
- 建图有额外成本，先用指标验证确有需要再引入
