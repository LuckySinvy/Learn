# 隐私与合规

RAG 要把企业文档喂给模型和向量库，天然触碰数据合规红线。本章讲如何在不泄密的前提下把 RAG 用起来。

## 1. 三类典型风险

```text
风险1 数据出域: 内部文档上传到第三方 API，违反「数据不出域」
风险2 越权访问: 普通员工通过问答看到本无权查看的机密
风险3 残留泄露: 敏感字段未脱敏就进索引，被检索原文直接暴露
```

## 2. 数据不出域

- **私有化部署**：模型与向量库都跑在自有机房 / 专有云，文档不离开边界。
- **本地向量库**：用自托管 Milvus / pgvector，而非把数据存进第三方托管库。
- **网关审计**：所有对外 API 调用经内网网关，留全量日志。

<Callout type="info" title="合规前提：谁的数据在哪里">
先画一张数据流向图：文档从哪来、存哪、被谁处理、发往哪个模型。任一段落到外部，都要有书面授权。
</Callout>

## 3. 脱敏与红线过滤

入库前对敏感字段做识别与脱敏：

```python
import re
def mask(text):
    text = re.sub(r"\d{17}[\dXx]", "[身份证号]", text)   # 身份证
    text = re.sub(r"1[3-9]\d{9}", "[手机号]", text)        # 手机号
    return text

chunk_clean = mask(raw_chunk)   # 脱敏后再切分、嵌入、入库
```

也可在生成侧加输出过滤，防止模型「吐回」残留敏感信息。

## 4. 权限隔离（基于属性的检索）

检索时带上用户权限，只召回其可见文档：

```python
hits = store.search(
    vec,
    k=5,
    filter={"dept": user.dept, "level": {"<=": user.clearance}},
)
```

<Callout type="warn" title="别只在展示层过滤">
只在生成后「隐藏答案」不够——检索阶段就可能把机密片段送进 Prompt。权限过滤必须下沉到**检索查询**本身。
</Callout>

## 5. 审计与留存

- 记录每次问答的「用户、问题、命中文档、是否含敏感标记」
- 对高敏感库启用水印与访问告警
- 保留期符合行业监管要求（如金融、医疗）

<Callout type="tip" title="脱敏 + 行级权限双保险">
脱敏防「内容泄露」，行级权限防「越权获取」。两者叠加，再配合审计，基本覆盖企业合规三要素。
</Callout>

**参考答案：**

**第一步：定义密级与用户权限**

```python
from enum import IntEnum

class Level(IntEnum):
    PUBLIC   = 0    # 公开：官网 FAQ、产品说明
    INTERNAL = 1    # 内部：流程规范、部门文档
    SECRET   = 2    # 机密：薪酬、并购、客户名单

class User:
    def __init__(self, uid, dept, clearance: Level):
        self.uid = uid
        self.dept = dept
        self.clearance = clearance      # 该用户可访问的最高密级
```

用 `IntEnum` 而不是字符串，是为了能直接做 `<=` 比较，避免在过滤条件里写一长串 `in ["公开","内部"]`。

**第二步：入库时打标 + 脱敏**

```python
import re

PATTERNS = [
    (re.compile(r"(?<!\d)\d{6}(?:19|20)\d{2}(?:0[1-9]|1[0-2])"
                r"(?:0[1-9]|[12]\d|3[01])\d{3}[\dXx](?!\d)"), "[身份证]"),
    (re.compile(r"(?<!\d)1[3-9]\d{9}(?!\d)"),                  "[手机号]"),
    (re.compile(r"(?<!\d)\d{16,19}(?!\d)"),                    "[银行卡]"),
    (re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+"),                   "[邮箱]"),
]

def mask(text: str) -> tuple[str, list[str]]:
    """脱敏并返回命中的敏感类型，用于审计"""
    hit = []
    for pat, repl in PATTERNS:
        text, n = pat.subn(repl, text)
        if n:
            hit.append(repl)
    return text, hit


def ingest(chunk_text, meta):
    clean, sensitive = mask(chunk_text)
    store.add(
        vector=embed(clean),                 # 关键：向量也基于脱敏后文本生成
        payload={
            "text": clean,
            "level": int(meta["level"]),
            "dept": meta["dept"],
            "source": meta["source"],
            "has_sensitive": bool(sensitive),
            "sensitive_types": sensitive,
        },
    )
```

**这里有个极易被忽略的坑：向量必须用脱敏后的文本生成。**

如果先用原文算向量、再存脱敏文本，等于埋了一颗雷——向量里仍然编码着原始身份证号的信息，攻击者可以通过精心构造的查询（比如逐位试探）来判断某个号码是否在库中，这是一种**嵌入反演攻击**。脱敏必须发生在 Embedding **之前**。

正则也要注意用 `(?<!\d)` 和 `(?!\d)` 做边界约束，否则 18 位身份证里的一段会被误判成手机号，或者订单号被当成银行卡。

**第三步：检索时下沉权限过滤**

```python
from qdrant_client import models

def search(user: User, question: str, k=5):
    flt = models.Filter(
        must=[
            # 条件 1：密级不超过用户权限
            models.FieldCondition(
                key="level",
                range=models.Range(lte=int(user.clearance)),
            ),
        ],
        should=[
            # 条件 2：本部门文档，或全公司通用文档
            models.FieldCondition(key="dept",
                                  match=models.MatchValue(value=user.dept)),
            models.FieldCondition(key="dept",
                                  match=models.MatchValue(value="ALL")),
        ],
        min_should=models.MinShould(conditions=2, min_count=1),
    )
    hits = client.search("kb", embed(question), query_filter=flt, limit=k)

    audit_log(user, question, hits)      # 每次检索都留痕
    return hits
```

**第四步：验证权限确实生效**

只测「有权限能看到」不够，**必须测「无权限看不到」**：

```python
alice = User("u1", "HR",    Level.SECRET)     # HR 主管
bob   = User("u2", "SALES", Level.PUBLIC)     # 销售新人

q = "公司高管的薪酬结构是怎样的？"

a_hits = search(alice, q)
b_hits = search(bob, q)

print(f"alice(机密/HR)  召回 {len(a_hits)} 条")
print(f"bob  (公开/销售) 召回 {len(b_hits)} 条")

# 硬性断言
assert all(h.payload["level"] <= int(bob.clearance) for h in b_hits), "越权泄露！"
assert not any(h.payload["level"] == Level.SECRET for h in b_hits), "机密文档泄露给低权限用户！"

# 更重要：验证「无权限时不会硬答」
ans = generate(q, b_hits)
assert "薪酬" not in ans or "未找到" in ans, "无资料却编造了答案！"
print("权限隔离验证通过")
```

**四条关键原则**

1. **过滤必须在检索层，不能在展示层。** 这是课文强调过但值得再说一遍的：如果先检索全库、再在返回前把机密片段剔掉，那些片段**已经进过 Prompt 了**——LLM 看过了，就可能在答案里泄露其中的信息，哪怕原始片段没有展示给用户。权限必须下沉到向量库的 query filter 里。

2. **零召回要优雅处理，且不能暴露「存在但无权访问」。** bob 查不到薪酬资料时，正确的回复是「未找到相关资料」，**而不是**「该内容需要更高权限」——后者本身就泄露了「公司确实有这份文档」这一信息。在高敏感场景下，这种存在性泄露也是合规问题。

3. **脱敏和权限是两道独立的防线，缺一不可。** 脱敏防的是「内容本身泄露」（哪怕有权限的人也不该看到完整身份证号）；权限防的是「越权获取」（无关人员拿不到这份文档）。只做一个都不够：只脱敏则销售能看到 HR 全部政策；只做权限则 HR 内部人员能看到所有员工的身份证号。

4. **审计日志本身也要脱敏。** `audit_log` 里记录用户问题时，用户可能在提问中输入了自己的身份证号。日志同样要过一遍 `mask()`，否则合规审计的日志反而成了新的泄露点——这是实践中非常常见的疏漏。

**补充：脱敏可以做成可逆的**

如果业务需要在回答里展示部分信息（如「尾号 1234 的银行卡」），可以用 token 化替代直接抹除：把 `6222021234567890` 替换成 `[CARD_a3f2]`，映射关系存在独立的加密库里，生成完答案后再按用户权限决定是否还原成脱敏展示形式（`****7890`）。这样既保证向量库和 LLM 都接触不到原始数据，又不损失可用性。

## 小结

- 三类风险：数据出域、越权访问、残留泄露
- 数据不出域靠私有化部署 + 本地向量库 + 网关审计
- 入库前脱敏，检索查询下沉行级权限过滤
- 全程审计留存，满足行业监管要求
