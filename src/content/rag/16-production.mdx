# 生产化

Demo 跑通只是开始。把 RAG 放到真实流量下，要面对**延迟、成本、不稳定**三座大山。本章覆盖关键工程化手段。

## 1. 缓存：最常见也最划算的优化

相同/相似问题重复出现（客服场景尤甚），可直接命中缓存，省去检索+生成。

```python
import hashlib, json
cache = {}   # 生产用 Redis

def ask(question):
    key = hashlib.md5(question.strip().lower().encode()).hexdigest()
    if key in cache:
        return cache[key]                 # 命中，毫秒级返回
    ans = rag_pipeline(question)
    cache[key] = ans
    return ans
```

<Callout type="info" title="语义缓存更进一步">
精确字符串缓存命中率低。可用「问题向量近邻」做语义缓存：新问题向量与历史问题相似度超阈值即复用答案，对口语化提问更友好。
</Callout>

## 2. 并发与异步

检索、重排、LLM 调用都应异步化，避免阻塞：

```python
import asyncio

async def retrieve_and_gen(question):
    vec = await embed_async(question)
    hits = await search_async(vec, k=20)
    reranked = await rerank_async(question, hits)
    return await llm_async(build_prompt(question, reranked[:5]))
```

## 3. 成本控制

| 大头 | 控制手段 |
|---|---|
| LLM 生成 token | 限制 max_tokens、精简 Prompt、缓存复用 |
| Embedding 调用 | 批量嵌入、缓存向量、离线批处理 |
| 向量库查询 | 限制 top_k、加 score 阈值减少后续处理 |

```python
# 给 LLM 调用加上限与超时
resp = llm.chat(
    messages=..., 
    max_tokens=512,      # 防超长输出
    timeout=10,          # 防挂起
)
```

<Callout type="warn" title="警惕无限长输出与重试雪崩">
不设 `max_tokens` 可能输出几千字烧钱；重试不加退避（backoff）会在下游抖动时打满请求，造成雪崩。两者都要有上限。
</Callout>

## 4. 重试与降级

外部依赖（LLM、向量库）会抖动，需优雅降级：

```python
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, max=8))
def call_llm(prompt):
    return llm.chat(messages=prompt)

def rag_with_fallback(question):
    try:
        return call_llm(build_prompt(question, top5))
    except Exception:
        # 降级：只返回检索到的原文片段，不做生成
        return "（生成服务暂时不可用）相关原文：\n" + "\n".join(top5_texts)
```

## 5. 可观测性

```text
记录每次请求：问题、召回片段、耗时、token 数、是否命中缓存、是否降级
```
接入日志/监控（如你站点的 Grafana），才能定位「为什么这次答得差」。

<Callout type="tip" title="先加缓存和降级，再谈扩缩容">
对小中型应用，语义缓存 + 重试 + 降级三件套能解决 80% 的生产稳定性问题，远比急着上分布式更划算。
</Callout>

**完整实现**

```python
import json, hashlib, logging
import numpy as np
import redis
from tenacity import (retry, stop_after_attempt, wait_exponential,
                      retry_if_exception_type, RetryError)

log = logging.getLogger(__name__)
r = redis.Redis(host="localhost", port=6379, decode_responses=False)

CACHE_TTL = 3600 * 24          # 24 小时
SIM_THRESHOLD = 0.95           # 语义缓存命中阈值，宁高勿低
KB_VERSION = "v3"              # 知识库每次重建就 +1，用于整体失效


# ---------- 1. 语义缓存 ----------
class SemanticCache:
    """精确缓存 + 向量近邻缓存两级"""

    def __init__(self, index_key=f"qcache:{KB_VERSION}"):
        self.index_key = index_key

    def _exact_key(self, q):
        h = hashlib.md5(q.strip().lower().encode()).hexdigest()
        return f"qexact:{KB_VERSION}:{h}"

    def get(self, question, q_vec):
        # 一级：精确匹配，O(1)，最快
        hit = r.get(self._exact_key(question))
        if hit:
            log.info("cache hit: exact")
            return json.loads(hit)

        # 二级：语义近邻
        entries = r.hgetall(self.index_key)
        if not entries:
            return None
        keys = list(entries.keys())
        mat = np.stack([np.frombuffer(entries[k], dtype=np.float32) for k in keys])
        sims = mat @ q_vec                       # 向量均已归一化
        best = int(np.argmax(sims))
        if sims[best] >= SIM_THRESHOLD:
            cached = r.get(keys[best].decode())
            if cached:
                log.info("cache hit: semantic sim=%.3f", sims[best])
                return json.loads(cached)
        return None

    def set(self, question, q_vec, answer):
        key = self._exact_key(question)
        r.setex(key, CACHE_TTL, json.dumps(answer, ensure_ascii=False))
        r.hset(self.index_key, key, q_vec.astype(np.float32).tobytes())
        r.expire(self.index_key, CACHE_TTL)


# ---------- 2. 带退避的重试 ----------
class LLMError(Exception):
    pass

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=1, max=8),   # 1s → 2s → 4s
    retry=retry_if_exception_type(LLMError),
    reraise=True,
)
def call_llm(prompt: str) -> str:
    try:
        resp = llm.chat(
            messages=[{"role": "user", "content": prompt}],
            max_tokens=512,
            timeout=15,
        )
        return resp.choices[0].message.content
    except Exception as e:
        # 4xx 参数错误重试也没用，直接抛出不重试
        if getattr(e, "status_code", 500) < 500 and getattr(e, "status_code", 0) != 429:
            raise
        raise LLMError(str(e)) from e


# ---------- 3. 主流程 + 降级 ----------
cache = SemanticCache()

def ask(question: str) -> dict:
    q_vec = embed_normalized(question)

    cached = cache.get(question, q_vec)
    if cached:
        return {**cached, "cached": True}

    chunks = retrieve(q_vec, top_k=20)
    top = rerank(question, chunks)[:5]

    try:
        answer = call_llm(build_prompt(question, top))
        result = {
            "answer": answer,
            "citations": [c["meta"] for c in top],
            "degraded": False,
        }
        cache.set(question, q_vec, result)      # 只缓存成功结果
        return {**result, "cached": False}

    except (LLMError, RetryError) as e:
        log.error("LLM 连续失败，触发降级: %s", e)
        return degrade(top[:3])


def degrade(top3) -> dict:
    """降级：不生成，直接把检索到的原文交给用户"""
    body = "\n\n".join(
        f"【{i+1}】{c['text']}\n　　—— 来源：{c['meta'].get('source')} "
        f"第 {c['meta'].get('page', '?')} 页"
        for i, c in enumerate(top3)
    )
    return {
        "answer": "生成服务暂时不可用，以下是为你检索到的最相关原文，请直接参考：\n\n" + body,
        "citations": [c["meta"] for c in top3],
        "degraded": True,
    }
```

**降级为什么这样设计**

关键在于：**降级不等于报错**。直接返回「服务异常，请稍后重试」是最差的做法——检索明明已经成功了，最有价值的原文就在手上，只是最后一步「润色成自然语言」失败了。把原文原样交给用户，他自己读一样能解决问题，体验远好于一个错误页。

这体现了一个通用原则：**降级要沿着「能力递减」的阶梯走，而不是直接掉到零**。

```text
完整能力: 检索 → 重排 → 生成 → 带引用的流畅答案
  ↓ LLM 挂了
降级 1:  检索 → 重排 → 直接返回 Top-3 原文（本练习）
  ↓ 重排也挂了
降级 2:  检索 → 返回向量 Top-3 原文
  ↓ 向量库也挂了
降级 3:  返回缓存中最相似的历史问答（标注「可能不完全匹配」）
  ↓ 全挂
降级 4:  明确告知不可用 + 人工客服入口
```

**六个生产要点**

1. **阈值宁高勿低。** 语义缓存阈值设 0.95 而不是 0.85，因为**缓存返回错答案的代价远大于缓存未命中**。第 5 章那个实验已经证明了：反义句的相似度能到 0.85——「A 产品支持退款吗」和「B 产品支持退款吗」相似度极高但答案可能完全相反。上线后要抽查语义命中的样本，确认没有张冠李戴。

2. **缓存 key 必须带知识库版本号。** 文档更新后旧答案就过期了，靠 TTL 自然淘汰太慢。用 `KB_VERSION` 做前缀，重建索引时版本号一变，全部旧缓存自动失效。

3. **区分「该重试」和「不该重试」的错误。** 429（限流）、5xx、超时值得重试；400（参数错误）、401（鉴权失败）重试三次只是浪费 3 倍时间和配额。代码里用 `status_code` 做了区分。

4. **退避必须是指数级的。** `wait_exponential` 是 1s → 2s → 4s。如果用固定间隔重试，下游抖动时所有请求会同时重试，形成脉冲把服务彻底打死——这就是课文警告的「重试雪崩」。生产上还建议加随机抖动（jitter）打散重试时刻。

5. **降级要打点，而且要告警。** `degraded: True` 这个字段要进监控。降级本身是正常的保护行为，但**降级率突然升高**是重大故障信号，必须触发告警。同时缓存命中率也要监控——命中率异常下跌通常意味着缓存配置出了问题。

6. **只缓存成功的结果。** 千万别把降级答案写进缓存，否则一次短暂故障会污染缓存 24 小时，所有相似问题都拿到「服务不可用」的回答。

## 小结

- 语义缓存是性价比最高的优化，复用相似问题答案
- 检索/重排/生成全程异步，避免阻塞
- 控成本：限 max_tokens、批量嵌入、限 top_k
- 重试加退避，失败有降级分支，全程可观测
