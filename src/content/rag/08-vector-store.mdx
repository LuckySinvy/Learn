# 索引与向量存储

上一章选了数据库，这章讲怎么把「向量 + 原文 + 元数据」真正落进去并高效查出来。存储设计直接决定检索质量与运维复杂度。

## 1. 一条记录里该存什么

向量库里的每条数据建议包含三部分：

```text
{
  "id": "chunk_1024",
  "vector": [0.12, -0.33, ...],   # Embedding
  "text": "原始 chunk 文本",        # 检索命中后要回传给 LLM
  "metadata": {                    # 用于过滤 + 引用溯源
    "source": "员工手册.pdf",
    "page": 12,
    "category": "HR",
    "updated_at": "2024-08-01"
  }
}
```

<Callout type="info" title="原文必须存回去">
向量只用于「找」，真正喂给 LLM 的是 `text` 原文。很多新手只存向量，检索命中后却拿不到内容，无法组装 Prompt。
</Callout>

## 2. 写入（Upsert）

「Upsert」= 存在则更新、不存在则插入，便于增量更新文档。

```python
# 以 Qdrant 风格为例
points = [
    {
        "id": i,
        "vector": vecs[i],
        "payload": {"text": texts[i], "source": sources[i], "page": pages[i]},
    }
    for i in range(len(vecs))
]
client.upsert(collection_name="kb", points=points)
```

## 3. 持久化

不同方案持久化方式不同：

| 方案 | 持久化要点 |
|---|---|
| FAISS | `index.write_index()` 落盘为文件，重启 `read_index` 读回 |
| Qdrant | 挂载卷 + 快照（snapshot），或启用持久化模式 |
| Milvus | 独立存储（对象存储/ETCD），配置副本 |
| PGVector | 就是 Postgres 表，靠数据库备份保证持久 |

```python
# FAISS 持久化
faiss.write_index(index, "kb.index")
index = faiss.read_index("kb.index")
```

<Callout type="warn" title="别忘了增量更新">
文档改了，要删旧 chunk 再插新 chunk，否则库里会有过期内容。用稳定 `id`（如 `文件 hashes + 页码 + 段号`）做 upsert key，能避免重复与泄漏。
</Callout>

## 4. 元数据过滤

只在某些范围内检索，既提升精度也降成本：

```python
# Qdrant：只在 HR 分类且 2024 后的文档里搜
hits = client.search(
    collection_name="kb",
    query_vector=q_vec,
    query_filter=models.Filter(
        must=[
            models.FieldCondition(key="category", match=models.MatchValue(value="HR")),
            models.FieldCondition(key="updated_at", range=models.Range(gte="2024-01-01")),
        ]
    ),
    limit=5,
)
```

## 5. 索引类型与权衡

```text
IndexFlatL2  精确检索，慢，适合小库验证
IndexIVF    倒排聚类，快，需训练，recall 略降
IndexHNSW   图索引，快且 recall 高，占内存，生产常用
```

<Callout type="tip" title="先用精确索引调通，再上 ANN">
开发期用 `IndexFlat`（精确）确认检索逻辑正确；上线前再换 HNSW/IVF 做性能压测，对比召回率是否可接受。
</Callout>

<Callout type="exercise" title="练习">
给你的向量库加上 `category` 和 `updated_at` 两个元数据字段，写一条「只检索技术类且半年内更新」的过滤查询，验证结果确实被过滤了。

<Answer>
**参考答案：**

**第一步：入库时写入元数据**

```python
from datetime import datetime, timedelta
from qdrant_client import QdrantClient, models

client = QdrantClient(url="http://localhost:6333")
client.recreate_collection(
    collection_name="kb",
    vectors_config=models.VectorParams(size=1024, distance=models.Distance.COSINE),
)

points = []
for i, (vec, text, meta) in enumerate(zip(vecs, texts, metas)):
    points.append(models.PointStruct(
        id=i,
        vector=vec.tolist(),
        payload={
            "text": text,
            "source": meta["source"],
            "category": meta["category"],                 # "技术" / "HR" / "财务"
            "updated_at": int(meta["updated_at"].timestamp()),  # 存 Unix 时间戳
        },
    ))
client.upsert(collection_name="kb", points=points)
```

**关键细节：时间存成 Unix 时间戳（整数），不要存字符串。** 字符串日期只有在严格 `YYYY-MM-DD` 定长格式下字典序才等于时间序，一旦混入 `2024-3-5` 这种没补零的写法，范围查询就会静默出错。整数时间戳没有这个隐患，且各家向量库对数值范围查询的支持最完善。

**第二步：建立 payload 索引（否则过滤会很慢）**

```python
client.create_payload_index("kb", "category",
                            field_schema=models.PayloadSchemaType.KEYWORD)
client.create_payload_index("kb", "updated_at",
                            field_schema=models.PayloadSchemaType.INTEGER)
```

不建索引也能过滤，但 Qdrant 只能逐条扫描 payload，数据量大时延迟会明显上升。这一步很多人会漏掉。

**第三步：写过滤查询**

```python
half_year_ago = int((datetime.now() - timedelta(days=182)).timestamp())

hits = client.search(
    collection_name="kb",
    query_vector=q_vec.tolist(),
    query_filter=models.Filter(
        must=[
            models.FieldCondition(
                key="category",
                match=models.MatchValue(value="技术"),
            ),
            models.FieldCondition(
                key="updated_at",
                range=models.Range(gte=half_year_ago),
            ),
        ]
    ),
    limit=5,
    with_payload=True,
)
```

**第四步：验证过滤确实生效**

光看结果「像是对的」不算验证，要做**对照实验**：

```python
def show(hits, title):
    print(f"\n--- {title}: {len(hits)} 条 ---")
    for h in hits:
        ts = datetime.fromtimestamp(h.payload["updated_at"]).date()
        print(f"  score={h.score:.3f} [{h.payload['category']}] {ts} "
              f"{h.payload['text'][:40]}")

no_filter = client.search("kb", q_vec.tolist(), limit=5, with_payload=True)
show(no_filter, "不过滤")
show(hits, "过滤后")

# 断言式验证
assert all(h.payload["category"] == "技术" for h in hits), "混入了非技术类！"
assert all(h.payload["updated_at"] >= half_year_ago for h in hits), "混入了过期文档！"
print("\n过滤验证通过")
```

典型输出：

```text
--- 不过滤: 5 条 ---
  score=0.891 [技术] 2026-06-12 服务部署流程说明...
  score=0.874 [HR]   2023-01-08 员工设备申领规定...     ← 类别不符
  score=0.866 [技术] 2022-11-30 旧版接口文档...          ← 已过期
  ...

--- 过滤后: 5 条 ---
  score=0.891 [技术] 2026-06-12 服务部署流程说明...
  score=0.802 [技术] 2026-03-21 灰度发布规范...
  ...

过滤验证通过
```

注意看：**过滤后第二名的分数（0.802）比不过滤时的第二名（0.874）低**。这正是过滤在起作用的证据——它把分数更高但不符合条件的结果剔除了，让排名靠后但合规的结果补位。

**PGVector 版本的等价写法**

```sql
SELECT id, content, category, updated_at,
       emb <=> :q_vec AS distance
FROM docs
WHERE category = '技术'
  AND updated_at >= NOW() - INTERVAL '6 months'
ORDER BY emb <=> :q_vec
LIMIT 5;
```

**三个容易踩的坑**

1. **过滤太严可能返回空**。「技术类 + 半年内」如果本来就没几篇，可能一条都返回不了。生产上要处理空结果：要么放宽条件重试一次，要么明确告诉用户「在指定范围内没有找到资料」，而不是让 LLM 在零上下文下瞎编。
2. **前置过滤 vs 后置过滤**。Qdrant/Milvus 做的是「前置过滤」——在 ANN 搜索过程中就排除不符合的点，能保证返回满 k 条。有些方案是「先取 top-k 再过滤」（后置），那样过滤完可能只剩 1 条。选型时要确认清楚，这直接影响召回数量的稳定性。
3. **过滤字段务必在入库时就写好**。事后想加 `category` 就得把全库 payload 更新一遍，成本很高。设计 schema 时宁可多留几个字段（部门、密级、文档类型、有效期），也别等上线后返工。
</Answer>
</Callout>

## 小结

- 每条记录 = vector + text + metadata，原文务必存回
- Upsert 用稳定 id 实现增量更新，避免过期数据
- 持久化按数据库类型落盘/快照/备份
- 元数据过滤提升精度，索引类型在速度与召回间权衡
