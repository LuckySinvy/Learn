# useEffect 与副作用

`useEffect` 是 React 里最容易误用的 Hook。它看起来像「生命周期钩子」，但它不是；它看起来能「监听某个值的变化」，但那通常是错误的用法。这一章先讲清楚它是什么，再讲什么时候**不该**用它。

## 1. 什么是副作用

### 1.1 定义

第 3 章说过组件必须是纯函数：给定相同输入，返回相同输出，不影响外部世界。但真实应用总要做一些「影响外部世界」的事：

- 发起网络请求
- 订阅 WebSocket、事件监听、定时器
- 手动操作 DOM（聚焦输入框、测量尺寸、集成第三方图表库）
- 读写 localStorage
- 修改文档标题

这些统称**副作用**。它们不能写在渲染期间，必须放到两个地方之一：**事件处理函数**，或者 **useEffect**。

### 1.2 优先考虑事件处理函数

这是最重要的判断：**这个副作用是由「某个具体的用户操作」引起的，还是由「组件出现在屏幕上」引起的？**

| 场景 | 归属 |
|---|---|
| 点击提交按钮发请求 | 事件处理函数 |
| 组件挂载后拉取列表数据 | useEffect |
| 点击后写入 localStorage | 事件处理函数 |
| 订阅一个外部数据源 | useEffect |
| 表单提交成功后跳转 | 事件处理函数 |
| 根据 props 同步文档标题 | useEffect |

初学者常犯的错是「点击按钮 → 改一个 state → 用 effect 监听这个 state → 在 effect 里发请求」。这中间的绕行毫无必要，而且带来了额外的渲染和时序问题。**能写在事件里就写在事件里。**

## 2. useEffect 的基本用法

### 2.1 三种依赖形式

```tsx
// 形式一：没有依赖数组 —— 每次渲染后都执行
useEffect(() => {
  console.log("每次渲染都跑");
});

// 形式二：空数组 —— 只在挂载后执行一次
useEffect(() => {
  console.log("只在挂载后跑一次");
}, []);

// 形式三：有依赖 —— 依赖变化时执行
useEffect(() => {
  document.title = "共 " + count + " 项";
}, [count]);
```

执行时机是**在渲染结果被提交到 DOM 之后**，浏览器绘制之前（对于 `useEffect` 是绘制之后异步执行；需要在绘制前同步执行的用 `useLayoutEffect`，第 7 章会讲）。

### 2.2 清理函数

effect 可以返回一个函数，React 会在「下次执行这个 effect 之前」和「组件卸载时」调用它：

```tsx
useEffect(() => {
  const timer = setInterval(() => tick(), 1000);
  return () => clearInterval(timer);
}, []);

useEffect(() => {
  const socket = connect(roomId);
  socket.on("message", onMessage);
  return () => socket.close();
}, [roomId]);
```

第二个例子的完整时序值得记住：roomId 从 A 变成 B 时，React 会先执行**上一次**的清理（关闭 A 的连接），再执行新的 effect（连接 B）。所以「一个 effect 里建立的资源，一定在同一个 effect 的清理函数里释放」——这个配对关系是自洽的，不需要额外记录状态。

<Callout type="warn" title="忘记清理是内存泄漏的第一大来源">
定时器、事件监听、订阅、AbortController，只要是「会持续存在」的东西，都必须清理。忘记清理的典型症状是：路由切走后控制台报「不能在已卸载组件上更新 state」，或者页面用久了越来越卡（定时器越积越多）。
</Callout>

### 2.3 严格模式会执行两次

React 18 的开发模式下，`StrictMode` 会把每个 effect 执行两遍：挂载 → 清理 → 再挂载。这不是 bug，是**故意的压力测试**——用来暴露「没有正确清理」的 effect。

如果你的 effect 在执行两次后行为异常（比如数据重复了、连接建立了两个），说明清理逻辑有问题。生产构建不会有这个行为，但不要因此就把 StrictMode 关掉。

## 3. 依赖数组的规则

### 3.1 比较方式是浅比较 + Object.is

React 保存上一次的依赖数组，和这次的逐位比较。只要有一位 `Object.is` 判定不同，就重新执行 effect。

这意味着：

```tsx
// 每次渲染 options 都是新对象 → 依赖永远"变了" → effect 每次都跑
const options = { limit: 10 };
useEffect(() => {
  fetchData(options);
}, [options]);
```

对象、数组、函数字面量在每次渲染都是新引用，放进依赖数组等于没写依赖数组。解决办法有三种：把依赖拆成原始值（`[options.limit]`）、把对象移到组件外、或者用 `useMemo` 缓存（第 7 章）。

function depsChanged(prev: Deps, next: Deps): boolean {

  if (prev.length !== next.length) return true;

### 3.3 不要对 lint 规则说谎

`react-hooks/exhaustive-deps` 会检查 effect 里用到的所有响应式值是否都在依赖数组里。它偶尔会误报，但**九成情况下它是对的**。

```tsx
// 危险：明明用了 userId 却不声明，userId 变化时不会重新请求
useEffect(() => {
  fetchUser(userId).then(setUser);
}, []);  // eslint-disable-next-line ← 不要这样做
```

想减少依赖，正确的方向是**改代码结构**，而不是删依赖：

- 把不需要响应的逻辑移出 effect
- 用函数式更新去掉对 state 的依赖：`setCount(c => c + 1)` 而不是 `setCount(count + 1)`
- 把函数移进 effect 内部，或用 `useCallback` 稳定它
- 把对象依赖拆成原始值

## 4. 闭包陷阱

### 4.1 过期的闭包

```tsx
function Timer() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1);   // 永远是 0 + 1
    }, 1000);
    return () => clearInterval(id);
  }, []);   // 空依赖，effect 只跑一次

  return <p>{count}</p>;
}
```

数字停在 1 不动了。原因是 effect 只在挂载时执行过一次，它内部的箭头函数**捕获了第一次渲染时的 count（值为 0）**。之后 count 变成 1、2、3，但定时器里的闭包看到的永远是那个 0。

这就是「闭包陷阱」：**每次渲染都有自己独立的一套变量，effect 捕获的是它被创建那次渲染的变量。**

三种解法：

```tsx
// 解法一：函数式更新，不再依赖外部的 count（推荐）
useEffect(() => {
  const id = setInterval(() => setCount((c) => c + 1), 1000);
  return () => clearInterval(id);
}, []);

// 解法二：把 count 加进依赖（每秒重建定时器，可行但浪费）
useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000);
  return () => clearInterval(id);
}, [count]);

// 解法三：用 ref 保存最新值（第 7 章会详细讲）
const countRef = useRef(count);
countRef.current = count;
```

### 4.2 竞态条件

异步请求带来另一类问题：请求 A 先发出，请求 B 后发出，但 B 先返回、A 后返回，结果界面显示的是过期的 A 的数据。

```tsx
// 有 bug 的版本
useEffect(() => {
  fetchUser(userId).then(setUser);
}, [userId]);
```

用清理函数加一个「忽略标记」解决：

```tsx
useEffect(() => {
  let ignore = false;

  fetchUser(userId).then((data) => {
    if (!ignore) setUser(data);
  });

  return () => {
    ignore = true;
  };
}, [userId]);
```

或者用 AbortController 直接取消请求：

```tsx
useEffect(() => {
  const ctrl = new AbortController();

  fetch("/api/users/" + userId, { signal: ctrl.signal })
    .then((r) => r.json())
    .then(setUser)
    .catch((e) => {
      if (e.name !== "AbortError") setError(e);
    });

  return () => ctrl.abort();
}, [userId]);
```

<Callout type="tip" title="这就是为什么大家用数据请求库">
竞态、缓存、重试、加载态、错误态、聚焦刷新、去重……手写 effect 请求要处理的边界情况多得离谱。第 16 章会讲 TanStack Query 这类库如何把这些问题一次性解决。
</Callout>

## 5. 你可能不需要 effect

这是 React 官方文档专门用一整篇讲的主题，也是本章最有价值的部分。

### 5.1 反模式一：用 effect 计算派生数据

```tsx
// 不好
const [items, setItems] = useState<Item[]>([]);
const [total, setTotal] = useState(0);

useEffect(() => {
  setTotal(items.reduce((s, i) => s + i.price, 0));
}, [items]);

// 好：渲染时直接算
const total = items.reduce((s, i) => s + i.price, 0);
```

坏处不只是多写代码：effect 版本会多触发一次渲染（先渲染出旧 total，再更新），而且 `total` 和 `items` 之间存在一帧的不一致。

如果计算真的很昂贵，用 `useMemo` 而不是 effect。

### 5.2 反模式二：用 effect 响应用户事件

```tsx
// 不好
const [submitted, setSubmitted] = useState(false);
useEffect(() => {
  if (submitted) {
    post("/api/order", data);
    setSubmitted(false);
  }
}, [submitted]);

// 好
function handleSubmit() {
  post("/api/order", data);
}
```

### 5.3 反模式三：用 effect 同步 props 到 state

```tsx
// 不好
const [value, setValue] = useState(props.value);
useEffect(() => {
  setValue(props.value);
}, [props.value]);
```

如果只是想「props 变了就重置」，用第 2 章的 key 技巧；如果需要同时保留本地编辑能力，考虑「记录上一次的 props 值」这种模式，或者干脆把状态提升到父组件（第 11 章）。

### 5.4 反模式四：用 effect 通知父组件

```tsx
// 不好：先改 state，再用 effect 通知外面
const [isOpen, setIsOpen] = useState(false);
useEffect(() => {
  onToggle(isOpen);
}, [isOpen]);

// 好：在事件里一起做
function toggle() {
  const next = !isOpen;
  setIsOpen(next);
  onToggle(next);
}
```

### 5.5 那什么时候该用 effect

只剩下一类场景：**和 React 之外的系统同步**。

- 订阅浏览器 API（resize、online/offline、媒体查询）
- 建立和关闭连接（WebSocket、SSE）
- 集成命令式的第三方库（地图、图表、编辑器）
- 组件出现时就要发生的数据获取（更推荐交给数据请求库或框架）
- 手动操作 DOM（聚焦、滚动、测量）

判断口诀：**如果去掉 effect，React 树内部的数据流依然完整，那这个 effect 多半是多余的。**

## 6. 一个完整的 effect 示例

```tsx
function useOnlineStatus(): boolean {
  const [online, setOnline] = useState(() => navigator.onLine);

  useEffect(() => {
    function up() {
      setOnline(true);
    }
    function down() {
      setOnline(false);
    }

    window.addEventListener("online", up);
    window.addEventListener("offline", down);

    // 订阅后立刻同步一次，避免订阅前发生的变化被漏掉
    setOnline(navigator.onLine);

    return () => {
      window.removeEventListener("online", up);
      window.removeEventListener("offline", down);
    };
  }, []);

  return online;
}
```

这个例子集齐了所有要素：外部系统、订阅与取消订阅配对、空依赖数组（订阅目标不随 props 变化）、初始值同步。注意它已经被抽成了一个自定义 Hook——这是下一章的主题。

判断依据始终是那一句：**这个副作用是「某个具体用户操作」引起的，还是「组件出现在屏幕上/某个值变了」引起的？**

**1. 点击「收藏」，调接口并弹 toast —— 事件处理函数**

典型的用户操作触发。绕道 state + effect 不但多一次渲染，还会带来「快速点两次会怎样」这类时序问题。

```tsx
async function handleFav() {
  await api.favorite(id);
  toast.success("已收藏");
}
```

**2. 商品详情页打开时上报浏览埋点 —— useEffect**

没有任何用户操作，是「组件出现」这件事本身引起的，只能用 effect。

```tsx
useEffect(() => {
  reportView(productId);
}, [productId]);
```

⚠️ 但要注意 **StrictMode 会让它跑两次**，埋点会重复。三种处理方式：

- 让服务端做幂等去重（最稳妥）
- 用 `useRef` 记住「这个 id 上报过了」
- 更好的做法是把埋点提到**路由层**做——「页面被访问」本来就是路由的概念，不是某个组件的概念

**3. 搜索框输入，300ms 防抖后请求联想词 —— useEffect**

这题最容易答错。表面看是「用户输入触发的」，但真正要表达的是「**当 query 稳定在某个值时，让联想结果与它同步**」——这是一个持续的同步关系，不是一次性动作。而且它需要两件 effect 天生擅长的事：**输入变化时取消上一次的定时器**，以及**处理竞态**。

```tsx
useEffect(() => {
  if (!query) return;
  let ignore = false;

  const timer = setTimeout(async () => {
    const data = await fetchSuggestions(query);
    if (!ignore) setSuggestions(data);
  }, 300);

  return () => {
    clearTimeout(timer);   // query 一变就撤销上次的待发请求
    ignore = true;         // 已经发出去的，回来了也不采纳
  };
}, [query]);
```

写在 `onChange` 里当然也能实现，但你得自己用 ref 存 timer id、自己在卸载时清理、自己维护请求序号——等于把 effect 的清理机制重新实现一遍。

**4. 弹窗打开时禁止页面滚动，关闭时恢复 —— useEffect**

和外部系统（`document.body` 的样式）同步的教科书例子，而且**必须**用 effect：如果写在「打开/关闭」的点击事件里，一旦弹窗因为路由跳转、父组件卸载等原因**没有走关闭按钮就消失了**，页面就会永久卡住无法滚动。清理函数是唯一能保证「无论怎么消失都会恢复」的机制。

```tsx
useEffect(() => {
  if (!isOpen) return;
  const prev = document.body.style.overflow;
  document.body.style.overflow = "hidden";
  return () => {
    document.body.style.overflow = prev;   // 保存并还原，而不是硬写 "auto"
  };
}, [isOpen]);
```

**5. 表单保存成功后跳转到列表页 —— 事件处理函数**

「保存成功」是提交动作的一部分，直接接在后面写：

```tsx
async function handleSubmit(e: React.FormEvent) {
  e.preventDefault();
  await api.save(form);
  navigate("/list");
}
```

反面教材是「设一个 `saved` 状态，再用 effect 监听它跳转」——多一次渲染，而且 `saved` 这个状态在跳转后还得记得重置，纯属自找麻烦。

```tsx
const [seconds, setSeconds] = useState(0);
const [step, setStep] = useState(1);

useEffect(() => {
  const id = setInterval(() => {
    setSeconds(seconds + step);   // seconds 和 step 都被冻结在首次渲染
  }, 1000);
  return () => clearInterval(id);
}, []);
```

**两个问题的成因其实是同一个：** effect 只在挂载时执行了一次，它内部的箭头函数捕获了**第一次渲染**的 `seconds`（0）和 `step`（1）。

- 每秒都在算 `setSeconds(0 + 1)`，值恒为 1 → 秒数停在 1 不动
- `step` 永远是 1，改成 5 也不会被那个闭包看到 → 改 step 无效

---

**方案一：函数式更新 + 把 `step` 加进依赖**

```tsx
useEffect(() => {
  const id = setInterval(() => {
    setSeconds((s) => s + step);   // s 是 React 给的最新值，不再依赖闭包
  }, 1000);
  return () => clearInterval(id);
}, [step]);                        // step 变了就重建定时器
```

- **秒数问题** — 由函数式更新解决。`s` 由 React 从队列里取最新值传入，跟闭包无关。
- **step 问题** — 由依赖数组解决。`step` 一变，effect 重跑，新闭包拿到新 `step`。

**代价：定时器会被销毁重建。** 用户在第 900 毫秒改了 step，那 900 毫秒就白走了，计时从 0 重新开始。对「每秒 +N」这种场景通常可以接受；但如果是精确计时、或者 step 会被高频修改（比如绑在滑块上拖动），节奏会明显被打乱。

---

**方案二：用 ref 保存最新的 `step`，定时器只建一次**

```tsx
const stepRef = useRef(step);

// 每次渲染后把最新值同步进 ref
useEffect(() => {
  stepRef.current = step;
}, [step]);

useEffect(() => {
  const id = setInterval(() => {
    setSeconds((s) => s + stepRef.current);   // 每次触发时才读，读到的一定是最新的
  }, 1000);
  return () => clearInterval(id);
}, []);                                       // 空依赖：定时器全程只有一个
```

- **秒数问题** — 同样靠函数式更新解决。
- **step 问题** — `stepRef.current` 是在**定时器触发的那一刻**读取的，而不是在 effect 创建时捕获的，所以总能读到最新值。

**代价：**

- 定时器**不会**重建，计时节奏完全不受影响 ✅
- 但多了一个 ref 和一个同步 effect，样板代码变多
- `step` 变成了「非响应式」的读取——如果哪天需求变成「改 step 时要立刻重置计时」，这个方案反而挡路了

---

**两种方案的选择标准：**

| | 方案一（加依赖） | 方案二（用 ref） |
|---|---|---|
| 定时器重建 | 会 | 不会 |
| 计时节奏 | 改 step 时被打断 | 始终连续 |
| 代码量 | 少 | 多一个 ref + 一个 effect |
| 语义 | step 是**订阅参数**，变了就该重连 | step 是**只读的最新值**，不该影响订阅 |

**问自己一句话就能选对：「这个值变化时，我到底想不想重新建立这个副作用？」** 想 → 放依赖数组；不想但要读最新值 → 用 ref。

聊天室的 `roomId` 属于前者（换房间当然要重连），这里的 `step` 属于后者。

---

**补充：一个错误的「修复」**

```tsx
// ⚠️ 能跑，但每秒都在销毁重建定时器
useEffect(() => {
  const id = setInterval(() => setSeconds(seconds + step), 1000);
  return () => clearInterval(id);
}, [seconds, step]);
```

把 `seconds` 也塞进依赖确实能让数字增长，但代价是**每一秒都要清理并重建一次定时器**。更麻烦的是计时会持续偏移：每次重建都从 0 开始计新的 1000 毫秒，而中间渲染的耗时会不断累加进去，跑久了明显变慢。

**React 未来的正式解法是 `useEffectEvent`**（目前还是实验特性），它相当于把方案二的 ref 模式内置了：

```tsx
const onTick = useEffectEvent(() => setSeconds((s) => s + step));

useEffect(() => {
  const id = setInterval(onTick, 1000);
  return () => clearInterval(id);
}, []);   // onTick 不需要进依赖，但内部总能读到最新的 step
```
</Answer>
</Callout>

<Callout type="exercise" title="练习 3：消除多余的 effect">
一个搜索页有 state：`query`、`allItems`、`filteredItems`、`isEmpty`。目前用两个 effect 分别在 query 变化时更新 filteredItems、在 filteredItems 变化时更新 isEmpty。

重写这个组件，去掉所有 effect。说明你删掉了哪些 state。

<Answer>
**参考答案：**

**改写前（4 个 state + 2 个 effect）：**

```tsx
function SearchPage() {
  const [query, setQuery] = useState("");
  const [allItems, setAllItems] = useState<Item[]>([]);
  const [filteredItems, setFilteredItems] = useState<Item[]>([]);
  const [isEmpty, setIsEmpty] = useState(false);

  useEffect(() => {
    setFilteredItems(allItems.filter((i) => i.name.includes(query)));
  }, [query, allItems]);

  useEffect(() => {
    setIsEmpty(filteredItems.length === 0);
  }, [filteredItems]);

  // ...
}
```

**改写后（2 个 state + 0 个 effect）：**

```tsx
function SearchPage() {
  const [query, setQuery] = useState("");
  const [allItems, setAllItems] = useState<Item[]>([]);

  // 派生值：渲染时直接算
  const filteredItems = allItems.filter((i) => i.name.includes(query));
  const isEmpty = filteredItems.length === 0;

  return (
    <div>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      {isEmpty ? <Empty /> : <List items={filteredItems} />}
    </div>
  );
}
```

**删掉的 state：`filteredItems` 和 `isEmpty`。**

判断标准很简单：**能从其他 state 算出来的，就不是 state。** `filteredItems` 完全由 `query` + `allItems` 决定，`isEmpty` 完全由 `filteredItems` 决定，两者都不携带任何新信息。

---

**为什么原来的写法不只是「啰嗦」，而是**有 bug**：**

原版输入一个字符会经历 **3 次渲染**，而且中间两次的界面是**自相矛盾**的：

| 渲染 | `query` | `filteredItems` | `isEmpty` | 界面状态 |
|---|---|---|---|---|
| 1 | 新值 | **旧值** | 旧值 | 搜索框已更新，列表还是上次的结果 ❌ |
| 2 | 新值 | 新值 | **旧值** | 列表对了，但空状态提示可能反了 ❌ |
| 3 | 新值 | 新值 | 新值 | 终于一致 ✅ |

用户能不能看到这两帧取决于机器性能，但**「取决于机器性能」本身就是最糟糕的一类 bug**——本地跑得快看不出来，用户的旧手机上就是一闪一闪的。

改写后只渲染 1 次，且 `query`、`filteredItems`、`isEmpty` 天然同步——因为它们本来就是同一次计算的产物。这正是第 1 章说的：**消灭第二份真相**。

---

**关于性能：**

「每次渲染都 filter 一遍会不会慢？」——绝大多数情况下不会。几百上千条数据的 `filter` 是微秒级的，比 React 渲染本身便宜得多。

只有当数据量真的很大（上万条）或计算真的很重时，才用 `useMemo` 缓存：

```tsx
const filteredItems = useMemo(
  () => allItems.filter((i) => i.name.includes(query)),
  [allItems, query]
);
const isEmpty = filteredItems.length === 0;   // 这行永远不值得 memo
```

注意：**`useMemo` 是缓存，不是 state。** 它依然是「派生」的——依赖变了就自动重算，不需要你手动同步。而 effect + state 的写法，同步的责任在你身上。这是本质区别。

`isEmpty` 这种一次比较的计算永远不要 memo，`useMemo` 自身的开销比 `.length === 0` 大得多。
</Answer>
</Callout>

然后修复 fetch 那个 effect 的重复执行问题：把依赖从 `[config]` 改成 `[config.limit]`，重新运行看输出变化。

```ts
function renderComponent(roomId: string): void {
  cursor = 0;

  );

```

**运行输出：**

```text
渲染 1: roomId=A
  [socket] 首次挂载，执行
      connect(A)
  [fetch] 首次挂载，执行
      fetch(limit=10)
  [log] 首次挂载，执行
      render log: A
渲染 2: roomId=A （只是父组件重渲染）
  [socket] 依赖未变，跳过
  [fetch] 依赖未变，跳过
  [log] 依赖变了 -> 先清理上一次
  [log] 再执行新的

渲染 3: roomId=B
  [socket] 依赖变了 -> 先清理上一次
      close(A)
  [socket] 再执行新的
      connect(B)
  [fetch] 依赖未变，跳过
  [log] 依赖变了 -> 先清理上一次
  [log] 再执行新的
      render log: B

      close(B)
```

**观察点一：`null` 依赖（没写依赖数组）**

三次渲染**每次都重新执行**。原因在 `depsChanged` 的第一行：

```ts
if (prev === null || next === null) return true;   // 直接判定「变了」
```

React 根本不做比较，无条件重跑。所以「不写依赖数组」的语义是「**每次渲染后都执行一遍，包括先清理上一次**」——这也是为什么它几乎从不该被使用：如果 effect 里有请求，那就是每次渲染都发一次请求。

**观察点二：`[config]` 改成 `[config.limit]` 之后**

| 渲染 | 改之前 | 改之后 |
|---|---|---|
| 1 | 首次挂载，执行 | 首次挂载，执行 |
| 2 | **依赖变了 → 白跑一次** | **依赖未变，跳过** ✅ |
| 3 | **依赖变了 → 白跑一次** | **依赖未变，跳过** ✅ |

`config` 是每次渲染新建的对象字面量，`Object.is(旧对象, 新对象)` 恒为 `false`，所以依赖永远「变了」——**放进去等于没写依赖数组**。而 `config.limit` 是原始值 `10`，`Object.is(10, 10)` 为 `true`，比较才真正生效。

**这就是「接口被重复请求」最常见的一种成因。** 三个等价的修法：

```ts
// ① 依赖拆成原始值（本题的做法，最简单）
useEffect(() => { fetchData(config); }, [config.limit]);

// ② 对象移到组件外部（配置是常量时最干净）
const CONFIG = { limit: 10 };
useEffect(() => { fetchData(CONFIG); }, []);

// ③ 用 useMemo 稳定引用（对象字段较多、或依赖 props 时用）
const config = useMemo(() => ({ limit: pageSize }), [pageSize]);
useEffect(() => { fetchData(config); }, [config]);
```

同样的陷阱也适用于**数组**和**函数**——`[]`、`() => {}` 写在组件体里，每次渲染都是新引用。函数的对应解法是 `useCallback`（第 7 章）。
</Answer>

## 小结

- 副作用只能放在**事件处理函数**或 **useEffect** 里，绝不能写在渲染期间
- 优先问「这是用户操作引起的，还是组件出现引起的」——前者放事件里
- 依赖数组用 `Object.is` 逐位浅比较；对象、数组、函数字面量每次渲染都是新引用
- 清理函数在「下次执行前」和「卸载时」调用；建立与释放必须在同一个 effect 里配对
- StrictMode 下 effect 执行两次是**故意的**，用于暴露清理缺陷
- 闭包陷阱：effect 捕获的是它创建那次渲染的变量；用函数式更新或 ref 破解
- 异步请求要处理**竞态**，用 ignore 标记或 AbortController
- **大多数 effect 都是多余的**：派生数据现算、事件逻辑写事件里、props 同步用 key
