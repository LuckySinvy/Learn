# 泛型

**泛型（generics）** 让你写出不依赖具体类型、又能保持类型安全的代码，避免为 `i32`/`f64`/`String` 各写一份逻辑。

## 1. 泛型函数

<Playground
  language="rust"
  id="rust-13-generic-fn"
  title="泛型函数"
  code={`fn largest<T: PartialOrd + Copy>(list: &[T]) -> T {
    let mut max = list[0];
    for &item in list {
        if item > max {
            max = item;
        }
    }
    max
}

fn main() {
    let a = largest(&[1, 5, 3]);      // T = i32
    let b = largest(&[1.0, 2.5]);     // T = f64
    println!("{} {}", a, b);
    println!("{}", largest(&['a', 'z', 'm']));   // T = char
}`}
  expectedOutput={`5 2.5\nz`}
/>

<Callout type="info" title="trait bound 限制能力">
`T: PartialOrd` 表示 T 必须可比较（才能用 `>`）；`+ Copy` 表示可复制（避免所有权移动）。泛型不会凭空获得操作能力。
</Callout>

## 2. 泛型结构体与枚举

<Playground
  language="rust"
  id="rust-13-generic-struct"
  title="泛型结构体"
  code={`struct Point<T> {
    x: T,
    y: T,
}

// 需要不同类型时用两个参数
struct Pair<T, U> {
    first: T,
    second: U,
}

fn main() {
    let int_point = Point { x: 5, y: 10 };
    let float_point = Point { x: 1.5, y: 2.5 };
    println!("整数点 ({}, {})", int_point.x, int_point.y);
    println!("浮点点 ({}, {})", float_point.x, float_point.y);

    let p = Pair { first: 1, second: String::from("one") };
    println!("{} -> {}", p.first, p.second);
}`}
  expectedOutput={`整数点 (5, 10)\n浮点点 (1.5, 2.5)\n1 -> one`}
/>

标准库的 `Option` 与 `Result` 正是泛型枚举：

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

<Callout type="warn" title="单类型参数要求同类型">
上面的 `Point<T>` 要求 `x` 与 `y` 同类型。若需不同，用两个参数 `Point<T, U>`。
</Callout>

## 3. 单态化（monomorphization）

Rust 在**编译期**为用到的每个具体类型生成专属代码：

```rust
let _ = largest(&[1, 2]);
let _ = largest(&[1.0, 2.0]);
```

编译器实际生成 `largest_i32` 与 `largest_f64` 两份函数。这就是「零成本抽象」——运行时没有泛型开销，性能等同手写专版。

<Callout type="tip" title="零成本的意义">
泛型不引入任何运行时间接层或额外内存。代价是二进制体积略增（每种类型一份代码），但速度是原生的。
</Callout>

## 4. trait bound 的两种写法

```rust
// 1. 在函数签名里
fn f<T: Display + Clone>(x: T) {}

// 2. where 子句，更清晰
fn f<T>(x: T)
where
    T: Display + Clone,
{
}
```

## 5. 默认类型参数

```rust
enum Result<T, E = std::io::Error> {
    Ok(T),
    Err(E),
}
```

<Callout type="exercise" title="练习">
实现一个泛型 `struct Pair<T> { first: T, second: T }`，加一个方法 `fn cmp(&self) -> ...`（提示：约束 `T: PartialOrd`）返回较大者。再写个 `where` 子句版本的打印函数。

<Answer>
**参考答案：**

```rust
use std::fmt::Display;

struct Pair<T> {
    first: T,
    second: T,
}

// 这个 impl 块不加约束：任何 T 都能构造
impl<T> Pair<T> {
    fn new(first: T, second: T) -> Self {
        Self { first, second }
    }
}

// 这个 impl 块只对可比较的 T 生效
impl<T: PartialOrd> Pair<T> {
    // 返回较大者的引用，避免要求 T: Copy
    fn larger(&self) -> &T {
        if self.first >= self.second {
            &self.first
        } else {
            &self.second
        }
    }
}

// where 子句版本的打印函数
fn print_pair<T>(p: &Pair<T>)
where
    T: Display + PartialOrd,
{
    println!("({}, {}) 中较大的是 {}", p.first, p.second, p.larger());
}

fn main() {
    let nums = Pair::new(10, 42);
    print_pair(&nums);

    let floats = Pair::new(3.7, 1.2);
    print_pair(&floats);

    let words = Pair::new(String::from("apple"), String::from("banana"));
    print_pair(&words);

    let chars = Pair::new('z', 'a');
    print_pair(&chars);
}
```

**输出：**

```text
(10, 42) 中较大的是 42
(3.7, 1.2) 中较大的是 3.7
(apple, banana) 中较大的是 banana
(z, a) 中较大的是 z
```

**为什么方法名叫 `larger` 而不是 `cmp`？**

`cmp` 是标准库 `Ord` trait 的方法名。虽然自己定义同名的固有方法（inherent method）在语法上合法，而且固有方法优先级更高，但这会让读代码的人困惑——他们会以为你在调用 `Ord::cmp`（返回 `Ordering`），实际上却返回了别的东西。**给方法起名时避开标准库的常用名**是个好习惯。

**为什么返回 `&T` 而不是 `T`？**

如果写成 `fn larger(&self) -> T`，就得从 `&self` 里把值搬出来——这需要额外加 `T: Copy` 或 `T: Clone` 约束，`String` 这种类型就用不了了。返回引用则零成本，任何 `T` 都适用。

**为什么分成两个 `impl` 块？**

这是泛型的一个重要技巧——**条件化实现**：

- `impl<T> Pair<T>`：所有 `Pair` 都有 `new`
- `impl<T: PartialOrd> Pair<T>`：只有元素可比较的 `Pair` 才有 `larger`

如果把 `PartialOrd` 约束加在结构体定义上，那么连构造一个不可比较类型的 `Pair` 都做不到了。**约束应该加在真正需要它的地方**，而不是一股脑加在类型定义上。

**为什么用 `PartialOrd` 而不是 `Ord`？**

因为浮点数只实现了 `PartialOrd`，没有实现 `Ord`——`f64::NAN` 与任何值比较都返回 `false`，不满足全序关系。用 `PartialOrd` 能同时支持整数和浮点数，代价是遇到 `NAN` 时结果没有意义。

**两种约束写法的对比：**

```rust
// 内联 bound：约束少时更紧凑
fn print_pair<T: Display + PartialOrd>(p: &Pair<T>) { }

// where 子句：约束多或复杂时可读性更好
fn complex<T, U>(a: T, b: U) -> String
where
    T: Display + Clone,
    U: Display + PartialOrd + Default,
{
    format!("{} {}", a, b)
}
```

两者语义完全相同，编译后代码也一样。签名一长，`where` 就明显更好读——函数名和参数列表不会被一堆约束淹没。
</Answer>
</Callout>

## 小结

- 泛型提升复用而不牺牲类型安全
- `T: Trait` 约束类型能做什么（如比较、复制）
- 单态化：编译期为各具体类型生成专属代码，零运行时开销
- `where` 子句让复杂 bound 更易读
