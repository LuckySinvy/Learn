# 进程管理：ps、信号、kill 与前后台任务

程序是磁盘上的文件，**进程**是它运行起来的实例——有自己的 PID、内存空间和三条标准流。服务卡死要不要杀？怎么优雅地杀？关掉终端后台任务还活着吗？这些日常问题都归本章管。

## 1. 进程的基本事实

- 每个进程有唯一 **PID**（进程号）；由**父进程**创建，记录 **PPID**（父进程号），整个系统构成一棵进程树，树根是 PID 1（init/systemd，容器里是入口进程）；
- 你在 Shell 里敲的每个命令，都是 Shell fork 出来的子进程；
- 进程退出时留下**退出码**（0 成功，非 0 失败），父进程用它判断结果（`$?`，第 15 章展开）。

## 2. ps：查看进程快照

ps 参数有 BSD（`ps aux`）和 System V（`ps -ef`）两大流派，输出大同小异：

```bash
ps aux              # 全部进程：用户、PID、CPU%、MEM%、启动命令
ps -ef              # 另一流派：多了 PPID 列
ps aux | grep nginx # 最常见组合：找特定进程
ps -o pid,ppid,comm # 自选输出列
```

`ps aux` 关键列：`%CPU`/`%MEM` 资源占比、`STAT` 状态（R 运行、S 睡眠、Z 僵尸、T 停止）、`TIME` 累计 CPU 时间、`COMMAND` 启动命令。

## 3. 信号：进程间的"敲门方式"

kill 不是"杀"，而是"发信号"——信号是内核递给进程的轻量通知，进程可以注册处理函数优雅响应。常用信号：

| 编号 | 名称 | 含义 | 能否被捕获/忽略 |
|---|---|---|---|
| 15 | SIGTERM | **礼貌地请求退出**（kill 默认） | 能——进程可做清理后退出 |
| 9 | SIGKILL | 立即强杀，进程无从得知 | 不能 |
| 2 | SIGINT | 中断（就是 Ctrl+C） | 能 |
| 1 | SIGHUP | 挂断；很多服务约定收到后**重载配置** | 能 |
| 19/18 | SIGSTOP/SIGCONT | 暂停 / 继续 | STOP 不能被忽略 |

```bash
kill 1234            # 默认发 SIGTERM，给进程清理退路
kill -9 1234         # SIGKILL 强杀——最后手段
kill -HUP 1234       # 通知重载配置（nginx 等服务支持）
killall python3      # 按名字杀（同名全杀，小心）
pkill -f 'worker.py' # 按完整命令行模糊匹配
```

<Callout type="warn" title="先 15 后 9：kill -9 是最后手段">
SIGKILL 让进程没有任何机会保存数据、释放锁、删除临时文件、关闭连接——数据库类进程被 -9 可能直接损坏数据文件。正确流程：先 `kill PID`（TERM），等几秒观察；仍不退再 `kill -9`。把 `kill -9` 当默认习惯是运维大忌。
</Callout>

## 4. 前台、后台与作业控制

默认命令在**前台**运行，占住终端直到结束。交互场景下的作业控制：

```bash
./build.sh &         # 末尾 & ：直接放后台运行
jobs                 # 列出当前 Shell 的后台作业
fg %1                # 把 1 号作业调回前台
# Ctrl+Z 把前台任务暂停并放到后台（状态是 Stopped）
bg %1                # 让暂停的作业在后台继续跑
```

这些命令依赖交互式终端，沙箱脚本模式下重点掌握 `&` 与 `$!`（最近一个后台进程的 PID）、`wait`（等待后台任务结束并取回退出码）。

## 5. nohup：关掉终端也要活

后台任务有个致命弱点：终端关闭（SSH 断开）时，Shell 会给所有子进程发 SIGHUP，任务随之被杀。`nohup` 让进程忽略 SIGHUP：

```bash
nohup ./train.sh > train.log 2>&1 &
#  │              │              └ 放后台
#  │              └ 输出重定向落盘（不指定则写 nohup.out）
#  └ 忽略挂断信号，SSH 断开也继续跑
echo $! > train.pid      # 把 PID 记下来，之后好管理
```

生产环境更完整的方案是交给进程管理器：systemd（第 17 章）、supervisor 或容器编排——它们额外提供开机自启、崩溃自动拉起、日志轮转。nohup 适合临时性的长任务（跑数、迁移脚本）。

<Callout type="info" title="僵尸进程是什么">
子进程退出后，父进程还没调用 wait 收尸，进程表里就残留一条 Z 状态记录——僵尸进程。它不占 CPU 内存，只占一个 PID 槽位；少量无害，大量出现说明父进程有 bug。杀僵尸没用（它已经死了），要么让父进程正确 wait，要么杀掉父进程让 init 领养收尸。
</Callout>

## 小结

- 进程 = 运行中的程序：PID/PPID 构成进程树，退出码 0 表成功
- `ps aux` 看快照、`top` 看实时；`ps aux | grep x` 是高频组合
- kill 发的是信号：默认 TERM(15) 优雅退出，KILL(9) 强杀不可捕获，HUP(1) 常约定为重载
- 先 15 后 9；`128+信号` 是被信号杀死的退出码（OOM 的 137）
- `&` 放后台、`$!` 取 PID、`wait` 收尾；防断线用 `nohup cmd > log 2>&1 &`

<Answer>
**参考答案：**

**第 1 题：启动 3 个后台 sleep 并全部杀掉**

```bash
sleep 300 &
sleep 300 &
sleep 300 &

ps            # 确认 3 个 sleep 都在
pkill sleep   # 方式一：按名字杀，一条命令解决
# 方式二：ps | grep | awk | xargs 管道
# ps | grep sleep | grep -v grep | awk '{print $1}' | xargs kill
```

验证：`ps` 后再看，sleep 进程应全部消失。注意 `pkill sleep` 的匹配规则是进程名，确认没有其它同名关键进程时再使用。

**第 2 题：143 与 137 的由来**

```bash
sleep 300 &
PID1=$!
kill -15 $PID1      # 发 SIGTERM
wait $PID1
echo "TERM exit = $?"    # 143

sleep 300 &
PID2=$!
kill -9 $PID2       # 发 SIGKILL
wait $PID2
echo "KILL exit = $?"    # 137
```

规律：被信号终止的进程，退出码 = **128 + 信号编号**。

- `kill -15` 发 SIGTERM（编号 15）→ 128 + 15 = **143**；
- `kill -9` 发 SIGKILL（编号 9）→ 128 + 9 = **137**。

137 在容器场景极常见：容器内存超限被 OOM Killer 强杀，看到的退出码就是 137。

**第 3 题：nohup + PID 文件的启停**

```bash
# 造一个循环写日志的脚本
cat > logger.sh << 'EOF'
#!/bin/bash
i=0
while true; do
  echo "tick $i"
  i=$((i+1))
  sleep 1
done
EOF
chmod +x logger.sh

# 启动并记录 PID
nohup ./logger.sh > logger.log 2>&1 &
echo $! > logger.pid
cat logger.pid

# 按 PID 文件停止
kill $(cat logger.pid)
```

`kill $(cat logger.pid)` 就是很多服务 stop 脚本的核心：先读 PID 文件拿到进程号，再对它发信号（默认 SIGTERM，留给进程优雅退出的机会）。

**第 4 题：为什么断开 SSH 后后台进程会消失**

SSH 会话结束时，Shell 退出前会向它的所有子进程发送 **SIGHUP**（挂断信号）。默认情况下进程收到 SIGHUP 就退出，所以 `./server &` 启动的后台进程也会跟着被 SIGHUP 杀死。

`nohup` 的作用就是让进程**忽略 SIGHUP**，SSH 断开后依然存活。但还要配合输出重定向 `> log 2>&1`，因为：

- 进程的 stdout/stderr 原本连着终端的伪终端（pty），会话关闭后这些通道就断了，进程再往 stdout 写内容会收到错误甚至触发异常退出；
- 重定向到文件后，进程的输出有稳定的去处，日志还能留档排查。

所以标准姿势是 `nohup cmd > log 2>&1 &`——nohup 保命，重定向保输出通道。
