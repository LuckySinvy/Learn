# 锁机制

并发写同一行会怎样？答案是：锁。锁是隔离性的实现手段之一，也是线上「更新卡住不动」「Deadlock found」报错的根源。本章按粒度从大到小讲清 MySQL 的锁体系，最后给出死锁的分析方法与预防守则。

## 1. 锁的全景图

```text
按粒度：
  全局锁 ──▶ 表级锁 ──▶ 行级锁
  (整库)     (表锁/MDL/意向锁)   (记录锁/间隙锁/临键锁)

按模式：
  S 锁（共享/读锁）：可以多个事务同时持有
  X 锁（排他/写锁）：独占，与任何锁互斥
```

兼容矩阵（行锁层面）：

| 已持有 \ 想加 | S | X |
|---|---|---|
| S | 兼容 | 冲突 |
| X | 冲突 | 冲突 |

## 2. 全局锁与表级锁

### 2.1 全局锁

```sql
FLUSH TABLES WITH READ LOCK;   -- 整库只读，逻辑备份老方案
UNLOCK TABLES;
```

整库只读期间所有写入阻塞，主库上代价极大。现代备份用 `mysqldump --single-transaction`（靠 MVCC 快照，不锁库，第 19 章）或物理备份代替。

### 2.2 表锁与 MDL

```sql
LOCK TABLES orders READ;    -- 显式表锁，InnoDB 时代很少手动用
UNLOCK TABLES;
```

更常打交道的是 **MDL（元数据锁）**，它是自动的：任何增删改查都持有 MDL 读锁，DDL 需要 MDL 写锁。第 4 章讲过的「长事务堵 DDL、DDL 再堵所有查询」连锁事故就是 MDL 排队造成的。

### 2.3 意向锁：表级与行级的协调员

事务要给某行加 X 锁前，会先给**表**加 IX（意向排他）锁；加行 S 锁前先加表 IS 锁。意向锁之间几乎全兼容，它存在的唯一目的：**让「给整表加锁」的操作不用逐行检查**——看到表上有 IX，就知道里面有行被写锁着，直接等待即可。你几乎不用管它，但死锁日志里会出现它的名字，认识即可。

## 3. 行锁：InnoDB 的核心

**行锁加在索引记录上**——这句话是理解一切行锁行为的钥匙。

```sql
-- 会话 A
BEGIN;
UPDATE products SET stock = stock - 1 WHERE id = 1;   -- 对 id=1 的索引记录加 X 锁

-- 会话 B（阻塞，直到 A 提交或锁等待超时）
UPDATE products SET stock = stock - 1 WHERE id = 1;
```

锁等待超时由 `innodb_lock_wait_timeout` 控制（默认 50 秒），超时报错 `Lock wait timeout exceeded`。

### 3.1 没走索引 = 锁全表的行

InnoDB 只能全表扫描，**扫过的每一行都会加锁**（RR 级别下还加间隙锁），效果接近锁全表。这是「一条不起眼的 UPDATE 让整个系统卡死」的经典案例——**UPDATE/DELETE 的 WHERE 条件必须能走索引**。

`FOR UPDATE` 是「先锁再改」的悲观并发控制；`SKIP LOCKED` 是实现「多个 worker 抢任务队列」的利器（谁锁到算谁的，其他 worker 跳过去拿下一条）。

## 4. 间隙锁与临键锁（RR 级别）

在默认隔离级别 REPEATABLE READ 下，锁不仅加在记录上，还加在记录**之间的空隙**上，用来阻止幻读（防止有人在范围里插入新行）：

```text
索引上现有值：      5        10        15
可锁对象：
  记录锁 Record Lock：  锁住 10 本身
  间隙锁 Gap Lock：     锁住 (5,10) 这个开区间——不能往里插新值
  临键锁 Next-Key Lock：记录+前面的间隙 = (5,10]，InnoDB 的默认单位
```

示例：

```sql
-- 会话 A（RR 级别）
BEGIN;
SELECT * FROM products WHERE id BETWEEN 5 AND 15 FOR UPDATE;
-- 锁住范围内所有记录 + 间隙

-- 会话 B：阻塞！id=7 落在被锁的间隙里
INSERT INTO products (id, category_id, name, price) VALUES (7, 2, 'X', 1.00);
```

规则速记（细节繁多，记住主干）：

- 加锁基本单位是**临键锁**（左开右闭区间）；
- 等值查询命中**唯一索引的存在记录**时，退化为纯记录锁；
- 等值查询未命中时，退化为**间隙锁**；
- 范围查询会锁住覆盖范围的一串临键锁。

<Callout type="warn" title="间隙锁是死锁与阻塞的高发区">
两个事务可以**同时持有同一个间隙的间隙锁**（间隙锁之间互相兼容），但都想往里 INSERT 时就互相等待对方释放——这是线上最常见的死锁模式之一（先 SELECT FOR UPDATE 不存在的行再 INSERT）。绕法：用唯一索引 + `INSERT ... ON DUPLICATE KEY UPDATE` 代替「查了再插」；或将隔离级别降为 READ COMMITTED（间隙锁基本消失，第 17 章讨论代价）。
</Callout>

## 5. 死锁：分析与避免

### 5.1 一个最小死锁

```sql
-- 会话 A                          -- 会话 B
BEGIN;                             BEGIN;
UPDATE products SET stock=stock-1  UPDATE products SET stock=stock-1
  WHERE id = 1;   -- 锁住行1        WHERE id = 2;   -- 锁住行2

UPDATE products SET stock=stock-1  UPDATE products SET stock=stock-1
  WHERE id = 2;   -- 等 B 的行2      WHERE id = 1;   -- 等 A 的行1
                                   -- ERROR 1213: Deadlock found...
```

A 等 B、B 等 A，构成环。InnoDB 的死锁检测（`innodb_deadlock_detect=ON`）会立刻发现并**回滚代价较小的一方**，另一方继续执行——所以死锁报错不是灾难，但频繁死锁说明设计有问题。

### 5.2 看死锁日志

```sql
SHOW ENGINE INNODB STATUS\G
-- 找 LATEST DETECTED DEADLOCK 段落：
-- 两个事务各自「HOLDS THE LOCK(S)」和「WAITING FOR THIS LOCK TO BE GRANTED」
-- 精确到哪个索引的哪条记录，照着还原业务时序即可定位
```

也可以查实时锁等待：

```sql
SELECT * FROM performance_schema.data_lock_waits;   -- 谁在等谁
SELECT * FROM sys.innodb_lock_waits;                -- 可读性更好的视图
```

### 5.3 避免死锁的守则

1. **统一加锁顺序**：所有代码路径按同样的顺序更新多行/多表（比如永远按主键升序处理），环就构不成；
2. **事务小而短**：持锁时间越短，撞车概率越低；
3. **一次锁够**：批量更新用一条带 IN 的语句（按主键排序）代替循环多条；
4. WHERE 走索引，缩小加锁范围；
5. 热点行争抢（秒杀库存）考虑：队列串行化、Redis 预扣、或拆分热点行；
6. 应用层**捕获 1213 错误自动重试**（幂等前提下）——死锁回滚是常态化事件，代码要兜住。

## 小结

- 锁粒度：全局 → 表（表锁/MDL/意向锁）→ 行；模式分 S/X
- 行锁加在**索引记录**上；WHERE 不走索引等于锁全表的行
- RR 级别默认临键锁（记录 + 间隙），阻止幻读也带来更多阻塞与死锁
- SKIP LOCKED / NOWAIT 是 8.0 处理锁竞争的新工具
- 死锁被自动检测并回滚一方；预防靠统一顺序 + 短事务，应用要重试 1213

  WHERE id = 1;        -- ① A 拿到行1的 X 锁

**怎么读这份日志**（这是排查线上死锁的核心技能）：

| 段落 | 看什么 |
|---|---|
| `*** (1) TRANSACTION` | 事务 1 **正在执行**的那条 SQL（只显示最后一条，前面的要靠业务代码还原） |
| `(1) HOLDS THE LOCK(S)` | 事务 1 **已持有**的锁：哪张表、哪个索引、哪条记录 |
| `(1) WAITING FOR ...` | 事务 1 **在等**的锁 |
| `*** WE ROLL BACK TRANSACTION (2)` | InnoDB 选择回滚哪一方（通常是**修改行数较少**、代价小的） |

关键字段解读：

- `index PRIMARY of table shop.products` —— 锁加在**聚簇索引**上。行锁永远加在**索引记录**上，这里因为按主键更新，锁的是主键索引。
- `lock_mode X locks rec but not gap` —— **纯记录锁**（没有间隙锁）。这是因为按主键等值命中了存在的记录，临键锁退化为记录锁。
- `hex 01` / `hex 02` —— 被锁记录的主键值（十六进制），即 id = 1 和 id = 2。这是定位「到底锁了哪一行」的依据。

把两段拼起来：事务 1 持有 id=1 等 id=2，事务 2 持有 id=2 等 id=1，**环闭合** → InnoDB 的等待图检测（`innodb_deadlock_detect = ON`）立刻发现并回滚代价小的一方。

被回滚的一方**整个事务都被撤销**，另一方继续正常执行。所以死锁报错不是灾难，但频繁死锁说明加锁顺序设计有问题。

**根治方法**：让所有代码路径按**统一顺序**加锁，环就构不成。比如批量更新时永远按主键升序：

```sql
-- 用一条带 IN 的语句代替循环多条，且 InnoDB 会按索引顺序加锁
UPDATE products SET stock = stock - 1 WHERE id IN (1, 2) AND stock >= 1;
```

**2. 间隙锁实验：RR vs RC**

```sql
-- 先确认隔离级别
SELECT @@transaction_isolation;   -- REPEATABLE-READ
```

```sql
-- 会话 A（RR 级别）
BEGIN;
SELECT * FROM products WHERE id BETWEEN 5 AND 15 FOR UPDATE;
-- 锁住 [5,15] 范围内所有存在的记录 + 它们之间的间隙 + 15 到下一条记录之间的间隙
```

```sql
-- 会话 B
INSERT INTO products (id, category_id, name, price, stock)
  VALUES (7, 2, 'X', 1.00, 1);
-- 挂起！即使 id=7 这行根本不存在，也插不进去
```

在第三个会话观察：

```sql
SELECT * FROM sys.innodb_lock_waits\G
-- waiting_lock_mode: X,GAP  ← 等的是间隙锁

SELECT object_name, index_name, lock_type, lock_mode, lock_status, lock_data
FROM performance_schema.data_locks WHERE object_name = 'products';
-- 会看到一串 lock_mode = X（临键锁）和 X,GAP（间隙锁）的记录
```

切到 READ COMMITTED 重来：

```sql
-- 会话 A
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN;
SELECT * FROM products WHERE id BETWEEN 5 AND 15 FOR UPDATE;
```

```sql
-- 会话 B
INSERT INTO products (id, category_id, name, price, stock)
  VALUES (7, 2, 'X', 1.00, 1);
-- 立即成功！RC 下间隙锁基本消失，只锁真实存在的记录
```

**对比总结：**

| | REPEATABLE READ | READ COMMITTED |
|---|---|---|
| 加锁单位 | **临键锁**（记录 + 前面的间隙，左开右闭） | **纯记录锁**，只锁存在的行 |
| 间隙 INSERT | 被阻塞 | 允许 |
| 幻读 | 被阻止（这正是间隙锁存在的意义） | 可能发生 |
| 锁冲突/死锁概率 | 高 | 低 |
| 并发度 | 低 | 高 |

**这是一个明确的权衡**：RR 用间隙锁换取了「防幻读」，代价是大幅增加阻塞和死锁；RC 反之。很多互联网公司（包括阿里的规范）默认把隔离级别调成 **RC**，理由是：

1. 业务上真正依赖「可重复读」的场景很少；
2. RC 下锁范围小，并发高，死锁少；
3. RC 配合 `binlog_format = ROW` 不会有主从数据不一致问题（老的 STATEMENT 格式才必须用 RR）。

但要清楚代价：RC 下同一事务内两次相同查询可能读到不同结果，且**没有间隙锁保护，「先查后插」的并发去重会失效**——必须靠唯一索引兜底。

**间隙锁最经典的死锁模式**（务必记住）：两个事务可以**同时持有同一个间隙的间隙锁**（间隙锁之间互相兼容！），但都想往里 INSERT 时就互相等待：

```sql
-- 会话 A                              -- 会话 B
BEGIN;                                 BEGIN;
SELECT * FROM t WHERE id = 7
  FOR UPDATE;  -- 不存在 → 拿间隙锁
                                       SELECT * FROM t WHERE id = 7
                                         FOR UPDATE;  -- 也拿到同一间隙锁（兼容）
INSERT INTO t VALUES (7, ...);
  -- 等 B 释放间隙锁
                                       INSERT INTO t VALUES (7, ...);
                                       -- 死锁！
```

绕法：用唯一索引 + `INSERT ... ON DUPLICATE KEY UPDATE` 代替「先查再插」。

**3. SKIP LOCKED 实现任务队列**

```sql
CREATE TABLE tasks (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  payload    VARCHAR(200)    NOT NULL,
  status     TINYINT         NOT NULL DEFAULT 0 COMMENT '0待处理 1处理中 2完成',
  worker     VARCHAR(50)     NOT NULL DEFAULT '',
  created_at DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_status (status)
) ENGINE=InnoDB;

INSERT INTO tasks (payload) VALUES ('job-1'),('job-2'),('job-3'),('job-4'),('job-5');
```

两个 worker 同时抢任务：

```sql
-- Worker A
BEGIN;
SELECT id, payload FROM tasks
WHERE status = 0
ORDER BY id
LIMIT 1
FOR UPDATE SKIP LOCKED;
-- 立即返回 id=1，并持有它的 X 锁

UPDATE tasks SET status = 1, worker = 'A' WHERE id = 1;
-- 先不提交，模拟正在处理
```

```sql
-- Worker B（同时执行）
BEGIN;
SELECT id, payload FROM tasks
WHERE status = 0
ORDER BY id
LIMIT 1
FOR UPDATE SKIP LOCKED;
-- 立即返回 id=2 —— 不阻塞！自动跳过了被 A 锁住的 id=1

UPDATE tasks SET status = 1, worker = 'B' WHERE id = 2;
COMMIT;
```

```sql
-- Worker A 完成
UPDATE tasks SET status = 2 WHERE id = 1;
COMMIT;

SELECT id, payload, status, worker FROM tasks ORDER BY id;
```

**核心价值**：如果**不加** `SKIP LOCKED`，Worker B 会**阻塞等待** A 释放 id=1 的锁——所有 worker 排成一队串行执行，多开进程毫无意义。加上 `SKIP LOCKED` 后，B 直接跳过被锁的行去拿下一条，**天然实现了无冲突的任务分发**，不需要任何额外的分布式锁。

三个 8.0 锁等待选项的对比：

| 写法 | 遇到被锁的行 |
|---|---|
| `FOR UPDATE` | **等待**，直到超时（`innodb_lock_wait_timeout`，默认 50 秒） |
| `FOR UPDATE NOWAIT` | **立即报错** `ERROR 3572: Statement aborted because lock(s) could not be acquired` |
| `FOR UPDATE SKIP LOCKED` | **跳过**这些行，只返回能锁住的 |

工程注意事项：

- `SKIP LOCKED` 会**返回不确定的结果集**（跳过了谁取决于当时谁被锁），所以**只适合任务队列这类"取哪条都行"的场景**，绝不能用于需要精确结果的查询（如对账、报表）。
- 一定要配 `ORDER BY id` 和 `LIMIT`，否则可能一次锁住大量行。
- 事务要短：worker 拿到任务后应**尽快提交**（把 status 改成「处理中」就提交），真正的业务处理放到事务外面。否则一个慢任务会长时间持锁，还会造成长事务。
- 需要容错时加超时回收：定期把「处理中且超过 N 分钟未完成」的任务重置回待处理。
