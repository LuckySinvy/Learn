# 执行计划 EXPLAIN

前两章你已经知道索引怎么工作、该怎么建，但「SQL 到底有没有走索引、走得好不好」不能靠猜——EXPLAIN 就是优化器交出的答卷。看懂它，慢 SQL 优化就从玄学变成工程。

## 1. 基本用法

几行数据的表优化器一律选全表扫描，所以先把 orders 灌大一点再看计划：

<Playground
  language="mysql"
  id="mysql-14-1"
  title="EXPLAIN 基本用法"
  code={`-- 造数：把订单表放大到约 700 行
INSERT INTO orders (order_no, user_id, status, total_amount, created_at)

       o.user_id, o.status, o.total_amount, o.created_at
FROM orders o,
     (SELECT 0 n UNION ALL SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT 3 UNION ALL SELECT 4
      UNION ALL SELECT 5 UNION ALL SELECT 6 UNION ALL SELECT 7 UNION ALL SELECT 8 UNION ALL SELECT 9) d1,
     (SELECT 0 n UNION ALL SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT 3 UNION ALL SELECT 4
      UNION ALL SELECT 5 UNION ALL SELECT 6 UNION ALL SELECT 7 UNION ALL SELECT 8 UNION ALL SELECT 9) d2;
ANALYZE TABLE orders;

EXPLAIN SELECT o.order_no, u.username
FROM orders o
JOIN users u ON u.id = o.user_id
WHERE o.user_id = 1;`}
/>

每行代表访问一张表（或物化结果），从上往下就是访问顺序（id 相同时）。上例中 users 因为按主键常量定位是 `const`，orders 走 `idx_user_created` 的 `ref`。

## 2. 核心列逐个讲

| 列 | 含义 |
|---|---|
| id | 子查询/UNION 的层级编号，越大越先执行；相同则自上而下 |
| select_type | SIMPLE / PRIMARY / SUBQUERY / DERIVED（派生表）/ UNION 等 |
| table | 访问的表（或 derived2 这类物化表） |
| **type** | **访问类型，最重要的一列**，见下节 |
| possible_keys | 候选索引 |
| **key** | **实际选用的索引**，NULL 即没走索引 |
| key_len | 用到的索引字节数——判断联合索引用了几列的关键 |
| ref | 与索引比较的对象（常量 const、另一表的列） |
| **rows** | **预估**扫描行数（基于统计信息，不是精确值） |
| filtered | 经过 WHERE 后剩余行数百分比估算 |
| **Extra** | 附加信息，藏着最多的优化线索 |

**key_len 的用法**：索引 `(user_id BIGINT, created_at DATETIME)` 全用上是 8 + 5 = 13；如果 key_len 只有 8，说明只用到了 user_id——最左前缀断了或范围截断了。这是判断「联合索引到底吃了几列」的硬指标。

## 3. type：访问类型等级表

从好到差：

| type | 含义 | 例子 |
|---|---|---|
| system/const | 主键或唯一索引的常量查询，最多一行 | `WHERE id = 1` |
| eq_ref | JOIN 时被驱动表按主键/唯一索引匹配，每行最多配一行 | `JOIN u ON u.id = o.user_id` |
| ref | 普通（非唯一）索引等值查询 | `WHERE user_id = 1` |
| range | 索引范围扫描 | `WHERE id > 100`、IN、BETWEEN |
| index | 扫整棵索引树（常配合覆盖索引） | 无条件但只取索引列 |
| **ALL** | **全表扫描** | 没索引可用 |

经验线：**核心业务查询至少要到 range，最好 ref 以上**。看到 ALL 先检查是不是缺索引或索引失效；但小表 ALL 无所谓，别教条。

把五个等级挨个跑一遍，对照 type 与 key_len：

<Playground
  language="mysql"
  id="mysql-14-2"
  title="type 等级实测"
  code={`-- const：主键常量
EXPLAIN SELECT * FROM orders WHERE id = 1;

-- eq_ref：被驱动表按主键匹配
EXPLAIN SELECT o.order_no, u.username FROM orders o JOIN users u ON u.id = o.user_id;

-- ref：普通索引等值，key_len=8 说明只吃了 user_id 一列
EXPLAIN SELECT * FROM orders WHERE user_id = 1;

-- range：索引范围
EXPLAIN SELECT * FROM orders WHERE user_id IN (1, 2, 3);

-- ALL：没有索引可用
EXPLAIN SELECT * FROM orders WHERE total_amount > 100;`}
/>

## 4. Extra 关键字解读

| Extra | 含义 | 态度 |
|---|---|---|
| Using index | 覆盖索引，无回表 | 很好 |
| Using index condition | 索引下推 ICP 生效 | 好 |
| Using where | Server 层过滤（引擎返回后再筛） | 中性，结合 rows 看 |
| Using filesort | 需要额外排序（内存或磁盘） | 大结果集时要优化 |
| Using temporary | 用了临时表（GROUP BY/DISTINCT 常见） | 大数据量时要优化 |
| Using join buffer (hash join) | 被驱动表无索引，走 Hash Join | 检查连接列索引 |

`Using filesort` + `Using temporary` 同时出现的 GROUP BY/ORDER BY 大查询，通常就是慢查询榜单的常客——解法多半是让联合索引同时满足过滤和排序（第 13 章）。

<Playground

  code={`-- Using index：三列全在 idx_user_created 里，不回表
EXPLAIN SELECT id, user_id, created_at FROM orders WHERE user_id = 1;

-- Using filesort：排序列没被索引的有序性覆盖
EXPLAIN SELECT id, total_amount FROM orders ORDER BY total_amount DESC LIMIT 10;

EXPLAIN SELECT status, COUNT(*) FROM orders GROUP BY status;

## 5. EXPLAIN ANALYZE（8.0.18+）：看真实执行

EXPLAIN 是**估算**，EXPLAIN ANALYZE **真的执行一遍**并报告实际耗时与行数：

```sql
EXPLAIN ANALYZE
SELECT user_id, COUNT(*) FROM orders
WHERE created_at >= '2026-07-01'
GROUP BY user_id;
```

```text
-> Table scan on <temporary>  (actual time=0.61..0.62 rows=3 loops=1)
    -> Aggregate using temporary table  (actual time=0.60..0.60 rows=3 loops=1)
        -> Filter: (orders.created_at >= TIMESTAMP'2026-07-01 00:00:00')
            (cost=0.65 rows=1.33) (actual time=0.05..0.07 rows=4 loops=1)
            -> Table scan on orders  (cost=0.65 rows=4) (actual time=0.04..0.05 rows=4 loops=1)
```

读法：树形结构自内向外执行；每个节点对比 `(cost=估算 rows=估算)` 与 `(actual time=首行..全部 rows=实际 loops=次数)`。**估算 rows 与实际 rows 差几个数量级**，就是统计信息过期或优化器误判的信号：

```sql
ANALYZE TABLE orders;   -- 重新收集统计信息，常能纠正误判
```

注意：EXPLAIN ANALYZE 会真实执行语句（8.0 只支持 SELECT），对大查询慎用于生产高峰。

## 6. 优化器提示（Hints）

统计信息修正后优化器仍然选错时，可以下「指令」：

```sql
-- 强制/禁止使用某索引
SELECT * FROM orders FORCE INDEX (idx_user_created) WHERE user_id = 1;
SELECT * FROM orders IGNORE INDEX (idx_user_created) WHERE user_id = 1;

-- 8.0 风格的注释 Hint（推荐，粒度更细）
SELECT /*+ INDEX(o idx_user_created) */ * FROM orders o WHERE o.user_id = 1;
SELECT /*+ NO_INDEX(o idx_user_created) */ * FROM orders o WHERE o.user_id = 1;

-- JOIN 顺序提示
SELECT /*+ JOIN_ORDER(o, u) */ * FROM orders o JOIN users u ON u.id = o.user_id;

-- 单条语句的资源护栏：最多执行 3000 毫秒
SELECT /*+ MAX_EXECUTION_TIME(3000) */ * FROM orders;
```

<Callout type="warn" title="Hint 是最后手段，不是常规武器">
硬编码的 FORCE INDEX 会随数据分布变化而过时——今天的最优索引可能是明年的性能炸弹，而且表删了该索引 SQL 直接报错。优先顺序永远是：改写 SQL → 调整索引 → ANALYZE TABLE → 最后才是 Hint，并留注释说明原因。
</Callout>

## 7. 实战分析套路

拿到一条慢 SQL 的固定流程：

```text
1. EXPLAIN 看全貌
   ├─ type 是 ALL？ → 缺索引 or 索引失效（函数/隐式转换/最左前缀）
   ├─ key 用的索引对吗？key_len 吃满了吗？
   ├─ rows 估算量级合理吗？
   └─ Extra 有 filesort / temporary？
2. EXPLAIN ANALYZE 对照实际行数与耗时，定位最耗时的节点
3. 措施：建/改联合索引（等值+范围+排序一体设计）、改写 SQL、ANALYZE TABLE
4. 再次 EXPLAIN 验证，对比前后 rows 与耗时
```

<Callout type="tip" title="EXPLAIN FORMAT=TREE 和 FORMAT=JSON">
`EXPLAIN FORMAT=TREE` 输出与 ANALYZE 相同的树形结构（不执行），比表格更容易看清 JOIN 顺序和 Hash Join；`FORMAT=JSON` 则包含成本数字 cost_info，适合深挖优化器为什么这么选。
</Callout>

## 小结

- EXPLAIN 五个关键读数：type（访问等级）、key（真用的索引）、key_len（联合索引吃了几列）、rows（估算量）、Extra（filesort/temporary/覆盖索引）
- type 至少 range，核心查询争取 ref/eq_ref；ALL + 大 rows = 优先处理对象
- EXPLAIN ANALYZE 给真实耗时，估算与实际差距大就 ANALYZE TABLE
- Hint 能救急，但优先改 SQL 和索引
- 优化闭环：EXPLAIN → 改 → 再 EXPLAIN 对比

<Answer>
**参考答案：**

**1. 函数条件 vs 范围条件**

先确保 `created_at` 上有索引并把表灌大（几行的表优化器一律全表扫，看不出差异）：

```sql
ALTER TABLE orders ADD INDEX idx_created (created_at);
ANALYZE TABLE orders;
```

```sql
-- 改写前
EXPLAIN SELECT id, order_no FROM orders WHERE DATE(created_at) = '2026-07-01';
```

```text
+------+---------------+------+------+-------------+
| type | possible_keys | key  | rows | Extra       |
+------+---------------+------+------+-------------+
| ALL  | NULL          | NULL |  700 | Using where |
+------+---------------+------+------+-------------+
```

```sql
-- 改写后：左闭右开的范围条件
EXPLAIN SELECT id, order_no FROM orders
WHERE created_at >= '2026-07-01' AND created_at < '2026-07-02';
```

```text
+-------+---------------+-------------+------+-----------------------+
| type  | possible_keys | key         | rows | Extra                 |
+-------+---------------+-------------+------+-----------------------+
| range | idx_created   | idx_created |  100 | Using index condition |
+-------+---------------+-------------+------+-----------------------+
```

对比记录：

| | 改写前 | 改写后 |
|---|---|---|
| type | `ALL`（全表扫描） | `range`（索引范围扫描） |
| possible_keys | `NULL`（优化器根本没把它当候选） | `idx_created` |
| key | `NULL` | `idx_created` |
| rows | 全表行数 | 只有命中区间的行数 |

**原因**：B+ 树是按 `created_at` 的**原始值**有序排列的。`DATE(created_at)` 是对列做函数变换，变换后的结果在索引里**没有任何有序性**，优化器无法用它做树上定位，只能全表扫描后逐行计算函数再比较。

`possible_keys` 都是 NULL 这一点很关键——说明优化器**连考虑都没考虑**这个索引，这和「考虑了但算下来不划算而放弃」（possible_keys 有值、key 为 NULL）是两回事。

同类失效写法：`WHERE YEAR(created_at) = 2026`、`WHERE id + 1 = 10`、`WHERE SUBSTR(order_no, 1, 2) = 'SO'`。**口诀：让列保持"裸露"，要变换就变换另一侧的常量。**

改写不了时用函数索引（8.0.13+）：

```sql
ALTER TABLE orders ADD INDEX idx_created_date ((DATE(created_at)));
-- 之后原 SQL 就能命中，但查询表达式必须与索引定义完全一致
```

**2. 用联合索引消除 filesort**

构造一条产生 filesort 的查询：

```sql
EXPLAIN SELECT id, order_no, total_amount, created_at
FROM orders
WHERE user_id = 1
ORDER BY total_amount DESC
LIMIT 20;
```

```text
type: ref
key : idx_user_created
Extra: Using where; Using filesort     ← 排序列 total_amount 不在索引有序性里
```

现有索引 `(user_id, created_at)` 只能保证组内按 `created_at` 有序，按 `total_amount` 排必须把命中行全读出来在 sort buffer 里排一遍。

加一个「等值列 + 排序列」的联合索引：

```sql
ALTER TABLE orders ADD INDEX idx_user_amount (user_id, total_amount);
ANALYZE TABLE orders;

EXPLAIN SELECT id, order_no, total_amount, created_at
FROM orders WHERE user_id = 1 ORDER BY total_amount DESC LIMIT 20;
```

```text
type: ref
key : idx_user_amount
Extra: Using where              ← Using filesort 消失了
```

**原理**：索引 `(user_id, total_amount)` 里，`user_id = 1` 的记录连续存放且组内**天然按 total_amount 有序**。要 DESC 只需沿叶子双向链表**反向扫描**，扫够 20 行即停——既不用读全部命中行，也不用排序。

三个容易踩的坑：

- **排序方向必须一致**。`ORDER BY a ASC, b DESC` 无法被普通的 `(a, b)` 索引消除排序，需要 8.0 的**降序索引**：`ADD INDEX idx (a ASC, b DESC)`。
- **等值列在前、排序列在后**。写成 `(total_amount, user_id)` 就没用了。
- **中间夹范围条件会破坏有序性**。`WHERE user_id = 1 AND status > 1 ORDER BY total_amount` 用 `(user_id, status, total_amount)` 仍会 filesort，因为范围之后的列不再有序。这时应建 `(user_id, total_amount)` 让排序优先。

顺带一提，`Using temporary` 也能用同样的思路消除：

```sql
EXPLAIN SELECT status, COUNT(*) FROM orders GROUP BY status;
-- Extra: Using temporary
ALTER TABLE orders ADD INDEX idx_status (status);
-- GROUP BY 可以顺着有序索引流式聚合，temporary 消失
```

**3. FORMAT=TREE 看三表 JOIN 与 JOIN_ORDER**

```sql
EXPLAIN FORMAT=TREE
SELECT o.order_no, u.username, p.name
FROM orders o
JOIN users u        ON u.id = o.user_id
JOIN order_items oi ON oi.order_id = o.id
JOIN products p     ON p.id = oi.product_id
WHERE o.status = 1;
```

典型输出：

```text
-> Nested loop inner join  (cost=12.4 rows=8)
    -> Nested loop inner join  (cost=8.2 rows=6)
        -> Nested loop inner join  (cost=4.1 rows=2)
            -> Filter: (o.status = 1)  (cost=1.4 rows=2)
                -> Index lookup on o using idx_status (status=1)
            -> Single-row index lookup on u using PRIMARY (id = o.user_id)
        -> Index lookup on oi using idx_order (order_id = o.id)
    -> Single-row index lookup on p using PRIMARY (id = oi.product_id)
```

**怎么读树形输出**（和表格格式的读法完全不同，这是关键）：

- **缩进最深的节点最先执行**。上例最深处是 `Index lookup on o`，所以 **`orders` 是驱动表**。
- 每个 `Nested loop inner join` 节点下有两个子节点：**上面的是外层（已积累的结果集），下面的是本次被驱动的表**。所以 JOIN 顺序是 `o → u → oi → p`。
- `Single-row index lookup ... using PRIMARY` 对应表格格式的 `type = eq_ref`（主键唯一匹配，每次最多一行），`Index lookup` 对应 `ref`。
- `cost` 和 `rows` 是**逐层累积**的：内层 2 行，接上 oi 变 6 行，再接 p 变 8 行——能直观看到「行数放大」发生在哪一步。

为什么优化器选 orders 做驱动表：`o.status = 1` 过滤后只剩 2 行，而其他三张表都是按主键/索引被精确探测（每次 1 行）。这符合**「小表（过滤后行数少的）驱动大表，被驱动表连接列必须有索引」**的原则。

用 Hint 强制改变顺序做对比实验：

```sql
EXPLAIN FORMAT=TREE
SELECT /*+ JOIN_ORDER(p, oi, o, u) */ o.order_no, u.username, p.name
FROM orders o
JOIN users u        ON u.id = o.user_id
JOIN order_items oi ON oi.order_id = o.id
JOIN products p     ON p.id = oi.product_id
WHERE o.status = 1;
```

```text
-> Nested loop inner join  (cost=48.6 rows=8)      ← cost 明显变高
    ...
        -> Table scan on p  (cost=0.9 rows=6)      ← products 变成驱动表，全表扫
        -> Index lookup on oi using idx_product (product_id = p.id)
```

对比结论：

- 强制让 `products` 打头后，它变成全表扫描的驱动表，外层循环次数从 2 变成 6，**cost 显著上升**（这里从 12.4 涨到 48.6）；
- 更糟的是 `o.status = 1` 这个高选择性的过滤条件被推迟到最后才生效，中间步骤白白放大了行数。

这恰好证明**优化器原来的选择是对的**——这也正是做这个实验的价值：Hint 主要用于**验证猜想**，而不是常规武器。真要用（比如优化器确实选错了），也应优先按「改写 SQL → 调整索引 → `ANALYZE TABLE` 更新统计信息 → 最后才是 Hint」的顺序，并在代码里留注释说明原因和有效期。

想看真实耗时而不是估算，把 `FORMAT=TREE` 换成 `ANALYZE`：

```sql
EXPLAIN ANALYZE SELECT ... ;
-- 每个节点会多出 (actual time=首行耗时..总耗时 rows=实际行数 loops=循环次数)
-- 重点看「估算 rows」与「actual rows」是否差了数量级 —— 差得多就 ANALYZE TABLE
```
