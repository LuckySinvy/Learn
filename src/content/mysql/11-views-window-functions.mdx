# 视图与窗口函数

本章两个主题：视图——把复杂查询封装成「虚拟表」；窗口函数——8.0 最值得学的特性，一举解决排名、分组 TOP N、环比这些用普通 SQL 写起来非常拧巴的问题。

## 1. 视图（VIEW）

### 1.1 创建与使用

视图是**存起来的 SELECT 语句**，用起来像表，但本身不存数据：

<Playground
  language="mysql"
  id="mysql-11-1"
  title="创建并查询视图"
  code={`CREATE VIEW v_order_detail AS
SELECT o.id AS order_id, o.order_no, o.status,
       u.username, p.name AS product_name, c.name AS category_name,
       oi.quantity, oi.price, oi.quantity * oi.price AS item_amount
FROM orders o
JOIN users u        ON u.id = o.user_id
JOIN order_items oi ON oi.order_id = o.id
JOIN products p     ON p.id = oi.product_id
JOIN categories c   ON c.id = p.category_id;

-- 之后五表 JOIN 一行搞定
SELECT order_no, username, product_name, category_name, item_amount
FROM v_order_detail WHERE username = 'alice';`}
/>

视图的价值：

- **封装复杂性**：报表、BI 工具直接查视图，不用人人都会写五表 JOIN；
- **权限隔离**：只授予视图的 SELECT 权限，隐藏敏感列（如手机号）；
- **稳定接口**：底层表重构时改视图定义，调用方无感。

管理命令：

```sql
SHOW CREATE VIEW v_order_detail\G
ALTER VIEW v_order_detail AS SELECT ...;   -- 修改定义
DROP VIEW v_order_detail;
```

### 1.2 可更新视图与性能真相

满足条件的视图可以直接 UPDATE/INSERT（单表、无聚合/DISTINCT/GROUP BY/UNION 等），修改会落到基表。带 `WITH CHECK OPTION` 可阻止把行改出视图可见范围：

```sql
CREATE VIEW v_active_users AS
SELECT id, username, email FROM users WHERE status = 1
WITH CHECK OPTION;

UPDATE v_active_users SET username = 'alice2' WHERE id = 1;  -- OK，落到 users
UPDATE v_active_users SET status = 2 WHERE id = 1;           -- 报错：status 不在视图列里
```

<Callout type="warn" title="视图不是性能优化手段">
MySQL 视图默认用 MERGE 算法把视图定义合并进外层查询——查视图和直接写完整 SQL 性能一样，**不会更快**。含 GROUP BY 等无法合并的视图会走 TEMPTABLE 算法（先物化成临时表），外层条件无法下推到临时表内，反而可能**更慢**。视图是为可维护性服务的，别指望它提速；MySQL 也没有 PostgreSQL 那种物化视图。
</Callout>

## 2. 窗口函数：改变游戏规则

### 2.1 与 GROUP BY 的本质区别

- GROUP BY：多行**坍缩**成一行，明细丢失；
- 窗口函数：**每行保留**，只是在行旁边「开个窗」看到同组其他行算出的值。

<Playground
  language="mysql"
  id="mysql-11-2"
  title="窗口函数：明细与汇总同框"
  code={`SELECT order_no, user_id, total_amount,
       SUM(total_amount) OVER (PARTITION BY user_id) AS user_total,
       ROUND(total_amount / SUM(total_amount) OVER (PARTITION BY user_id), 4) AS pct
FROM orders
ORDER BY user_id, order_no;

-- 对比 GROUP BY：明细被坍缩掉了
SELECT user_id, SUM(total_amount) AS user_total
FROM orders GROUP BY user_id;`}
/>

每行都在，旁边多了「本用户总额」和「本单占比」——GROUP BY 做不到这种「明细 + 汇总同框」。

语法骨架：

```text
函数() OVER (
  PARTITION BY 分组列     -- 窗口按什么分区（可省略 = 全表一个窗口）
  ORDER BY 排序列          -- 窗口内按什么排序（排名/偏移函数必需）
  [ROWS BETWEEN ...]      -- 窗口帧（滑动范围，做移动平均时用）
)
```

### 2.2 排名三兄弟：ROW_NUMBER / RANK / DENSE_RANK

区别在**并列名次怎么处理**：

<Playground
  language="mysql"
  id="mysql-11-3"
  title="排名三兄弟"
  code={`-- 无并列时三者完全一致
SELECT name, price,
       ROW_NUMBER() OVER (ORDER BY price DESC) AS row_num,
       RANK()       OVER (ORDER BY price DESC) AS rnk,
       DENSE_RANK() OVER (ORDER BY price DESC) AS dense_rnk
FROM products;

-- 按分类排序制造并列，差异立刻显现
SELECT name, category_id,
       ROW_NUMBER() OVER (ORDER BY category_id) AS row_num,
       RANK()       OVER (ORDER BY category_id) AS rnk,
       DENSE_RANK() OVER (ORDER BY category_id) AS dense_rnk
FROM products;`}
/>

- ROW_NUMBER：严格递增 1,2,3，并列也硬排先后；
- RANK：并列同名次，之后**跳号**（1,1,3）；
- DENSE_RANK：并列同名次，**不跳号**（1,1,2）。

### 2.3 分组内 TOP N：最高频的面试题与实战题

「每个分类价格最高的 2 个商品」——GROUP BY 无解，窗口函数标准解法：

<Playground
  language="mysql"
  id="mysql-11-4"
  title="分组内 TOP N"
  code={`WITH ranked AS (
  SELECT p.id, p.category_id, p.name, p.price,
         ROW_NUMBER() OVER (PARTITION BY category_id ORDER BY price DESC) AS rn
  FROM products p
)
SELECT category_id, name, price
FROM ranked
WHERE rn <= 2;`}
/>

同样的模板还能解决：每个用户最新一笔订单、每台设备最后一次上报、每篇文章最热的 3 条评论……记住这个 `PARTITION BY ... ORDER BY ... WHERE rn <= N` 模式，一招吃遍天。

注意：窗口函数不能直接写在 WHERE 里（逻辑执行顺序上 WHERE 先于窗口计算），必须像上面那样套一层 CTE 或派生表。

### 2.4 LAG / LEAD：跨行取值

LAG 取当前行**前面**第 n 行的值，LEAD 取后面的，做环比/间隔分析必备：

```sql
-- 每日 GMV 与环比增幅
WITH daily AS (
  SELECT DATE(created_at) AS d, SUM(total_amount) AS gmv
  FROM orders GROUP BY DATE(created_at)
)
SELECT d, gmv,
       LAG(gmv)  OVER (ORDER BY d)              AS prev_gmv,
       gmv - LAG(gmv) OVER (ORDER BY d)          AS diff,
       LAG(gmv, 7) OVER (ORDER BY d)             AS same_day_last_week
FROM daily;
```

再比如「用户相邻两单的间隔天数」：

```sql
SELECT user_id, created_at,
       DATEDIFF(created_at,
                LAG(created_at) OVER (PARTITION BY user_id ORDER BY created_at)
       ) AS days_since_last_order
FROM orders;
```

### 2.5 聚合窗口与移动平均

聚合函数 + ORDER BY 默认是「从分区开头累计到当前行」：

```sql
-- 累计 GMV 与 7 日移动平均
WITH daily AS (
  SELECT DATE(created_at) AS d, SUM(total_amount) AS gmv
  FROM orders GROUP BY DATE(created_at)
)
SELECT d, gmv,
       SUM(gmv) OVER (ORDER BY d) AS running_total,
       AVG(gmv) OVER (ORDER BY d ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS ma7
FROM daily;
```

`ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` 定义了 7 行的滑动窗口帧。

还有 `NTILE(n)`（把分区均分成 n 桶，做用户分层）和 `FIRST_VALUE` / `LAST_VALUE`（取窗口首尾值），语法同理。

## 小结

- 视图封装复杂查询、隔离权限，但不是性能工具（MERGE 不加速、TEMPTABLE 可能更慢）
- 窗口函数在保留明细的同时计算组内聚合/排名/偏移
- 排名三兄弟：ROW_NUMBER 硬排、RANK 跳号、DENSE_RANK 不跳号
- 分组 TOP N 模板：CTE + `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)` + `WHERE rn <= N`
- LAG/LEAD 做环比与间隔，ROWS BETWEEN 做移动平均

**参考答案：**

**1. 创建 v_user_stats 视图并授权**

```sql
CREATE VIEW v_user_stats AS
SELECT u.id                                AS user_id,
       u.username,
       COUNT(o.id)                         AS order_count,
       IFNULL(SUM(o.total_amount), 0)      AS total_spent,
       MAX(o.created_at)                   AS last_order_at
FROM users u
LEFT JOIN orders o
       ON o.user_id = u.id AND o.status IN (1, 2, 3)
GROUP BY u.id, u.username;

SELECT * FROM v_user_stats ORDER BY total_spent DESC;
```

设计要点：

- 用 **LEFT JOIN** 保证没下过单的用户也出现在结果里；
- **`COUNT(o.id)` 而不是 `COUNT(*)`**，否则无订单用户会被数成 1；
- **`IFNULL(SUM(...), 0)`**，SUM 对空集返回 NULL 而不是 0；
- 「只算有效订单」的条件 `o.status IN (1,2,3)` 放在 **ON** 里，放 WHERE 会让 LEFT JOIN 退化成 INNER JOIN。

创建只读账号并只授予视图权限：

```sql
CREATE USER 'report'@'%' IDENTIFIED BY 'R3port#Pass';

-- 只给视图，不给底层表
GRANT SELECT ON shop.v_user_stats TO 'report'@'%';

FLUSH PRIVILEGES;
SHOW GRANTS FOR 'report'@'%';
```

用 report 登录验证：查 `v_user_stats` 成功，查 `users` / `orders` 直接被拒：

```text
ERROR 1142 (42000): SELECT command denied to user 'report'@'%' for table 'users'
```

**这正是视图最实用的价值之一——权限隔离**。视图默认以 `DEFINER`（创建者）的权限执行，所以调用方即使没有底层表权限也能查视图，同时看不到视图里没暴露的敏感列（如 phone、email）。若希望改为按调用者权限校验，创建时加 `SQL SECURITY INVOKER`。

**2. 每个用户金额最大的那一笔订单（完整行）**

窗口函数写法（推荐）：

```sql
WITH ranked AS (
  SELECT o.*,
         ROW_NUMBER() OVER (
           PARTITION BY user_id
           ORDER BY total_amount DESC, id DESC
         ) AS rn
  FROM orders o
)
SELECT id, order_no, user_id, status, total_amount, created_at
FROM ranked
WHERE rn = 1;
```

注意两点：

- 窗口函数**不能直接写在 WHERE 里**（逻辑执行顺序上 WHERE 先于窗口计算），必须套一层 CTE 或派生表再过滤 `rn`。
- ORDER BY 里补 `, id DESC` 作为 tie-breaker：金额并列时 `ROW_NUMBER` 仍会硬排出先后，但不加确定的第二排序键，结果就不可复现。若希望**并列的都要**，把 `ROW_NUMBER()` 换成 `RANK()`。

不用窗口函数的三种传统写法：

```sql
-- 写法 A：关联子查询（可读性尚可，但每行都要跑一次子查询）
SELECT o.*
FROM orders o
WHERE o.total_amount = (
  SELECT MAX(o2.total_amount) FROM orders o2 WHERE o2.user_id = o.user_id
);
```

```sql
-- 写法 B：先聚合出最大值，再 JOIN 回明细
SELECT o.*
FROM orders o
JOIN (
  SELECT user_id, MAX(total_amount) AS max_amt
  FROM orders GROUP BY user_id
) m ON m.user_id = o.user_id AND m.max_amt = o.total_amount;
```

```sql
-- 写法 C：反连接——「不存在比我更大的」
SELECT o.*
FROM orders o
WHERE NOT EXISTS (
  SELECT 1 FROM orders o2
  WHERE o2.user_id = o.user_id AND o2.total_amount > o.total_amount
);
```

**可读性与正确性对比**：

| | 窗口函数 | 传统写法 |
|---|---|---|
| 可读性 | 一眼看懂「按用户分区、按金额排序、取第 1 名」 | 要在脑子里模拟两遍扫描 |
| 并列处理 | `ROW_NUMBER` 精确取 1 条，`RANK` 取全部，**可控** | A/B/C 三种写法**都会返回多行**，且无法只取一条 |
| 取 Top-N（N>1） | 改 `WHERE rn <= N` 即可 | 几乎写不出来 |
| 扫描次数 | 一遍 | A 是关联子查询、B/C 需要两次访问表 |

窗口函数最大的优势是**并列可控**和**易扩展到 Top-N**。传统写法 B 还有个隐蔽 bug：如果两笔订单金额相同且都等于最大值，JOIN 会返回两行——很多线上「数据莫名多一行」的报表问题就出在这里。

这个 `PARTITION BY ... ORDER BY ... WHERE rn <= N` 模板可以套用到：每个用户最新一单、每台设备最后一次上报、每篇文章最热评论……记住它就够了。

**3. 每日订单量的 3 日移动平均与累计值**

```sql
WITH daily AS (
  SELECT DATE(created_at)   AS d,
         COUNT(*)           AS order_cnt,
         SUM(total_amount)  AS gmv
  FROM orders
  GROUP BY DATE(created_at)
)
SELECT d,
       order_cnt,
       SUM(order_cnt) OVER (ORDER BY d)                AS running_total,
       ROUND(AVG(order_cnt) OVER (
         ORDER BY d
         ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
       ), 2)                                            AS ma3
FROM daily
ORDER BY d;
```

```text
+------------+-----------+---------------+------+
| d          | order_cnt | running_total | ma3  |
+------------+-----------+---------------+------+
| 2026-07-01 |         1 |             1 | 1.00 |
| 2026-07-02 |         1 |             2 | 1.00 |
| 2026-07-03 |         1 |             3 | 1.00 |
| 2026-07-04 |         1 |             4 | 1.00 |
+------------+-----------+---------------+------+
```

关键理解：

- **`SUM(x) OVER (ORDER BY d)` 就是累计求和**。带 ORDER BY 的聚合窗口默认帧是 `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`，即「从分区开头累加到当前行」。不带 ORDER BY 时帧是整个分区，得到的是全局总和。
- **`ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` 是 3 行的滑动窗口**（前 2 行 + 当前行）。N 日移动平均要写 `N-1 PRECEDING`，这里差一错很常见。
- 前两行因为「不足 3 天」，算的是 1 天和 2 天的平均，不是 NULL。要严格只在满 3 天时出值，需要额外判断：

```sql
CASE WHEN ROW_NUMBER() OVER (ORDER BY d) >= 3
     THEN ROUND(AVG(order_cnt) OVER (ORDER BY d ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 2)
END AS ma3_strict
```

**`ROWS` 与 `RANGE` 的区别**（面试常问）：`ROWS` 按**物理行数**取，`RANGE` 按**值的范围**取。如果日期有断档（某天没订单，该行根本不存在），`ROWS 2 PRECEDING` 取的是「前两个有数据的日子」而不是「前两个自然日」，移动平均就失真了。严谨做法是先用第 10 章的递归 CTE 生成完整日期序列，LEFT JOIN 补 0 后再算：

```sql
WITH RECURSIVE dates AS (
  SELECT DATE('2026-07-01') AS d
  UNION ALL
  SELECT d + INTERVAL 1 DAY FROM dates WHERE d < '2026-07-31'
),
daily AS (
  SELECT dt.d, COUNT(o.id) AS order_cnt
  FROM dates dt
  LEFT JOIN orders o ON DATE(o.created_at) = dt.d
  GROUP BY dt.d
)
SELECT d, order_cnt,
       SUM(order_cnt) OVER (ORDER BY d) AS running_total,
       ROUND(AVG(order_cnt) OVER (ORDER BY d ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 2) AS ma3
FROM daily
ORDER BY d;
```
