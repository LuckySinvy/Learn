# 多表连接 JOIN

关系型数据库的精髓就在「关系」——数据拆在多张表里，用 JOIN 按需拼回来。本章从四种 JOIN 的语义讲到底层的连接算法，让你既能写对，也能明白为什么有的 JOIN 快有的慢。

## 1. JOIN 的语义模型

理解 JOIN 的正确心智模型：**逐行匹配**。以 `A JOIN B ON 条件` 为例，拿 A 的每一行去 B 里找满足 ON 条件的行，找到就拼成一行输出。

```text
orders (A)                  users (B)
┌────┬─────────┐            ┌────┬──────────┐
│ id │ user_id │            │ id │ username │
├────┼─────────┤   ON       ├────┼──────────┤
│ 1  │   1     │──匹配──▶   │ 1  │ alice    │
│ 2  │   2     │──匹配──▶   │ 2  │ bob      │
│ 3  │   1     │──匹配──▶   │ 1  │ alice    │
│ 4  │   99    │──✗ 无匹配  │ 3  │ carol    │
└────┴─────────┘            └────┴──────────┘
INNER JOIN：丢弃 order 4        LEFT JOIN：保留 order 4，用户列补 NULL
```

## 2. 四种 JOIN

### 2.1 INNER JOIN：只保留两边都匹配的行

<Playground
  language="mysql"
  id="mysql-09-1"
  title="INNER JOIN：只留匹配行"
  code={`SELECT o.order_no, o.total_amount, u.username
FROM orders o
INNER JOIN users u ON o.user_id = u.id
WHERE o.status = 1;`}
/>

`INNER` 可省略，`JOIN` 默认就是内连接。

### 2.2 LEFT JOIN：左表全保留，右表没匹配补 NULL

<Playground
  language="mysql"
  id="mysql-09-2"
  title="LEFT JOIN 统计与反连接"
  code={`-- 所有用户及其订单数（包括从没下过单的用户）
SELECT u.id, u.username, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.username;

-- 对比：COUNT(*) 会把补 NULL 的那行也数成 1
SELECT u.id, u.username, COUNT(*) AS wrong_count
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.username;

-- 反连接：从没下过单的用户
SELECT u.id, u.username
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;`}
/>

注意 `COUNT(o.id)` 而不是 `COUNT(*)`：没订单的用户，o.id 是 NULL，COUNT(o.id) 正确计为 0；COUNT(*) 会把那行 NULL 也数成 1——上面第二条语句可以直观看到差异。

第三条语句是 LEFT JOIN 的经典用法——**找「没有」的行**（反连接）。

### 2.3 RIGHT JOIN

右表全保留，实践中几乎总能改写成 LEFT JOIN（交换表顺序），团队里统一用 LEFT JOIN 可读性更好。

### 2.4 CROSS JOIN：笛卡尔积

无条件两两组合，A 有 m 行、B 有 n 行则输出 m×n 行。偶尔用于生成组合（如「日期 × 门店」补全报表空洞），日常出现多半是**忘写 ON 条件的事故**。

<Callout type="warn" title="ON 与 WHERE 在 LEFT JOIN 里完全不同">
INNER JOIN 里条件放 ON 或 WHERE 结果一样；LEFT JOIN 里不一样：ON 里的右表条件只影响「怎么匹配」（不匹配的左表行照样保留、右表列补 NULL），而 WHERE 里的右表条件在拼接后过滤（会把补了 NULL 的行删掉，LEFT JOIN 悄悄退化成 INNER JOIN）。例：想看「所有用户及其已支付订单」，`o.status = 1` 必须放 ON；放 WHERE 就只剩有已支付订单的用户了。
</Callout>

亲手跑一遍，对比两者行数差异：

<Playground
  language="mysql"
  id="mysql-09-3"
  title="ON 与 WHERE 的差别"
  code={`-- 条件放 ON：所有用户都在，没有已支付订单的补 NULL
SELECT u.username, o.order_no, o.status
FROM users u
LEFT JOIN orders o ON o.user_id = u.id AND o.status = 1;

-- 条件放 WHERE：补 NULL 的行被过滤，退化成 INNER JOIN
SELECT u.username, o.order_no, o.status
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.status = 1;`}
/>

## 3. 自连接与多表 JOIN

自连接：同一张表用两个别名，当两张表用，分类的父子关系是典型场景；多表 JOIN 则能串起完整业务链路。下面两条一起跑：

<Playground
  language="mysql"
  id="mysql-09-4"
  title="自连接与五表 JOIN 报表"
  code={`-- 自连接：分类的父子关系
SELECT c.name AS child, p.name AS parent
FROM categories c
LEFT JOIN categories p ON c.parent_id = p.id;

-- 订单明细报表：谁、买了什么、什么分类、花了多少
SELECT o.order_no, u.username, p.name AS product,
       c.name AS category, oi.quantity, oi.price
FROM orders o
JOIN users u        ON u.id = o.user_id
JOIN order_items oi ON oi.order_id = o.id
JOIN products p     ON p.id = oi.product_id
JOIN categories c   ON c.id = p.category_id
WHERE o.status IN (1, 2, 3);`}
/>

## 4. 驱动表与 JOIN 顺序

JOIN 执行时有**驱动表**（外层，逐行取出）和**被驱动表**（内层，按连接条件查找）。你写的表顺序只是「建议」，优化器会自己决定谁做驱动表（LEFT JOIN 的左表除外，语义上必须保留）。

核心原则：**小表（过滤后行数少的表）做驱动表，被驱动表的连接列必须有索引**。

- 驱动表决定外层循环次数：结果集越小，循环越少；
- 被驱动表每次都要按连接条件查找：有索引是一次 B+ 树查找，没索引是一次全表扫描。

## 5. JOIN 算法

### 5.1 Nested-Loop Join（NLJ，嵌套循环）

被驱动表连接列**有索引**时的算法：

```text
for row in 驱动表(过滤后):            -- 外层：扫驱动表
    用 row 的连接值走被驱动表的索引     -- 内层：一次索引查找
    匹配则输出拼接行
```

成本约等于「驱动表行数 × 一次索引查找」，这是理想状态。

### 5.2 Block Nested-Loop（BNL）与 Hash Join

被驱动表连接列**没有索引**时，8.0.18 之前用 BNL：把驱动表分块读进 join buffer，被驱动表全表扫描逐块比对——被驱动表要被扫很多遍，极慢。

**8.0.18 起默认用 Hash Join** 取代 BNL：

```text
1. 构建：把驱动表（小表）按连接列建哈希表（放进 join buffer）
2. 探测：全表扫描被驱动表，每行按连接列查哈希表，O(1) 匹配
```

Hash Join 只需两边各扫一遍，比 BNL 好得多，尤其适合两张大表无索引等值连接、以及分析型查询。EXPLAIN FORMAT=TREE 里能看到 `hash join` 字样。

| 算法 | 触发条件 | 成本特征 |
|---|---|---|
| NLJ（索引） | 被驱动表连接列有索引 | 驱动表行数 × 索引查找，OLTP 最优 |
| Hash Join | 等值连接、无可用索引（8.0.18+） | 两表各扫一遍 + 哈希表内存 |
| BNL | 老版本无索引兜底 | 被驱动表反复全扫，应避免 |

<Callout type="tip" title="JOIN 慢的排查顺序">
1. 被驱动表连接列有没有索引？（EXPLAIN 看内层表 type 是否为 ref/eq_ref）
2. 两边连接列类型和字符集是否一致？不一致会隐式转换导致索引失效（如 utf8mb4 表 JOIN utf8 表的字符串列）。
3. 驱动表是不是选大了？可用 STRAIGHT_JOIN 强制顺序做实验，但生产慎用。
</Callout>

## 6. USING 与 NATURAL JOIN

```sql
-- 两表连接列同名时可用 USING 简写
SELECT o.order_no, u.username
FROM orders o JOIN users u USING (id);  -- 仅当列名都叫 id 才对，此例其实不适用
```

`NATURAL JOIN` 自动按所有同名列连接——列名巧合就出错，**不要在生产使用**。显式 ON 永远是最安全的。

## 小结

- JOIN 心智模型：逐行匹配拼接；INNER 只留匹配、LEFT 保左表补 NULL
- LEFT JOIN 中右表的过滤条件放 ON 还是 WHERE，语义完全不同
- LEFT JOIN + `IS NULL` 是「找没有」的标准姿势
- 小表驱动大表，被驱动表连接列必须有索引（NLJ）
- 8.0.18+ 无索引等值连接走 Hash Join，比老的 BNL 快得多

<Answer>
**参考答案：**

**1. 每个分类的商品数（含无商品分类）**

```sql
SELECT c.id,
       c.name,
       COUNT(p.id) AS product_count
FROM categories c
LEFT JOIN products p ON p.category_id = c.id
GROUP BY c.id, c.name
ORDER BY product_count DESC, c.id;
```

**COUNT 的写法是本题的考点**：

- `COUNT(p.id)` —— 正确。没有商品的分类，LEFT JOIN 补出的 `p.id` 是 NULL，COUNT 跳过 NULL，结果为 **0**。
- `COUNT(*)` —— 错误。它数的是「行数」，没有商品的分类也占一行（右表全 NULL），会被数成 **1**。

对比一下就一目了然：

```sql
SELECT c.id, c.name,
       COUNT(p.id) AS right_count,
       COUNT(*)    AS wrong_count
FROM categories c
LEFT JOIN products p ON p.category_id = c.id
GROUP BY c.id, c.name;
-- 「图书」这类没有直属商品的分类：right_count = 0，wrong_count = 1
```

规则可以记成：**LEFT JOIN 后统计右表数量，一律 `COUNT(右表的非空列)`**，通常用右表主键。同理 `SUM(p.price)` 对空组返回 NULL，需要 `IFNULL(SUM(p.price), 0)`。

**2. 待支付金额统计：ON 与 WHERE 的差别**

第一问，只要「有待支付订单」的用户（内连接语义）：

```sql
SELECT u.id, u.username,
       COUNT(o.id)            AS pending_count,
       SUM(o.total_amount)    AS pending_amount
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE o.status = 0
GROUP BY u.id, u.username;
```

第二问，所有用户都要（无待支付则为 0）——**条件必须放进 ON**：

```sql
SELECT u.id, u.username,
       COUNT(o.id)                       AS pending_count,
       IFNULL(SUM(o.total_amount), 0)    AS pending_amount
FROM users u
LEFT JOIN orders o
       ON o.user_id = u.id AND o.status = 0    -- 条件在 ON 里
GROUP BY u.id, u.username
ORDER BY pending_amount DESC;
```

**如果把 `o.status = 0` 挪到 WHERE**：

```sql
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.status = 0     -- ← LEFT JOIN 悄悄退化成 INNER JOIN
```

对没有待支付订单的用户，LEFT JOIN 补出的 `o.status` 是 NULL，而 `NULL = 0` 的结果是 UNKNOWN，WHERE 只保留 TRUE，于是这些用户**整行被过滤掉**了，回到了第一问的语义。

一句话总结这个高频陷阱：

| 位置 | 作用时机 | 效果 |
|---|---|---|
| `ON` 里的右表条件 | 拼接**时**决定「哪些右表行算匹配」 | 左表行全保留，不匹配的右表列补 NULL |
| `WHERE` 里的右表条件 | 拼接**后**过滤结果行 | 补 NULL 的行被删掉，LEFT JOIN 退化为 INNER JOIN |

唯一的例外是 `WHERE o.id IS NULL`——它恰恰是**利用**这个机制来做反连接（找「没有」的行）。

INNER JOIN 里则没有这个区别，条件放 ON 或 WHERE 结果完全一样（优化器也会等价改写）。

**3. EXPLAIN 观察 JOIN 执行计划**

```sql
EXPLAIN SELECT o.order_no, u.username
FROM orders o
JOIN users u ON u.id = o.user_id
WHERE o.status = 1;
```

典型输出：

```text
+----+-------+------+---------+---------+-------------+------+-------------+
| id | table | type | key     | ref     | rows | Extra              |
+----+-------+------+---------+---------+------+--------------------+
|  1 | o     | ALL  | NULL    | NULL    |    4 | Using where        |
|  1 | u     | eq_ref | PRIMARY | shop.o.user_id | 1 | NULL        |
+----+-------+------+---------+---------+------+--------------------+
```

怎么读：

- **`id` 相同的行，从上往下就是 JOIN 顺序**——第一行 `o` 是**驱动表**（外层循环），第二行 `u` 是**被驱动表**（内层查找）。
- 被驱动表 `u` 的 `key = PRIMARY`、`type = eq_ref`，说明每次拿 `o.user_id` 去 users 的**主键索引**做一次等值查找，命中唯一一行——这是 NLJ 的最优形态。`eq_ref` 比 `ref` 更好，表示走的是主键或唯一索引。
- `ref` 列的 `shop.o.user_id` 明确告诉你「用驱动表的哪个值去探测」。
- 驱动表 `o` 是 `ALL`（全表扫描）是因为示例数据太少，优化器认为扫 4 行比走索引便宜；数据量大时给 `status` 加索引后会变成 `ref`。

看得更清楚可以用树形输出：

```sql
EXPLAIN FORMAT=TREE SELECT o.order_no, u.username
FROM orders o JOIN users u ON u.id = o.user_id WHERE o.status = 1;
-- -> Nested loop inner join
--     -> Filter: (o.status = 1)  (cost=... rows=...)
--         -> Table scan on o
--     -> Single-row index lookup on u using PRIMARY (id = o.user_id)
```

**模拟无索引 JOIN 触发 Hash Join**：不要真去动 users 的主键，复制一张无索引的表更安全：

```sql
CREATE TABLE users_noidx AS SELECT * FROM users;   -- CREATE TABLE AS 不会复制索引

EXPLAIN FORMAT=TREE
SELECT o.order_no, u.username
FROM orders o
JOIN users_noidx u ON u.id = o.user_id;
```

```text
-> Inner hash join (u.id = o.user_id)
    -> Table scan on o
    -> Hash
        -> Table scan on u
```

出现 `Inner hash join` 就说明走了 **Hash Join**（8.0.18+ 默认开启）：先把小表按连接列构建成哈希表放进 join buffer，再全表扫描另一张表逐行探测，两边各扫一遍即可。这比 8.0.18 之前的 BNL（被驱动表要被反复全表扫描）快得多。

注意 `EXPLAIN`（传统表格格式）里看不到 `hash join` 字样，只会在 Extra 显示 `Using join buffer (hash join)`，所以**要看 JOIN 算法务必用 `FORMAT=TREE`**。

清理：

```sql
DROP TABLE users_noidx;
```
