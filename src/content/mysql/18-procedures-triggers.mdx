# 存储过程、触发器与事件

MySQL 允许把逻辑放进数据库：存储过程封装多条 SQL、触发器在增删改时自动执行、事件调度器定时跑任务。这些能力**要会**（造测试数据、接手遗留系统都用得上），但也要清楚**为什么现代互联网架构普遍把它们请出生产环境**。本章两件事都讲。

## 1. 存储过程（PROCEDURE）

### 1.1 基本语法

<Playground
  language="mysql"
  id="mysql-18-1"
  title="定义并调用存储过程"
  code={`DELIMITER //

CREATE PROCEDURE get_user_orders(IN p_user_id BIGINT, OUT p_total DECIMAL(12,2))
BEGIN
  SELECT order_no, status, total_amount, created_at
  FROM orders
  WHERE user_id = p_user_id
  ORDER BY created_at DESC;

  SELECT IFNULL(SUM(total_amount), 0) INTO p_total
  FROM orders
  WHERE user_id = p_user_id AND status IN (1,2,3);
END //

DELIMITER ;

-- 调用
CALL get_user_orders(1, @total);
SELECT @total AS paid_total;

SHOW PROCEDURE STATUS WHERE db = 'shop';`}
/>

要点：

- `DELIMITER //` 临时改结束符——过程体里有分号，得让客户端别在第一个分号处就把语句切断；
- 参数三种方向：`IN`（入参）、`OUT`（出参）、`INOUT`；
- `SELECT ... INTO 变量` 给变量赋值；`@total` 是会话级用户变量。

### 1.2 流程控制与批量造数

存储过程最实用的场景：**造测试数据**（第 7 章练习深分页就需要百万行）：

```sql
DELIMITER //

CREATE PROCEDURE gen_test_orders(IN p_count INT)
BEGIN
  DECLARE i INT DEFAULT 0;
  DECLARE v_user BIGINT;

  WHILE i < p_count DO
    SET v_user = FLOOR(1 + RAND() * 3);
    INSERT INTO orders (order_no, user_id, status, total_amount, created_at)
    VALUES (CONCAT('T', LPAD(i, 10, '0')),
            v_user,
            FLOOR(RAND() * 5),
            ROUND(RAND() * 10000, 2),
            NOW() - INTERVAL FLOOR(RAND() * 365) DAY);
    SET i = i + 1;
    IF i % 1000 = 0 THEN
      COMMIT;               -- 分批提交，避免超大事务
    END IF;
  END WHILE;
END //

DELIMITER ;

SET autocommit = 0;
CALL gen_test_orders(100000);
COMMIT;
SET autocommit = 1;
```

其他流程控制：`IF/ELSEIF/ELSE`、`CASE`、`REPEAT ... UNTIL`、`LOOP + LEAVE`，以及游标（CURSOR）逐行处理结果集——语法都不难，需要时查手册即可。

管理命令：

```sql
SHOW PROCEDURE STATUS WHERE db = 'shop';
SHOW CREATE PROCEDURE get_user_orders\G
DROP PROCEDURE IF EXISTS get_user_orders;
```

## 2. 自定义函数（FUNCTION）

函数必须返回单值，能嵌进 SQL 表达式里用：

<Playground
  language="mysql"
  id="mysql-18-2"
  title="自定义函数"
  code={`DELIMITER //

CREATE FUNCTION order_status_text(p_status TINYINT)
RETURNS VARCHAR(10)
DETERMINISTIC
BEGIN
  RETURN CASE p_status
    WHEN 0 THEN '待支付' WHEN 1 THEN '已支付' WHEN 2 THEN '已发货'
    WHEN 3 THEN '已完成' ELSE '已取消' END;
END //

DELIMITER ;

SELECT order_no, order_status_text(status) AS st FROM orders;`}
/>

与过程的区别：函数有 RETURNS、在表达式中调用、限制更多（不能返回结果集、默认要求声明 DETERMINISTIC 等特性，开了 binlog 时未声明会报 1418 错误）。

**注意**：SQL 里对每一行都调用一次函数，无法利用索引，大表上性能差。展示映射这种事放应用层做更好。

## 3. 触发器（TRIGGER）

在表的 INSERT/UPDATE/DELETE 前后自动执行，`NEW` / `OLD` 引用新旧行：

<Playground
  language="mysql"
  id="mysql-18-3"
  title="用触发器做价格审计"
  code={`-- 审计：记录 products 价格变动
CREATE TABLE product_price_log (
  id         BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  product_id BIGINT UNSIGNED NOT NULL,
  old_price  DECIMAL(10,2)   NOT NULL,
  new_price  DECIMAL(10,2)   NOT NULL,
  changed_at DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP
);

DELIMITER //

CREATE TRIGGER trg_product_price_audit
AFTER UPDATE ON products
FOR EACH ROW
BEGIN
  IF OLD.price <> NEW.price THEN
    INSERT INTO product_price_log (product_id, old_price, new_price)
    VALUES (OLD.id, OLD.price, NEW.price);
  END IF;
END //

DELIMITER ;

UPDATE products SET price = 4599.00 WHERE id = 1;
UPDATE products SET stock = stock - 1 WHERE id = 1;   -- 价格没变，不留痕
SELECT * FROM product_price_log;`}
/>

时机与事件组合：BEFORE/AFTER × INSERT/UPDATE/DELETE，每张表每种组合各最多一个（8.0 允许同组合多个，按顺序执行）。BEFORE 触发器还能改 `NEW.列` 的值（如自动填充、标准化数据）。

## 4. 事件调度器（EVENT）

数据库内置的定时任务：

```sql
-- 确认调度器开启
SHOW VARIABLES LIKE 'event_scheduler';
SET GLOBAL event_scheduler = ON;

-- 每天凌晨 3 点清理 90 天前的价格日志
CREATE EVENT ev_purge_price_log
ON SCHEDULE EVERY 1 DAY STARTS '2026-08-01 03:00:00'
DO
  DELETE FROM product_price_log
  WHERE changed_at < NOW() - INTERVAL 90 DAY
  LIMIT 10000;

SHOW EVENTS FROM shop;
```

## 5. 为什么生产上要慎用

这些特性在传统企业软件（Oracle 时代）里是主力，但互联网架构下普遍被限制使用，原因是系统性的：

### 5.1 共性问题

1. **不可观测**：逻辑藏在数据库里，应用日志、链路追踪、APM 全部失明。触发器尤甚——一条 UPDATE 悄悄引发连锁写入，排查者一脸茫然；
2. **难以版本管理与发布**：代码有 Git、CR、灰度、回滚，存储过程往往是 DBA 手工执行的脚本，变更不可追溯；
3. **难调试难测试**：没有断点、没有单测框架、报错信息贫瘠；
4. **占用数据库 CPU**：数据库是最难水平扩展的组件，应用服务器可以加机器，把计算塞进数据库等于把负载压到最脆弱的一环；
5. **分库分表不兼容**：数据拆到多个实例后，跨库的过程/触发器逻辑直接失效；
6. **主从与迁移隐患**：基于语句的复制下触发器行为可能不一致；换数据库（如迁 PG/TiDB）时这些方言代码全要重写。

### 5.2 各自的合理保留区

| 特性 | 可以用的场景 |
|---|---|
| 存储过程 | 造测试数据、一次性数据修复/迁移脚本、DBA 运维工具 |
| 函数 | 极简单且确定性的转换（且团队认可） |
| 触发器 | 遗留系统兼容、简单审计留痕（新系统建议用 binlog 订阅代替，如 Canal/Debezium） |
| 事件 | 无外部调度设施的小项目定时清理（有 K8s CronJob/XXL-Job 就用它们） |

<Callout type="warn" title="触发器是隐形炸弹">
接手老系统时务必先执行 `SELECT trigger_name, event_object_table, action_timing, event_manipulation FROM information_schema.triggers WHERE trigger_schema = 'shop';` 摸清所有触发器，否则「我只改了一行，为什么另一张表变了」会让你怀疑人生。批量导数据前尤其要检查——触发器会被逐行触发，性能雪崩。
</Callout>

<Callout type="info" title="业务逻辑的归属原则">
一句话准则：**数据的完整性约束（唯一、非空、外键）交给数据库，业务流程逻辑留在应用代码**。前者是数据的固有属性，后者需要可观测、可测试、可发布的工程设施。
</Callout>

## 小结

- 存储过程封装多条 SQL，DELIMITER + IN/OUT 参数 + 流程控制；造数据神器
- 函数返回单值可嵌入表达式，但逐行调用性能差
- 触发器 BEFORE/AFTER × 增删改自动执行，NEW/OLD 引用行；审计可用但要克制
- 事件调度器是库内 cron，有外部调度就别用
- 生产慎用的根因：不可观测、难发布、占数据库 CPU、不兼容分库分表

**参考答案：**

**1. 存储过程造 10 万行测试数据**

```sql
DROP PROCEDURE IF EXISTS gen_test_orders;

DELIMITER //

CREATE PROCEDURE gen_test_orders(IN p_count INT)
BEGIN
  DECLARE i INT DEFAULT 0;

  SET autocommit = 0;

  WHILE i < p_count DO
    INSERT INTO orders (order_no, user_id, status, total_amount, created_at)
    VALUES (CONCAT('T', LPAD(i, 10, '0')),
            FLOOR(1 + RAND() * 5),
            FLOOR(RAND() * 5),
            ROUND(RAND() * 10000, 2),
            NOW() - INTERVAL FLOOR(RAND() * 365) DAY);

    SET i = i + 1;

    IF i % 1000 = 0 THEN
      COMMIT;              -- 每 1000 行提交一次
    END IF;
  END WHILE;

  COMMIT;                  -- 提交尾巴上不足 1000 行的部分
  SET autocommit = 1;
END //

DELIMITER ;

CALL gen_test_orders(100000);
ANALYZE TABLE orders;      -- 重新收集统计信息，否则优化器还按老数据估算
SELECT COUNT(*) FROM orders;
```

**为什么必须分批提交**：10 万行放一个事务里会产生巨大的 undo log（MVCC 要保留所有旧版本无法清理）、长时间持有大量行锁、redo log 暴涨可能触发强制刷脏页卡顿，主从架构下还会造成明显延迟。分批提交把它拆成 100 个小事务。

`SET autocommit = 0` 是必须的：否则每条 INSERT 自己就是一个事务并立即 fsync，10 万次刷盘会慢到无法接受，`COMMIT` 也形同虚设。

**更快的替代方案**（存储过程逐行 INSERT 其实很慢，10 万行可能要几十秒）：用「自我复制倍增法」，17 次翻倍即可从 1 行到 13 万行，通常只要几秒：

```sql
INSERT INTO orders (order_no, user_id, status, total_amount, created_at)
SELECT CONCAT('X', LPAD(FLOOR(RAND()*1000000000), 10, '0')),
       user_id, status, total_amount, created_at
FROM orders;
-- 反复执行这一条即可
```

**验证第 7 章的深分页优化**：

```sql
-- 慢：扫描并丢弃前 9 万行
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 90000;
-- 约 0.2 ~ 0.8 sec

-- 延迟关联：子查询只在主键索引上翻页，不回表
SELECT o.* FROM orders o
JOIN (SELECT id FROM orders ORDER BY id LIMIT 20 OFFSET 90000) t
  ON o.id = t.id;
-- 明显更快

-- 游标分页：直接定位起点，与页码无关
SELECT * FROM orders WHERE id > 90000 ORDER BY id LIMIT 20;
-- 约 0.00 sec，和第一页一样快
```

用 EXPLAIN 看根因：第一条的 `rows` 是 90020，第三条只有 20。

**2. BEFORE INSERT 触发器：email 转小写**

```sql
DROP TRIGGER IF EXISTS trg_users_email_lower;

DELIMITER //

CREATE TRIGGER trg_users_email_lower
BEFORE INSERT ON users
FOR EACH ROW
BEGIN
  SET NEW.email = LOWER(TRIM(NEW.email));
END //

DELIMITER ;
```

验证：

```sql
INSERT INTO users (username, email, phone)
  VALUES ('Tom', '  ToM@DEMO.COM  ', '13900001111');

SELECT id, username, email FROM users WHERE username = 'Tom';
```

```text
+----+----------+---------------+
| id | username | email         |
+----+----------+---------------+
| 10 | Tom      | tom@demo.com  |
+----+----------+---------------+
```

要点：

- **只有 BEFORE 触发器能修改 `NEW.列`**。AFTER 触发器里改 NEW 无效（行已经写入了），MySQL 会直接报错 `Updating of NEW row is not allowed in after trigger`。
- `OLD` 在 INSERT 触发器里不可用，`NEW` 在 DELETE 触发器里不可用。
- 只覆盖 INSERT 是不够的——`UPDATE users SET email = 'ABC@X.COM'` 会绕过它。要完整覆盖得再建一个 BEFORE UPDATE 触发器：

```sql
DELIMITER //
CREATE TRIGGER trg_users_email_lower_upd
BEFORE UPDATE ON users
FOR EACH ROW
BEGIN
  SET NEW.email = LOWER(TRIM(NEW.email));
END //
DELIMITER ;
```

**这个需求其实不该用触发器**。更好的三种方案：

1. **依赖排序规则**：默认的 `utf8mb4_0900_ai_ci` 本身就不区分大小写，`WHERE email = 'ABC@X.COM'` 能匹配到 `abc@x.com`，唯一索引 `uk_email` 也会把两者判为重复——**大多数情况下根本不需要转小写**。
2. **生成列**（声明式，比触发器透明得多）：

```sql
ALTER TABLE users
  ADD COLUMN email_lower VARCHAR(100)
    GENERATED ALWAYS AS (LOWER(email)) STORED,
  ADD UNIQUE KEY uk_email_lower (email_lower);
```

3. **应用层规范化**：注册时就把邮箱转小写再入库，逻辑显式可见、可单测、可追踪。

触发器的问题正如本章所说：**不可观测**。「我明明插入的是大写，查出来怎么是小写」会让不知情的同事排查半天——逻辑藏在数据库里，应用日志和 APM 全部失明。

**3. 摸清并清理遗留触发器与事件**

**第一步：全量盘点（接手任何遗留系统的必做动作）**

```sql
-- 所有触发器：在哪张表、什么时机、什么事件
SELECT trigger_name,
       event_object_table AS on_table,
       action_timing,
       event_manipulation AS on_event,
       definer,
       created
FROM information_schema.triggers
WHERE trigger_schema = 'shop'
ORDER BY event_object_table, action_timing;
```

```sql
-- 所有事件（库内定时任务）
SELECT event_name, status, event_type, interval_value, interval_field,
       starts, last_executed, definer
FROM information_schema.events
WHERE event_schema = 'shop';

-- 别忘了存储过程和函数
SELECT routine_name, routine_type, definer, created, last_altered
FROM information_schema.routines
WHERE routine_schema = 'shop';
```

**第二步：备份定义（关键！DROP 之前必须做）**

```bash
# 单独导出所有例程、触发器、事件的定义，不含数据
mysqldump -uroot -p --no-data --no-create-info \
  --routines --triggers --events --skip-opt \
  --databases shop > shop_logic_backup.sql
```

也可以逐个查看：

```sql
SHOW CREATE TRIGGER trg_product_price_audit\G
SHOW CREATE EVENT ev_purge_price_log\G
SHOW CREATE PROCEDURE gen_test_orders\G
```

**第三步：清理**

```sql
DROP TRIGGER IF EXISTS trg_product_price_audit;
DROP TRIGGER IF EXISTS trg_users_email_lower;
DROP TRIGGER IF EXISTS trg_users_email_lower_upd;

DROP EVENT IF EXISTS ev_purge_price_log;

DROP PROCEDURE IF EXISTS gen_test_orders;
DROP PROCEDURE IF EXISTS get_user_orders;
DROP FUNCTION  IF EXISTS order_status_text;
```

批量生成 DROP 语句（表多时用）：

```sql
SELECT CONCAT('DROP TRIGGER IF EXISTS `', trigger_name, '`;') AS stmt
FROM information_schema.triggers WHERE trigger_schema = 'shop';
```

确认清理干净：

```sql
SELECT COUNT(*) FROM information_schema.triggers WHERE trigger_schema = 'shop';
SELECT COUNT(*) FROM information_schema.events   WHERE event_schema   = 'shop';
```

**这个排查过程要体会到什么：**

1. **触发器是隐形炸弹**。「我只 UPDATE 了 products 一行，为什么 product_price_log 多了记录」——不盘点根本想不到。批量导数据前尤其要检查：触发器会被**逐行触发**，导 100 万行就执行 100 万次，性能直接雪崩。
2. **`definer` 字段是个大坑**。触发器/过程默认以创建者权限执行。如果那个账号被删了或迁库时不存在，运行时会报 `The user specified as a definer does not exist`——迁移前必须检查这一列。
3. **`mysqldump` 默认不导出这些**。必须显式加 `--routines --triggers --events`，否则「备份恢复完发现触发器全没了」（第 19 章会再强调）。
4. **生产环境不能这样直接 DROP**。正确流程是：盘点 → 备份定义 → 分析每个对象是否还被依赖（查代码、查调用方）→ 逐个下线并观察 → 确认无影响后删除。这里为了练习才一次性清空。

替代方案上，新系统需要审计留痕应该用 **binlog 订阅**（Canal / Debezium）——逻辑在应用侧，可观测、可版本管理、不占数据库 CPU、也不影响分库分表。
