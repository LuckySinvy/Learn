# 事务与 ACID

转账扣了款却没入账、下单扣了库存却没生成订单——没有事务，这些「半截子操作」会摧毁数据的正确性。本章从事务的使用讲到 InnoDB 靠 redo log / undo log 实现 ACID 的底层机制，最后讲清面试必问的「两阶段提交」。

## 1. ACID：事务的四个承诺

| 特性 | 含义 | 由谁实现 |
|---|---|---|
| 原子性 Atomicity | 全做或全不做 | undo log（回滚日志） |
| 一致性 Consistency | 从一个合法状态到另一个合法状态 | 其余三者 + 应用约束共同保证 |
| 隔离性 Isolation | 并发事务互不干扰 | 锁 + MVCC（第 16、17 章） |
| 持久性 Durability | 提交了就不会丢 | redo log（重做日志） |

一致性是**目的**，原子性、隔离性、持久性是**手段**——这个关系理清了，ACID 就不再是背诵条目。

## 2. 事务的基本使用

### 2.1 autocommit

默认 `autocommit = 1`：每条 DML 单独成一个事务并立即提交。`BEGIN` 会临时接管直到 COMMIT/ROLLBACK。

```sql
SHOW VARIABLES LIKE 'autocommit';
SET autocommit = 0;   -- 慎用：之后每条语句都在未提交事务里
```

<Callout type="warn" title="长事务是万恶之源">
把 autocommit 关掉又忘了提交、或者事务里夹了 RPC 调用/人工等待，就会产生长事务。危害：undo log 无法清理（MVCC 要保留老版本）导致存储膨胀、行锁一直握着引发大面积锁等待、还会阻塞 DDL（MDL 锁）。排查：`SELECT * FROM information_schema.innodb_trx WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 60;` 生产建议监控并告警超过 N 秒的事务。
</Callout>

### 2.2 SAVEPOINT：部分回滚

INSERT INTO orders (order_no, user_id) VALUES ('SP-A', 1);

适合「批量处理中单条失败跳过」的场景，但逻辑复杂时更推荐拆小事务。

### 2.3 隐式提交

DDL（CREATE/ALTER/DROP）、`LOCK TABLES` 等语句会**隐式提交当前事务**——事务里混 DDL，前面的 DML 就被悄悄提交了，无法再回滚。事务里只放 DML。

## 3. undo log：原子性与回滚

执行 DML 时，InnoDB 先把「反向操作」记进 undo log：

- INSERT 一行 → undo 记「删掉这行」
- DELETE 一行 → undo 记「把这行加回来」
- UPDATE 一行 → undo 记「改回旧值」

ROLLBACK 就是**倒序重放 undo log**。上一章行格式里的 `roll_pointer` 隐藏列，指向的正是该行的 undo 记录——同一行的历史版本通过 roll_pointer 串成**版本链**，这条链同时也是 MVCC 读旧版本的依据（第 17 章）。这就是为什么长事务会让 undo 膨胀：只要还有老事务可能读旧版本，undo 就不能删。

## 4. redo log：持久性与崩溃恢复

### 4.1 为什么需要 redo log

修改数据时，InnoDB 改的是 **Buffer Pool 里的内存页**（脏页），不会立刻写磁盘——随机写 16KB 页太慢。但 COMMIT 承诺了持久性，机器一断电内存就没了，怎么办？

答案是 **WAL（Write-Ahead Logging）**：提交前，先把「对哪个页做了什么修改」这条物理日志**顺序追加**写入 redo log 并刷盘。顺序写比随机写快一个数量级，于是既快又不丢：

```text
UPDATE 提交流程：
1. 改 Buffer Pool 中的页（内存，产生脏页）
2. 写 redo log buffer → COMMIT 时 fsync 刷盘   ← 顺序写，快
3. 脏页由后台线程在之后「慢慢」刷回磁盘         ← 随机写，异步

崩溃恢复：重启后重放 redo log，把没来得及落盘的修改补回来
```

### 4.2 刷盘策略

`innodb_flush_log_at_trx_commit` 控制 redo 刷盘时机：

| 值 | 行为 | 安全性 |
|---|---|---|
| 1（默认） | 每次提交 fsync | 崩溃不丢已提交事务，**生产标配** |
| 2 | 提交写 OS 缓存，每秒 fsync | MySQL 崩溃不丢，主机断电丢约 1 秒 |
| 0 | 每秒才写 + fsync | 最快，可丢约 1 秒，仅适合可重灌的数据 |

redo log 是固定大小的循环文件（8.0.30+ 由 `innodb_redo_log_capacity` 控制），写满会强制刷脏页、造成写入卡顿——写入密集的库要给足容量（第 21 章）。

## 5. 两阶段提交：redo log 与 binlog 的一致性

Server 层还有一份 **binlog**（归档日志，主从复制和备份恢复用，第 19 章）。一次提交要写两份日志，如果在两次写入之间崩溃，就可能出现「redo 有、binlog 无」或反之——主库恢复的数据和从库复制的数据就不一致了。

InnoDB 用**两阶段提交（2PC）**解决：

```text
       ┌─────────────────────────────────────────┐
       │ 1. redo log 写入，标记为 prepare 状态      │
       │ 2. 写 binlog 并刷盘                       │
       │ 3. redo log 标记为 commit 状态            │
       └─────────────────────────────────────────┘

崩溃恢复时的裁决规则：
- redo 是 commit 状态            → 事务有效，重放
- redo 是 prepare，binlog 完整   → 提交（binlog 可能已传给从库）
- redo 是 prepare，binlog 不完整 → 回滚
```

裁决标准统一以 **binlog 是否完整**为准，保证了「主库自身恢复」与「从库复制到的内容」永远一致。面试问「为什么要两阶段提交」，答案就是这句：**让 redo log 和 binlog 这两份独立的日志，在任何崩溃点上都能达成一致**。

## 6. 事务使用的工程守则

1. **事务要小而快**：只包住必须原子的 DML，RPC、发消息、文件 IO 都放到事务外；
2. **先想清楚失败路径**：哪些错误要 ROLLBACK、应用层怎么感知（如扣库存 affected rows = 0）；
3. **不要在事务里等待用户输入**（Web 应用一般不会，但脚本和运维操作常犯）；
4. 写操作顺序在多个事务间保持一致，能显著减少死锁（第 16 章）；
5. 框架的声明式事务（如 Spring `@Transactional`）失效场景很多（自调用、异常被吞），关键路径要验证事务真的生效——一个简单办法是在事务中查 `SELECT trx_id FROM information_schema.innodb_trx`。

## 小结

- ACID：一致性是目标；原子性靠 undo、持久性靠 redo、隔离性靠锁 + MVCC
- undo log 记反向操作，串成版本链，同时服务回滚与 MVCC
- redo log 是 WAL：顺序写日志先行，脏页异步落盘，崩溃后重放
- `innodb_flush_log_at_trx_commit = 1` 是生产安全底线
- 两阶段提交让 redo 与 binlog 在任意崩溃点保持一致
- 长事务危害巨大：undo 膨胀、锁等待、堵 DDL，必须监控

**1. 两会话演练：读不阻塞、写要排队**

```sql
-- 会话 A
BEGIN;
UPDATE products SET stock = 999 WHERE id = 1;
SELECT stock FROM products WHERE id = 1;   -- A 自己看到 999
-- 先不提交
```

```sql
-- 会话 B
SELECT stock FROM products WHERE id = 1;
-- 立即返回！而且看到的是【旧值】，不是 999
```

```sql
-- 会话 B 继续
UPDATE products SET stock = stock - 1 WHERE id = 1;
-- 挂起，一直等待……
```

```sql
-- 会话 A
COMMIT;
-- 此刻 B 的 UPDATE 立即完成，且是基于 A 提交后的新值 999 计算的 → 998
```

```sql
-- 会话 B
SELECT stock FROM products WHERE id = 1;   -- 998
COMMIT;
```

**两个关键现象要解释清楚：**

**（1）B 的 SELECT 为什么不阻塞、还看到旧值？**

普通 `SELECT` 是**快照读（一致性非锁定读）**，它不加任何锁，而是通过 **MVCC** 顺着 undo log 的版本链找到「对本事务可见的历史版本」。A 未提交的修改对 B 不可见，所以 B 读到旧值。这就是 InnoDB 的核心优势——**读写不互相阻塞**（第 17 章展开）。

**（2）B 的 UPDATE 为什么阻塞？**

`UPDATE` 是**当前读**，必须读最新版本并加 **X 行锁**。A 已经持有 `id = 1` 这行的 X 锁，X 锁互斥，所以 B 只能等。等待上限由 `innodb_lock_wait_timeout` 控制（默认 50 秒），超时报：

```text
ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction
```

在第三个会话里可以看到等待现场：

```sql
SELECT * FROM sys.innodb_lock_waits\G
-- 谁在等谁、等的是哪个索引上的哪条记录

SELECT trx_id, trx_state, trx_started, trx_rows_locked, trx_query
FROM information_schema.innodb_trx;
-- A 是 RUNNING，B 是 LOCK WAIT
```

**（3）还有一个必须注意的细节**：A 提交后，B 的 `stock = stock - 1` 是基于 **999** 算的，不是基于它事务开始时看到的旧值。因为当前读总是读最新已提交版本——这正是「先 SELECT 检查再 UPDATE」不安全、而 `UPDATE ... WHERE stock >= 1` 安全的原因。

**2. SAVEPOINT 部分回滚**

```sql
BEGIN;

INSERT INTO orders (order_no, user_id, status, total_amount)
  VALUES ('SP-001', 1, 0, 100.00);
SAVEPOINT sp1;

INSERT INTO orders (order_no, user_id, status, total_amount)
  VALUES ('SP-002', 2, 0, 200.00);
SAVEPOINT sp2;

INSERT INTO orders (order_no, user_id, status, total_amount)
  VALUES ('SP-003', 3, 0, 300.00);

-- 目标：撤销第 2 笔，保留第 1、3 笔
```

**这里有个陷阱**：`ROLLBACK TO sp1` 会把 sp1 **之后的所有操作**都撤销掉——包括第 3 笔。SAVEPOINT 只能回退到某个时间点，**不能"挖掉中间一笔"**。

正确做法是调整顺序，把要回滚的那笔放在最后再撤销：

```sql
BEGIN;

INSERT INTO orders (order_no, user_id, status, total_amount)
  VALUES ('SP-001', 1, 0, 100.00);

SAVEPOINT sp_before_2;
INSERT INTO orders (order_no, user_id, status, total_amount)
  VALUES ('SP-002', 2, 0, 200.00);
ROLLBACK TO sp_before_2;      -- 只撤销第 2 笔

INSERT INTO orders (order_no, user_id, status, total_amount)
  VALUES ('SP-003', 3, 0, 300.00);

COMMIT;

SELECT order_no FROM orders WHERE order_no LIKE 'SP-%' ORDER BY order_no;
```

```text
+----------+
| order_no |
+----------+
| SP-001   |
| SP-003   |
+----------+
```

其他要点：

- `ROLLBACK TO sp1` **不结束事务**，事务仍在进行，锁也**不会释放**（这点常被误解）；只有 `COMMIT` / `ROLLBACK` 才结束事务。
- 回滚到某个 savepoint 后，它**之后**创建的 savepoint 全部失效。
- `RELEASE SAVEPOINT sp1` 可以手动释放一个保存点。
- 自增值不会回退：即使第 2 笔被撤销，它消耗掉的 AUTO_INCREMENT 值也不会还回来，`SP-003` 的 id 会跳号。这是设计使然（自增值分配不参与事务，否则会成为并发瓶颈）。

**适用场景**：批量处理中「单条失败跳过、其余继续」。但逻辑一复杂就很容易出错，**更推荐拆成多个小事务** + 应用层记录失败项。

**3. `innodb_flush_log_at_trx_commit` 三个取值的丢数据分析**

先理解数据要落盘经过的两道关：

```text
redo log buffer（MySQL 进程内存）
        │  ① write：写入 OS Page Cache
        ▼
OS Page Cache（操作系统内存）
        │  ② fsync：真正落到磁盘
        ▼
磁盘上的 redo log 文件
```

- **MySQL 进程崩溃**（kill -9、OOM、bug）：进程内存丢失，但 **OS Page Cache 由操作系统持有，仍然存在**，操作系统会继续把它写到磁盘。
- **主机断电 / 内核崩溃**：进程内存和 OS Page Cache **全部丢失**，只有已经 fsync 到磁盘的才算数。

| 取值 | 行为 | MySQL 进程崩溃 | 主机断电 |
|---|---|---|---|
| **1**（默认） | 每次事务提交都 write + **fsync** | **不丢** | **不丢** |
| **2** | 每次提交只 write 到 OS Cache，后台每秒 fsync | **不丢** | 丢**约 1 秒**的已提交事务 |
| **0** | 提交时什么都不做，后台每秒 write + fsync | 丢**约 1 秒** | 丢**约 1 秒** |

逐个解释：

- **`= 1`**：提交时同步刷盘，返回成功就意味着数据已在磁盘上。**这是唯一真正满足 ACID 中 D（持久性）的取值，也是生产环境的安全底线。** 代价是每次提交一次 fsync，高并发写入时是主要瓶颈（可用 `sync_binlog = 1` 配套，见第 19 章）。
- **`= 2`**：数据交给了操作系统。MySQL 进程怎么死都不丢（OS Cache 还在），但主机层面的故障会丢最后约 1 秒。适合「允许丢一点、要吞吐」的场景。
- **`= 0`**：提交时连 write 都不做，全靠后台线程每秒一次。MySQL 进程崩溃就会丢——因为数据还在进程自己的 redo log buffer 里。性能最好，只适合可以随时重灌的数据（如爬虫中间结果、可重算的统计表）。

**要点提炼**：`0` 和 `2` 的区别，本质就是「**数据有没有交出进程边界**」。交给了 OS（= 2），MySQL 自己死了不要紧；没交出去（= 0），MySQL 一死就没了。

配套的还有 binlog 的 `sync_binlog`，含义完全平行：

```sql
SET GLOBAL innodb_flush_log_at_trx_commit = 1;
SET GLOBAL sync_binlog = 1;
-- 这组「双 1」配置是金融级不丢数据的标配，代价是每次提交两次 fsync
```

真正的高可用不能只靠单机刷盘策略——即使配了「双 1」，磁盘物理损坏照样丢数据。生产上应配合**半同步复制 / MGR**（第 20 章），让数据至少落到两台机器上。
