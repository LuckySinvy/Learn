# 索引设计

上一章懂了 B+ 树，这一章解决实际问题：**给什么列建索引、怎么组合、建几个**。索引设计是有章法的，掌握最左前缀和覆盖索引两个核心概念，就能应对 90% 的场景。

## 1. 联合索引与最左前缀

联合索引 `(a, b, c)` 是**一棵**B+ 树，键按「先 a、a 相同比 b、b 相同比 c」的顺序排列——像字典先按首字母、再按第二个字母排序：

```text
索引 (user_id, created_at) 的叶子节点排列：
(1, 07-01) → (1, 07-03) → (1, 07-15) → (2, 07-02) → (3, 07-04)
 └── user_id=1 的行连续存放，且组内按 created_at 有序 ──┘
```

**最左前缀原则**：查询条件必须从索引最左列开始、连续命中，才能用上索引。对 `(a, b, c)`：

| WHERE 条件 | 能用到的部分 |
|---|---|
| a = 1 | a ✓ |
| a = 1 AND b = 2 | a, b ✓ |
| a = 1 AND b = 2 AND c = 3 | 全部 ✓ |
| b = 2（缺 a） | 用不上 |
| a = 1 AND c = 3（跳过 b） | 只有 a（c 无法定位，但见下文 ICP） |
| `a = 1 AND b > 2 AND c = 3` | a, b（**范围之后的列失效**） |

「范围之后失效」的原因：b 是范围时，满足条件的行里 c 不再有序，无法继续二分。

由此得出联合索引的**列顺序设计口诀**：

1. **等值条件列放前面，范围条件列放最后**；
2. 排序需求也算「有序性消费」：`WHERE a = ? ORDER BY b` 完美匹配 `(a, b)`；
3. 区分度高（不同值多）的等值列优先——但要服从查询模式，别死背。

```sql
-- 典型订单查询：WHERE user_id = ? AND created_at >= ? ORDER BY created_at DESC
-- 正确索引：(user_id, created_at) —— 等值在前、范围/排序在后
ALTER TABLE orders ADD INDEX idx_user_created (user_id, created_at);
```

另一个推论：**有了 `(a, b)` 就不需要单独的 `(a)`**——前者完全覆盖后者的能力，冗余索引白白增加写入成本。

## 2. 覆盖索引：消灭回表

上一章讲过：二级索引查到主键后要**回表**取整行。如果查询需要的列全部在索引里（索引列 + 主键），就不用回表——这就是覆盖索引：

预置的 orders 表已经有 `idx_user_created (user_id, created_at)`，主键是 id。下面先把表灌到几百行（7 行的表优化器一律选全扫，看不出效果），再用 EXPLAIN 验证最左前缀与覆盖索引：

       o.user_id, o.status, o.total_amount, o.created_at
FROM orders o,

      UNION ALL SELECT 5 UNION ALL SELECT 6 UNION ALL SELECT 7 UNION ALL SELECT 8 UNION ALL SELECT 9) d1,
     (SELECT 0 n UNION ALL SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT 3 UNION ALL SELECT 4
      UNION ALL SELECT 5 UNION ALL SELECT 6 UNION ALL SELECT 7 UNION ALL SELECT 8 UNION ALL SELECT 9) d2;

-- 命中最左列：key = idx_user_created
EXPLAIN SELECT id, user_id, created_at FROM orders WHERE user_id = 1;

-- 缺最左列：用不上这棵索引树
EXPLAIN SELECT id, user_id, created_at FROM orders WHERE created_at >= '2026-02-01';

-- 覆盖：三列全在索引里，Extra 显示 Using index
EXPLAIN SELECT id, user_id, created_at FROM orders WHERE user_id = 1;

-- 不覆盖：total_amount 不在索引里，每行都要回表
EXPLAIN SELECT id, user_id, total_amount FROM orders WHERE user_id = 1;`}
/>

实战手法：把 SELECT 里少数几个额外列**追加进联合索引尾部**，专门喂高频查询：

```sql
-- 订单列表页只展示这几个字段，建一个「宽」索引把它们全包住
ALTER TABLE orders ADD INDEX idx_user_list (user_id, created_at, status, total_amount);
```

这是「用空间换时间」的典型手法，只对高频核心查询这么做，别滥用。这也是不写 `SELECT *` 的最硬理由——多取一个不需要的列，覆盖索引就废了。

## 3. 索引下推（ICP，5.6+）

对索引 `(name, phone)` 执行：

```sql
SELECT * FROM users WHERE name LIKE '张%' AND phone = '13800000001';
```

`LIKE '张%'` 是范围，phone 无法用于树上定位。没有 ICP 时：索引层找出所有姓张的主键 → 逐个回表 → Server 层再过滤 phone，回表次数 = 姓张的人数。

**索引下推**（Index Condition Pushdown）：phone 虽不能定位，但它的值**就在索引里**，存储引擎在遍历索引时顺手把 `phone = ?` 过滤掉，只有通过的才回表。回表次数从「姓张的人数」降到「姓张且手机号匹配的人数」。EXPLAIN Extra 显示 `Using index condition`。

ICP 是自动的，你要做的是理解它：**联合索引里「用不上定位」的列并非无用，还能减少回表**。

## 4. 前缀索引

长字符串列（URL、邮箱）整列建索引太占空间，可以只索引前 N 个字符：

<Playground
  language="mysql"
  id="mysql-13-2"
  title="测算前缀长度并建前缀索引"
  code={`-- 先测算不同前缀长度的区分度（越接近 1 越好）
SELECT COUNT(DISTINCT LEFT(name, 3))  / COUNT(DISTINCT name) AS sel3,
       COUNT(DISTINCT LEFT(name, 5))  / COUNT(DISTINCT name) AS sel5,
       COUNT(DISTINCT LEFT(name, 10)) / COUNT(DISTINCT name) AS sel10
FROM products;

-- 选一个区分度接近 1 的最短长度
ALTER TABLE products ADD INDEX idx_name_prefix (name(10));
SHOW INDEX FROM products;`}
/>

代价：前缀索引**不能做覆盖索引**（索引里不是完整值，必须回表核对），也不能支持 `ORDER BY email` 免排序。区分度够就尽量短，但核心唯一列（如登录邮箱）通常还是全列唯一索引。

## 5. 函数索引与生成列（8.0.13+）

对列做函数运算会让普通索引失效：

<Playground
  language="mysql"
  id="mysql-13-3"
  title="函数让索引失效，改写成范围救回来"
  code={`ALTER TABLE orders ADD INDEX idx_created (created_at);

-- 索引失效：函数包住了列，key 为 NULL、走全表
EXPLAIN SELECT id, order_no FROM orders WHERE DATE(created_at) = '2026-02-01';

-- 改写成范围（首选方案，第 6 章讲过的左闭右开）
EXPLAIN SELECT id, order_no FROM orders
WHERE created_at >= '2026-02-01' AND created_at < '2026-02-02';`}
/>

改写不了的场景用**函数索引**：

```sql
ALTER TABLE users ADD INDEX idx_email_lower ((LOWER(email)));
SELECT * FROM users WHERE LOWER(email) = 'alice@ex.com';   -- 能走 idx_email_lower
```

注意查询表达式必须与索引定义**完全一致**才会命中。函数索引本质是隐藏的生成列 + 普通索引。

## 6. 什么时候不该建索引

索引不是越多越好——每个索引都是一棵要随 DML 同步维护的 B+ 树：

1. **区分度极低的列**：`status` 只有 3 个值、`gender` 只有 2 个值，单独建索引筛完还剩 30%+ 的行，优化器多半不用，还不如全扫。（但作为联合索引的**一员**可以有价值。）
2. **写多读少的表**：日志表、流水表，每个索引都在拖慢 INSERT。
3. **小表**：几百行全扫也就一两个页的事。
4. **不出现在 WHERE/JOIN/ORDER BY 的列**：纯展示列建索引毫无意义。
5. **已被联合索引最左覆盖的单列**：`(a,b)` 存在时 `(a)` 是冗余。

```sql
-- 找冗余和从未使用的索引
SELECT * FROM sys.schema_redundant_indexes;
SELECT * FROM sys.schema_unused_indexes;
```

<Callout type="warn" title="索引失效的高频原因清单">
1. 列上有函数/运算：`WHERE id + 1 = 10`、`DATE(created_at) = ...`；
2. 隐式类型转换：字符串列不加引号、两表 JOIN 列字符集不同；
3. 前导通配 `LIKE '%x'`；
4. 违反最左前缀；
5. OR 两侧有一侧无索引（整条退化全扫，可拆成 UNION）；
6. 优化器估算回表太多主动放弃（不算失效，是理性选择——见第 14 章用 EXPLAIN 确认）。
</Callout>

<Callout type="tip" title="不可见索引：安全下线索引的姿势">
怀疑某索引没用想删掉？先设为不可见观察一段时间：`ALTER TABLE t ALTER INDEX idx_x INVISIBLE;` 优化器立刻不再使用它，但索引数据还在——线上出问题一秒改回 VISIBLE，比删了重建（大表建索引可能几小时）安全得多。
</Callout>

## 小结

- 联合索引一棵树、按列顺序逐级有序；最左前缀 + 「范围之后失效」决定命中范围
- 列顺序：等值在前、范围/排序在后；`(a,b)` 覆盖 `(a)` 的能力
- 覆盖索引免回表，是高频查询的大杀器；`SELECT *` 是它的天敌
- ICP 让索引里的「非定位列」也能减少回表
- 长字符串用前缀索引省空间；函数条件用改写或函数索引
- 低区分度、写多读少、小表、冗余——四类情况不建索引；删索引前先 INVISIBLE

<Answer>
**参考答案：**

**1. 为 `status` 等值 + `created_at` 范围/排序设计索引**

```sql
ALTER TABLE orders ADD INDEX idx_status_created (status, created_at);
```

**列顺序理由**（这是索引设计的核心口诀）：

- **等值条件列必须放最前面**。`status = 1` 是等值，把它放第一列后，索引树上所有 `status = 1` 的记录**连续存放**，一次定位即可圈定范围。
- **范围 / 排序列放在等值列后面**。在 `status = 1` 这一段连续区间内部，记录**天然按 `created_at` 有序**——于是 `created_at >= ?` 可以直接在这段区间里二分定位起点，而 `ORDER BY created_at DESC` 只需**沿叶子双向链表反向扫描**，完全不需要排序，EXPLAIN 的 Extra 里不会出现 `Using filesort`。
- 配合 `LIMIT 20`，扫够 20 行就能停止，这是「索引消除排序」带来的最大收益：**不需要把满足条件的全部行读出来排序后再取前 20**。

如果顺序反过来建成 `(created_at, status)` 会怎样：

- `created_at` 是范围条件，**「范围之后的列失效」**——`status` 无法用于树上定位，只能靠 ICP 在索引里过滤或回表后过滤；
- 更糟的是索引里记录先按 `created_at` 排，`status = 1` 的行散落各处，要扫描整个时间范围的所有行。

验证：

```sql
EXPLAIN SELECT id, order_no, status, total_amount, created_at
FROM orders
WHERE status = 1 AND created_at >= '2026-07-01'
ORDER BY created_at DESC
LIMIT 20;
-- key: idx_status_created
-- type: range
-- Extra: 不含 Using filesort   ← 关键
```

**进一步优化成覆盖索引**：如果这个列表页只展示 `order_no / total_amount`，可以把它们追加到索引尾部，彻底消灭回表：

```sql
ALTER TABLE orders
  ADD INDEX idx_status_created_cover (status, created_at, order_no, total_amount);
-- EXPLAIN 的 Extra 会出现 Using index
```

代价是索引变宽、写入变慢，只对高频核心查询这么做。

**一个反直觉的补充**：`status` 只有 5 个值，区分度极低，**单独**给它建索引几乎没用（筛完还剩 20%+ 的行，优化器多半直接全表扫）。但作为联合索引的**第一列**它很有价值——因为真正干活的是后面的 `created_at`，`status` 只是把范围收窄一档。所以「低区分度列不建索引」是针对单列索引说的，别教条。

**2. 覆盖 vs 非覆盖的 EXPLAIN 对比**

```sql
ALTER TABLE orders ADD INDEX idx_user_created (user_id, created_at);
ANALYZE TABLE orders;   -- 数据太少时记得先造数，否则优化器一律选全表扫
```

```sql
-- 覆盖查询：id 是主键（二级索引叶子里本就有）、user_id 和 created_at 是索引列
EXPLAIN SELECT id, user_id, created_at FROM orders WHERE user_id = 1;
```

```text
type: ref
key : idx_user_created
Extra: Using index          ← 覆盖索引，全程不回表
```

```sql
-- 非覆盖查询：total_amount 不在索引里
EXPLAIN SELECT id, user_id, total_amount FROM orders WHERE user_id = 1;
```

```text
type: ref
key : idx_user_created
Extra: NULL                 ← 没有 Using index，说明每行都要回表
```

两者 `key` 和 `type` **完全一样**，唯一差别就在 Extra 的 `Using index`。这说明：**光看「走没走索引」是不够的，还要看「回不回表」**。

`SELECT *` 则连索引都可能不走：

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 1;
-- 若 user_id=1 的行占比较大，优化器会算出「回表 N 次的随机 IO」
-- 比「全表顺序扫描」还贵，于是 key = NULL、type = ALL 主动放弃索引
```

这正是不写 `SELECT *` 的最硬理由——**多取一个不需要的列，覆盖索引就废了**，甚至可能让索引整个被放弃。

别把三个长得像的 Extra 搞混：

| Extra | 含义 | 是否回表 |
|---|---|---|
| `Using index` | 覆盖索引 | **不回表** |
| `Using index condition` | 索引下推 ICP | 回表，但回表次数被减少了 |
| `Using where` | Server 层拿到行后再过滤 | 通常回表了 |

**3. 三条索引失效的 SQL 及修正**

**（1）列上包了函数 / 参与运算**

```sql
-- 失效：函数包住了列，B+ 树是按 created_at 原值排序的，
-- 无法按 DATE(created_at) 的结果定位 → type=ALL
SELECT id, order_no FROM orders WHERE DATE(created_at) = '2026-07-01';

-- 修正 A（首选）：改写成范围条件，左闭右开
SELECT id, order_no FROM orders
WHERE created_at >= '2026-07-01' AND created_at < '2026-07-02';

-- 修正 B：实在改写不了就建函数索引（8.0.13+）
ALTER TABLE orders ADD INDEX idx_created_date ((DATE(created_at)));
```

同类问题还有 `WHERE id + 1 = 10`（改成 `WHERE id = 9`）、`WHERE YEAR(created_at) = 2026`。**口诀：永远不要让列出现在函数或运算符里面，要变换就变换另一侧的常量。**

**（2）隐式类型转换**

```sql
-- 失效：phone 是 VARCHAR，条件值是数字。
-- MySQL 会把「列值」CAST 成数字再比较，等价于给列套了函数 → 索引失效
SELECT * FROM users WHERE phone = 13800000001;

-- 修正：字符串列的条件值必须加引号
SELECT * FROM users WHERE phone = '13800000001';
```

除了性能，这里还有**正确性**风险：`'138abc'` 转成数字是 138，可能造成误匹配。

同类的隐蔽场景是 **JOIN 两侧字符集/排序规则不一致**（如 utf8mb4 表关联 utf8mb3 表的字符串列），也会触发隐式转换让被驱动表索引失效——EXPLAIN 里表现为该表 `type = ALL`。修正是统一两表的字符集：

```sql
ALTER TABLE t2 CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

**（3）前导通配符 / 违反最左前缀 / OR**

```sql
-- 失效 a：前导 %，B+ 树按前缀有序，开头不确定无从定位
SELECT * FROM products WHERE name LIKE '%Pro%';
-- 修正：改成前缀匹配；真要全文检索用 FULLTEXT 索引或 Elasticsearch
SELECT * FROM products WHERE name LIKE 'iPhone%';
ALTER TABLE products ADD FULLTEXT INDEX ft_name (name);
SELECT * FROM products WHERE MATCH(name) AGAINST('Pro' IN NATURAL LANGUAGE MODE);

-- 失效 b：索引是 (user_id, created_at)，条件跳过了最左列
SELECT * FROM orders WHERE created_at >= '2026-07-01';
-- 修正：补上最左列，或为该查询单建 (created_at) 索引
SELECT * FROM orders WHERE user_id = 1 AND created_at >= '2026-07-01';

-- 失效 c：OR 一侧无索引，整条语句退化为全表扫描
SELECT * FROM orders WHERE user_id = 1 OR total_amount > 10000;
-- 修正：拆成 UNION（两边各走各的索引），或给 total_amount 补索引
SELECT * FROM orders WHERE user_id = 1
UNION
SELECT * FROM orders WHERE total_amount > 10000;
```

注意失效 c 用 `UNION` 而非 `UNION ALL`——OR 的语义是取并集且去重，两个分支可能返回同一行。

最后提醒：EXPLAIN 显示 `type = ALL` 不一定都是「索引失效」。如果表很小，或优化器估算出「回表次数太多、随机 IO 比顺序全扫还贵」，主动放弃索引是**理性选择**。这时可以用 `FORCE INDEX` 对照跑一下，如果强制走索引反而更慢，说明优化器是对的。
