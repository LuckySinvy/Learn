# 映射类型与条件类型

上一章我们学会了从已有类型「取东西」（`keyof`、`T[K]`）。这一章学的是**改造**和**判断**：映射类型批量地把一个类型的每个属性变个样，条件类型则让类型系统具备「如果……那么……」的能力。这两者加在一起，构成了 TypeScript 的类型编程内核——标准库里所有内置工具类型都由它们写成。

## 1. 映射类型

### 1.1 基本语法

映射类型的形状就是「一个带 `in` 的索引签名」：

```ts
type Mapped<T> = {
  [K in keyof T]: T[K];
};
```

读作：对 `keyof T` 里的每一个键 `K`，产生一个类型为 `T[K]` 的属性。上面这个 `Mapped<T>` 什么也没改，等于 `T` 本身。把冒号右边换掉，就能批量改造：

```ts
type Stringify<T> = {
  [K in keyof T]: string;      // 所有属性都变成 string
};

type Nullable<T> = {
  [K in keyof T]: T[K] | null;  // 所有属性都可以为空
};
```

### 1.2 修饰符的增删

属性前可以加 `readonly`，属性名后可以加 `?`。映射类型允许用 `+` / `-` 显式**添加或移除**这两个修饰符：

| 写法 | 效果 |
|---|---|
| `readonly [K in keyof T]` | 全部加只读（`+readonly` 的简写） |
| `-readonly [K in keyof T]` | 全部去掉只读 |
| `[K in keyof T]?` | 全部变可选 |
| `[K in keyof T]-?` | 全部变必选（同时去掉 `undefined`） |

内置的 `Partial`、`Required`、`Readonly` 就是这么实现的：

```ts
type Partial<T> = { [K in keyof T]?: T[K] };
type Required<T> = { [K in keyof T]-?: T[K] };
type Readonly<T> = { readonly [K in keyof T]: T[K] };
```

<Callout type="info" title="映射类型也是「同态」的">
当映射的是 `keyof T` 时，TypeScript 会保留原类型的 `readonly` 与 `?` 修饰符（除非你显式增删）。这种映射叫**同态映射**，也是它能正确处理数组和元组的原因——`Partial<string[]>` 得到的还是数组而不是普通对象。
</Callout>

## 2. key remapping：改键名

TypeScript 4.1 给映射类型加了 `as` 子句，可以**重写键名**：

```ts
type Getters<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K];
};
```

上面用到了模板字面量类型和内置的 `Capitalize`。`Getters<{ name: string }>` 会得到 `{ getName: () => string }`。

### 2.1 用 never 过滤键

`as` 子句求值为 `never` 时，这个键会被**丢弃**。这是「按条件筛选属性」的标准手法：

```ts
type OnlyStrings<T> = {
  [K in keyof T as T[K] extends string ? K : never]: T[K];
};
```

### 2.2 配合模板字面量类型改名

真正「改名」时要用模板字面量类型（用反引号包裹的类型），可运行示例框里没法展示反引号，所以放在这里：

```ts
type Getters<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K];
};

type PersonGetters = Getters<{ name: string; age: number }>;
// 等价于 { getName: () => string; getAge: () => number }

type EventHandlers<T> = {
  [K in keyof T as `on${Capitalize<string & K>}Change`]?: (v: T[K]) => void;
};
```

内置的 `Uppercase`、`Lowercase`、`Capitalize`、`Uncapitalize` 四个字符串工具类型专门为这种场景准备。

## 3. 条件类型

### 3.1 基本语法

```ts
type IsString<T> = T extends string ? true : false;

type A = IsString<"hi">;     // true
type B = IsString<42>;       // false
```

语法刻意做得和三元表达式一样。`T extends U` 在这里读作「T 可以赋给 U 吗」。

条件类型的价值在于**让类型随输入变化**。例如根据传入的字面量决定返回类型：

```ts
type Unwrap<T> = T extends Array<infer E> ? E : T;
```

### 3.2 infer：从类型里「捕获」子类型

`infer X` 只能出现在条件类型的 `extends` 右侧，作用是「在这个位置放一个占位符，匹配成功后把匹配到的类型绑定给 X」。它很像正则表达式的捕获组。

```ts
type ReturnOf<F> = F extends (...args: any[]) => infer R ? R : never;
type ElementOf<T> = T extends Array<infer E> ? E : never;
type Head<T> = T extends [infer H, ...unknown[]] ? H : never;
```

内置的 `ReturnType`、`Parameters`、`Awaited` 全部基于 `infer`。

### 3.3 分发式条件类型

第 9 章提过：当条件类型作用在**裸的类型参数**上，而实参是联合类型时，会自动分发：

```ts
type ToArray<T> = T extends unknown ? T[] : never;
type R = ToArray<string | number>;   // string[] | number[]
```

正因为有分发，`Exclude` 才能这样简单地实现：

```ts
type Exclude<T, U> = T extends U ? never : T;
type X = Exclude<"a" | "b" | "c", "a">;   // "b" | "c"
```

逐个成员判断，命中的变 `never`，联合里的 `never` 会被自动剔除。

关掉分发的办法还是用方括号包起来：

```ts
type IsUnion<T> = [T] extends [infer _] ? false : false;   // 简化示意
type NoDist<T> = [T] extends [string] ? true : false;
```

<Callout type="warn" title="never 在分发里的陷阱">
`ToArray<never>` 的结果是 `never`，而不是 `never[]`。因为 `never` 是「空联合」，分发时没有任何成员可以遍历，结果自然是空。这个行为经常让人一头雾水，遇到「明明写了条件类型却得到 never」时先想想是不是它。
</Callout>

## 5. 组合起来看内置工具类型

学完这两章，标准库里的工具类型就没有秘密了：

| 工具类型 | 实现 |
|---|---|
| `Partial<T>` | `{ [K in keyof T]?: T[K] }` |
| `Required<T>` | `{ [K in keyof T]-?: T[K] }` |
| `Readonly<T>` | `{ readonly [K in keyof T]: T[K] }` |
| `Pick<T, K>` | `{ [P in K]: T[P] }` |
| `Record<K, V>` | `{ [P in K]: V }` |
| `Exclude<T, U>` | `T extends U ? never : T` |
| `Extract<T, U>` | `T extends U ? T : never` |
| `Omit<T, K>` | `Pick<T, Exclude<keyof T, K>>` |
| `NonNullable<T>` | `T & {}` |
| `ReturnType<F>` | `F extends (...a: any) => infer R ? R : any` |

## 6. 递归与性能

映射类型和条件类型都可以递归调用自身，这让它们具备了图灵完备的表达能力。最常见的例子是深度只读：

```ts
type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends object ? DeepReadonly<T[K]> : T[K];
};
```

递归很强大，但有两个现实约束：

1. **递归深度上限**。TypeScript 对类型实例化深度有硬限制（约 50 层，尾递归条件类型能放宽到 1000 层）。超过就会报「类型实例化过深」。
2. **编译时间**。复杂递归类型是大型项目里类型检查变慢的头号原因。一个写得随意的递归工具类型，可能让整个项目的检查时间从 5 秒涨到 30 秒。

排查类型性能问题时，`tsc --diagnostics` 会打印实例化次数与检查耗时，`tsc --generateTrace` 能导出可视化的火焰图。发现某个工具类型的实例化次数异常高，通常就是它了。

<Callout type="warn" title="递归类型要设终止条件">
上面的 `DeepReadonly` 遇到函数、`Date`、`Map` 这类「也是 object 但不该被展开」的类型时会出问题——函数的属性会被逐个映射，结果面目全非。实用的版本需要先排除这些特殊情况，比如 `T extends Function ? T : ...`。写递归类型时，**先想清楚在哪里停下来**。
</Callout>

<Callout type="tip" title="类型编程要克制">
映射类型和条件类型很容易上瘾——写出一个七层嵌套的「聪明」类型会很有成就感。但请记住：类型是给人看的。编译变慢、报错信息长达几十行、同事读不懂，代价往往超过收益。**能用一个简单的联合或接口解决，就别上类型体操。**
</Callout>

**参考答案：**

**第 1 题：手写 MyPick 与 MyOmit**

```ts
type MyPick<T, K extends keyof T> = {
  [P in K]: T[P];
};

// Omit = 先用 Exclude 把要删的键从 keyof T 里剔掉，再 Pick 剩下的
type MyOmit<T, K extends keyof T> = MyPick<T, Exclude<keyof T, K>>;

interface User {
  id: number;
  name: string;
  password: string;
  email: string;
}

type PublicUser = MyPick<User, "id" | "name">;
// { id: number; name: string }

type SafeUser = MyOmit<User, "password">;
// { id: number; name: string; email: string }

const a: PublicUser = { id: 1, name: "Ada" };
// const bad: PublicUser = { id: 1, name: "Ada", email: "x" };  // 错误：email 不存在

const b: SafeUser = { id: 2, name: "Alan", email: "alan@x.com" };
// b.password;   // 错误：属性 password 不存在

console.log(a.name + " / " + b.email);
```

要点：

- `MyPick` 映射的是 `K` 而不是 `keyof T`，所以只产出被挑中的那几个键。注意它**不是同态映射**（映射源不是 `keyof T`），因此不会自动保留原有的 `readonly` 与 `?` 修饰符——这也是内置 `Pick` 的真实行为。
- `MyOmit` 完全建立在 `MyPick` + `Exclude` 之上，一行搞定。这体现了工具类型的可组合性：`Exclude` 负责在键名联合上做减法，`Pick` 负责按键名构造对象。
- 这里的 `Exclude<keyof T, K>` 用到了分发：`keyof T` 是联合，逐个成员判断是否属于 `K`，命中的变 `never` 被自动剔除。

**第 2 题：DeepReadonly**

```ts
type DeepReadonly<T> = T extends (...args: any[]) => any
  ? T                                    // 函数原样返回，不要展开它的属性
  : T extends object
    ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
    : T;                                 // 原始类型是递归的终点

interface Config {
  name: string;
  server: {
    host: string;
    ports: number[];
    auth: { user: string; token: string };
  };
  onError: (e: Error) => void;
}

type FrozenConfig = DeepReadonly<Config>;

const cfg: FrozenConfig = {
  name: "prod",
  server: {
    host: "example.com",
    ports: [80, 443],
    auth: { user: "admin", token: "t0ken" },
  },
  onError: (e) => console.log(e.message),
};

console.log(cfg.server.auth.user);   // admin

// 下面每一行都会报错：只读一直穿透到最深层
// cfg.name = "dev";
// cfg.server.host = "other.com";
// cfg.server.auth.token = "new";
// cfg.server.ports.push(8080);       // 数组也变成了 readonly number[]
```

要点：

- **终止条件有两个**：原始类型（`string`、`number` 等不满足 `extends object`）直接返回自身；函数被单独挡在最前面。
- 为什么要特判函数？函数在 TypeScript 里满足 `T extends object`。如果不排除，`onError` 会被当成对象逐个映射属性，结果变成 `{ readonly length: ...; readonly name: ... }` 这种面目全非的东西，再也没法调用了。这正是本章 Callout 强调的「**先想清楚在哪里停下来**」。
- 实际项目中通常还要排除 `Date`、`Map`、`Set`、`RegExp` 等内置对象：

```ts
type DeepReadonly<T> = T extends (...args: any[]) => any
  ? T
  : T extends Date | RegExp
    ? T
    : T extends Map<infer K, infer V>
      ? ReadonlyMap<DeepReadonly<K>, DeepReadonly<V>>
      : T extends object
        ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
        : T;
```

分支越加越多，编译也越来越慢——这就是本章说「类型编程要克制」的现实原因。日常项目里，内置的浅层 `Readonly<T>` 往往就够用了。

**第 3 题：FunctionKeys**

```ts
type FunctionKeys<T> = {
  [K in keyof T as T[K] extends (...args: any[]) => any ? K : never]: T[K];
};

// 只想要键名的联合，而不是整个对象类型时，再取一次 keyof
type FunctionKeyNames<T> = keyof FunctionKeys<T>;

interface Service {
  name: string;
  version: number;
  start(): void;
  stop(): Promise<void>;
  onTick: (n: number) => void;
  config: { retries: number };
}

type Methods = FunctionKeys<Service>;
// { start(): void; stop(): Promise<void>; onTick: (n: number) => void }

type MethodNames = FunctionKeyNames<Service>;
// "start" | "stop" | "onTick"

const names: MethodNames[] = ["start", "stop", "onTick"];
// const bad: MethodNames = "name";   // 错误：name 的值不是函数，已被过滤

console.log(names.join(", "));   // start, stop, onTick

// 实用场景：只允许调用对象上的方法
function callMethod<T, K extends FunctionKeyNames<T>>(obj: T, key: K): void {
  const fn = obj[key as keyof T];
  if (typeof fn === "function") (fn as () => void).call(obj);
}
```

要点：

- 核心机制是 `as` 子句求值为 `never` 时**该键会被整个丢弃**。值不是函数的键（`name`、`version`、`config`）在 `as` 处映射为 `never`，于是从结果类型中消失。
- 注意 `onTick` 也被保留了：它是一个**属性**而非方法，但值的类型确实是函数，符合题目要求「值为函数的键」。
- 函数的匹配模式统一写 `(...args: any[]) => any`。这里用 `any` 而不是 `unknown` 是有原因的：`(...args: unknown[]) => unknown` 会因为参数的逆变规则漏掉一部分函数类型（比如 `(n: number) => void` 就匹配不上）。这是少数几个 `any` 更合适的场合。

**第 4 题：验证 never 陷阱**

```ts
type Wrap<T> = T extends unknown ? T[] : never;

type W1 = Wrap<string>;            // string[]        —— 符合直觉
type W2 = Wrap<string | number>;   // string[] | number[]  —— 分发了
type W3 = Wrap<never>;             // never           —— 陷阱在这里！
```

很多人会预期 `Wrap<never>` 得到 `never[]`，实际却是 `never`。用赋值来验证：

```ts
const w1: W1 = ["a", "b"];         // 合法
const w3a: W3 = [];                // 错误：不能将类型 never[] 分配给类型 never
// 事实上 W3 是 never，没有任何值能赋给它
```

**原因：** `never` 是**空联合**——不包含任何成员的联合类型。分发式条件类型的工作方式是「把联合拆成成员，逐个代入，再把结果并起来」。空联合里没有成员可以遍历，所以循环一次都不执行，结果自然是空联合，也就是 `never`。

用 `Exclude` 更能看清这个逻辑：

```ts
type E1 = Exclude<"a" | "b", "a">;   // "b"      —— 遍历 2 个成员
type E2 = Exclude<"a", "a">;         // never    —— 遍历 1 个，被剔除
type E3 = Exclude<never, "a">;       // never    —— 遍历 0 个
```

**关掉分发就能拿到「直觉答案」：**

```ts
type WrapNoDist<T> = [T] extends [unknown] ? T[] : never;

type W4 = WrapNoDist<never>;   // never[]   ← 这次符合直觉了
const w4: W4 = [];             // 合法
```

因为 `[never]` 是一个元组类型，不是裸类型参数，分发被关闭，`T` 被整体当作 `never` 代入 `T[]`。

**实践提醒：** 遇到「我的条件类型明明写对了，结果却是 `never`」，第一个要怀疑的就是输入是不是 `never`。这种情况常出现在链式的类型运算中——上一步的 `Exclude` 或 `Extract` 恰好把所有成员都过滤光了，产出 `never`，后续每一步都跟着变成 `never`，而报错却出现在很远的地方。

## 小结

- 映射类型 `[K in keyof T]` 批量改造属性；`+` / `-` 增删 `readonly` 与 `?`
- 同态映射会保留原有修饰符，也能正确处理数组与元组
- `as` 子句可以重写键名；求值为 `never` 时该键被丢弃，这是筛选属性的标准手法
- 条件类型 `T extends U ? X : Y` 让类型具备分支能力
- `infer` 像正则捕获组，从匹配到的位置提取子类型
- 裸类型参数上的条件类型会对联合**分发**，`[T] extends [U]` 可关闭；`never` 分发结果是 `never`
- 所有内置工具类型都由这两套机制写成，但日常代码里要克制使用
- 至此，TypeScript 的核心类型系统已经完整 →
