# 泛型进阶

上一章的泛型参数是完全自由的——`T` 可以是任何类型。这带来了一个问题：函数体内部什么都不能对 `T` 做，因为编译器不知道它有什么能力。这一章讲怎么给类型参数**加约束**、**给默认值**、**建立多个参数之间的关联**，以及泛型遇到联合类型时的分发行为。

## 1. extends 约束

### 1.1 问题：裸类型参数太自由

```ts
function longest<T>(a: T, b: T): T {
  // return a.length > b.length ? a : b;   // 错误：T 上不存在 length
  return a;
}
```

编译器是对的：如果有人传两个数字进来，`length` 就不存在。解决办法是**约束** `T` 必须具备某种结构：

```ts
function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length > b.length ? a : b;
}

longest("hello", "hi");        // 字符串有 length
longest([1, 2], [1, 2, 3]);    // 数组有 length
// longest(10, 20);            // 错误：number 没有 length
```

`T extends X` 读作「T 必须可以赋给 X」。约束之后，函数体内就能安全使用 X 上的成员，同时**返回值仍然保留了调用方传入的精确类型**——这正是泛型比 `(a: { length: number })` 强的地方。

### 1.2 常见约束写法

| 约束 | 含义 |
|---|---|
| `T extends string` | 必须是字符串或其字面量子类型 |
| `T extends object` | 必须是对象（排除原始类型） |
| `T extends unknown[]` | 必须是数组 |
| `T extends (...args: any[]) => unknown` | 必须是函数 |
| `K extends keyof T` | K 必须是 T 的某个键名 |

最后一条是全场最实用的，它把两个类型参数**绑定**在一起。

<Callout type="warn" title="约束会「收窄」传入值吗">
不会。`T extends { length: number }` 只是准入门槛，函数体内 `T` 依然是「某个具有 length 的未知类型」，你不能凭空创造一个 `T` 的值（`return { length: 0 }` 会报错，因为调用方可能要的是 `string`）。约束限制的是「能传什么进来」，不是「T 是什么」。
</Callout>

## 2. 默认类型参数

和函数参数的默认值一样，类型参数也能有默认值，写在约束之后：

```ts
interface ApiResponse<TData = unknown, TError = Error> {
  ok: boolean;
  data?: TData;
  error?: TError;
}

type Simple = ApiResponse;              // TData = unknown, TError = Error
type UserResp = ApiResponse<User>;      // 只覆盖第一个
```

默认类型参数让泛型 API「简单场景简单用，复杂场景可定制」。规则和函数默认值一致：**有默认值的参数必须排在没有默认值的后面**。

## 3. 多类型参数的关联

泛型真正的威力在于**表达多个位置之间的关系**。看一个改造对象某个字段的函数：

```ts
function withProp<T, K extends string, V>(
  obj: T,
  key: K,
  value: V,
): T & Record<K, V> {
  return { ...obj, [key]: value } as T & Record<K, V>;
}
```

返回类型精确地表达了「原对象 + 新增的这个键」。这类签名在写工具库时非常常见。

## 4. 泛型与联合：分发行为

当一个类型参数被用在条件类型里，而实参是联合类型时，TypeScript 会**把联合拆开、逐个处理、再合并回去**，这叫分发（distribution）。完整的条件类型在第 11 章讲，这里先建立直觉：

```ts
type ToArray<T> = T extends unknown ? T[] : never;

type A = ToArray<string>;            // string[]
type B = ToArray<string | number>;   // string[] | number[]  ← 分发了
```

注意 `B` 不是 `(string | number)[]`。理解这一点，能解释很多「泛型工具类型结果和预期不一样」的困惑。

想**关掉**分发，把类型参数用方括号包起来：

```ts
type ToArrayNoDist<T> = [T] extends [unknown] ? T[] : never;
type C = ToArrayNoDist<string | number>;   // (string | number)[]
```

<Callout type="info" title="为什么默认要分发">
因为绝大多数工具类型都希望「对联合的每个成员分别处理」。比如 `Exclude<"a" | "b" | "c", "a">` 要得到 `"b" | "c"`，就必须逐个成员判断。分发是默认行为，不分发才需要特殊写法。
</Callout>

function pick<T extends object, K extends keyof T>(obj: T, keys: K[]): Pick<T, K> {
  const out = {} as Pick<T, K>;
  for (const k of keys) out[k] = obj[k];
  return out;
}

// 2) groupBy：按键函数分组
function groupBy<T>(items: T[], key: (item: T) => string): Map<string, T[]> {
  const map = new Map<string, T[]>();
  for (const item of items) {
    const k = key(item);
    const bucket = map.get(k);
    if (bucket === undefined) map.set(k, [item]);
    else bucket.push(item);
  }
  return map;
}

// 3) zip：把两个数组配对
function zip<A, B>(as: A[], bs: B[]): [A, B][] {
  const n = Math.min(as.length, bs.length);
  const out: [A, B][] = [];
  for (let i = 0; i < n; i++) out.push([as[i] as A, bs[i] as B]);
  return out;
}

// 4) sortBy：按可比较的字段排序，返回新数组
function sortBy<T>(items: T[], by: (item: T) => number): T[] {
  return [...items].sort((x, y) => by(x) - by(y));
}

  id: number;
  name: string;
  grade: string;
  score: number;
}

const students: Student[] = [
  { id: 1, name: "Ada", grade: "A", score: 95 },
  { id: 2, name: "Alan", grade: "B", score: 82 },
  { id: 3, name: "Grace", grade: "A", score: 91 },
];

const brief = pick(students[0] as Student, ["name", "score"]);
console.log("pick: " + brief.name + " " + brief.score);

const byGrade = groupBy(students, (s) => s.grade);
for (const [g, list] of byGrade) {
  console.log("等级 " + g + " 有 " + list.length + " 人");
}

const pairs = zip(["a", "b", "c"], [1, 2]);
console.log("zip 结果长度 = " + pairs.length + "，第一对 = " + pairs[0]?.[0] + pairs[0]?.[1]);

<Callout type="warn" title="不要滥用 as">
上面 `pick` 里的 `{} as Pick<T, K>` 是一处必要的妥协：空对象在填充完成前确实不满足目标类型，编译器无法跟踪这个过程。这类断言应当**局部、可审阅**，并且函数对外的签名必须是准确的。如果一个函数需要三四处 `as` 才能通过检查，通常说明类型设计出了问题。
</Callout>

## 6. 泛型设计的几条经验

1. **先写调用方，再写签名**。想清楚希望调用处推断出什么类型，再倒推签名。
2. **约束要恰到好处**。约束太松，函数体没法用；约束太紧，调用方传不进来。
3. **类型参数至少出现两次**。只出现一次的类型参数应该换成 `unknown`。
4. **别怕显式指定**。推断失败时让调用方写 `fn<Foo>(...)` 完全合理，比设计一个扭曲的签名好。

### 6.1 推断失败的三种常见原因

遇到「推断结果不是我想要的」，八成是下面之一：

| 现象 | 原因 | 对策 |
|---|---|---|
| 推断成 `never` | 没有任何实参能提供信息（如传空数组） | 显式指定类型参数 |
| 推断成宽类型（`string` 而非字面量） | 类型参数没有约束，走了默认的拓宽规则 | 加 `T extends string` 约束，或调用处加 `as const` |
| 推断成联合而非精确分支 | 多个参数位置提供了冲突的候选类型 | 调整参数顺序，或把其中一个位置改成非推断位置 |

第二条特别常见。对比一下：

```ts
function pickA<T>(v: T): T { return v; }
function pickB<T extends string>(v: T): T { return v; }

const a = pickA("hello");    // string
const b = pickB("hello");    // "hello"  ← 约束让它保留了字面量
```

加上 `extends string` 之后，编译器知道你关心的是字符串的**具体值**，于是不再拓宽。这个技巧在设计接受字面量键名的 API 时非常有用。

**第 1 题：omit**

```ts
function omit<T extends object, K extends keyof T>(obj: T, keys: K[]): Omit<T, K> {
  const out = { ...obj } as T;                 // 先整体复制
  for (const k of keys) {
    delete out[k];                             // 再删掉不要的键
  }
  return out as Omit<T, K>;
}

interface User {
  id: number;
  name: string;
  password: string;
  email: string;
}

const user: User = {
  id: 1,
  name: "Ada",
  password: "s3cret",
  email: "ada@example.com",
};

const safe = omit(user, ["password"]);
// safe 的类型是 Omit<User, "password">，即 { id, name, email }

console.log(JSON.stringify(safe));
// {"id":1,"name":"Ada","email":"ada@example.com"}
console.log(safe.name);
// safe.password;              // 错误：属性 password 在类型上不存在
// omit(user, ["nickname"]);   // 错误：nickname 不是 User 的键
```

要点：

- `K extends keyof T` 保证只能删真实存在的键，拼错键名会在编译期被抓住。
- 返回类型用内置的 `Omit<T, K>`，调用方拿到的类型里**真的没有**被删掉的键，这正是 `omit` 与 `pick` 互补的地方。
- 这里同样有本章 Callout 提到的 `as` 妥协：`delete` 之后对象的静态类型仍是 `T`，编译器无法跟踪「键被删掉了」这个事实，所以需要在**函数出口处**断言一次。断言局限在函数内部，对外签名是准确的，这是可接受的用法。
- 不想用 `delete`（它对 V8 的隐藏类有性能影响）时，可以改成过滤 `Object.entries` 再重建对象：

```ts
function omit<T extends object, K extends keyof T>(obj: T, keys: K[]): Omit<T, K> {
  const drop = new Set<PropertyKey>(keys);
  return Object.fromEntries(
    Object.entries(obj).filter(([k]) => !drop.has(k)),
  ) as Omit<T, K>;
}
```

**第 2 题：带默认类型参数的 Paged**

```ts
interface Paged<TItem, TCursor = string> {
  items: TItem[];
  nextCursor?: TCursor;
}

function paginate<TItem, TCursor = string>(
  items: TItem[],
  nextCursor?: TCursor,
): Paged<TItem, TCursor> {
  return nextCursor !== undefined ? { items, nextCursor } : { items };
}

interface Post {
  id: number;
  title: string;
}

// 用默认游标类型（string），只写一个类型参数
const page1: Paged<Post> = paginate(
  [
    { id: 1, title: "第一篇" },
    { id: 2, title: "第二篇" },
  ],
  "cursor_abc",
);

console.log("本页 " + page1.items.length + " 条，下一页游标 " + String(page1.nextCursor));
// 本页 2 条，下一页游标 cursor_abc

// 覆盖游标类型为数字（比如用自增 ID 做游标）
const page2: Paged<Post, number> = paginate([{ id: 3, title: "第三篇" }], 3);
console.log("数字游标 = " + String(page2.nextCursor));   // 3

// 最后一页，没有游标
const last = paginate<Post>([{ id: 9, title: "末篇" }]);
console.log("还有下一页? " + (last.nextCursor !== undefined));  // false
```

要点：

- `TCursor = string` 让 90% 的调用方只写 `Paged<Post>` 即可，需要时才用 `Paged<Post, number>` 定制——这就是默认类型参数的意义。
- 规则提醒：**有默认值的类型参数必须排在没有默认值的后面**。把它写成 `Paged<TCursor = string, TItem>` 会直接报错。
- `nextCursor` 用可选属性表达「最后一页没有下一页游标」，符合业务语义。

**第 3 题：验证分发行为**

```ts
type Boxed<T> = T extends unknown ? { value: T } : never;

// 情况 A：传入单一类型
type B1 = Boxed<string>;
// 结果：{ value: string }

// 情况 B：传入联合类型 —— 发生分发
type B2 = Boxed<string | number>;
// 结果：{ value: string } | { value: number }
// 注意：不是 { value: string | number }！
```

用变量赋值来验证编译器的实际行为：

```ts
// B2 是「两个盒子的联合」，所以下面两行都合法
const b1: B2 = { value: "hello" };
const b2: B2 = { value: 42 };

// 但它绝不等于 { value: string | number }。下面这行揭示了差别：
declare const mixed: string | number;
// const b3: B2 = { value: mixed };
// 错误：类型“{ value: string | number; }”不能赋给类型“B2”。
//   不能将类型“string | number”分配给类型“string”。

// 反过来，把 B2 赋给「一个盒子装联合」是可以的
type OneBox = { value: string | number };
const b4: OneBox = b1;   // 合法
```

**关掉分发做对比：**

```ts
type BoxedNoDist<T> = [T] extends [unknown] ? { value: T } : never;

type B3 = BoxedNoDist<string | number>;
// 结果：{ value: string | number }

declare const mixed2: string | number;
const b5: B3 = { value: mixed2 };   // 这次就合法了
```

**结论：**

| 写法 | `Boxed<string \| number>` 的结果 | 能装 `string \| number` 变量吗 |
|---|---|---|
| `T extends unknown ? ...` | `{ value: string } \| { value: number }` | 不能 |
| `[T] extends [unknown] ? ...` | `{ value: string \| number }` | 能 |

分发的判定条件是：条件类型中被检查的类型是一个**裸的类型参数**（naked type parameter）。一旦把它包进元组 `[T]`、数组或其它结构里，就不再是「裸」的，分发随之关闭。

这个区别在实践中很常见。比如你写了个 `Boxed<Payload>` 想表示「一个装着 payload 的容器」，结果 `Payload` 恰好是联合类型，你拿到的却是「多个容器的联合」，赋值处莫名其妙地报错——这时候就该想起 `[T] extends [X]` 这个开关了。
</Answer>

## 小结

- `T extends X` 给类型参数设准入门槛，同时保留调用方的精确类型
- `K extends keyof T` 是把多个类型参数绑定起来的核心手法
- 默认类型参数让泛型 API 兼顾易用与可定制，有默认值的必须排在后面
- 泛型遇到联合会**分发**，用 `[T] extends [X]` 可以关掉
- 手写 `pick` / `groupBy` / `zip` / `sortBy` 是练习泛型的最佳方式
- 类型参数只出现一次说明不需要泛型；约束要松紧适度
