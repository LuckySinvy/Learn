# 错误处理

TypeScript 在错误处理上有一个绕不开的现实：**`throw` 可以抛出任何值，而且函数签名里无法声明它会抛什么**。Java 有 `throws`，Rust 有 `Result`，TS 两样都没有。

```ts
function risky(): number {
  throw "字符串也能抛";     // 签名仍然是 () => number
}
```

这意味着：类型系统默认帮不了你。要想让错误处理也变得类型安全，得靠**主动建模**。本章给出三条互补的路线：规范化异常、把错误编码进返回值、以及用断言表达不变量。

## 1. `catch` 里的值是 `unknown`

开启 `strict`（准确说是 `useUnknownInCatchVariables`）之后，`catch (e)` 中 `e` 的类型是 `unknown`，必须先收窄才能用：

```ts
try {
  doSomething();
} catch (e) {
  // e.message         // 报错：unknown 上没有 message
  if (e instanceof Error) console.error(e.message);
  else console.error(String(e));
}
```

这个改动经常被抱怨「太啰嗦」，但它反映的是真实情况：第三方库抛字符串、抛对象、抛 `undefined` 的都有。实践中最好写一个统一的**规范化函数**，把任何抛出物变成 `Error`：

```ts
function toError(e: unknown): Error {
  if (e instanceof Error) return e;
  if (typeof e === "string") return new Error(e);
  return new Error("非 Error 抛出物: " + JSON.stringify(e));
}
```

<Callout type="warn" title="别用 catch (e: any)">
`catch (e: any)` 能让编译通过，但它把整条错误处理链变成了无类型区。TS 只允许 `catch` 参数标注为 `any` 或 `unknown` 两种，选 `unknown` 并配一个 `toError`，成本很低收益很大。
</Callout>

## 2. 自定义 Error 子类

内置的 `Error` 只有 `name`／`message`／`stack`／`cause`。要携带业务信息（HTTP 状态码、字段名、重试标记），就需要子类化。

三个要点：

1. 构造函数里必须 `super(message)`；
2. 手动设置 `this.name`，否则 `err.name` 一直是 `"Error"`；
3. `target` 低于 ES2015 时，`extends Error` 会丢失原型链，需要 `Object.setPrototypeOf(this, new.target.prototype)`。现代项目 `target: ES2022` 无此问题。

`cause` 是 ES2022 新增的标准字段，用来串联错误链，比自己发明 `originalError` 字段更好：

```ts
throw new Error("加载配置失败", { cause: ioError });
```

</Callout>

## 3. 类型安全的错误联合

比子类化更「TS 味」的做法：把错误建模成**可辨识联合**，用 `switch` 做穷尽性处理。这样新增一种错误时，编译器会指出所有需要补分支的地方。

```ts
type AppFailure =
  | { kind: "not_found"; id: string }
  | { kind: "validation"; field: string; message: string }
  | { kind: "network"; status: number };
```

它的优势是**错误集合是封闭的、可枚举的**；劣势是没有 stack trace，且不能直接 `throw` 后被通用中间件识别。两种方式常常混用：内层用联合，边界处包装成 Error 抛出。

## 4. Result 模式：把错误放进返回值

既然 `throw` 无法出现在类型签名里，那就干脆不抛——把「成功或失败」编码成返回值。这就是 Rust 的 `Result`、Haskell 的 `Either` 在 TS 里的翻版：

```ts
type Ok<T> = { ok: true; value: T };
type Err<E> = { ok: false; error: E };
type Result<T, E> = Ok<T> | Err<E>;
```

调用方**必须**先检查 `ok` 字段才能拿到 `value`，编译器强制你面对失败分支。

| 方案 | 优点 | 缺点 |
|---|---|---|
| `throw` + 子类 | 符合 JS 习惯、有 stack、能跨层冒泡 | 签名不体现、容易漏 catch |
| 错误联合 | 可穷尽、易测试 | 需要手动传递 |
| `Result` | 类型强制处理、无隐藏控制流 | 调用链啰嗦、与生态不兼容 |

实践建议：**领域核心逻辑用 `Result`，进程边界（HTTP handler、CLI 入口）用 `throw` + 统一 catch**。

type Err<E> = { readonly ok: false; readonly error: E };
type Result<T, E> = Ok<T> | Err<E>;

function ok<T>(value: T): Ok<T> {
  return { ok: true, value };
}
function err<E>(error: E): Err<E> {
  return { ok: false, error };
}

type ParseFailure =
  | { kind: "empty" }
  | { kind: "not_a_number"; raw: string }
  | { kind: "out_of_range"; value: number; max: number };

function parseAge(raw: string): Result<number, ParseFailure> {
  if (raw.trim() === "") return err<ParseFailure>({ kind: "empty" });
  const n = Number(raw);
  if (Number.isNaN(n)) return err<ParseFailure>({ kind: "not_a_number", raw });
  if (n > 150) return err<ParseFailure>({ kind: "out_of_range", value: n, max: 150 });
  return ok(n);
}

function assertNever(x: never): never {
  throw new Error("未处理的错误分支: " + JSON.stringify(x));
}

function describe(f: ParseFailure): string {
  switch (f.kind) {
    case "empty":
      return "输入为空";
    case "not_a_number":
      return "不是数字: " + f.raw;
    case "out_of_range":
      return f.value + " 超过上限 " + f.max;
    default:
      return assertNever(f);
  }
}

for (const raw of ["30", "", "abc", "999"]) {
  const r = parseAge(raw);
  if (r.ok) console.log("输入", JSON.stringify(raw), "-> 年龄", r.value);
  else console.log("输入", JSON.stringify(raw), "-> 失败:", describe(r.error));
}

// 组合子：map 与 andThen，让 Result 可以链式串联
function map<T, U, E>(r: Result<T, E>, fn: (v: T) => U): Result<U, E> {
  return r.ok ? ok(fn(r.value)) : r;
}
function andThen<T, U, E>(r: Result<T, E>, fn: (v: T) => Result<U, E>): Result<U, E> {
  return r.ok ? fn(r.value) : r;
}

const pipeline = andThen(map(parseAge("42"), (n) => n * 2), (n) =>
  n < 100 ? ok("合法: " + n) : err({ kind: "out_of_range", value: n, max: 100 } as ParseFailure),
);
console.log("链式结果:", pipeline.ok ? pipeline.value : describe(pipeline.error));`}
/>

<Callout type="tip" title="把 throw 包装成 Result">
在边界处写一个 `tryCatch` 辅助函数：`function attempt<T>(fn: () => T): Result<T, Error>`，内部 `try { return ok(fn()) } catch (e) { return err(toError(e)) }`。这样第三方库的异常能一次性接入你的 Result 体系。
</Callout>

## 5. 断言与不变量

第 14 章讲过断言函数。在错误处理语境下，它们用来表达**「这里如果不成立，程序就该崩」**的假设：

- **可恢复错误**：用户输入非法、网络超时——用 `Result` 或受检异常处理。
- **不变量违背**：数组本该非空却为空、状态机进入了不可能的状态——用 `invariant` 直接崩溃。

区分这两类非常重要。把「程序 bug」伪装成「可恢复错误」去 catch，只会让问题在更远的地方以更诡异的形式爆发。

  constructor(message: string) {
    super("不变量被破坏: " + message);
    this.name = "InvariantError";
  }
}

function invariant(cond: unknown, msg: string): asserts cond {
  if (!cond) throw new InvariantError(msg);
}

function toError(e: unknown): Error {
  if (e instanceof Error) return e;
  if (typeof e === "string") return new Error(e);
  return new Error("非 Error 抛出物: " + JSON.stringify(e));
}

type Ok<T> = { ok: true; value: T };
type Err = { ok: false; error: Error };
type Attempt<T> = Ok<T> | Err;

function attempt<T>(fn: () => T): Attempt<T> {
  try {
    return { ok: true, value: fn() };
  } catch (e) {
    return { ok: false, error: toError(e) };
  }
}

type State = "idle" | "running" | "done";

class Machine {
  private state: State = "idle";
  start(): void {
    invariant(this.state === "idle", "只能从 idle 启动，当前是 " + this.state);
    this.state = "running";
  }
  finish(): void {
    invariant(this.state === "running", "只能从 running 完成，当前是 " + this.state);
    this.state = "done";
  }
  get current(): State {
    return this.state;
  }
}

const m = new Machine();
m.start();
console.log("状态:", m.current);

const bad = attempt(() => {
  m.start();
  return "不会到这里";
});
console.log("attempt 捕获:", bad.ok ? bad.value : bad.error.message);

m.finish();
console.log("状态:", m.current);

const good = attempt(() => JSON.parse('{"a":1}') as { a: number });
console.log("解析成功:", good.ok ? good.value.a : good.error.message);

console.log("解析失败:", worse.ok ? "?" : worse.error.name);`}

<Callout type="warn" title="不要吞掉错误">
`catch (e) {}` 是代码库里最危险的五个字符。即使确实要忽略，也应该写明理由并至少打一条 debug 日志。真正需要「尽力而为」的场景（如清理临时文件），把忽略逻辑封装成一个命名清晰的函数，比裸的空 catch 好得多。
</Callout>

## 6. 检查清单

1. `catch` 参数一律 `unknown`，配一个 `toError` 规范化。
2. 业务错误子类化，带稳定的 `code`；用 `cause` 串错误链。
3. 可枚举的失败用可辨识联合 + `assertNever` 保证穷尽。
4. 核心逻辑考虑 `Result`，边界处统一转成异常或 HTTP 响应。
5. 程序 bug 用 `invariant` 直接崩溃，不要伪装成可恢复错误。
6. 永远不要空 catch。

**第 1 题：AppError.toJSON()**

```ts
interface SerializedError {
  name: string;
  code?: string;
  message: string;
  cause?: SerializedError;
}

function serializeError(e: unknown, depth = 0): SerializedError {
  // 防御无限递归：错误链可能成环（A.cause = B, B.cause = A）
  if (depth > 5) {
    return { name: "Truncated", message: "错误链过深，已截断" };
  }
  if (!(e instanceof Error)) {
    return { name: "NonError", message: String(e) };
  }
  const out: SerializedError = {
    name: e.name,
    message: e.message,
  };
  if (e instanceof AppError) {
    out.code = e.code;
  }
  if (e.cause !== undefined) {
    out.cause = serializeError(e.cause, depth + 1);
  }
  return out;
}

class AppError extends Error {
  readonly code: string;
  readonly retryable: boolean;

  constructor(
    message: string,
    code: string,
    options?: { retryable?: boolean; cause?: unknown },
  ) {
    super(message, { cause: options?.cause });
    this.name = "AppError";
    this.code = code;
    this.retryable = options?.retryable ?? false;
  }

  toJSON(): SerializedError {
    return serializeError(this);
  }
}
```

要点：

- **`toJSON` 是 `JSON.stringify` 的约定钩子。** 定义了它之后，直接 `JSON.stringify(err)` 就会调用它。这一点很关键——因为原生 `Error` 的 `name` / `message` / `stack` 都是**不可枚举**属性，不加 `toJSON` 的话 `JSON.stringify(new Error("x"))` 得到的是 `{}`。这是结构化日志里最经典的坑。
- **深度限制不是过度设计。** 错误链成环在包装层数多的系统里真的会发生（比如重试逻辑把捕获的错误又设成新错误的 cause）。没有这道防线，一次日志打印就能让进程栈溢出。
- `cause` 用 `!== undefined` 判断而不是真值判断——虽然罕见，但 `cause` 理论上可以是 `0` 或 `""`。
- 生产环境通常还要按环境决定是否包含 `stack`：开发环境带上便于定位，生产环境省略以免日志膨胀和泄露路径信息。

**第 2 题：attemptAsync**

```ts
type Ok<T> = { readonly ok: true; readonly value: T };
type Err<E> = { readonly ok: false; readonly error: E };
type Result<T, E> = Ok<T> | Err<E>;

function ok<T>(value: T): Ok<T> {
  return { ok: true, value };
}
function err<E>(error: E): Err<E> {
  return { ok: false, error };
}

function toError(e: unknown): Error {
  if (e instanceof Error) return e;
  if (typeof e === "string") return new Error(e);
  return new Error("非 Error 抛出物: " + JSON.stringify(e));
}

async function attemptAsync<T>(fn: () => Promise<T>): Promise<Result<T, Error>> {
  try {
    return ok(await fn());     // await 必须在 try 内部
  } catch (e) {
    return err(toError(e));
  }
}
```

改写前（传统 try/catch）：

```ts
async function loadUserProfile(id: string): Promise<string> {
  let user: User;
  try {
    user = await fetchUser(id);
  } catch (e) {
    console.error("拉取用户失败", e);
    return "匿名用户";
  }

  let avatar: string;
  try {
    avatar = await fetchAvatar(user.avatarId);
  } catch {
    avatar = "/default.png";
  }

  return user.name + " " + avatar;
}
```

改写后：

```ts
async function loadUserProfile(id: string): Promise<string> {
  const userResult = await attemptAsync(() => fetchUser(id));
  if (!userResult.ok) {
    console.error("拉取用户失败", userResult.error.message);
    return "匿名用户";
  }
  const user = userResult.value;      // 收窄后类型是 User，不再需要 let

  const avatarResult = await attemptAsync(() => fetchAvatar(user.avatarId));
  const avatar = avatarResult.ok ? avatarResult.value : "/default.png";

  return user.name + " " + avatar;
}
```

改写带来的三个实际收益：

1. **`let` 变成了 `const`。** try/catch 版本里，变量必须先 `let` 声明再在 try 内赋值（因为 `const` 的作用域出不了 try 块），这会丢掉类型收窄并留下「可能未赋值」的隐患。
2. **失败处理紧贴调用点。** 不再需要「跳读」到几行之外的 catch 块。
3. **控制流是显式的。** 没有隐藏的异常跳转，每一步的成功/失败都体现在类型里，编译器强制你处理。

一个关键细节：**`return ok(await fn())` 里的 `await` 必须写在 `try` 内部**。如果写成 `return fn().then(ok)`，Promise 的 rejection 会逃出 `try/catch`——这正是本章第 17 章「常见坑」里提到的第 2 条。

**第 3 题：unwrapOr、mapErr 与何时不该用 unwrap**

```ts
// 取值，失败时返回兜底值
function unwrapOr<T, E>(r: Result<T, E>, fallback: T): T {
  return r.ok ? r.value : fallback;
}

// 惰性版本：兜底值计算昂贵时用它，避免无谓计算
function unwrapOrElse<T, E>(r: Result<T, E>, fn: (e: E) => T): T {
  return r.ok ? r.value : fn(r.error);
}

// 只转换错误分支，成功分支原样透传
function mapErr<T, E, F>(r: Result<T, E>, fn: (e: E) => F): Result<T, F> {
  return r.ok ? r : err(fn(r.error));
}

// 危险的那个：失败直接抛
function unwrap<T, E>(r: Result<T, E>): T {
  if (r.ok) return r.value;
  throw r.error instanceof Error ? r.error : new Error(String(r.error));
}
```

用法：

```ts
const r1 = parseAge("30");
const r2 = parseAge("abc");

console.log(unwrapOr(r1, 0));    // 30
console.log(unwrapOr(r2, 0));    // 0

// mapErr 的典型用途：把底层错误翻译成面向用户的信息
const friendly = mapErr(r2, (f) => {
  switch (f.kind) {
    case "empty":
      return "请填写年龄";
    case "not_a_number":
      return "年龄必须是数字";
    case "out_of_range":
      return "年龄不能超过 " + f.max + " 岁";
  }
});
console.log(friendly.ok ? friendly.value : friendly.error);
// 年龄必须是数字
```

`mapErr` 最大的价值是**在分层架构中做错误翻译**：数据层返回 `DbError`，服务层用 `mapErr` 转成 `DomainError`，接口层再转成 HTTP 响应。每一层只认识自己那套错误类型，`Result` 的成功分支在整个过程中完全不受影响。

**什么时候不该用 unwrap：**

`unwrap` 会把「编译器强制你处理错误」这个 Result 模式的**唯一好处**给扔掉——它等于在说「我赌这里不会失败」。以下场景明确不该用：

| 场景 | 为什么不该用 | 该用什么 |
|---|---|---|
| 处理用户输入 | 失败是**预期内**的正常路径 | `if (!r.ok)` 分支或 `unwrapOr` |
| 网络、文件 IO | 失败是常态，不是异常 | 显式分支处理 + 重试 |
| 库/框架的公共 API 内部 | 你替调用方决定了「崩溃」，剥夺了他的选择权 | 把 `Result` 原样返回给调用方 |
| 只是「懒得写 if」 | 把编译期保障换成了运行时崩溃 | 老老实实写分支 |

**可以用的场景**只有两类：

1. **不变量场景**——失败意味着程序有 bug，本来就该崩。这时更推荐用语义明确的 `invariant`，而不是 `unwrap`。
2. **测试代码**——测试里失败就该让用例红掉，`unwrap` 反而让代码简洁。

一个判断标准：**问自己「这里失败了，是外部世界的问题还是我的代码写错了？」** 前者用分支处理，后者才可以崩。这正是本章第 5 节「可恢复错误 vs 不变量违背」的区分在 Result 模式下的具体应用。

最后提一句：`unwrapOr` 和 `unwrapOrElse` 的区别在于**兜底值是否惰性求值**。`unwrapOr(r, expensiveDefault())` 无论成功与否都会执行 `expensiveDefault()`，而 `unwrapOrElse(r, () => expensiveDefault())` 只在失败时才执行。兜底值涉及 IO 或复杂计算时，一定要用后者。
</Answer>
</Callout>

## 小结

- TS 无法在签名中表达「会抛什么」，错误安全必须靠主动建模
- `catch` 参数是 `unknown`，统一用 `toError` 规范化
- 自定义 Error 记得设 `this.name`，用 ES2022 的 `cause` 串错误链
- 可辨识联合 + `assertNever` 让错误集合可穷尽
- `Result` 把失败编码进返回值，适合领域核心；边界处再转回异常
- 区分「可恢复错误」与「不变量违背」，后者应该直接崩溃
