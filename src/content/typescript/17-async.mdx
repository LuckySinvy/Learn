# 异步编程的类型

JavaScript 的异步生态经历了回调、Promise、`async/await` 三代演进。TypeScript 给每一代都提供了精确的类型建模，其中最核心的一个泛型就是 `Promise<T>`——它表示「将来会得到一个 `T`」。

本章我们把异步相关的类型工具串起来：怎么标注异步函数、`Awaited` 解决了什么、并发时元组类型如何保留、以及取消与流式数据怎么建模。

## 1. `Promise<T>` 与 async 函数

### 1.1 基本标注

`async` 函数的返回类型**永远**是一个 Promise。你标注的是它 resolve 之后的类型：

```ts
async function getName(): Promise<string> {
  return "Ada";        // 返回 string，会被自动包装成 Promise<string>
}
```

写成 `async function getName(): string` 会直接报错：「异步函数的返回类型必须是 Promise」。

### 1.2 三个泛型位置

| 写法 | 含义 |
|---|---|
| `Promise<void>` | 完成但没有有意义的返回值 |
| `Promise<never>` | 永远不会成功（只会 reject 或永不结束） |
| `Promise<T>` 的 reject | **没有类型**，永远是 `any`／`unknown` |

第三条是 TypeScript 一个长期的设计缺口：**Promise 的失败分支不可标注**。`.catch(e => ...)` 里的 `e` 永远是 `any`。第 18 章我们会讲用 Result 模式绕开它。

<Callout type="warn" title="忘记 await 是最隐蔽的 bug">
`if (checkAsync())` 里如果 `checkAsync` 是 async 函数，条件永远为真——因为 Promise 对象是真值。TS 本身不会报错，需要靠 ESLint 的 `no-misused-promises` 与 `no-floating-promises` 规则兜底。这两条规则强烈建议开启。
</Callout>

## 2. 并发：Promise 的四个组合子

| 方法 | 何时结束 | 返回 |
|---|---|---|
| `Promise.all` | 全部成功，或任一失败 | 结果**元组**（类型一一对应） |
| `Promise.allSettled` | 全部结束（成功失败都算） | 状态对象数组 |
| `Promise.race` | 第一个结束的（成功或失败） | 那一个的结果 |
| `Promise.any` | 第一个**成功**的 | 那一个的值；全失败则抛 `AggregateError` |

`Promise.all` 的类型定义非常精巧：传入元组时，它会保留每个位置的类型，而不是退化成联合数组。这让解构赋值也能拿到正确类型。

<Callout type="tip" title="all 还是 allSettled">
需要「全部成功才继续」用 `all`；需要「无论成败都收集结果」用 `allSettled`。给用户批量发通知这类场景，用 `all` 会因为一个失败而丢掉其它结果，几乎总是错的。
</Callout>

### 2.1 并发上限

`Promise.all` 会一次性发起所有请求。当任务有几百个时，需要限制并发数。标准做法是开 N 个「worker」共享一个游标：

  items: readonly T[],
  limit: number,
  fn: (item: T, index: number) => Promise<R>,
): Promise<R[]> {
  const out: R[] = new Array<R>(items.length);
  let cursor = 0;

  async function worker(): Promise<void> {
    while (cursor < items.length) {
      const i = cursor;
      cursor += 1;

    }

  for (let w = 0; w < Math.min(limit, items.length); w += 1) {
    workers.push(worker());
  }
  await Promise.all(workers);
  return out;
}

## 3. 取消：AbortController 与 AbortSignal

Promise 一旦创建就无法「撤回」。标准的取消方案是 `AbortController`：它产出一个 `AbortSignal`，把 signal 传给可取消的操作，调用 `controller.abort()` 时操作自行终止。

`fetch`、Node 的 `fs.promises`、`setTimeout`（`timers/promises` 版本）都原生支持它。自己写的异步函数也应该接受一个可选的 `signal` 参数——这是现代 TS/JS 库的通用约定。

## 4. 异步迭代器与 `for await...of`

当数据是**逐块到达**的（分页 API、文件流、数据库游标），用 `AsyncIterable` 建模比一次性返回数组更合适。

```ts
async function* pages(total: number): AsyncGenerator<number[], void, unknown> {
  for (let p = 0; p < total; p++) {
    yield await fetchPage(p);
  }
}

for await (const page of pages(3)) {
  console.log(page.length);
}
```

`AsyncGenerator<Y, R, N>` 的三个类型参数分别是：`yield` 出去的类型、`return` 的类型、外部通过 `next(v)` 传进来的类型。大多数时候只关心第一个。

## 5. 常见坑总结

1. **`void` 返回的回调里用 async**。`arr.forEach(async (x) => { await f(x); })` 不会等待任何东西。要串行用 `for...of`，要并发用 `Promise.all(arr.map(...))`。
2. **在 `try` 里 `return promise` 而不 `await`**。异常会逃出 `try/catch`。要么 `return await`，要么把 `await` 放进 try。
3. **`Promise.all` 的失败会丢弃其它结果**，但其它 Promise 仍在跑，它们的错误可能变成未处理拒绝。
4. **`async` 构造函数不存在**。需要异步初始化时用静态工厂方法 `static async create()`。
5. **不要用 `Promise` 包裹已经是 Promise 的东西**，`new Promise(res => somePromise.then(res))` 是反模式。

**第 1 题：给 mapLimit 加上取消支持**

```ts
async function mapLimit<T, R>(
  items: readonly T[],
  limit: number,
  fn: (item: T, index: number, signal?: AbortSignal) => Promise<R>,
  signal?: AbortSignal,
): Promise<R[]> {
  // 入口先检查一次：已经取消了就别白费力气
  if (signal?.aborted === true) {
    throw new Error("操作已取消");
  }

  const out: R[] = new Array<R>(items.length);
  let cursor = 0;

  async function worker(): Promise<void> {
    while (cursor < items.length) {
      // 每次派发新任务前检查，取消后立即停止派发
      if (signal?.aborted === true) {
        throw new Error("操作已取消");
      }
      const i = cursor;
      cursor += 1;
      out[i] = await fn(items[i] as T, i, signal);
    }
  }

  const workers: Promise<void>[] = [];
  for (let w = 0; w < Math.min(limit, items.length); w += 1) {
    workers.push(worker());
  }

  await Promise.all(workers);
  return out;
}
```

用法：

```ts
function delay(ms: number): Promise<void> {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

async function main(): Promise<void> {
  const controller = new AbortController();

  // 30ms 后取消
  setTimeout(() => controller.abort(), 30);

  try {
    const result = await mapLimit(
      [1, 2, 3, 4, 5, 6, 7, 8],
      2,
      async (n) => {
        await delay(20);
        console.log("完成任务 " + n);
        return n * n;
      },
      controller.signal,
    );
    console.log(result);
  } catch (e) {
    console.log("捕获: " + (e as Error).message);   // 捕获: 操作已取消
  }
}
```

要点：

- **检查点放在 while 循环的开头**，也就是「派发下一个任务之前」。这满足题目要求的「立即停止派发新任务」：已经在跑的任务会自然跑完（除非 `fn` 自己也响应 signal），但不会再开新的。
- `signal` 被透传给 `fn`，这样单个任务内部（比如 `fetch`）也能响应取消。这是现代库的通用约定。
- 用 `signal?.aborted === true` 而不是 `signal?.aborted`：`signal` 为 `undefined` 时前者明确得到 `false`，后者得到 `undefined`，虽然在 `if` 里效果相同，但显式比较更清晰，也符合 `strict` 下的习惯。
- **完全遵循 Web 标准的写法**应该抛 `DOMException` 并使用 signal 自带的原因：

```ts
if (signal?.aborted === true) {
  throw signal.reason;   // reason 默认是一个 name 为 "AbortError" 的 DOMException
}
// 或者直接用标准方法（Node 18+ / 现代浏览器）
signal?.throwIfAborted();
```

`signal.throwIfAborted()` 就是「检查并抛出」的标准封装，生产代码里优先用它。

**第 2 题：withTimeout**

```ts
function withTimeout<T>(p: Promise<T>, ms: number): Promise<T> {
  let timer: ReturnType<typeof setTimeout>;

  const timeout = new Promise<never>((_resolve, reject) => {
    timer = setTimeout(() => {
      reject(new Error("操作超时（" + ms + "ms）"));
    }, ms);
  });

  // race：谁先结束用谁的结果
  return Promise.race([p, timeout]).finally(() => {
    clearTimeout(timer);   // 无论哪边赢，都要清理定时器
  });
}
```

验证：

```ts
function delay<T>(ms: number, value: T): Promise<T> {
  return new Promise((resolve) => setTimeout(() => resolve(value), ms));
}

async function main(): Promise<void> {
  // 情况 1：按时完成
  const fast = await withTimeout(delay(10, "完成"), 100);
  console.log(fast);   // 完成

  // 情况 2：超时
  try {
    await withTimeout(delay(200, "太慢了"), 50);
  } catch (e) {
    console.log((e as Error).message);   // 操作超时（50ms）
  }
}
```

要点：

- 超时那个 Promise 的类型是 **`Promise<never>`**，因为它只会 reject、永远不会 resolve。这样 `Promise.race([Promise<T>, Promise<never>])` 的结果类型正好是 `Promise<T>`——`never` 在联合里被自动吸收。这是 `never` 在实际代码中一个非常漂亮的用法。
- **`clearTimeout` 不能省。** 如果原 Promise 10ms 就完成了，而超时设的是 60 秒，不清理的话进程会被这个定时器多挂住 60 秒（Node 里表现为程序不退出）。用 `.finally()` 保证两种结局都清理。
- **重要局限：超时不等于取消。** `Promise.race` 只是「不再等待」原 Promise，原操作**仍在后台继续运行**。真正需要中止底层操作时，必须配合 `AbortController`：

```ts
async function fetchWithTimeout(url: string, ms: number): Promise<Response> {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), ms);
  try {
    return await fetch(url, { signal: controller.signal });
  } finally {
    clearTimeout(timer);
  }
}
```

顺带一提，现代运行时已经内置了这个能力：`AbortSignal.timeout(ms)` 可以直接生成一个到点自动 abort 的 signal。

**第 3 题：异步生成器 chunk**

```ts
async function* chunk<T>(
  source: AsyncIterable<T>,
  size: number,
): AsyncGenerator<T[], void, unknown> {
  if (size < 1) throw new RangeError("size 必须大于等于 1");

  let buffer: T[] = [];

  for await (const item of source) {
    buffer.push(item);
    if (buffer.length === size) {
      yield buffer;
      buffer = [];        // 必须新建数组，不能 buffer.length = 0
    }
  }

  // 收尾：剩余不足一批的元素也要吐出去
  if (buffer.length > 0) {
    yield buffer;
  }
}
```

验证：

```ts
function delay(ms: number): Promise<void> {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

async function* numbers(n: number): AsyncGenerator<number, void, unknown> {
  for (let i = 1; i <= n; i += 1) {
    await delay(2);
    yield i;
  }
}

async function main(): Promise<void> {
  for await (const batch of chunk(numbers(7), 3)) {
    console.log(JSON.stringify(batch));
  }
  // [1,2,3]
  // [4,5,6]
  // [7]        ← 最后一批不足 3 个，同样被 yield 出来
}
```

要点：

- **`buffer = []` 而不是 `buffer.length = 0`。** 这是最容易踩的坑：`yield buffer` 交出去的是数组的**引用**，如果原地清空，消费者手里的数组也会跟着变空。必须新建一个数组。
- **收尾的 `if` 不能漏。** 元素总数不是 `size` 整数倍时，最后那批会留在缓冲区里。这是这类「攒批」函数最常见的 bug。
- `AsyncGenerator<T[], void, unknown>` 三个参数：yield 出去的是 `T[]`，函数结束时 return 的是 `void`，外部不通过 `next(v)` 传值所以是 `unknown`。
- 参数类型用 `AsyncIterable<T>` 而不是 `AsyncGenerator<T>`：前者是更宽的接口，任何实现了异步迭代协议的对象（包括 Node 的可读流）都能传进来。**在参数位置要求最小接口**是良好的类型设计习惯。
- 实际用途：数据库批量插入、批量调用有条数限制的 API、日志攒批上报——都是「逐条到达但需要成批处理」的典型场景。
</Answer>

## 小结

- `async` 函数返回 `Promise<T>`，`T` 是 resolve 的类型；reject 分支**没有类型**
- `Awaited<T>` 递归解开 Promise，是标注异步返回值的利器
- `Promise.all` 保留元组类型；`allSettled`／`race`／`any` 各有适用场景
- 并发上限用「共享游标 + N 个 worker」实现；取消用 `AbortController`／`AbortSignal`
- 流式数据用 `AsyncIterable` 与 `for await...of` 建模
