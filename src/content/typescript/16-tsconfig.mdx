# tsconfig.json 详解

`tsconfig.json` 是 TypeScript 项目的「宪法」。它决定了三件事：**哪些文件参与编译**、**用多严格的规则检查**、**编译成什么样的 JS**。

很多人的 tsconfig 是从模板复制来的，出问题时只能上网搜。这一章我们把最关键的选项讲清楚，让你能自己判断每一行该不该开。

## 1. 骨架结构

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "lib": ["ES2022"],
    "strict": true,
    "outDir": "dist",
    "rootDir": "src",
    "skipLibCheck": true,
    "esModuleInterop": true,
    "forceConsistentCasingInFileNames": true
  },
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist"]
}
```

`include`／`exclude`／`files` 决定文件集合。注意 `exclude` **只影响 `include` 的展开**，如果某个被排除的文件被其它文件 import 了，它照样会进入编译。

## 2. strict 家族逐条拆解

`"strict": true` 是一个开关组，一次性打开下面这些子选项。它们是 TypeScript 价值的核心，**新项目请全部开启**。

| 选项 | 作用 | 不开的后果 |
|---|---|---|
| `strictNullChecks` | `null`／`undefined` 不再能赋给任意类型 | 空指针错误全部漏到运行时 |
| `strictFunctionTypes` | 函数参数按逆变检查 | 回调签名不兼容却能通过 |
| `strictBindCallApply` | `bind`/`call`/`apply` 参数被检查 | 参数写错不报错 |
| `strictPropertyInitialization` | 类字段必须初始化 | 实例字段可能是 `undefined` |
| `noImplicitAny` | 推不出类型时报错而不是当作 `any` | 类型洞悄悄扩散 |
| `noImplicitThis` | `this` 类型不明时报错 | `this` 指向错误 |
| `alwaysStrict` | 产物加 `"use strict"` | 沿用非严格模式语义 |
| `useUnknownInCatchVariables` | `catch (e)` 中 `e` 是 `unknown` | 直接 `e.message` 埋雷 |

<Callout type="warn" title="strictNullChecks 是不可回头的开关">
在老项目里打开它，常常会一次性冒出上千个错误。正确的做法不是关掉它，而是先开 `strict` 只对新增目录生效（拆分 tsconfig + 项目引用），再逐步迁移。关掉 `strictNullChecks` 的 TypeScript，价值大概只剩三成。
</Callout>

### 2.1 strict 之外的推荐选项

这些不在 `strict` 里，但强烈建议开：

| 选项 | 作用 |
|---|---|
| `noUncheckedIndexedAccess` | `arr[i]` 与 `obj[key]` 的类型自动带上 `undefined` |
| `exactOptionalPropertyTypes` | 区分「没有这个属性」和「属性值是 undefined」 |
| `noImplicitOverride` | 覆写父类方法必须写 `override` |
| `noFallthroughCasesInSwitch` | 禁止 case 穿透 |
| `noPropertyAccessFromIndexSignature` | 索引签名只能用方括号访问 |
| `verbatimModuleSyntax` | 只用于类型的导入必须写 `import type` |

<Callout type="tip" title="noUncheckedIndexedAccess 值得忍受">
它会让 `arr[0]` 变成 `T | undefined`，一开始很烦。但数组越界是 JS 里最高频的运行时错误之一，忍过两周你会离不开它。

</Callout>

## 3. target / lib：语法与 API 分开控制

这两个选项经常被搞混：

- **`target`** 决定**语法**降级到哪一版。设为 `ES2015` 时，`async/await` 会被编译成状态机；设为 `ES2022` 则原样保留。
- **`lib`** 决定**有哪些内置 API 的类型声明**。它不影响产物，只影响类型检查。

举例：`target: "ES5"` 但 `lib: ["ES2022"]`，你能写 `arr.at(-1)` 通过类型检查，但运行时如果环境不支持 `Array.prototype.at`，照样报错。TS **不提供 polyfill**，语法降级和 API 补丁是两件事。

不写 `lib` 时，它会根据 `target` 取一个默认值。前端项目通常还要加 `"DOM"`：

```json
{ "target": "ES2022", "lib": ["ES2022", "DOM", "DOM.Iterable"] }
```

## 4. module / moduleResolution

`module` 决定**产物用哪种模块语法**，`moduleResolution` 决定**编译器怎么找模块文件**。

| 组合 | 适用场景 |
|---|---|
| `module: NodeNext` + `moduleResolution: NodeNext` | Node.js 项目，同时支持 CJS/ESM，按 `package.json` 判定 |
| `module: ESNext` + `moduleResolution: Bundler` | 前端项目，交给 Vite/webpack 处理 |
| `module: CommonJS` + `moduleResolution: Node10` | 传统 Node 项目，逐渐淘汰 |
| `module: Preserve` | TS 5.4+，原样保留导入语法，交给下游工具 |

`moduleResolution: Bundler` 是 TS 5.0 引入的，它允许省略扩展名、支持 `exports` 字段，最贴近打包器的真实行为。**如果你的代码经过打包器，就该用它**。

<Callout type="warn" title="NodeNext 下的双重陷阱">
`NodeNext` 会读 `package.json` 的 `type` 字段判定每个文件是 ESM 还是 CJS。同一个仓库里两种模块混用时，很容易出现「同名类型不兼容」「默认导入不可调用」的报错。排查思路永远是：先确认这个文件被判定成了哪种模块。
</Callout>

## 5. 输出相关

| 选项 | 说明 |
|---|---|
| `outDir` / `rootDir` | 产物目录 / 源码根目录，决定产物的目录结构 |
| `declaration` | 生成 `.d.ts`，写库必开 |
| `declarationMap` | 生成 `.d.ts.map`，让「转到定义」跳到源码而非声明 |
| `sourceMap` | 生成 source map，调试必备 |
| `noEmit` | 只做类型检查，不产出文件 |
| `isolatedModules` | 保证每个文件能被单独转译（Babel/esbuild/SWC 需要） |
| `skipLibCheck` | 跳过 `.d.ts` 的类型检查，显著提速 |

<Callout type="info" title="为什么几乎人人都开 skipLibCheck">
`node_modules` 里成百上千个 `.d.ts` 互相冲突是常态，检查它们既慢又无法修复。开启后 TS 只检查你自己的代码，编译时间常能减半。代价是可能漏掉库之间的类型冲突——这个交换是划算的。
</Callout>

## 6. paths 与 baseUrl

```json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"],
      "@config": ["src/config/index.ts"]
    }
  }
}
```

TS 5.0 起，用 `moduleResolution: Bundler` 时 `paths` 可以不配 `baseUrl`（相对 tsconfig 所在目录解析）。再强调一次上一章的坑：**`paths` 只影响类型解析，运行时需要打包器或 Node 的 `imports` 字段配合**。

## 7. 增量编译与项目引用

### 7.1 incremental

```json
{ "incremental": true, "tsBuildInfoFile": ".cache/tsbuildinfo" }
```

TS 会把上次编译的依赖图写进 `.tsbuildinfo`，下次只重新检查变化的部分。大项目上二次编译能快数倍。记得把这个文件加进 `.gitignore`。

### 7.2 Project References

当仓库里有多个包（monorepo）或需要区分「源码 / 测试 / 脚本」时，可以拆成多个 tsconfig 并用 `references` 串起来：

```json
{
  "files": [],
  "references": [
    { "path": "./packages/shared" },
    { "path": "./packages/server" },
    { "path": "./packages/web" }
  ]
}
```

被引用的项目必须开启 `"composite": true`（它会隐含 `declaration: true` 和 `incremental: true`）。之后用 `tsc --build`（简写 `tsc -b`）构建，TS 会：

- 按依赖顺序依次构建；
- 跳过没有变化的项目；
- 让 `packages/server` 引用 `packages/shared` 时只读它的 `.d.ts`，而不是重新检查全部源码。

这是大型 TS 仓库保持编译速度的关键手段。

<Callout type="warn" title="composite 要求 rootDir 明确">
开启 `composite` 后，所有输入文件必须在 `rootDir` 之内，且 `include` 不能为空（除非显式写 `files: []` 作为纯聚合根）。这两条限制是新手配置 Project References 时最常撞的墙。
</Callout>

**参考答案：**

**第 1 题：五个容易被忽略的选项**

`npx tsc --init --strict` 生成的文件里注释掉的选项有七八十个。下面五个是实践中价值高、却最常被忽略的：

| 选项 | 作用 | 为什么值得注意 |
|---|---|---|
| `forceConsistentCasingInFileNames` | 禁止同一文件用不同大小写引用 | macOS/Windows 文件系统不区分大小写，Linux 区分。本地一切正常、CI 上「找不到模块」，十有八九是它 |
| `allowUnreachableCode: false` | 不可达代码报错而非警告 | `return` 之后的语句、恒假条件分支，往往是重构没删干净的残留 |
| `noImplicitReturns` | 函数有的分支返回值、有的不返回时报错 | 漏写一个 `return` 导致隐式返回 `undefined`，是很隐蔽的逻辑 bug |
| `noUnusedLocals` / `noUnusedParameters` | 未使用的局部变量与参数报错 | 建议交给 ESLint 管，因为 lint 能提供自动修复且不阻断编译 |
| `resolveJsonModule` | 允许 `import data from "./x.json"` 并推断出精确类型 | 配置文件、mock 数据直接当模块用，还能拿到字面量类型 |

再补充三个「知道了会少踩坑」的：

- **`skipLibCheck`** 默认是关的，但 `--init` 生成的模板里通常帮你开了。别随手关掉，编译时间会翻倍。
- **`exactOptionalPropertyTypes`** 区分「没有这个键」与「键存在但值是 `undefined`」。语义上更正确，但会和很多第三方库的类型定义打架，老项目慎开。
- **`lib` 不写时的默认值跟随 `target`**。前端项目忘了加 `"DOM"`，就会出现 `document is not defined` 这种类型错误。

**第 2 题：noUncheckedIndexedAccess 的典型修法**

```json
{
  "compilerOptions": {
    "noUncheckedIndexedAccess": true
  }
}
```

开启后所有索引访问的类型都会带上 `undefined`。常见的四类报错与对应修法：

```ts
const arr = [1, 2, 3];

// ── 情况 1：直接使用首元素 ──────────────────────
// const first: number = arr[0];   // 错误：number | undefined 不能赋给 number

// 修法 A：显式判空（最推荐，逻辑最诚实）
const first = arr[0];
if (first !== undefined) {
  console.log(first * 2);
}

// 修法 B：给一个兜底值
const firstOrZero = arr[0] ?? 0;

// 修法 C：确实能保证非空时用非空断言，但要留个注释说明理由
const head = arr[0]!;   // 上游已保证 arr.length > 0


// ── 情况 2：for 循环里的索引访问 ────────────────
for (let i = 0; i < arr.length; i++) {
  // const v: number = arr[i];   // 错误：编译器不做「i < length 所以一定有值」的推理
}

// 修法：改用 for...of，元素类型不带 undefined
for (const v of arr) {
  console.log(v * 2);   // v 是 number
}

// 需要下标时用 entries()
for (const [i, v] of arr.entries()) {
  console.log(i + ": " + v);
}


// ── 情况 3：对象字典查表 ────────────────────────
const scores: Record<string, number> = { math: 90 };
// const s: number = scores["english"];   // 错误：可能不存在

const s = scores["english"] ?? 0;
console.log(s);   // 0


// ── 情况 4：解构 ────────────────────────────────
const [a, b] = arr;      // a、b 的类型都是 number | undefined
console.log((a ?? 0) + (b ?? 0));
```

**统计不安全访问的实操办法：**

```bash
# 只做类型检查，把报错按错误码分组统计
npx tsc --noEmit 2>&1 | grep -c "TS2532\|TS18048\|TS2322"
```

真实项目里第一次打开这个选项，通常会冒出几十到上百个错误。**绝大多数确实是潜在 bug**——尤其是「用了 `find()` 的结果却没判空」「假设 `split()` 一定有第二段」这两类。

一个重要认知：修的时候要**优先选修法 A（显式判空）**，而不是无脑加 `!`。如果全靠 `!` 消错，等于把选项开了个寂寞——`!` 只是让编译器闭嘴，运行时该崩还是崩。`!` 应该只用在「有明确不变量保证」的地方，并且写注释说明这个保证是什么。

**第 3 题：src / tests 拆分与项目引用**

目录结构：

```text
my-project/
├── tsconfig.json           ← 聚合根，本身不编译任何文件
├── tsconfig.base.json      ← 共享的 compilerOptions
├── src/
│   ├── tsconfig.json
│   └── index.ts
└── tests/
    ├── tsconfig.json
    └── index.test.ts
```

`tsconfig.base.json`（共享配置）：

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "strict": true,
    "skipLibCheck": true,
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true
  }
}
```

`src/tsconfig.json`：

```json
{
  "extends": "../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": ".",
    "outDir": "../dist/src"
  },
  "include": ["**/*.ts"]
}
```

`tests/tsconfig.json`（依赖 src）：

```json
{
  "extends": "../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": ".",
    "outDir": "../dist/tests",
    "types": ["node", "vitest/globals"]
  },
  "include": ["**/*.ts"],
  "references": [{ "path": "../src" }]
}
```

根 `tsconfig.json`（纯聚合，不含任何文件）：

```json
{
  "files": [],
  "references": [{ "path": "./src" }, { "path": "./tests" }]
}
```

构建命令：

```bash
npx tsc -b              # 按依赖顺序构建全部
npx tsc -b --verbose    # 打印每个项目是「已是最新」还是「需要重建」
npx tsc -b --watch      # 监听模式，同样是增量的
npx tsc -b --clean      # 删除所有产物与 .tsbuildinfo
```

**能观察到的效果：**

1. 第一次 `tsc -b` 会依次构建 `src` 和 `tests`。
2. **只改 `tests` 下的文件**再次构建，`--verbose` 会输出「Project 'src' is up to date」，直接跳过——这就是增量的收益。
3. **只改 `src` 下的文件**，两个项目都会重建，但 `tests` 读的是 `src` 产出的 `.d.ts`，不会重新检查 `src` 的全部源码。
4. 更妙的是：如果改动只影响 `src` 的函数体而不改变任何签名，生成的 `.d.ts` 内容不变，TypeScript 会判定下游无需重建。

**几个容易撞墙的点**（对应本章的 Callout）：

- 被引用的项目**必须**开 `composite: true`。它会强制要求 `rootDir` 明确、`include` 不为空。
- 根 tsconfig 用 `"files": []` 表示「我自己不编译任何文件，只负责聚合」。漏写这行会导致根项目试图编译整个仓库。
- 必须用 `tsc -b` 而不是 `tsc`。普通的 `tsc` 完全无视 `references`。
- `.tsbuildinfo` 文件要加进 `.gitignore`。
- 编辑器（VS Code）能自动理解 references，跳转定义时若配了 `declarationMap: true`，会直接跳到 `.ts` 源码而不是 `.d.ts`——这一条体验提升很大，别漏配。

**这样拆分的实际收益：** 测试文件不会被打包进生产产物，`tests` 可以单独声明 `types: ["vitest/globals"]` 这类只有测试才需要的全局类型，而 `src` 保持干净——不会出现「生产代码里误用了 `describe`」还能通过类型检查的情况。
</Answer>

## 小结

- `strict` 是一组开关的总闸，新项目必开；`strictNullChecks` 是其中价值最高的一条
- `target` 管语法降级，`lib` 管 API 类型，TS 不提供 polyfill
- `module` 管产物语法，`moduleResolution` 管找文件；打包项目用 `Bundler`，纯 Node 用 `NodeNext`
- `skipLibCheck` 换编译速度，`incremental` 缓存依赖图，`composite` + `references` 支撑大仓库
- `paths` 只解决类型解析，运行时另需配置
