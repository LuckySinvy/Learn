# 团队协作工作流：Feature Branch、GitFlow 与 Fork/PR

Git 本身只提供分支、合并这些原语，**怎么用**是团队约定的事。这一章盘点主流协作工作流，并亲手用本地仓库模拟其中最关键的"功能分支"和"Fork + PR"两种机制。

## 1. 为什么需要工作流

没有约定的团队，所有人往 `main` 直接提交，结果就是：互相覆盖、无法并行、发布时一团乱。工作流的本质是用**分支分工**把"开发""审查""发布"隔离开。

| 工作流 | 核心思想 | 适合 |
|---|---|---|
| 集中式 | 所有人都推 main（几乎不用分支） | 个人 / 极简单项目 |
| 功能分支 Feature Branch | 每个功能一个分支，合并回 main | 绝大多数团队（基础） |
| GitFlow | main / develop / feature / release / hotfix 多角色分支 | 有固定版本发布的传统软件 |
| GitHub Flow | 只有 main + 短期功能分支 + PR | SaaS / 持续部署 |
| Trunk-Based | 极短分支、频繁合 main、靠 CI 保护 | 高成熟度高吞吐团队 |
| Fork + PR | 贡献者用 fork 而非直接 push | 开源 / 跨组织协作 |

## 2. 功能分支工作流（最该掌握的 baseline）

每个功能从 `main` 切一个 `feature/xxx` 分支，在上面开发、提交，完成后 `--no-ff` 合并回 `main` 再删除分支。好处：main 永远是可发布状态；并行功能互不干扰；合并时的 merge commit 保留"这次合入了一个功能"的痕迹。

<Playground
  language="git"
  title="功能分支工作流完整演练"
  id="git-15-1"
  code={`echo '===== 功能分支工作流（Feature Branch）====='
git init -q --bare /tmp/up.git
git clone -q /tmp/up.git proj && cd proj
echo 'init' > app.txt && git add . && git commit -q -m "init"
git push -q -u origin main 2>/dev/null
echo '开一个功能分支开发新功能：'
git checkout -q -b feature/login
echo 'username field' > login.txt && git add . && git commit -q -m "feat: 登录表单"
echo 'username + password' >> login.txt && git add . && git commit -q -m "feat: 登录校验"
echo '功能分支历史：'
git log --oneline
echo
echo '回到 main 合并功能分支（--no-ff 保留分支痕迹）：'
git checkout -q main
git merge --no-ff -m "merge: 合入登录功能" feature/login
git log --oneline --graph --all
echo
echo '删除已合并的功能分支：'
git branch -d feature/login
git push -q origin main 2>/dev/null
echo 'main 最终历史：'
git log --oneline
cd ..`}
/>

`--no-ff` 在这里很重要：它强制生成一个 merge commit，让"哪些提交属于同一个功能"在历史上清晰可辨。如果允许 fast-forward，功能提交会直接贴到 main 上，丢失分组信息。

## 3. GitFlow：多角色分支模型

GitFlow 用一组**长期 + 短期**分支区分软件的不同状态：

```text
main        —— 永远对应已发布的生产代码（每个点都打 tag）
develop     —— 集成分支，下个版本的功能在此汇聚
feature/*   —— 从 develop 切出，开发完合回 develop（短期）
release/*   —— 从 develop 切出，只修 bug、打 tag，合回 main + develop
hotfix/*    —— 从 main 切出，紧急修生产 bug，合回 main + develop
```

优点：版本边界极其清晰，适合有"季度发布""严格版本号"的传统产品。缺点：分支多、流程重、release/hotfix 的双向合并容易出错，对小团队偏繁琐。

## 4. GitHub Flow / Trunk-Based：轻量现代派

**GitHub Flow** 是 GitFlow 的极简版：只有 `main`（永远可部署）+ 短期功能分支 + **Pull Request**。流程：`main` 切分支 -> 开发 -> 开 PR -> 审查+CI 通过 -> 合回 `main` -> 自动部署。适合持续部署的互联网服务。

**Trunk-Based Development** 更激进：功能分支**存在时间极短**（几小时到一天），频繁合回主干，几乎不用长期分支，靠强大的 CI 和特性开关（feature flag）保证主干随时可发布。Google、Meta 这类高频交付团队采用。

<Callout type="tip" title="怎么选">
小团队 / 初创 / SaaS：GitHub Flow 或 Trunk-Based。传统版本化软件（客户端、嵌入式）：GitFlow。不确定时，从**功能分支 + PR** 起步，永远不会错——它是一切现代工作流的公共基础。
</Callout>

## 5. Fork + Pull Request：开源协作机制

开源项目里陌生人不能直接 push 官方仓库。机制是：**贡献者先 fork（复制）官方仓库到自己的空间，在自己的 fork 上开发，然后向官方发一个 Pull Request（请求官方拉取自己的改动）**。官方维护者审查、讨论、合并。下面用两个本地裸仓库完整模拟这一机制。

<Playground
  language="git"
  title="Fork + PR 机制的本地完整模拟"
  id="git-15-2"
  code={`echo '===== Fork + Pull Request 机制的本地模拟 ====='
git init -q --bare /tmp/up.git
git init -q --bare /tmp/fork.git
git clone -q /tmp/up.git mainline && cd mainline
echo 'project' > app.txt && git add . && git commit -q -m "init"
git push -q -u origin main 2>/dev/null
cd ..

echo '贡献者：克隆「自己的 fork」而不是官方仓库：'
git clone -q /tmp/fork.git contributor && cd contributor
git fetch -q /tmp/up.git main && git merge -q FETCH_HEAD 2>/dev/null
git push -q origin main 2>/dev/null
git remote add upstream /tmp/up.git
echo '贡献者的两个 remote（origin=fork, upstream=官方）：'
git remote -v
echo
echo '贡献者在功能分支上开发：'
git checkout -q -b fix/typo
echo 'fixed' >> app.txt && git add . && git commit -q -m "fix: 修正拼写"
echo '推到「自己的 fork」的 fix/typo 分支（这就是开 PR 的前提）：'
git push -q -u origin fix/typo 2>/dev/null
echo 'fork 上的分支：'
git branch -r
echo
cd ../mainline
echo '维护者：把贡献者 fork 里的分支 fetch 下来审查：'
git remote add contributor /tmp/fork.git
git fetch -q contributor fix/typo
echo '审查贡献者的提交：'
git log --oneline contributor/fix/typo
echo '没问题，合入官方 main：'
git merge --no-ff -m "merge PR#1: 修正拼写" contributor/fix/typo
git push -q origin main 2>/dev/null
echo '官方最终历史：'
git log --oneline --graph --all
cd ..`}
/>

关键认知：

- 贡献者 `origin` 指向**自己的 fork**，`upstream` 指向官方。日常从 `upstream` 同步，推到 `origin`。
- 开 PR 的本质 = "请官方 fetch 我 fork 上的某个分支并合并"。GitHub/GitLab 的 PR 按钮只是把这串 fetch+merge 包装成了网页操作。
- 维护者合并前可以 `git fetch` 贡献者的分支，在本地**先审一遍、甚至跑测试**，再决定合并——这才是 PR 真正的价值（代码审查 + CI）。

## 6. 小结

- 工作流 = 团队对"如何用分支"的约定；功能分支是一切现代流程的基石
- 功能分支：`feature/*` 开发，`--no-ff` 合回 main，保留功能分组痕迹
- GitFlow：main/develop/feature/release/hotfix 多角色，适合版本化软件，但偏重
- GitHub Flow / Trunk-Based：轻量、靠 PR+CI，适合持续部署
- Fork+PR：贡献者 fork -> 推自己 fork -> 官方 fetch 分支审查合并；PR 按钮背后就是 fetch+merge

<Answer>
**参考答案：**

**1. 功能分支 + `--no-ff` vs fast-forward**

```bash
git init -q --bare /tmp/up.git
git clone -q /tmp/up.git proj && cd proj
echo init > app.txt && git add . && git commit -q -m "init"
git push -q -u origin main 2>/dev/null

# 开功能分支做两个提交
git switch -qc feature/pay
echo pay1 > pay.txt && git add . && git commit -q -m "feat: 支付表单"
echo pay2 >> pay.txt && git add . && git commit -q -m "feat: 支付接口"
git switch -q main

# 方式 A：默认（能 fast-forward）
git merge feature/pay
git log --oneline --graph
```

`--graph` 里是一条直线，功能提交直接贴到 main 上，**看不出"这是一个功能"的分组**。

```bash
# 方式 B：--no-ff（先 reset 回未合并状态再试）
git reset --hard HEAD~1
git merge --no-ff -m "merge: 合入支付功能" feature/pay
git log --oneline --graph
```

`--graph` 里多了一个合并提交（气泡），功能提交在一条侧线上，main 通过 merge commit 接入——**"哪些提交属于支付功能"一目了然**。这就是功能分支工作流用 `--no-ff` 的原因。

**2. Fork+PR 中冲突的处理**

构造冲突：维护者 main 上先改了 `app.txt` 的最后一行，贡献者的 `fix/typo` 也改同一行。

```bash
# 维护者：fetch 贡献者分支后 merge 冲突
git remote add contributor /tmp/fork.git
git fetch contributor fix/typo
git merge contributor/fix/typo
# CONFLICT (content): Merge conflict in app.txt
```

解决流程（和第 6 章一致）：

```bash
cat app.txt                 # 看冲突标记，手工融合两个版本
git add app.txt             # 标记已解决
git commit --no-edit        # 完成合并（信息已预填）
git push origin main
```

这里的"提示"其实准确描述了冲突的实质：维护者**先有自己的 main 改动**（合入前应先把本地 main 与远程 main 同步），再 merge 贡献者分支时，Git 以共同祖先为基准发现两边都改了同一行，所以需要人决定取舍。冲突只发生在这次 merge 里，贡献者自己的 fork 不受影响。

**3. merge 还是 rebase 同步官方？**

```bash
git fetch upstream main
# 方案一：git merge upstream/main
# 方案二：git rebase upstream/main
```

- **merge**：把官方最新提交合并进本地分支，产生一个合并提交，历史保留分叉。优点：不改写历史、冲突只需解决一次；缺点：多了 "Merge branch 'upstream/main'" 噪音提交。
- **rebase**：把本地**未推送的提交**重放到官方最新之上，历史变直线。优点：干净；缺点：改写本地提交哈希，若本地已 push 到自己的 fork，需要 `--force-with-lease`。

实践建议：如果本地分支**还没推送到自己 fork**（或只有自己用），用 `rebase` 保持线性；如果已经通过 PR 共享给维护者审阅中，用 `merge` 更安全（维护者已经看过你的提交哈希/内容）。核心判断标准仍是第 7 章黄金法则：这些提交有没有被别人基于它工作。

**4. GitFlow 里线上紧急 bug 的路径**

线上紧急 bug 应该走 **`hotfix/*` 分支**：

```bash
git checkout -b hotfix/v1.0.1 main   # 从 main（线上版）切出
# 修复并提交
git checkout main
git merge --no-ff hotfix/v1.0.1      # 合回 main（线上发布）
git tag -a v1.0.1 -m "修复紧急 bug"  # 打新版本 tag
git checkout develop
git merge --no-ff hotfix/v1.0.1      # 也必须合回 develop，否则修复会丢失
git branch -d hotfix/v1.0.1
```

原因：GitFlow 里 `main` 永远是已发布的生产代码，紧急修复必须**从 main 切出**（而不是 develop，因为 develop 上带着 v2 未发布的功能）；而它要**同时合回 main 和 develop**——合回 main 是发布修复，合回 develop 是保证 v2 开发线也带上这个修复，避免"修复只存在于旧版本、下个版本又复现"。
