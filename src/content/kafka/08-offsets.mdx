# Offset 管理

Offset 提交策略决定了你的系统在"至少一次"和"至多一次"之间站在哪边。提交早了会丢消息，提交晚了会重复消费——没有免费的午餐，但你必须清楚自己选了什么。本章讲清 offset 存哪、怎么提交、怎么重置。

## 1. Offset 存在哪：__consumer_offsets

消费进度存储在 Kafka 内部 topic `__consumer_offsets`（默认 50 分区、compact 清理策略）中：

```text
key:   (group.id, topic, partition)
value: (offset, 元数据, 提交时间戳)

group=inventory, topic=orders, p0 -> offset=1500
group=inventory, topic=orders, p1 -> offset=980
group=report,    topic=orders, p0 -> offset=52000
```

- 每次提交就是往这个 topic 写一条消息；compact 策略保证每个 key 只留最新值。
- 提交的 offset 语义是"**下一条要消费的位置**"：处理完 offset=5 应提交 6。
- 消费组的进度按 group.id 隔离，所以不同组互不影响。

注意区分两个易混概念：

| 概念 | 含义 |
|---|---|
| 消费位置（position） | 消费者内存里"下次 poll 从哪读"，poll 自动推进 |
| 提交位移（committed offset） | 持久化到 __consumer_offsets 的进度，重启/Rebalance 后从这里恢复 |

两者不同步是所有重复消费问题的根源。

## 2. 自动提交的隐患

```properties
enable.auto.commit=true       # 默认开启
auto.commit.interval.ms=5000  # 每 5 秒在 poll 内部顺带提交
```

自动提交在 **poll 调用时** 检查距上次提交是否超过间隔，超过就把**上一次 poll 返回的所有消息**的 offset 提交掉。两个隐患：

```text
隐患 1: 重复消费
  poll 拉到 100 条 -> 处理到第 60 条时进程崩溃
  -> 崩溃前没到提交时机, offset 还停在批次开头
  -> 重启后这 100 条全部重来, 前 60 条被处理两次

隐患 2: 消息丢失 (更隐蔽)
  poll 拉到 100 条 -> 交给另一个线程池异步处理 -> 立刻进入下一轮 poll
  -> 下一轮 poll 时自动提交了这 100 条的 offset
  -> 线程池处理失败/进程崩溃 -> 这批消息再也不会被消费 -> 丢了
```

结论：**只要"拉取"与"处理完成"不同步，自动提交就可能丢消息**。业务系统建议一律手动提交。

## 3. 手动提交

```properties
enable.auto.commit=false
```

### 3.1 同步与异步提交

```java
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String, String> r : records) {
        process(r);
    }
    // 同步: 阻塞直到成功, 失败自动重试 —— 简单可靠, 吞吐略降
    consumer.commitSync();
}
```

```java
// 异步: 不阻塞, 高吞吐; 失败不重试(重试可能把新 offset 覆盖成旧的)
consumer.commitAsync((offsets, ex) -> {
    if (ex != null) log.warn("commit failed: {}", offsets, ex);
});
```

生产常用**组合模式**：循环内 commitAsync 保吞吐，关闭前 commitSync 兜底：

```java
try {
    while (running) {
        ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
        records.forEach(this::process);
        consumer.commitAsync();
    }
} finally {
    try {
        consumer.commitSync();    // 最后一次务必同步提交
    } finally {
        consumer.close();
    }
}
```

### 3.2 按分区精细提交

一批消息里不同分区处理进度不同时，可以按分区提交，缩小重复范围：

```java
for (TopicPartition tp : records.partitions()) {
    List<ConsumerRecord<String, String>> partRecords = records.records(tp);
    partRecords.forEach(this::process);
    long lastOffset = partRecords.get(partRecords.size() - 1).offset();
    // 提交 "已处理的最后一条 + 1"
    consumer.commitSync(Map.of(tp, new OffsetAndMetadata(lastOffset + 1)));
}
```

Python 对照（按消息提交）：

```python
while True:
    msg = consumer.poll(0.5)
    if msg is None or msg.error():
        continue
    process(msg)
    consumer.commit(message=msg, asynchronous=False)  # 提交 msg.offset()+1
```

<Callout type="warn" title="提交的是 offset+1">
提交语义是"下一条要读的位置"。处理完 offset=100 要提交 101。手动构造 OffsetAndMetadata 时忘了 +1，每次重启都会重复消费最后一条——这是隐蔽度极高的经典 bug。
</Callout>

## 4. auto.offset.reset 与 seek

### 4.1 auto.offset.reset

只在**找不到已提交 offset**时生效（新组、offset 过期被清理、数据被删）：

| 值 | 行为 |
|---|---|
| `latest`（默认） | 从最新开始，历史消息不读 |
| `earliest` | 从最早开始，读全部历史 |
| `none` | 抛异常，交给应用决策 |

新上线的消费组用默认 latest 会**跳过所有历史数据**；要补历史必须 earliest。

### 4.2 seek：程序内重置

```java
// 必须在分区分配完成后调用
consumer.subscribe(List.of("orders"), new ConsumerRebalanceListener() {
    public void onPartitionsAssigned(Collection<TopicPartition> parts) {
        // 回到 1 小时前
        long ts = System.currentTimeMillis() - 3600_000;
        Map<TopicPartition, Long> query = new HashMap<>();
        parts.forEach(tp -> query.put(tp, ts));
        consumer.offsetsForTimes(query).forEach((tp, ot) -> {
            if (ot != null) consumer.seek(tp, ot.offset());
        });
    }
    public void onPartitionsRevoked(Collection<TopicPartition> parts) {}
});
```

运维场景更常用 CLI 重置（需先停消费者，见第 4 章 `--reset-offsets`）。

## 5. 重复与丢失的成因矩阵

| 提交时机 | 语义 | 崩溃后果 |
|---|---|---|
| 处理**前**提交（或自动提交+异步处理） | 至多一次 at-most-once | **丢消息**：已提交未处理 |
| 处理**后**提交（手动 commitSync） | 至少一次 at-least-once | **重复消费**：已处理未提交 |
| 处理与提交原子化（事务/外部存储） | 精确一次 exactly-once | 不丢不重，成本最高 |

工程实践中的主流选择是**至少一次 + 下游幂等**：

- 数据库写入带唯一键（如 order_id），重复消息触发唯一约束直接跳过；
- 或用 `INSERT ... ON DUPLICATE KEY UPDATE` / upsert；
- Redis 用 SETNX 记录已处理的消息 ID。

<Callout type="tip" title="offset 过期清理">
__consumer_offsets 中的记录在消费组空置超过 `offsets.retention.minutes`（默认 7 天）后会被清理。一个下线两周的服务重新上线时，已提交进度已不存在，会按 auto.offset.reset 走——latest 则跳过两周数据，earliest 则全量重刷。长期停用的组要心里有数。
</Callout>

## 小结

- Offset 存在内部 topic __consumer_offsets，按 (group, topic, partition) 记录"下一条位置"
- 自动提交在拉取与处理解耦时会丢消息，业务系统用手动提交
- 生产模式：循环 commitAsync + 关闭前 commitSync；精细化用按分区提交
- auto.offset.reset 只在无已提交 offset 时生效；程序内用 seek，运维用 CLI reset
- 成因矩阵：先提交=可能丢，后提交=可能重；主流方案是至少一次+下游幂等

**参考答案：**

**第 1 题 · 自动提交丢消息 vs 手动提交重复消费**

**A. 自动提交 + 异步处理 = 丢消息**

```java
Properties props = new Properties();
props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ConsumerConfig.GROUP_ID_CONFIG, "auto-lose");
props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, true);      // 自动提交
props.put(ConsumerConfig.AUTO_COMMIT_INTERVAL_MS_CONFIG, 1000);
props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");

ExecutorService pool = Executors.newFixedThreadPool(4);
KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(List.of("offset-demo"));

Set<String> processed = ConcurrentHashMap.newKeySet();
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String, String> r : records) {
        pool.submit(() -> {
            if (r.offset() % 3 == 0) {                // 1/3 的消息处理失败
                throw new RuntimeException("处理失败 offset=" + r.offset());
            }
            processed.add(r.value());
        });
    }
    System.out.println("已成功处理: " + processed.size());
}
```

跑一会儿后停掉重启，你会发现**那些抛异常的消息再也不会被重新消费**。原因是：

```text
时间线：
  t0  poll() 拿到 offset 0..99
  t1  丢进线程池，poll() 立即返回进入下一轮
  t2  下一次 poll() 触发自动提交 -> 提交 offset=100
      ↑ 此时线程池里的任务可能还没跑完，甚至已经抛异常了
  t3  进程重启 -> 从 100 开始读 -> 0..99 里失败的那些永久丢失
```

**关键点**：自动提交的时机是**下一次 `poll()` 调用时**（且距上次提交超过 `auto.commit.interval.ms`），它提交的是"上一批拉到的最大 offset + 1"。Kafka 完全不知道你的业务处理成功没有——**它只知道你把消息拉走了**。一旦拉取和处理解耦（丢线程池、写入队列、异步回调），自动提交就等价于"处理前提交"，语义退化成 **at-most-once（至多一次）**，崩溃即丢数据。

**B. 处理完再手动提交 = 重复消费**

```java
props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);      // 关闭自动提交
props.put(ConsumerConfig.GROUP_ID_CONFIG, "manual-dup");

while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String, String> r : records) {
        process(r);                    // 同步处理，在当前线程完成
        System.out.println("处理完成 offset=" + r.offset());
    }
    if (!records.isEmpty()) {
        consumer.commitSync();         // 全部处理完才提交
    }
}
```

在处理到一半时 `kill -9`，重启后观察日志：

```text
第一次运行：
  处理完成 offset=0
  处理完成 offset=1
  ...
  处理完成 offset=57      <- 此时 kill -9，还没到 commitSync()

重启后：
  处理完成 offset=0       <- 0..57 全部重放了一遍
  处理完成 offset=1
  ...
```

**语义变成了 at-least-once（至少一次）**：消息一定不会丢，但崩溃前已处理未提交的部分会被重放。

**C. 两者的本质与工程选择**

```text
处理前提交（自动提交 + 异步处理）  ->  at-most-once  ->  可能丢
处理后提交（手动 commitSync）      ->  at-least-once ->  可能重
```

这不是"哪个更好"的问题，而是**在崩溃这个不可避免的事件面前，你选择容忍丢还是容忍重**。工程上的答案几乎总是：**选至少一次，然后在下游做幂等**。因为"重复"可以通过技术手段消除，而"丢失"通常无法补救。

下游幂等的三种常见实现：

```sql
-- 1. 唯一键 + upsert（最常用）
INSERT INTO orders (order_id, amount) VALUES (?, ?)
  ON DUPLICATE KEY UPDATE amount = VALUES(amount);

-- 2. 唯一约束 + 捕获冲突跳过
INSERT INTO orders (order_id, amount) VALUES (?, ?);
-- 捕获 DuplicateKeyException 后直接 return
```

```java
// 3. Redis SETNX 去重（适合无天然唯一键的场景）
String dedupKey = "msg:" + r.topic() + ":" + r.partition() + ":" + r.offset();
if (!redis.setIfAbsent(dedupKey, "1", Duration.ofDays(3))) {
    return;   // 已处理过，跳过
}
process(r);
```

**注意第 3 种有个坑**：如果 SETNX 成功后、`process()` 完成前崩溃，这条消息重放时会被误判为"已处理"而跳过，反而变成丢消息。严谨做法是把去重标记和业务操作放在同一个数据库事务里。

**第 2 题 · 按分区提交，崩溃后只重放未提交的分区**

```java
props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);
consumer.subscribe(List.of("offset-demo"));

while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    for (TopicPartition tp : records.partitions()) {
        List<ConsumerRecord<String, String>> partRecords = records.records(tp);

        // 故意在处理第 1 号分区时崩溃
        if (tp.partition() == 1) {
            System.out.println("处理 p1 时崩溃！");
            Runtime.getRuntime().halt(1);
        }

        partRecords.forEach(r -> System.out.printf("处理 p%d offset=%d%n",
            tp.partition(), r.offset()));

        long lastOffset = partRecords.get(partRecords.size() - 1).offset();
        // 关键：处理完一个分区就立即提交这个分区
        consumer.commitSync(Map.of(tp, new OffsetAndMetadata(lastOffset + 1)));
        System.out.printf(">> 已提交 p%d 到 %d%n", tp.partition(), lastOffset + 1);
    }
}
```

崩溃前的输出：

```text
处理 p0 offset=0 ... offset=9
>> 已提交 p0 到 10
处理 p1 时崩溃！
```

用 CLI 确认各分区的提交状态：

```bash
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group per-partition-demo
```

```text
PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
0          10              10              0     <- 已提交，不会重放
1          0               10              10    <- 未提交，全部重放
2          0               10              10    <- 还没轮到处理
```

重启后的输出：

```text
处理 p1 时崩溃！     <- p0 的消息一条都没重放，直接从 p1 开始
```

**这就是按分区提交相比 `commitSync()` 全量提交的价值**：

| 提交方式 | 崩溃后重放范围 |
|---|---|
| `commitSync()`（提交整批） | 本批**所有分区**的消息全部重放，包括已处理成功的 p0 |
| 按分区 `commitSync(Map)` | 只重放**未提交的那个分区**，已完成的分区不受影响 |

重复量的差异在大批量场景下很可观：一批 500 条跨 6 个分区，全量提交要重放 500 条，按分区提交可能只重放 80 条。

**适用场景与代价**：

- **适合**：单条处理耗时长（写库、调外部 API）、下游幂等成本高、批次跨多个分区的场景。
- **代价**：提交次数变多（每分区一次），`__consumer_offsets` 写入压力和协调器 RPC 都会上升。分区数很多时建议改用 `commitAsync(Map, callback)` 避免逐个同步等待。

**另一个实用变体**是"每处理 N 条提交一次"，在重复量和提交开销之间取平衡：

```java
Map<TopicPartition, OffsetAndMetadata> pending = new HashMap<>();
int count = 0;
for (ConsumerRecord<String, String> r : records) {
    process(r);
    pending.put(new TopicPartition(r.topic(), r.partition()),
                new OffsetAndMetadata(r.offset() + 1));
    if (++count % 100 == 0) {
        consumer.commitAsync(pending, null);
    }
}
consumer.commitSync(pending);   // 批次结束兜底同步提交
```

**第 3 题 · offsetsForTimes + seek 从 10 分钟前重放**

```java
props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);
KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);

consumer.subscribe(List.of("orders"), new ConsumerRebalanceListener() {
    @Override
    public void onPartitionsRevoked(Collection<TopicPartition> parts) { }

    @Override
    public void onPartitionsAssigned(Collection<TopicPartition> parts) {
        long tenMinAgo = System.currentTimeMillis() - 10 * 60 * 1000L;

        // 1) 为每个分区构造 "分区 -> 目标时间戳" 的查询
        Map<TopicPartition, Long> query = new HashMap<>();
        parts.forEach(tp -> query.put(tp, tenMinAgo));

        // 2) 查出该时间点之后第一条消息的 offset
        Map<TopicPartition, OffsetAndTimestamp> found = consumer.offsetsForTimes(query);

        // 3) 逐个 seek
        found.forEach((tp, ot) -> {
            if (ot != null) {
                consumer.seek(tp, ot.offset());
                System.out.printf("p%d -> seek 到 offset=%d (ts=%d)%n",
                    tp.partition(), ot.offset(), ot.timestamp());
            } else {
                // null 表示该分区在这个时间点之后没有任何消息
                consumer.seekToEnd(List.of(tp));
                System.out.printf("p%d -> 无匹配消息，跳到末尾%n", tp.partition());
            }
        });
    }
});

while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    records.forEach(r -> System.out.printf("p%d@%d ts=%d %s%n",
        r.partition(), r.offset(), r.timestamp(), r.value()));
}
```

**三个必须注意的实现细节：**

1. **`seek()` 必须在分区分配完成之后调用。** `subscribe()` 只是声明订阅意向，真正的分区归属要等第一次 `poll()` 触发 JoinGroup 之后才确定。在 `subscribe()` 后立刻 `seek()` 会抛 `IllegalStateException: No current assignment for partition`。放进 `onPartitionsAssigned` 回调是最可靠的写法（也能正确处理后续 Rebalance）。若不用回调，也可以先 `poll(0)` 拿到分配再 seek。

2. **`offsetsForTimes` 可能返回 `null`。** 当目标时间戳晚于该分区最后一条消息时就没有匹配结果，必须判空，否则 NPE。

3. **依赖的是消息时间戳而非墙上时钟。** 查询按 topic 配置的 `message.timestamp.type` 进行：默认 `CreateTime`（Producer 写入时打的时间，可能乱序甚至被伪造）；若设为 `LogAppendTime` 则是 broker 落盘时间，单调递增更可靠。做时间点回溯前最好确认一下这个配置。

**它和 CLI `--reset-offsets --to-datetime` 的区别**

```bash
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group my-group --topic orders \
  --reset-offsets --to-datetime 2026-08-01T10:00:00.000 --execute
```

| 维度 | `offsetsForTimes` + `seek` | CLI `--to-datetime` |
|---|---|---|
| 是否改变已提交 offset | **不改**，只改当前会话的读取位置 | **持久化写入** `__consumer_offsets` |
| 是否需要停消费者 | 不需要，本来就是消费者自己在跑 | **必须停**，组内有活跃成员时会报错 |
| 作用范围 | 仅当前进程当前会话；重启后回到已提交位点 | 整个消费组，所有实例重启后都从新位点开始 |
| 谁来执行 | 开发者写在代码里 | 运维在命令行执行 |
| 可编程性 | 强：可按分区差异化、可加条件判断、可循环 | 弱：一刀切 |

**选型判断：**

- **用 `seek`**：需求是"程序逻辑的一部分"。比如启动时总是回溯 10 分钟做去重预热、实时大屏启动时加载最近窗口数据、数据修复工具按分区精确定位、每次启动都从最新开始（`seekToEnd`）而不管历史提交。特点是**每次运行都要这么干**。
- **用 CLI reset**：需求是"一次性运维操作"。比如发现昨天的消费逻辑有 bug，需要把整个消费组回拨重算；或者积压太多决定弃单跳到 latest。特点是**执行一次、永久生效、影响整个组**。

**一个常见误用**：想做一次性数据修复，却在代码里写死 `seek`，结果每次服务重启都重放一遍历史数据，下游被打爆。一次性操作就该用 CLI，不要固化进代码。

**补充**：CLI 除了 `--to-datetime` 还有 `--to-earliest`、`--to-latest`、`--shift-by ±N`、`--to-offset N`、`--by-duration PT1H` 等，且**永远先用 `--dry-run` 确认将要设置的 offset，再换成 `--execute`**。
