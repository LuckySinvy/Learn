# Producer 可靠性与幂等事务

"消息会不会丢？会不会重？"是 Kafka 面试与生产环境的头号问题。答案不是一个开关，而是 acks、重试、min.insync.replicas、幂等、事务这一整条链的组合。本章把每一环的原理讲透。

## 1. acks：写入确认的三档语义

`acks` 决定 broker 在什么时机向 Producer 返回"写入成功"：

```text
acks=0:  Producer ──发──>  (不等任何确认)          最快, 网络抖动就丢
acks=1:  Producer ──发──> Leader 写入本地日志 ──确认   Leader 挂且未同步则丢
acks=all: Producer ──发──> Leader 写入
                            └─> 等 ISR 中所有副本同步完成 ──确认   最可靠
```

| acks | 语义 | 丢失场景 | 延迟 |
|---|---|---|---|
| 0 | 发出即成功 | 网络丢包、broker 挂 | 最低 |
| 1 | leader 落盘即成功 | leader 确认后立刻宕机，follower 未同步 | 低 |
| all(-1) | ISR 全部同步才成功 | 几乎不丢（配合 min.insync.replicas） | 较高 |

**acks=all 单独并不安全**。如果 ISR 收缩到只剩 leader 自己，acks=all 就退化成 acks=1。必须配合 topic/broker 级参数：

```properties
# ISR 中至少 2 个副本确认, 否则 Producer 收到 NotEnoughReplicas 异常
min.insync.replicas=2
```

**黄金组合**：`replication.factor=3` + `min.insync.replicas=2` + `acks=all`——允许挂 1 台 broker 且不丢数据、不停写。

## 2. 重试与乱序

```properties
retries=2147483647          # 默认无限重试, 由 delivery.timeout.ms 兜底
delivery.timeout.ms=120000  # 两分钟内没成功就报失败
max.in.flight.requests.per.connection=5   # 单连接未确认请求数
```

重试带来两个副作用：

1. **重复**：broker 已写入但 ACK 丢失，Producer 重发 → 消息重复。
2. **乱序**：`max.in.flight` 大于 1 时，批次 1 失败重试、批次 2 已成功 → 顺序颠倒。

```text
乱序示意 (max.in.flight=2, 无幂等):
  发送: batch1, batch2
  batch1 失败, batch2 成功写入
  batch1 重试成功
  分区里的顺序: batch2, batch1   <- 乱了!
```

老式解法是 `max.in.flight=1`（吞吐惨烈）。现代解法是**幂等 Producer**，两个问题一起解决。

## 3. 幂等 Producer：PID + 序列号

```properties
enable.idempotence=true   # Kafka 3.x 默认已开启
```

原理：

- Producer 初始化时向 broker 申请一个 **PID**（Producer ID）。
- 发往每个分区的每个批次带上单调递增的**序列号**（sequence number）。
- Broker 为每个"PID + 分区"记录最近序列号：
  - 收到**重复序列号** → 直接丢弃（去重），仍返回成功；
  - 收到**跳号** → 拒绝并报 OutOfOrderSequence，保证顺序。

```text
Producer(PID=88) -> partition-0
  发送 seq=0 [写入]  seq=1 [写入]  seq=1 重试 [重复, 丢弃]  seq=2 [写入]
  分区日志: seq0, seq1, seq2   -- 不重不漏不乱
```

幂等开启后，`max.in.flight` 最多 5 也能保证单分区内有序。

**边界**：幂等只保证"**单个 Producer 会话内、单分区**"不重不乱。Producer 重启会拿到新 PID，重启前后的重发无法去重；跨分区、跨 topic 也不在保护范围。要更强的语义就需要事务。

## 4. 事务 Producer 与 exactly-once

事务提供**跨分区、跨 topic 的原子写入**：一批消息要么全部对消费者可见，要么全部不可见。

```text
组件:
  transactional.id  -- 用户指定, 重启后不变, 用来找回之前的事务状态
  事务协调器 (Transaction Coordinator) -- broker 端模块
  __transaction_state -- 内部 topic, 持久化事务状态

流程:
  initTransactions()  向协调器注册 transactional.id, 递增 epoch
       |                (旧 epoch 的僵尸 Producer 之后的写入会被拒绝)
  beginTransaction()
  send() x N          消息正常写入各分区, 但标记为"未提交"
  commitTransaction() 协调器两阶段提交:
       |               1. 写 PREPARE_COMMIT 到 __transaction_state
       |               2. 向各分区写入 "提交标记" (control record)
  消费端 isolation.level=read_committed 只读已提交消息
```

Java 代码：

```java
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "order-svc-tx-01"); // 实例唯一且稳定
// 事务自动隐含 enable.idempotence=true, acks=all

Producer<String, String> producer = new KafkaProducer<>(props);
producer.initTransactions();

try {
    producer.beginTransaction();
    producer.send(new ProducerRecord<>("orders", "u1", "order-created"));
    producer.send(new ProducerRecord<>("order-events", "u1", "audit-log"));
    producer.commitTransaction();          // 两条消息原子可见
} catch (ProducerFencedException e) {
    producer.close();                      // 被新实例顶替(僵尸), 直接退出
} catch (KafkaException e) {
    producer.abortTransaction();           // 回滚, 消费者永远看不到这批消息
}
```

Python（confluent-kafka）：

```python
from confluent_kafka import Producer, KafkaException

p = Producer({
    "bootstrap.servers": "localhost:9092",
    "transactional.id": "order-svc-tx-01",
})
p.init_transactions()
p.begin_transaction()
try:
    p.produce("orders", key="u1", value="order-created")
    p.produce("order-events", key="u1", value="audit-log")
    p.commit_transaction()
except KafkaException:
    p.abort_transaction()
```

<Callout type="info" title="exactly-once 的真正含义">
Kafka 的 EOS（exactly-once semantics）指的是 **"消费-处理-再生产" 这条 Kafka 内部链路**上的精确一次（配合 sendOffsetsToTransaction，见第 20 章）。它不能让"写数据库 + 发消息"自动原子——那需要 Outbox 模式或业务侧幂等。别把 EOS 当银弹。
</Callout>

## 5. 可靠性配置矩阵

| 场景 | 推荐配置 |
|---|---|
| 日志/埋点（允许少量丢） | acks=1，retries 默认，linger 大批次 |
| 普通业务消息（不能丢，可容忍重复+下游幂等） | acks=all + 幂等 + min.insync.replicas=2 |
| 金融/账务（不丢不重，链路在 Kafka 内） | 事务 Producer + read_committed 消费 |

<Callout type="warn" title="常见坑">
1. **只设 acks=all 不设 min.insync.replicas**：ISR 缩到 1 时静默退化，照样丢数据。
2. **transactional.id 多实例共用**：后启动的实例会 fence 掉先启动的（ProducerFencedException），必须每实例唯一且重启保持不变（如"服务名-分区号"）。
3. **事务超时**：`transaction.timeout.ms`（默认 60s）内没 commit 会被协调器主动 abort，长事务要调大但别超过 broker 的 `transaction.max.timeout.ms`。
4. **误以为幂等能跨重启去重**：重启换 PID，去重失效。跨会话不重复要靠事务或业务幂等键。
</Callout>

## 小结

- acks=0/1/all 是延迟与可靠性的三档开关；acks=all 必须搭配 `min.insync.replicas=2` 才有意义
- 黄金组合：3 副本 + min.insync.replicas=2 + acks=all
- 幂等 Producer 用 PID + 序列号在单会话单分区内去重防乱序，3.x 默认开启
- 事务提供跨分区原子写与 read_committed 隔离，transactional.id 要实例唯一且稳定
- exactly-once 只覆盖 Kafka 链路内部，跨系统仍需业务幂等

**第 1 题 · 触发 NotEnoughReplicasException**

```bash
# 1) 建 3 副本 topic，并把 min.insync.replicas 设为 2
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic isr-demo --partitions 1 --replication-factor 3 \

bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic isr-demo
# Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3

# 2) 先确认正常情况能写成功
echo "before" | bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic isr-demo --request-required-acks all

# 3) 停掉两个 follower（保留 leader 所在的 broker）
docker stop kafka2 kafka3
sleep 15
bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic isr-demo
# Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1     <- ISR 只剩 1 个

# 4) 再用 acks=all 发送
echo "after" | bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic isr-demo --request-required-acks all
```

报错：

```text
ERROR Error when sending message to topic isr-demo with key: null, value: 5 bytes
org.apache.kafka.common.errors.NotEnoughReplicasException: Messages are rejected
since there are fewer in-sync replicas than required.
```

**发生了什么**：`min.insync.replicas=2` 是一个**服务端强制的写入门槛**。当 `acks=all` 时，leader 在接收写入前会先检查"当前 ISR 大小是否 ≥ min.insync.replicas"，不满足就直接拒绝，连数据都不会落盘。

这套机制的设计意图值得细品：

- 只剩 1 个副本时如果还允许写入，这台机器一旦挂掉，刚写进去的数据就**永久丢失**且无法恢复。
- Kafka 在这里选择了**牺牲可用性来保证不丢数据**（CAP 里偏 CP）。宁可让写入失败让上游感知到，也不要静默地把数据写进一个随时会消失的地方。

**由此得出本章最重要的一条结论**：`acks=all` 单独用是**不完整**的。`acks=all` 的语义只是"等 ISR 中所有副本确认"，如果 ISR 已经缩水到只剩 leader 一个，那 `acks=all` 就退化成了 `acks=1`——**表面上你配了最高可靠性，实际上一台机器宕机就丢数据，而且毫无报错**。只有配上 `min.insync.replicas=2`，才能把这种静默退化变成显式失败。

`min.insync.replicas` 也可以在 broker 级别配默认值，或对已有 topic 动态修改：

```bash
bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --alter --entity-type topics --entity-name isr-demo \
  --add-config min.insync.replicas=2
```

**为什么推荐 3 副本 + min.insync=2 而不是 3 副本 + min.insync=3**：后者要求三个副本全在 ISR 才能写，任意一台机器重启（哪怕是滚动升级）都会让整个 topic 不可写。`3 + 2` 的组合允许挂掉一台仍可正常写入，是可用性和可靠性的最佳平衡点。

**注意**：客户端侧还要确认 `acks` 真的是 `all`。如果 Producer 配的是 `acks=1`，即使 ISR 只剩 1 个也**不会报错**——`min.insync.replicas` 只对 `acks=all` 生效，这是个常见误解。

**第 2 题 · 事务回滚与两种隔离级别的可见性**

```java
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "tx-demo-01");

Producer<String, String> producer = new KafkaProducer<>(props);
producer.initTransactions();

// --- 事务 A: 正常提交 ---
producer.beginTransaction();
producer.send(new ProducerRecord<>("tx-demo", "k1", "COMMITTED-1"));
producer.send(new ProducerRecord<>("tx-demo", "k1", "COMMITTED-2"));
producer.commitTransaction();

// --- 事务 B: 中途异常 -> 回滚 ---
try {
    producer.beginTransaction();
    producer.send(new ProducerRecord<>("tx-demo", "k2", "ABORTED-1")).get();
    if (true) throw new RuntimeException("业务异常");   // 模拟处理失败
    producer.send(new ProducerRecord<>("tx-demo", "k2", "ABORTED-2"));
    producer.commitTransaction();
} catch (Exception e) {
    System.out.println("回滚: " + e.getMessage());
    producer.abortTransaction();
}
producer.close();
```

两种消费者对比：

```bash
# read_uncommitted（默认）—— 能看到被回滚的消息
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic tx-demo --from-beginning --timeout-ms 5000 \
  --isolation-level read_uncommitted

# read_committed —— 只能看到已提交的消息
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic tx-demo --from-beginning --timeout-ms 5000 \
  --isolation-level read_committed
```

结果对照：

| 隔离级别 | 读到的消息 |
|---|---|
| `read_uncommitted`（默认） | `COMMITTED-1`、`COMMITTED-2`、`ABORTED-1` |
| `read_committed` | `COMMITTED-1`、`COMMITTED-2` |

**关键认知一：回滚不是删除。** `ABORTED-1` 这条消息**确实已经物理写进了日志文件**，`abortTransaction()` 做的只是追加一条 **abort 类型的控制记录（control record）**。数据还在磁盘上，只是被打上了"这批不算数"的标记。

**关键认知二：过滤发生在消费端。** 配置 `isolation.level=read_committed` 的消费者会：

1. 只读到 **LSO（Last Stable Offset）** 为止的数据。LSO 是"最早的那个仍未决的事务的起始位置"，未决事务之后的消息即使已提交也读不到，必须等前面的事务尘埃落定。
2. 在客户端根据控制记录**过滤掉被 abort 的批次**，同时也不把控制记录本身返回给业务代码。

**关键认知三：事务 Producer 的默认值会被强制修改。** 一旦设置 `transactional.id`，Kafka 会自动把 `enable.idempotence` 设为 `true`、`acks` 设为 `all`、`retries` 设为 `Integer.MAX_VALUE`。如果你显式配了冲突的值（比如 `acks=1`），启动时会直接抛 `ConfigException`。

**两个实践要点**：

- **只用事务 Producer 而消费端仍是默认的 `read_uncommitted`，事务就白做了**——被回滚的消息照样被下游消费。事务是"生产端 + 消费端"两侧配合才成立的。
- `read_committed` 会引入额外延迟：消费者必须等事务提交后才能读到消息，所以延迟至少是"事务时长"级别。对延迟敏感的链路要权衡，或者把事务做小做短。

**第 3 题 · ProducerFencedException（僵尸实例隔离）**

用同一份代码启动两个进程，`transactional.id` 都写死为 `tx-fence-01`：

```java
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "tx-fence-01");  // 两个进程完全相同

Producer<String, String> producer = new KafkaProducer<>(props);
producer.initTransactions();
System.out.println("initTransactions 完成，开始循环发送");

for (int i = 0; ; i++) {
    try {
        producer.beginTransaction();
        producer.send(new ProducerRecord<>("fence-demo", "msg-" + i)).get();
        producer.commitTransaction();
        System.out.println("已提交 #" + i);
        Thread.sleep(2000);
    } catch (ProducerFencedException e) {
        System.out.println("!!! 被 fence 了: " + e.getMessage());
        producer.close();      // 只能关闭退出，不能 abort 也不能继续用
        return;
    }
}
```

操作顺序与现象：

```text
[进程 A] 先启动，正常循环
  已提交 #0
  已提交 #1
  已提交 #2

[进程 B] 此时启动，也用 tx-fence-01
  initTransactions 完成，开始循环发送
  已提交 #0

[进程 A] 下一次 commit 时立刻挂掉
  !!! 被 fence 了: Producer attempted an operation with an old epoch.
      Either there is a newer producer with the same transactionalId,
      or the producer's transaction has been expired by the broker.
```

**原理**：事务协调器为每个 `transactional.id` 维护一个单调递增的 **epoch**。新 Producer 调用 `initTransactions()` 时，协调器会把 epoch 加一，并**主动 abort 掉旧 epoch 遗留的未决事务**。之后任何携带旧 epoch 的请求都会被拒绝，抛出 `ProducerFencedException`。

**这个机制解决的真实问题**是"僵尸实例"：假设服务实例 A 发生长时间 GC 或网络分区，被编排系统判定为死亡并拉起了实例 B；结果 A 又活了过来，继续往 Kafka 写数据 —— 这时 A 和 B 会写出重复甚至互相冲突的数据。epoch fencing 保证**同一个 `transactional.id` 在任意时刻只有最新的那个实例能写入**，老实例被彻底封死。

**因此 `transactional.id` 的命名规则至关重要**，必须同时满足两个看似矛盾的要求：

| 要求 | 原因 |
|---|---|
| **实例之间唯一** | 否则多个正常运行的实例会互相 fence，形成"你踢我我踢你"的死循环，谁都写不进去 |
| **同一实例重启后保持不变** | 协调器靠这个 ID 找到上次的事务状态并完成恢复（提交或回滚未决事务）；每次随机生成的话，遗留的未决事务永远悬在那里，会一直阻塞 `read_committed` 消费者的 LSO |

常见的正确取值：

- Kafka Streams 场景：框架自动生成 `应用ID-任务ID`；
- 自研消费-处理-生产链路：用 `服务名-输入分区号`（分区归属稳定，重启后仍能拿回同一个 ID）；
- K8s StatefulSet：用 `服务名-有序序号`（Pod 名天然稳定）。

**反面教材**：用 `UUID.randomUUID()` 或 `服务名 + 时间戳`。这样虽然不会误 fence，但每次重启都会在协调器里留下一个再也不会被清理的事务状态，日积月累拖垮 `__transaction_state`，同时未决事务会卡住 LSO 让下游 `read_committed` 消费者永久积压。

**最后注意异常处理姿势**：捕获 `ProducerFencedException` 后**只能 `close()` 退出**，不能调 `abortTransaction()`（会再抛异常），也不能重新 `initTransactions()` 继续用（那等于把对方 fence 回去，形成拉锯）。正确做法是让进程退出，交给编排系统处理。这也是为什么章节示例代码里 `ProducerFencedException` 和普通 `KafkaException` 要**分开两个 catch 块**——前者退出，后者回滚重试。
</Answer>
