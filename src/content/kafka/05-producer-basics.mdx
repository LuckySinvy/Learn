# Producer 原理与核心配置

`producer.send()` 一行代码背后，消息经历了拦截器、序列化、分区路由、内存攒批、网络发送五个阶段。理解这条链路，你才能解释"为什么消息没有立刻发出去"、"为什么内存爆了"、"batch.size 和 linger.ms 到底怎么配"。

## 1. 发送流程全景

Producer 内部是**双线程模型**：主线程负责把消息放进缓冲区，Sender 线程负责真正的网络 IO。

```text
主线程 (你的业务线程)
  send(record)
    |
    v
  [拦截器 Interceptors]        onSend() 加工消息 (打标、埋点)
    |
    v
  [序列化器 Serializer]        key/value 对象 -> byte[]
    |
    v
  [分区器 Partitioner]         决定去哪个分区 (有 key 按哈希)
    |
    v
  [RecordAccumulator 缓冲区]   按 "topic-分区" 维度攒批
    |  buffer.memory=32MB       batch1[msg,msg,..] batch2[..]
    |                                 |
- - | - - - - - - - - - - - - - - - - | - - - - - -
    v                                 v
Sender 线程 (IO 线程)          批次满(batch.size) 或到时(linger.ms)
  把就绪批次组装成请求 ──> 网络发送到分区 leader 所在 broker
  等待 acks 响应 ──> 成功: 执行回调 / 失败: 重试或抛错
```

关键点：

- `send()` 返回时消息**只是进了本地缓冲区**，并没有发出去。
- 一个批次（batch）只属于一个分区，发往同一 broker 的多个批次会合并成一个请求。
- Sender 线程异步工作，主线程几乎无阻塞——除非缓冲区满。

## 2. 攒批三参数

| 参数 | 默认值 | 含义 |
|---|---|---|
| `batch.size` | 16384 (16KB) | 单个批次的字节上限，攒满立即可发 |
| `linger.ms` | 0 | 批次未满时最多等多久，到时也发 |
| `buffer.memory` | 33554432 (32MB) | 整个 Producer 缓冲区总大小 |

发送时机 = 批次攒满 `batch.size` **或** 等待达到 `linger.ms`，先到先发。

- `linger.ms=0`（默认）：消息尽快发出，延迟最低，但批次很小、吞吐差。
- `linger.ms=5~100`：故意等一等换取更大的批次，吞吐大幅提升，延迟增加几毫秒——**高吞吐场景必调**。
- 缓冲区满时 `send()` 会阻塞，最长 `max.block.ms`（默认 60 秒），超时抛异常。

```text
linger.ms=0:    [m][m][m][m]         每条几乎单独一个请求, 请求数多
linger.ms=20:   [m m m m m m m][...] 攒成大批次, 请求数骤减, 吞吐up
```

## 3. 压缩

`compression.type` 对**整个批次**压缩，批次越大压缩比越高（这也是要攒批的原因之一）：

| 算法 | 压缩比 | CPU 开销 | 建议 |
|---|---|---|---|
| none | - | 无 | 默认 |
| lz4 | 中 | 低 | 通用首选 |
| snappy | 中 | 低 | 与 lz4 接近 |
| zstd | 高 | 中 | 带宽敏感首选（2.1+） |
| gzip | 高 | 高 | 不推荐新项目 |

## 4. Java 客户端实战

依赖 `org.apache.kafka:kafka-clients:3.7.1`。

```java
import org.apache.kafka.clients.producer.*;
import org.apache.kafka.common.serialization.StringSerializer;
import java.util.Properties;
import java.util.concurrent.Future;

public class OrderProducer {
    public static void main(String[] args) throws Exception {
        Properties props = new Properties();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        // 攒批与压缩
        props.put(ProducerConfig.BATCH_SIZE_CONFIG, 32768);        // 32KB
        props.put(ProducerConfig.LINGER_MS_CONFIG, 20);            // 等 20ms
        props.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, "lz4");
        props.put(ProducerConfig.BUFFER_MEMORY_CONFIG, 64 * 1024 * 1024L);

        Producer<String, String> producer = new KafkaProducer<>(props);
        ProducerRecord<String, String> record =
            new ProducerRecord<>("orders", "user-1", "{\"orderId\":1001}");

        // 方式1: 发后即忘 —— 最快, 可能丢消息且无感知
        producer.send(record);

        // 方式2: 同步发送 —— 逐条确认, 吞吐最低
        RecordMetadata meta = producer.send(record).get();
        System.out.printf("sync -> partition=%d offset=%d%n",
            meta.partition(), meta.offset());

        // 方式3: 异步 + 回调 —— 生产推荐, 高吞吐且能感知失败
        producer.send(record, (metadata, exception) -> {
            if (exception != null) {
                // 记日志/告警/落补偿表, 不要吞掉
                exception.printStackTrace();
            } else {
                System.out.printf("async -> partition=%d offset=%d%n",
                    metadata.partition(), metadata.offset());
            }
        });

        producer.flush();   // 强制清空缓冲区
        producer.close();   // 会先 flush 再关闭
    }
}
```

<Callout type="warn" title="Producer 是线程安全的, 全局一个就够">
KafkaProducer 线程安全且很重——内部有缓冲区和 IO 线程。正确用法是**整个应用共享一个实例**。每次发送 new 一个 Producer 是最常见的性能反模式，会导致连接风暴且完全无法攒批。另外，进程退出前必须调用 `close()`，否则缓冲区里还没发出去的消息会直接丢失。
</Callout>

## 5. Python 对照（confluent-kafka）

```python
from confluent_kafka import Producer

producer = Producer({
    "bootstrap.servers": "localhost:9092",
    "batch.size": 32768,
    "linger.ms": 20,
    "compression.type": "lz4",
})

def on_delivery(err, msg):
    if err is not None:
        print(f"delivery failed: {err}")
    else:
        print(f"delivered to {msg.topic()}[{msg.partition()}]@{msg.offset()}")

for i in range(10):
    producer.produce(
        topic="orders",
        key=f"user-{i % 3}",
        value=f'{{"orderId": {1000 + i}}}',
        on_delivery=on_delivery,
    )
    producer.poll(0)   # 触发已完成发送的回调

producer.flush()       # 退出前必须 flush
```

`produce()` 同样只是入队；`poll(0)` 驱动回调执行；`flush()` 阻塞直到全部送达。

## 6. 其他重要参数速查

| 参数 | 默认 | 说明 |
|---|---|---|
| `max.request.size` | 1MB | 单个请求最大字节数，超大消息会被直接拒绝 |
| `request.timeout.ms` | 30000 | 等 broker 响应的超时 |
| `delivery.timeout.ms` | 120000 | send() 到确认成功/失败的总时限（含重试） |
| `max.block.ms` | 60000 | 缓冲区满或元数据不可用时 send() 最长阻塞时间 |
| `client.id` | 空 | 客户端标识，方便服务端日志与配额定位 |

<Callout type="tip" title="吞吐调优三板斧">
高吞吐场景先调这三个：`linger.ms=20~100`、`batch.size=64KB~128KB`、`compression.type=lz4/zstd`。通常能把吞吐提升 3-10 倍，代价只是几十毫秒的发送延迟。可靠性相关的 acks、retries、幂等在下一章专门讲。
</Callout>

## 小结

- Producer 双线程模型：主线程写缓冲区，Sender 线程网络发送；`send()` 返回不等于已发送
- 链路：拦截器 → 序列化 → 分区器 → RecordAccumulator 攒批 → Sender
- 攒批由 `batch.size` 与 `linger.ms` 共同控制，先到先发；压缩作用于整个批次
- 三种发送：发后即忘（慎用）、同步（低吞吐）、异步回调（生产推荐）
- 全局共享一个 Producer 实例，退出前 close/flush

**第 1 题 · linger.ms 与压缩的吞吐对比**

用同一份代码跑两组配置即可，关键是把配置抽成参数：

```java
public class ThroughputBench {
    static void run(String label, int lingerMs, String compression) throws Exception {
        Properties props = new Properties();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        props.put(ProducerConfig.LINGER_MS_CONFIG, lingerMs);
        props.put(ProducerConfig.BATCH_SIZE_CONFIG, 65536);
        props.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, compression);

        String payload = "x".repeat(500);   // 500B 的消息体
        long start = System.currentTimeMillis();
        try (Producer<String, String> p = new KafkaProducer<>(props)) {
            for (int i = 0; i < 100_000; i++) {
                p.send(new ProducerRecord<>("bench", "k" + (i % 100), payload));
            }
        }   // try-with-resources 的 close() 会自动 flush, 计时包含全部落盘
        long cost = System.currentTimeMillis() - start;
        System.out.printf("%s: %d ms, %.0f msg/s%n",
            label, cost, 100_000 * 1000.0 / cost);
    }

    public static void main(String[] args) throws Exception {
        run("linger=0  none", 0, "none");
        run("linger=50 lz4 ", 50, "lz4");
    }
}
```

也可以直接用 Kafka 自带的压测工具，连代码都不用写：

```bash
# 不攒批、不压缩
bin/kafka-producer-perf-test.sh --topic bench --num-records 100000 \
  --record-size 500 --throughput -1 \
  --producer-props bootstrap.servers=localhost:9092 linger.ms=0 compression.type=none

# 攒批 + lz4
bin/kafka-producer-perf-test.sh --topic bench --num-records 100000 \
  --record-size 500 --throughput -1 \
  --producer-props bootstrap.servers=localhost:9092 linger.ms=50 \
  batch.size=65536 compression.type=lz4
```

典型结果（本地单机，数量级供参考，绝对值取决于硬件）：

| 配置 | 耗时 | 吞吐 | 单条延迟 |
|---|---|---|---|
| `linger.ms=0` + 不压缩 | ~9 s | ~11,000 msg/s | 低（几乎立刻发出） |
| `linger.ms=50` + lz4 | ~2 s | ~50,000 msg/s | 高（最多多等 50ms） |

**为什么差这么多**——三个叠加效应：

1. **请求次数骤减**：`linger.ms=0` 时 Sender 线程一有空就发，一个请求可能只带几条消息，10 万条要发上万次网络往返；`linger.ms=50` 让消息在 RecordAccumulator 里攒够 64KB（约 130 条）再发，请求数降低一两个数量级。
2. **压缩作用于整批**：Kafka 压缩的是**整个 batch** 而不是单条消息。批次越大，重复的 key、字段名越多，压缩率越高。示例中重复字符串压缩后能小 10 倍以上，网络传输量随之骤降。
3. **broker 侧开销降低**：每个请求 broker 都要走一遍网络线程 → 请求队列 → IO 线程 → 写日志的流程，请求少了 CPU 和锁竞争都下来了。

**结论与取舍**：`linger.ms` 是拿**延迟换吞吐**的旋钮。它不是"必须等满 50ms"，而是"最多等 50ms"——只要 batch 先攒满 `batch.size` 就立即发送。所以流量大时实际等待远小于 50ms，几乎是白赚吞吐；只有流量稀疏时才会真的等满。这也是为什么生产环境几乎总该把 `linger.ms` 设成 5~100 而不是 0。

**第 2 题 · buffer.memory 打满与 max.block.ms**

```java
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.BUFFER_MEMORY_CONFIG, 1 * 1024 * 1024);  // 只给 1MB
props.put(ProducerConfig.MAX_BLOCK_MS_CONFIG, 3000);              // 最多阻塞 3 秒
props.put(ProducerConfig.LINGER_MS_CONFIG, 1000);                 // 故意拖慢发送

Producer<String, String> producer = new KafkaProducer<>(props);
String big = "x".repeat(100 * 1024);   // 100KB 一条, 10 条就能撑满 1MB

for (int i = 0; i < 100; i++) {
    long t0 = System.currentTimeMillis();
    try {
        producer.send(new ProducerRecord<>("bench", big));
        long blocked = System.currentTimeMillis() - t0;
        if (blocked > 5) System.out.printf("#%d send() 阻塞了 %d ms%n", i, blocked);
    } catch (org.apache.kafka.common.errors.TimeoutException e) {
        System.out.printf("#%d 抛出异常: %s%n", i, e.getMessage());
        break;
    }
}
```

观察到的现象分两个阶段：

```text
#12 send() 阻塞了 842 ms      <- 缓冲区满, 等 Sender 释放空间
#13 send() 阻塞了 1003 ms
#14 抛出异常: Failed to allocate memory within the configured max blocking
    time 3000 ms.
```

**原理**：`send()` 之所以"非阻塞"，前提是 RecordAccumulator 里还有空闲内存。当已缓冲但未发送的数据达到 `buffer.memory` 上限时，`send()` 会在分配内存处**阻塞等待** Sender 线程把批次发出去释放空间。等待时长超过 `max.block.ms` 就抛 `TimeoutException`。

`max.block.ms` 实际覆盖两种阻塞：

1. **缓冲区满**（本例）；
2. **元数据未就绪**——首次给某个 topic 发消息时要先拉元数据，如果 broker 连不上会卡在这里，最终报 `Topic xxx not present in metadata after 60000 ms`。

**这个实验的生产意义**：`send()` 抛 `TimeoutException` 是一个非常强的**背压信号**，说明"业务产生消息的速度 > Kafka 消化的速度"。此时正确做法不是无脑调大 `buffer.memory`（那只是延后崩溃），而是排查根因：broker 是否变慢、网络是否打满、分区数是否不足、是否该开启压缩。同时应用侧要捕获这个异常并降级（写本地队列、丢弃低优先级消息、限流上游），而不是让它冒泡把请求线程打挂。

**第 3 题 · 不调 flush 会丢多少条**

```java
AtomicInteger ok = new AtomicInteger();
AtomicInteger fail = new AtomicInteger();
int TOTAL = 10_000;

Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
props.put(ProducerConfig.LINGER_MS_CONFIG, 100);   // 放大效果

Producer<String, String> producer = new KafkaProducer<>(props);
for (int i = 0; i < TOTAL; i++) {
    producer.send(new ProducerRecord<>("flush-demo", "msg-" + i),
        (meta, ex) -> {
            if (ex == null) ok.incrementAndGet();
            else fail.incrementAndGet();
        });
}

// 关键对照: 注释掉下面两行 vs 保留
// producer.flush();
// producer.close();

System.out.printf("回调统计: ok=%d fail=%d, 未回调=%d%n",
    ok.get(), fail.get(), TOTAL - ok.get() - fail.get());
Runtime.getRuntime().halt(0);   // 强制退出, 模拟进程被 kill
```

对照结果：

| 做法 | 回调统计 | 服务端实收 |
|---|---|---|
| 不 flush、不 close，直接强制退出 | `ok≈300 fail=0 未回调≈9700` | 只有几百条 |
| 调 `flush()` 或 `close()` | `ok=10000 fail=0` | 10000 条 |

服务端计数用这条命令核对：

```bash
bin/kafka-get-offsets.sh --bootstrap-server localhost:9092 \
  --topic flush-demo --time -1
```

**为什么会丢**：`send()` 只是把消息**放进内存中的 RecordAccumulator 就返回了**，真正的网络发送由后台 Sender 线程异步完成。进程被强制终止时，缓冲区里还没轮到发送的消息随进程内存一起蒸发，而且**回调根本不会被触发**——所以你连"丢了"这件事都感知不到，这是最危险的地方。丢失条数取决于 `linger.ms`、`batch.size` 和退出时机，没有固定值。

**正确的收尾姿势**：

- `flush()`：阻塞直到缓冲区中所有消息都收到 broker 响应（成功或最终失败），之后 Producer 还能继续用。
- `close()`：内部会**先执行一次 flush** 再释放资源。所以只要正常调用了 `close()`（或用 try-with-resources），就不会有这个问题。
- 生产服务应注册 JVM 关闭钩子，保证收到终止信号时也能优雅退出：

```java
Runtime.getRuntime().addShutdownHook(new Thread(producer::close));
```

**注意 `close()` 不是万能的**：强制杀进程、容器 OOMKilled、机器断电这些场景下钩子根本不会执行。所以对"绝对不能丢"的消息，光靠 Producer 缓冲区不够，需要 Outbox 模式（先落库再异步投递）这类方案兜底——这正是下一章可靠性要展开的话题。

Python 侧同理，`produce()` 入队即返回，退出前必须：

```python
producer.flush()   # 返回值是仍未送达的消息数, 正常应为 0
```
