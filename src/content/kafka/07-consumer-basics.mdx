# Consumer 与消费组

Kafka 消费端是**拉模型**：消费者主动 `poll()` 拉取消息，自己控制节奏。这个设计把复杂度从 broker 移到了客户端——poll 循环怎么写、三个超时参数怎么配，直接决定你的服务会不会陷入"反复 Rebalance、消息重复消费"的泥潭。

## 1. 为什么是拉（pull）而不是推（push）

- **消费者自己控制速率**：处理慢就少拉点，不会被 broker 压垮（天然背压）。
- **方便批量**：一次 poll 拉一批，摊薄网络开销。
- **支持回放**：拉模型下消费位置由消费者决定，seek 到任意 offset 都行。

代价是消费者要维护一个**不停轮询的循环**，这就是 poll 循环模型。

## 2. poll 循环模型

标准骨架（Java）：

```java
import org.apache.kafka.clients.consumer.*;
import org.apache.kafka.common.serialization.StringDeserializer;
import java.time.Duration;
import java.util.*;

public class OrderConsumer {
    public static void main(String[] args) {
        Properties props = new Properties();
        props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        props.put(ConsumerConfig.GROUP_ID_CONFIG, "inventory-service");
        props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
        props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
        props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");
        props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "false"); // 手动提交

        KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
        consumer.subscribe(List.of("orders"));   // 订阅后并未立刻分配分区

        try {
            while (true) {
                // poll 做三件事: 心跳协调、拉取消息、触发 Rebalance 回调
                ConsumerRecords<String, String> records =
                    consumer.poll(Duration.ofMillis(500));
                for (ConsumerRecord<String, String> r : records) {
                    System.out.printf("p=%d offset=%d key=%s value=%s%n",
                        r.partition(), r.offset(), r.key(), r.value());
                    // 业务处理...
                }
                consumer.commitSync();   // 处理完一批再提交 (第 8 章详解)
            }
        } finally {
            consumer.close();   // 主动离组, 立刻触发 Rebalance 而非等超时
        }
    }
}
```

Python（confluent-kafka）对照：

```python
from confluent_kafka import Consumer

consumer = Consumer({
    "bootstrap.servers": "localhost:9092",
    "group.id": "inventory-service",
    "auto.offset.reset": "earliest",
    "enable.auto.commit": False,
})
consumer.subscribe(["orders"])

try:
    while True:
        msg = consumer.poll(timeout=0.5)    # 一次一条 (也可用 consume 批量)
        if msg is None:
            continue
        if msg.error():
            print(f"error: {msg.error()}")
            continue
        print(f"p={msg.partition()} offset={msg.offset()} value={msg.value()}")
        consumer.commit(asynchronous=False)
finally:
    consumer.close()
```

<Callout type="warn" title="KafkaConsumer 不是线程安全的">
与 Producer 相反，KafkaConsumer **只能被一个线程使用**。要并行消费就启动多个消费者实例（每个自己的线程/进程），靠消费组机制分摊分区。在多个线程里共用一个 consumer 会直接抛 ConcurrentModificationException。
</Callout>

## 3. 消费组协调机制

每个消费组在 broker 端有一个 **Group Coordinator**（按 group.id 哈希落到某个 broker）。消费者启动后：

```text
1. FindCoordinator  找到自己组的协调器
2. JoinGroup        入组; 协调器选一个消费者当 "组长" (group leader)
3. 组长根据分配策略计算 分区->消费者 的映射
4. SyncGroup        组长上报方案, 协调器下发给所有成员
5. 各消费者开始 poll 自己名下的分区, 周期性发心跳
```

分配语义回顾（第 2 章）：一个分区在组内同一时刻只属于一个消费者；消费者数超过分区数则多余的闲置。

## 4. 三个超时参数：最容易配错的地方

这是消费端故障排查的核心知识点。三个参数管的是**两条独立的线**：

```text
线 1: 心跳线程 (后台自动)                线 2: 你的业务处理 (poll 间隔)
 ├ heartbeat.interval.ms  发心跳周期      └ max.poll.interval.ms
 └ session.timeout.ms     判死时限            两次 poll 之间的最大间隔
   "进程还活着吗?"                            "还在正常处理消息吗?"
```

| 参数 | 默认 | 管什么 | 超了会怎样 |
|---|---|---|---|
| `heartbeat.interval.ms` | 3000 | 后台心跳发送间隔 | - |
| `session.timeout.ms` | 45000 | 协调器多久没收到心跳判定死亡 | 踢出组，触发 Rebalance |
| `max.poll.interval.ms` | 300000 | 两次 poll 调用的最大间隔 | 主动离组，触发 Rebalance |

关键区别：

- **进程崩溃 / 网络断开** → 心跳停止 → `session.timeout.ms` 后被踢。
- **进程活着但处理太慢**（一批消息 6 分钟没处理完，超过 max.poll.interval 默认 5 分钟）→ 心跳还在发，但消费者自己判定"我可能死循环了"，主动离组。

最经典的故障就是第二种：

```text
症状: 消费组反复 Rebalance, 日志出现
  "consumer poll timeout has expired ... max.poll.interval.ms"
原因: 单批消息处理时间 > max.poll.interval.ms
解法 (按优先级):
  1. 减小 max.poll.records (默认 500), 一批少拉点
  2. 加快单条处理 (异步化、批量写库)
  3. 调大 max.poll.interval.ms (治标)
```

配置建议：

```properties
session.timeout.ms=45000
heartbeat.interval.ms=15000        # 一般设为 session 的 1/3
max.poll.interval.ms=300000
max.poll.records=500               # 每批最大条数, 按单条处理耗时倒推
fetch.min.bytes=1                  # broker 攒够多少字节才返回
fetch.max.wait.ms=500              # 攒不够时最多等多久
```

估算公式：`max.poll.records × 单条最大处理时间 < max.poll.interval.ms`，留 50% 余量。

## 5. subscribe 与 assign

| 方式 | 说明 | Rebalance |
|---|---|---|
| `subscribe(topics)` | 加入消费组，由协调器分配分区 | 参与 |
| `assign(partitions)` | 手动指定分区，不走消费组协调 | 不参与 |

`assign` 适合：数据修复工具、精确控制分区的 ETL、单实例消费全部分区的小场景。它没有故障转移——实例挂了没人接管分区。

```java
// 手动指定消费 orders 的 0 号分区
TopicPartition p0 = new TopicPartition("orders", 0);
consumer.assign(List.of(p0));
consumer.seekToBeginning(List.of(p0));
```

## 6. 消费者数量怎么定

- 起点：消费者数 = 分区数 ÷ 2 到分区数之间，观察 LAG 再调。
- 上限：组内消费者数超过分区数没有意义。
- 单消费者吞吐不够时，先确认瓶颈在业务处理还是拉取（通常是业务写库慢），处理逻辑内部再做异步/批量优化，比无脑加实例有效。

<Callout type="tip" title="优雅停机">
收到 SIGTERM 时调用 `consumer.wakeup()` 打断阻塞中的 poll（会抛 WakeupException），在 finally 里 `close()`。close 会发 LeaveGroup 请求，让 Rebalance 立即发生，而不是干等 session.timeout —— 滚动发布时这能把消费中断从 45 秒降到秒级。
</Callout>

## 小结

- Kafka 消费是拉模型，poll 循环同时承担拉消息、心跳协调、Rebalance 参与三个职责
- Consumer 非线程安全，一个线程一个实例，并行靠消费组分摊分区
- 三个超时：session.timeout 判"进程死没死"，max.poll.interval 判"处理卡没卡"，heartbeat 是心跳频率
- `max.poll.records × 单条耗时` 必须小于 max.poll.interval.ms
- subscribe 走组协调有故障转移，assign 手动控制无接管

在第四个终端查看分配结果：

```bash
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group g1
```

```text
GROUP  TOPIC  PARTITION  CURRENT-OFFSET  LAG  CONSUMER-ID              HOST
g1     six    0          0               0    console-consumer-a1b2..  /127.0.0.1
g1     six    1          0               0    console-consumer-a1b2..  /127.0.0.1
```

6 ÷ 3 = 2，**每人两个分区，正好均分**。默认的 `RangeAssignor` 按 topic 内分区序号切段分配，所以是连续的 `[0,1] [2,3] [4,5]`；如果换成 `RoundRobinAssignor` 会变成 `[0,3] [1,4] [2,5]`——分配结果不同但每人 2 个这一点不变。

关掉其中一个（`Ctrl-C`）后再次 describe：

```text
g1     six    0    ...  console-consumer-a1b2..
g1     six    1    ...  console-consumer-a1b2..
g1     six    2    ...  console-consumer-a1b2..   <- 接管了原来 c3d4 的分区
g1     six    3    ...  console-consumer-e5f6..
g1     six    4    ...  console-consumer-e5f6..
g1     six    5    ...  console-consumer-e5f6..
```

**6 个分区被重新分给剩下 2 个消费者，每人 3 个**。这就是 **Rebalance（再平衡）**——消费组成员变化时，协调器会重新计算分区归属，保证没有分区无人消费、也没有分区被两人同时消费。

三个值得注意的现象：

1. **接管是自动的**，不需要任何人工干预，这正是 `subscribe()` 相比 `assign()` 的核心价值（`assign()` 手动指定分区，实例挂了那些分区就彻底没人管了）。
2. **Rebalance 期间整组暂停消费**（Stop-The-World，Eager 协议下）。如果组很大、分区很多，这个停顿可能达到秒级甚至更久，这是第 9 章要重点解决的问题。
3. **`Ctrl-C` 优雅退出 vs 直接 `kill -9` 差别巨大**：前者消费者会主动发 `LeaveGroup` 请求，Rebalance 立刻触发；后者协调器要干等 `session.timeout.ms`（默认 45 秒）才发现成员失联。可以用 `kill -9` 对照实验一次，会明显感觉到"半分钟内那几个分区完全没人消费"。

如果继续加消费者到 7 个，第 7 个会拿到空分配、完全空转——**组内有效并发上限 = 分区数**，这是 Kafka 扩容的硬天花板，也是"分区数要预留余量"的原因。

**第 2 题 · 慢处理触发 max.poll.interval.ms 超时**

```java
Properties props = new Properties();
props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ConsumerConfig.GROUP_ID_CONFIG, "slow-demo");
props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
props.put(ConsumerConfig.MAX_POLL_INTERVAL_MS_CONFIG, 10000);  // 调成 10 秒便于观察

KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(List.of("six"));

while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String, String> r : records) {
        System.out.println("处理: " + r.value());
        Thread.sleep(20000);      // 远超 max.poll.interval.ms
    }
    consumer.commitSync();
}
```

日志中会依次出现：

```text
WARN  [Consumer clientId=..., groupId=slow-demo] consumer poll timeout has
      expired. This means the time between subsequent calls to poll() was
      longer than the configured max.poll.interval.ms, which typically implies
      that the poll loop is spending too much time processing messages.
      You can address this either by increasing max.poll.interval.ms or by
      reducing the maximum size of batches returned in poll() with max.poll.records.

INFO  Member consumer-slow-demo-1-xxx sending LeaveGroup request to coordinator
      due to consumer poll timeout has expired.

ERROR org.apache.kafka.clients.consumer.CommitFailedException: Commit cannot be
      completed since the group has already rebalanced and assigned the
      partitions to another member.
```

**完整的因果链**（这是线上最高频的消费故障，务必理解透）：

```text
1. 业务处理 20 秒 > max.poll.interval.ms=10 秒
2. 消费者自己检测到"我太久没调 poll 了" -> 主动发 LeaveGroup 离组
3. 协调器触发 Rebalance，把分区分给别人
4. 原消费者处理完后调 commitSync() -> 分区已不属于它 -> CommitFailedException
5. 消息没被提交 -> 新接手的消费者从旧 offset 重新拉到同一批消息
6. 新消费者同样处理 20 秒 -> 又超时 -> 又 Rebalance ...
```

结果就是**无限 Rebalance 循环 + 消息被反复重复消费，整组吞吐归零**。日志里刷屏的 Rebalance 是最典型的特征。

**为什么需要 `max.poll.interval.ms` 这个独立于心跳的机制**：从 0.10.1 起，心跳被移到**独立的后台线程**。这意味着即使你的业务线程卡在一个死循环里，心跳依然在正常发送，协调器会认为"这个成员活得好好的"，于是分区一直挂在它名下无人处理。`max.poll.interval.ms` 就是为了堵上这个漏洞——它检测的不是"进程是否存活"，而是"**业务是否还在推进**"。

**按优先级排列的解决方案：**

| 优先级 | 做法 | 说明 |
|---|---|---|
| 1 | 减小 `max.poll.records` | 治本且零风险。一批从 500 降到 50，单批处理时间直接降 10 倍 |
| 2 | 优化单条处理耗时 | 批量写库代替逐条、去掉同步远程调用、加索引 |
| 3 | 处理逻辑异步化 | 丢进线程池后立即 poll，但**必须自己管好 offset 提交**，否则会丢消息（见第 8 章） |
| 4 | 调大 `max.poll.interval.ms` | 治标。而且调得越大，真正卡死的实例被发现得越晚 |

估算公式记牢：`max.poll.records × 单条最坏耗时 < max.poll.interval.ms`，并留 50% 余量。比如单条最坏 200ms、`max.poll.interval.ms` 默认 300 秒，那么 `max.poll.records` 应 ≤ 750，取 500 是安全的；但如果单条要 2 秒（比如调了外部 API），500 条就是 1000 秒，必然超时，必须降到 75 以下。

**第 3 题 · max.poll.records 10 vs 500 的对比**

```java
long t0 = System.currentTimeMillis();
ConsumerRecords<String, String> records = consumer.poll(Duration.ofSeconds(1));
long pollCost = System.currentTimeMillis() - t0;

long t1 = System.currentTimeMillis();
for (ConsumerRecord<String, String> r : records) {
    Thread.sleep(10);            // 模拟单条 10ms 的业务处理
}
long processCost = System.currentTimeMillis() - t1;

System.out.printf("拉到 %d 条 | poll 耗时 %d ms | 处理耗时 %d ms | 单轮合计 %d ms%n",
    records.count(), pollCost, processCost, pollCost + processCost);
```

先灌 5000 条数据，然后两种配置各跑一遍：

| 配置 | 每轮条数 | 每轮处理耗时 | 消费 5000 条总轮数 | 总耗时 |
|---|---|---|---|---|
| `max.poll.records=500` | 500 | ~5000 ms | 10 | ~50 s |
| `max.poll.records=10` | 10 | ~100 ms | 500 | ~52 s |

**要从这组数据里读出三个结论：**

1. **总耗时几乎一样。** 因为瓶颈是"单条处理 10ms × 5000 条 = 50 秒"这个总量，`max.poll.records` 并不改变总工作量，只改变**任务的切分粒度**。指望调小它来提升吞吐是常见的误解。

2. **单轮耗时差 50 倍，这才是它的真正意义。** `max.poll.records=500` 时单轮 5 秒，意味着两次 poll 之间间隔 5 秒；如果业务处理慢一点（单条 700ms），单轮就是 350 秒，直接撞破默认的 300 秒 `max.poll.interval.ms`。**`max.poll.records` 的核心作用是控制"两次 poll 的间隔"，从而避免超时被踢出组**，而不是调吞吐。

3. **调太小有反效果。** 每轮 poll 都是一次网络往返 + 协调器交互，条数太少时这些固定开销占比升高（上表中 10 条时总耗时反而多了 2 秒）。极端情况下调到 1，网络开销会成为新瓶颈。

**怎么定这个值**：从业务的单条最坏处理耗时倒推。

```text
max.poll.records ≤ max.poll.interval.ms / 单条最坏耗时 / 2   (留一半余量)

例：单条最坏 500ms，max.poll.interval.ms=300000
    => max.poll.records ≤ 300000 / 500 / 2 = 300
```

另外两个相关参数也顺带理解一下：

- `fetch.min.bytes`（默认 1）：broker 攒够多少字节才返回。调大能减少空轮询、提升吞吐，代价是延迟升高。
- `fetch.max.wait.ms`（默认 500）：攒不够 `fetch.min.bytes` 时最多等多久。这两个和 Producer 端的 `batch.size` / `linger.ms` 是完全对称的设计思路。

注意 **`max.poll.records` 是纯客户端参数**，它只控制 `poll()` 从本地已拉取的缓冲区里一次返回多少条给你，不影响 broker 实际传输的数据量（那由 `fetch.max.bytes` 和 `max.partition.fetch.bytes` 控制）。所以调小它不会减少网络流量。
