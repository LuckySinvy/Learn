# 命令行工具实战

Kafka 自带的脚本工具是日常开发与排障的瑞士军刀。本章用一条完整的工作流串起最常用的六个工具：建 topic → 生产 → 消费 → 查消费组 → 改配置 → 查水位。建议开着一个本地集群跟着敲。

以下命令假设在 Kafka 安装目录执行，`localhost:9092` 换成你的地址。

## 1. kafka-topics.sh：主题管理

```bash
# 创建: 3 分区, 2 副本
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic orders --partitions 3 --replication-factor 2

# 建 topic 时附带配置
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic events --partitions 6 --replication-factor 3 \
  --config retention.ms=259200000 --config cleanup.policy=delete

# 列出所有 topic
bin/kafka-topics.sh --bootstrap-server localhost:9092 --list

# 查看详情: 分区分布 / Leader / ISR
bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders

# 扩分区 (只能增不能减!)
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --alter --topic orders --partitions 6

# 删除
bin/kafka-topics.sh --bootstrap-server localhost:9092 --delete --topic orders

# 只看有问题的分区: 缺副本 / 无 leader
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --under-replicated-partitions
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --unavailable-partitions
```

<Callout type="warn" title="扩分区会打乱 key 的路由">
分区从 3 扩到 6 后，同一个 key 的哈希落点会变化——扩容前 user-1 的消息在 p1，扩容后可能进 p4。依赖"同 key 同分区保证顺序"的业务，扩分区等于破坏历史顺序语义，要在业务低峰、消费者清空积压后谨慎操作（详见第 10 章）。
</Callout>

## 2. kafka-console-producer.sh：命令行生产

```bash
# 交互式生产: 每行一条消息, Ctrl-D 退出
bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders

# 发送带 key 的消息: 格式 "key:value"
bin/kafka-console-producer.sh --bootstrap-server localhost:9092 \
  --topic orders \
  --property parse.key=true --property key.separator=:
# 输入示例:
#   user-1:{"order_id":1001,"amount":99.9}
#   user-2:{"order_id":1002,"amount":15.0}

# 从文件批量灌入
bin/kafka-console-producer.sh --bootstrap-server localhost:9092 \
  --topic orders < orders.txt

# 带可靠性参数
bin/kafka-console-producer.sh --bootstrap-server localhost:9092 \
  --topic orders --request-required-acks all \
  --producer-property enable.idempotence=true
```

## 3. kafka-console-consumer.sh：命令行消费

```bash
# 从最新位置开始消费 (默认), 只看新消息
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders

# 从头消费全部历史
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic orders --from-beginning

# 显示 key、时间戳、分区、offset —— 排障必备
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic orders --from-beginning \
  --property print.key=true --property print.timestamp=true \
  --property print.partition=true --property print.offset=true

# 只消费指定分区、从指定 offset 开始
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic orders --partition 0 --offset 100 --max-messages 10

# 以指定消费组身份消费 (会提交 offset, 影响该组进度!)
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic orders --group inventory-service
```

<Callout type="tip" title="排障时别用业务的 group.id">
不带 `--group` 时 console consumer 会生成一次性临时组，不影响任何人。带上业务的 group.id 去"看一眼"，会把人家的 offset 提交掉，导致业务服务漏消费。查数据永远用 `--from-beginning` + 临时组。
</Callout>

## 4. kafka-consumer-groups.sh：消费组管理

这是排查"消息积压"最重要的工具：

```bash
# 列出所有消费组
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --list

# 查看消费组详情: 每个分区的进度与 LAG
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group inventory-service
```

输出解读：

```text
GROUP             TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID
inventory-service orders  0          1500            1520            20   consumer-1-xxx
inventory-service orders  1          980             2400            1420 consumer-2-xxx
```

- **CURRENT-OFFSET**：该组已提交的消费位置
- **LOG-END-OFFSET**：分区最新消息位置（LEO）
- **LAG** = 两者之差，即积压量。p1 积压 1420 条，该看看 consumer-2 是不是卡了。

重置 offset（必须先停掉该组所有消费者）：

```bash
# 预览: 重置到最早 (--dry-run 只显示不执行)
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group inventory-service --topic orders \
  --reset-offsets --to-earliest --dry-run

# 真正执行
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group inventory-service --topic orders \
  --reset-offsets --to-earliest --execute

# 其他重置方式
#   --to-latest                    跳到最新, 放弃积压
#   --to-datetime 2026-07-30T00:00:00.000  按时间点
#   --shift-by -100                回退 100 条
#   --to-offset 5000               指定绝对位置

# 删除消费组 (组内无活跃成员时)
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --delete --group old-service
```

## 5. kafka-configs.sh：动态配置

不重启就能改 topic / broker / 客户端配额等配置：

```bash
# 修改 topic 保留时间为 3 天
bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --alter --entity-type topics --entity-name orders \
  --add-config retention.ms=259200000

# 查看 topic 的非默认配置
bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --describe --entity-type topics --entity-name orders

# 删除覆盖, 恢复默认值
bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --alter --entity-type topics --entity-name orders \
  --delete-config retention.ms

# 动态调 broker 日志清理线程数 (entity-name 是 node.id)
bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --alter --entity-type brokers --entity-name 1 \
  --add-config log.cleaner.threads=2
```

## 6. kafka-get-offsets.sh：查询水位

查看每个分区的最早/最新 offset，常用于估算数据量和验证保留策略：

```bash
# 最新 offset (LEO), -1 表示 latest
bin/kafka-get-offsets.sh --bootstrap-server localhost:9092 \
  --topic orders --time -1

# 最早 offset, -2 表示 earliest
bin/kafka-get-offsets.sh --bootstrap-server localhost:9092 \
  --topic orders --time -2

# 按时间戳查: 该时间之后的第一条消息 offset
bin/kafka-get-offsets.sh --bootstrap-server localhost:9092 \
  --topic orders --time 1722297600000
```

输出 `orders:0:1520` 表示分区 0 的目标 offset 是 1520。最新减最早即当前分区实际存储的消息条数。

## 7. 一条完整工作流

```bash
T=demo-$(date +%s)
# 1. 建 topic
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic $T --partitions 3 --replication-factor 1
# 2. 灌 5 条带 key 的消息
printf 'a:1\nb:2\na:3\nc:4\nb:5\n' | bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic $T \
  --property parse.key=true --property key.separator=:
# 3. 带分区信息消费, 验证同 key 进同分区
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic $T --from-beginning --max-messages 5 \
  --property print.key=true --property print.partition=true
# 4. 查水位
bin/kafka-get-offsets.sh --bootstrap-server localhost:9092 --topic $T --time -1
# 5. 清理
bin/kafka-topics.sh --bootstrap-server localhost:9092 --delete --topic $T
```

## 小结

- `kafka-topics.sh`：建/查/扩/删 topic，describe 看 Leader 与 ISR
- `kafka-console-producer/consumer.sh`：手工收发，排障时打印 key/分区/offset
- `kafka-consumer-groups.sh`：看 LAG、重置 offset——积压排查第一入口
- `kafka-configs.sh`：动态改配置不用重启
- `kafka-get-offsets.sh`：查询分区水位
- 重置 offset 前必须停消费者；查数据别用业务 group.id

<Callout type="exercise" title="练习">
1. 创建 4 分区 topic，用带 key 生产写入 20 条消息（5 个不同 key），消费时打印分区号，验证同 key 落同分区。
2. 用一个固定 group.id 消费 10 条后停止，再用 kafka-consumer-groups 查看该组的 CURRENT-OFFSET 与 LAG。
3. 把该组 offset 重置到 earliest（先 dry-run 再 execute），重新消费验证消息被重复消费。

<Answer>
**参考答案：**

**第 1 题 · 验证同 key 落同分区**

```bash
# 1) 建 4 分区 topic
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic key-demo --partitions 4 --replication-factor 1

# 2) 生成 20 条消息，5 个 key（k1..k5）各 4 条
for i in $(seq 1 20); do
  echo "k$(( (i - 1) % 5 + 1 )):msg-$i"
done | bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic key-demo \
  --property parse.key=true --property key.separator=:

# 3) 打印分区号消费
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic key-demo --from-beginning --max-messages 20 \
  --property print.key=true --property print.partition=true \
  --property key.separator=' | '
```

输出（分区号可能与下面不同，但**同一个 key 的 4 条一定在同一分区**）：

```text
Partition:2  k1 | msg-1
Partition:0  k2 | msg-2
Partition:3  k3 | msg-3
Partition:1  k4 | msg-4
Partition:1  k5 | msg-5
Partition:2  k1 | msg-6      <- k1 又回到 2
Partition:0  k2 | msg-7      <- k2 又回到 0
...
```

用 `sort | uniq` 可以一眼确认每个 key 只对应一个分区：

```bash
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic key-demo --from-beginning --max-messages 20 \
  --property print.key=true --property print.partition=true 2>/dev/null \
  | awk '{print $1, $2}' | sort -u
```

**原理**：默认分区器用 `murmur2(keyBytes) % numPartitions` 计算目标分区，key 相同 → 字节相同 → 哈希相同 → 分区相同。注意 5 个 key 分到 4 个分区必然有碰撞（示例中 k4、k5 同落 p1），这是正常的——保证的是"同 key 同分区"，不是"不同 key 不同分区"。

如果不带 key（`--property parse.key=false`），Kafka 3.x 使用 **Sticky Partitioner**：先粘住一个分区攒满一批再换下一个，所以你会看到连续若干条集中在同一分区，而不是严格轮询。

**第 2 题 · 查看 CURRENT-OFFSET 与 LAG**

```bash
# 消费 10 条后自动退出（--max-messages 会在退出前提交 offset）
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic key-demo --group demo-group --from-beginning --max-messages 10

# 查看该组状态
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group demo-group
```

输出：

```text
GROUP       TOPIC     PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID  HOST  CLIENT-ID
demo-group  key-demo  0          3               5               2    -            -     -
demo-group  key-demo  1          3               6               3    -            -     -
demo-group  key-demo  2          2               5               3    -            -     -
demo-group  key-demo  3          2               4               2    -            -     -
```

三列的含义务必分清：

| 列 | 含义 |
|---|---|
| `CURRENT-OFFSET` | 该组**已提交**的位点，即"下一条要读的位置" |
| `LOG-END-OFFSET` | 分区的 LEO，即"最新一条消息的下一个位置"，代表数据总量 |
| `LAG` | `LOG-END-OFFSET - CURRENT-OFFSET`，即积压条数 |

四个分区的 LAG 加起来正好是 20 − 10 = 10，符合预期。

`CONSUMER-ID / HOST / CLIENT-ID` 显示为 `-`，说明**当前组内没有活跃成员**（消费者已退出），组处于 `Empty` 状态。可以用下面的命令确认：

```bash
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group demo-group --state
# STATE 列应为 Empty
```

**第 3 题 · 重置到 earliest 并验证重复消费**

```bash
# 1) dry-run：不加 --execute 时只打印将要设置成什么，不真正生效
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group demo-group --topic key-demo \
  --reset-offsets --to-earliest --dry-run
```

```text
GROUP       TOPIC     PARTITION  NEW-OFFSET
demo-group  key-demo  0          0
demo-group  key-demo  1          0
demo-group  key-demo  2          0
demo-group  key-demo  3          0
```

```bash
# 2) 确认无误后 execute
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group demo-group --topic key-demo \
  --reset-offsets --to-earliest --execute

# 3) 再查，LAG 应该回到 20（等于 LOG-END-OFFSET 之和）
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group demo-group

# 4) 用同一个 group 重新消费，20 条全部重放
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic key-demo --group demo-group --max-messages 20
```

注意第 4 步**没有加 `--from-beginning`** 却依然读到了全部 20 条——因为 `auto.offset.reset` 只在"组没有已提交 offset"时才生效，这里组的 offset 已经被显式重置为 0，消费者直接按提交的位点读。这也说明：**消费起点由已提交 offset 决定，`--from-beginning` 只是首次消费时的兜底策略。**

**三个必须记住的注意事项：**

1. **重置前必须停掉组内所有消费者。** 组里还有活跃成员时执行会直接报错：

   ```text
   Error: Assignments can only be reset if the group 'demo-group' is inactive,
   but the current state is Stable.
   ```

   这是 Kafka 的保护机制——避免重置和正在运行的消费者提交互相覆盖。

2. **永远先 dry-run。** 生产环境重置到 earliest 意味着把几天的数据全部重放一遍，如果下游没有幂等处理，会造成重复扣款、重复发短信这类事故。

3. **排查数据时不要复用业务 group.id。** 用 `kafka-console-consumer` 时如果不指定 `--group`，Kafka 会自动生成一个随机的 `console-consumer-xxxxx` 组，读完即弃、互不干扰；一旦手滑指定成线上服务的 group，你的调试消费会把线上服务的 offset 顶掉，导致线上漏消费。
</Answer>
