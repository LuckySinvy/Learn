# 存储与日志压实

"Kafka 为什么快"的答案不在网络层，而在存储层：顺序写、PageCache、零拷贝、稀疏索引。理解磁盘上实际发生了什么，也能帮你回答"数据存多久、占多大、怎么清理"这些容量规划问题。

## 1. 磁盘目录结构

每个"分区副本"对应磁盘上一个目录，目录里是一段段 **segment** 文件：

```text
/var/kafka/data/orders-0/            # topic "orders" 的 0 号分区
  00000000000000000000.log           # segment: 消息本体
  00000000000000000000.index         # offset 索引
  00000000000000000000.timeindex     # 时间戳索引
  00000000000005368769.log           # 下一个 segment, 文件名 = 起始 offset
  00000000000005368769.index
  00000000000005368769.timeindex
  leader-epoch-checkpoint            # 第 11 章的 epoch 记录
  partition.metadata
```

- **只有最后一个 segment（active segment）在写入**，其余都是只读的。
- 滚动条件：`log.segment.bytes`（默认 1GB）或 `log.roll.ms`/`log.roll.hours`（默认 7 天），先到先滚。
- 删除过期数据 = 直接删除整个老 segment 文件——这就是 Kafka 清理数据近乎零成本的原因。

## 2. 稀疏索引：按 offset 找消息

`.index` 文件是**稀疏**的：不是每条消息一个条目，而是每写入 `log.index.interval.bytes`（默认 4KB）才记一条：

```text
.index (offset -> 物理位置)          .log
  相对offset  文件位置                 [msg 5368769] pos 0
  0          0                       [msg 5368770] pos 210
  35         4102          ------>   ...
  70         8230                    [msg 5368804] pos 4102
                                     ...
查找 offset=5368790:
  1. 二分定位 segment 文件 (文件名即起始 offset)
  2. 在 .index 里二分找 <= 目标的最大条目 (35 -> 4102)
  3. 从 4102 顺序扫描 .log 找到精确位置
```

稀疏索引把索引体积压到极小（可全部驻留内存），代价是最后一小段顺序扫描——对顺序读写为主的日志系统是完美取舍。`.timeindex` 同理，支撑按时间戳定位（offsetsForTimes、--to-datetime 重置）。

## 3. 为什么快：顺序写 + PageCache + 零拷贝

### 3.1 顺序写

追加写让磁盘免于寻道。机械盘顺序写可达数百 MB/s，与随机写差 3 个数量级；SSD 上顺序写同样对写放大更友好。

### 3.2 PageCache 而非进程内缓存

Kafka **写入只到 PageCache 就返回**（依赖副本机制而非单机 fsync 保证可靠），读取也优先命中 PageCache：

```text
传统做法: 应用堆内缓存 -> GC 压力大, 数据在堆内外复制两份
Kafka:    直接用 OS PageCache
  写: producer -> socket -> broker 写 PageCache (OS 异步刷盘)
  读: 消费不落后时, 直接从 PageCache 返回, 磁盘毫无压力
```

这就是"给 Kafka 机器留一半以上内存给 OS"的原因——那些内存都是缓存。

### 3.3 零拷贝（sendfile）

消费路径上，传统读文件发网络要 4 次拷贝、4 次上下文切换。Kafka 用 `sendfile` 系统调用：

```text
传统:  磁盘 -> 内核缓冲 -> 用户空间 -> socket 缓冲 -> 网卡   (4 次拷贝)
零拷贝: 磁盘 -> 内核缓冲 ----------------------> 网卡        (2 次, 且不经过用户态)
```

注意：开启 SSL 后数据必须进入用户态加解密，零拷贝失效——这是 SSL 集群吞吐下降的重要原因之一。

## 4. 保留策略（cleanup.policy=delete）

默认按时间或大小删除老 segment：

```properties
log.retention.hours=168        # 默认 7 天 (retention.ms 优先级更高)
log.retention.bytes=-1         # 每分区大小上限, 默认不限制
log.retention.check.interval.ms=300000   # 清理线程检查周期
```

- 判定单位是 **segment**：整个 segment 里最新消息也过期了才会删（所以实际保留时间略长于配置）。
- topic 级覆盖：`retention.ms`、`retention.bytes`（用 kafka-configs 动态改，见第 4 章）。
- 容量估算：`每分区磁盘 ≈ 写入速率 × retention 时间 × (1 + 副本数-1)/生产端压缩比`，规划时按峰值算。

## 5. Log Compaction（cleanup.policy=compact）

压实策略保留**每个 key 的最新值**，而不是按时间删除。适合"数据是状态而非事件"的场景：

```text
压实前:
  offset: 0        1        2        3        4        5
  key:    u1       u2       u1       u3       u2       u1
  value:  addr=A   addr=X   addr=B   addr=M   null     addr=C

压实后:
  offset: 3        5
  key:    u3       u1
  value:  addr=M   addr=C
  (u2 最新值是 null 墓碑 -> 整个 key 被删除)
```

规则与要点：

- 消息**必须有 key**，无 key 消息发到 compact topic 会报错。
- value=null 是**墓碑（tombstone）**，表示删除该 key；墓碑本身在 `delete.retention.ms`（默认 24h）后清除。
- 压实只处理"干净段"之外的部分，active segment 永不压实，所以**近期数据总是完整的**。
- offset 不会重排：压实后 offset 不连续是正常现象，消费逻辑不能假设 offset 连续。
- 触发时机由 `min.cleanable.dirty.ratio`（默认 0.5，脏数据过半才清）与 `log.cleaner.threads` 控制。

典型用途：

| 场景 | 说明 |
|---|---|
| __consumer_offsets | Kafka 自己用 compact 存消费进度 |
| 数据库变更流（CDC） | 每个主键只需最新镜像 |
| Kafka Streams 的 changelog | 状态存储的备份，恢复时只需最新状态 |
| 配置/字典分发 | 新消费者从头读一遍即得全量最新配置 |

```bash
# 创建 compact topic
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic user-profiles --partitions 6 --replication-factor 3 \
  --config cleanup.policy=compact \
  --config min.cleanable.dirty.ratio=0.2
# 也可以组合: 既压实又按时间删
#   --config cleanup.policy=compact,delete --config retention.ms=2592000000
```

<Callout type="warn" title="常见误区">
1. **把 compact 当去重**：压实是后台异步的，消费者完全可能读到同一 key 的多个历史版本，业务端仍需按"后读覆盖先读"处理。
2. **retention.ms 设太短**：消费者积压超过保留时间，数据被删，LAG 永远追不回来且静默丢数据。保留时间至少要覆盖"最长可能的消费中断 + 修复时间"。
3. **误以为 flush 了才安全**：Kafka 默认不主动 fsync（log.flush 参数别乱动），可靠性来自多副本。单副本 topic 掉电就可能丢数据，与 acks 无关。
</Callout>

<Callout type="tip" title="快速估算某 topic 的磁盘占用">
用 kafka-log-dirs 工具直接查：`bin/kafka-log-dirs.sh --bootstrap-server localhost:9092 --describe --topic-list orders`，输出每个分区副本的字节数，比去机器上 du 方便得多。
</Callout>

## 小结

- 分区 = 一串 segment 文件；只写 active segment，过期删除以 segment 为单位
- 稀疏 offset/时间索引 + 二分定位 + 短距顺序扫描，索引小到可常驻内存
- 快的三大支柱：顺序写、PageCache（内存留给 OS）、sendfile 零拷贝（SSL 会失效）
- delete 策略按时间/大小删段；compact 策略按 key 留最新值，null 为墓碑
- compact 不等于实时去重；retention 必须覆盖最长消费中断时间

ls -lh /tmp/kraft-combined-logs/seg-demo-0/

-rw-r--r--  10M  00000000000000000000.index
-rw-r--r--  1.0M 00000000000000000000.log
-rw-r--r--  10M  00000000000000000000.timeindex
-rw-r--r--  10M  00000000000000001021.index

-rw-r--r--  1.0M 00000000000000002042.log
-rw-r--r--  10M  00000000000000002042.timeindex
-rw-r--r--  10M  00000000000000004084.index      <- active segment
-rw-r--r--  356K 00000000000000004084.log        <- 还没写满
-rw-r--r--  10M  00000000000000004084.timeindex
-rw-r--r--  8    leader-epoch-checkpoint
-rw-r--r--  43   partition.metadata

**命名规律**：文件名是该 segment 中**第一条消息的 offset**，左侧补零到 20 位。所以 `00000000000000001021.log` 表示"这个段从 offset 1021 开始"。

三类文件的分工：

| 后缀 | 内容 |
|---|---|
| `.log` | 实际消息数据，追加写 |
| `.index` | offset → 文件物理位置的**稀疏索引** |
| `.timeindex` | 时间戳 → offset 的稀疏索引，供 `offsetsForTimes` 使用 |

**为什么用起始 offset 命名**：查找 offset=1500 的消息时，Kafka 对文件名做**二分查找**，立刻定位到 `00000000000000001021.log`（1021 ≤ 1500 < 2042），再查该段的 `.index` 找到最近的索引点，最后顺序扫描少量数据。整个过程是 `O(log n)` 定位 + 短距顺序读，这就是为什么 Kafka 在 TB 级数据上按 offset 查找依然极快。

**索引文件为什么显示 10MB**：这是 `log.index.size.max.bytes` 预分配的大小（稀疏文件，实际占用远小于此），段关闭时会被裁剪到真实大小。

用官方工具可以直接查看内容：

```bash
# 看消息
bin/kafka-dump-log.sh --files /tmp/kraft-combined-logs/seg-demo-0/00000000000000000000.log \
  --print-data-log | head -20

# 看索引（能直观看到"稀疏"：不是每条消息都有索引项）
bin/kafka-dump-log.sh --files /tmp/kraft-combined-logs/seg-demo-0/00000000000000000000.index
```

```text
offset: 0     position: 0
offset: 42    position: 4128       <- 每约 4KB 才建一个索引项
offset: 84    position: 8256
```

索引稀疏度由 `log.index.interval.bytes`（默认 4096）控制。稀疏是刻意为之——索引足够小可以常驻内存，代价只是定位后多扫几 KB。

**segment 滚动的四个触发条件**（满足任一即滚动）：

| 配置 | 默认 | 含义 |
|---|---|---|
| `segment.bytes` | 1GB | 段文件大小上限 |
| `segment.ms` | 7 天 | 段的最长存活时间 |
| `index.interval.bytes` 累积导致索引写满 | - | 索引文件达到 `segment.index.bytes` |
| offset 超出 32 位表示范围 | - | 极少触发 |

**为什么这件事重要**：**删除的最小单位是 segment，而 active segment 永远不会被删除或压实**。如果 `segment.bytes` 设成 1GB 而某个 topic 每天只写 10MB，那么这个段要 100 天才写满，期间 `retention.ms=7天` 完全不起作用——数据会一直堆着不删。这是"明明配了保留 7 天，磁盘却一直涨"的常见原因。解决办法是同时配 `segment.ms` 强制按时间滚动。

**第 2 题 · compact 压实实验**

```bash
# 建 compact topic，参数调到最激进以便快速看到效果
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic compact-demo --partitions 1 --replication-factor 1 \
  --config cleanup.policy=compact \
  --config min.cleanable.dirty.ratio=0.01 \
  --config segment.ms=5000 \
  --config delete.retention.ms=1000 \
  --config max.compaction.lag.ms=5000 \
  --config min.compaction.lag.ms=0
```

```bash
# 写入：u1 的 5 个版本 + u2 的 3 个版本 + u2 的墓碑
printf 'u1:v1\nu1:v2\nu1:v3\nu1:v4\nu1:v5\nu2:a\nu2:b\nu2:c\nu2:\n' | \
  bin/kafka-console-producer.sh --bootstrap-server localhost:9092 \
    --topic compact-demo \
    --property parse.key=true --property key.separator=: \
    --property null.marker=NULL
```

注意：console-producer 里空 value 默认是空字符串而不是 null。要发真正的墓碑，用 `--property null.marker=NULL` 然后写 `u2:NULL`，或者用代码：

```java
producer.send(new ProducerRecord<>("compact-demo", "u2", null));  // 墓碑
```

**压实前**（立即消费）：

```bash
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic compact-demo --from-beginning --timeout-ms 5000 \
  --property print.key=true --property print.offset=true
```

```text
Offset:0  u1  v1
Offset:1  u1  v2
Offset:2  u1  v3
Offset:3  u1  v4
Offset:4  u1  v5
Offset:5  u2  a
Offset:6  u2  b
Offset:7  u2  c
Offset:8  u2  null
```

**触发压实**：需要让消息离开 active segment（active segment 永不压实）。再写几条消息推动段滚动，然后等待 cleaner 线程运行：

```bash
# 推动段滚动
printf 'u3:x\nu4:y\n' | bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic compact-demo \
  --property parse.key=true --property key.separator=:

sleep 30   # 等 log cleaner 工作（log.cleaner.backoff.ms 默认 15s）
```

**压实后**：

```text
Offset:4  u1  v5      <- u1 只剩最新版本，offset 保持原值 4
Offset:9  u3  x
Offset:10 u4  y
                      <- u2 完全消失（墓碑生效后连墓碑一起清除）
```

**四个必须理解的要点：**

1. **offset 不重排、不连续。** 压实后 `u1` 仍在 offset 4，中间的 0、1、2、3 变成了空洞。**消费逻辑绝不能假设 offset 连续**——这是从 compact topic 消费时最容易踩的坑。

2. **墓碑的两阶段生命周期。** `u2:null` 先标记删除，`delete.retention.ms`（默认 24 小时）后墓碑本身才被清除。这个延迟是必需的：要给所有消费者留出足够时间读到"这个 key 被删了"的信号。如果墓碑立刻消失，一个正在追赶的消费者会永远认为 `u2` 还是旧值 `c`。生产环境**不要把 `delete.retention.ms` 调得太小**。

3. **active segment 永不压实。** 所以最近写入的数据总是完整保留所有版本，压实只作用于已关闭的历史段。实验中必须推动段滚动才能看到效果。

4. **压实是异步的、尽力而为的。** 由 `min.cleanable.dirty.ratio`（默认 0.5，脏数据过半才清）触发，`log.cleaner.threads` 控制并发。**这意味着消费者完全可能读到同一 key 的多个历史版本**——compact 绝不等于实时去重，业务端必须按"后读覆盖先读"的语义处理。

**其他约束**：compact topic 的消息**必须有 key**，发送无 key 消息会导致该分区无法被压实（服务端日志报错）。另外可以组合两种策略：

```bash
--config cleanup.policy=compact,delete --config retention.ms=2592000000
# 既按 key 留最新值，又删除超过 30 天的数据（防止无限增长）
```

**第 3 题 · `__consumer_offsets` 为什么用 compact**

```bash
bin/kafka-log-dirs.sh --bootstrap-server localhost:9092 \
  --describe --topic-list __consumer_offsets | \
  python3 -c "
import sys, json
d = json.loads(sys.stdin.read().split('\n')[-2])
total = 0
for b in d['brokers']:
    s = sum(p['size'] for p in b['logDirs'][0]['partitions'])
    total += s
    print(f\"broker {b['broker']}: {s/1024/1024:.2f} MB\")
print(f'总计: {total/1024/1024:.2f} MB')
"
```

或者直接看原始输出：

```bash
bin/kafka-log-dirs.sh --bootstrap-server localhost:9092 \
  --describe --topic-list __consumer_offsets

# 确认它的配置
bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --describe --entity-type topics --entity-name __consumer_offsets
# cleanup.policy=compact, segment.bytes=104857600
```

一个跑了很久的集群，`__consumer_offsets` 通常也只有几十到几百 MB——**尽管它承载的写入量极其巨大**。

**为什么必须用 compact 而不能用 delete：**

先看它的数据模型：

```text
key   = (group.id, topic, partition)      <- 有限的、稳定的实体集合
value = (offset, metadata, timestamp)     <- 频繁变化的状态
```

这是一个典型的**"数据是状态而非事件"**的场景。对于 `(order-service, orders, 0)` 这个 key，我们**只关心它当前的消费位点是多少**，历史上它曾经是 100、200、300 这些中间值毫无价值。

**写入量有多大**：每个消费组、每个分区，默认每 5 秒（`auto.commit.interval.ms`）提交一次。假设集群有 100 个消费组，每组 50 个分区：

```text
100 组 × 50 分区 ÷ 5 秒 = 1000 条/秒
一天 = 8640 万条
一年 = 315 亿条
```

**如果用 delete 策略会怎样：**

| 保留时间设置 | 后果 |
|---|---|
| 设短（如 7 天） | 一个**空置超过 7 天**的消费组，其位点记录被整段删除。重新上线时 offset 丢失，只能按 `auto.offset.reset` 走——`latest` 则跳过所有积压，`earliest` 则全量重刷。**位点是必须长期持有的状态，不能因为"旧"就删掉** |
| 设长（如永久） | 上面算过，一年 315 亿条记录，磁盘无限膨胀。而且 broker 启动时要**加载全部位点到内存**建立缓存，海量历史记录会让启动变得极其缓慢甚至 OOM |

**compact 完美契合这个场景：**

```text
无论一个 (group, topic, partition) 被提交过多少亿次，
压实后磁盘上永远只保留【最新的那一条】。

存储量 ≈ 消费组数 × topic 数 × 分区数  （与提交频率完全无关）
100 组 × 50 分区 × 约 100 字节 ≈ 500 KB
```

**同时它天然支持 broker 的状态恢复**：组协调器启动时，只需从头把 `__consumer_offsets` 完整读一遍，就能重建所有消费组的当前位点——因为每个 key 的最新值就是当前状态。这正是 compact 的核心价值：**日志既是变更流，又是状态快照**。

**顺带解释"消费组下线太久位点会消失"**：这不是 compact 造成的，而是 `offsets.retention.minutes`（默认 7 天）这个独立机制——组变为 Empty 状态超过该时长后，协调器会主动写入**墓碑消息**删除其位点。一个停用两周的服务重新上线时进度已不存在，会按 `auto.offset.reset` 处理。长期停用的组要心里有数。

**同样思路的其他 compact 用途：**

| topic | 为什么用 compact |
|---|---|
| `__transaction_state` | 每个 `transactional.id` 只需最新事务状态 |
| Kafka Streams 的 changelog | 状态存储备份，恢复时只需每个 key 的最新值 |
| CDC 数据库变更流 | 每个主键只需最新镜像，新消费者读一遍即得全量快照 |
| 配置/字典分发 | 消费者从头读完即得全量最新配置 |

**判断口诀**：问自己"这个 key 的历史版本还有价值吗？"——没有价值就用 compact（状态型数据），有价值就用 delete（事件型数据，如订单流水、点击日志）。
