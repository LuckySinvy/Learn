# 副本机制与 ISR

副本机制是 Kafka 可靠性的地基。acks=all 为什么可靠？min.insync.replicas 为什么必须配？leader 切换会不会丢数据？这些问题的答案都藏在 ISR、HW/LEO、Leader Epoch 这三组概念里。这是全课程最"原理"的一章，值得慢慢读。

## 1. Leader / Follower 分工

每个分区的副本分为一个 leader 和若干 follower：

```text
        Producer 写           Consumer 读
             \                 /
              v               v
        +------------------+
        |  Leader (broker1)|   处理全部读写
        +------------------+
          ^              ^
          | Fetch        | Fetch (follower 主动拉, 类似消费者)
  +---------------+  +---------------+
  |Follower(brk2) |  |Follower(brk3) |   只同步, 不服务客户端
  +---------------+  +---------------+
```

- follower 通过 **Fetch 请求主动拉取** leader 的数据（不是 leader 推送）。
- follower 不服务读写（2.4+ 支持就近读 follower 的特例，主要用于跨机房省流量）。
- 副本分布由 controller 决定，同一分区的副本必须在不同 broker。

## 2. ISR：同步副本集合

**ISR（In-Sync Replicas）** = leader + "跟得上"的 follower。判定标准只有一个时间维度：

```properties
replica.lag.time.max.ms=30000
# follower 超过 30 秒没有追上 leader 的最新位置 -> 踢出 ISR (收缩)
# 被踢的 follower 追上后 -> 重新加入 (扩张)
```

被踢出的副本进入 **OSR**（Out-of-Sync Replicas）。ISR 的意义：

- **acks=all 只等 ISR 中的副本确认**，不等 OSR——慢副本不拖累写入。
- `min.insync.replicas=2` 要求 ISR 大小至少为 2，否则拒绝 acks=all 的写入。
- leader 挂掉时，**默认只从 ISR 中选新 leader**——保证新 leader 拥有全部已确认数据。

```text
正常:      ISR = [1(L), 2, 3]        acks=all 等 3 个副本
broker3 卡了 30 秒:
  收缩:    ISR = [1(L), 2]           acks=all 只等 2 个, 写入不受阻
broker2 也挂了:
  收缩:    ISR = [1(L)]              min.insync.replicas=2 -> 拒绝写入!
                                     (宁可不可写, 也不冒丢数据风险)
```

## 3. HW 与 LEO：两个水位

| 概念 | 全称 | 含义 |
|---|---|---|
| LEO | Log End Offset | 每个副本日志末端的下一个写入位置 |
| HW | High Watermark | ISR 中**所有副本都已复制到**的位置 = min(ISR 各副本 LEO) |

```text
          offset:  0   1   2   3   4   5
Leader  日志:     [a] [b] [c] [d] [e]        LEO=5
Follower2 日志:   [a] [b] [c] [d]            LEO=4
Follower3 日志:   [a] [b] [c]                LEO=3

HW = min(5,4,3) = 3
消费者只能读到 offset 0..2 (HW 之前的消息)
offset 3,4 已在 leader 上, 但 "未提交", 不可见
```

两条铁律：

1. **消费者只能读到 HW 之前的消息**。避免读到"可能在 leader 切换后消失"的数据。
2. **acks=all 的成功响应发生在消息进入所有 ISR 副本之后**，即该消息一定低于新的 HW。

这就是"acks=all 已确认的消息，换 leader 也不丢"的数学保证：新 leader 来自 ISR，而 ISR 成员必然拥有 HW 之前的全部消息。

## 4. Leader Epoch：修复截断错误

老版本 Kafka 用 HW 做副本恢复时的日志截断依据，有一个著名缺陷：follower 的 HW 更新总是滞后 leader 一轮 Fetch，故障时机不巧会**把已提交的消息截断掉**，甚至造成副本间数据分歧。

**Leader Epoch** 机制（0.11+）解决了这个问题。每次 leader 变更，epoch 加一，并记录"该 epoch 从哪个 offset 开始"：

```text
epoch 文件:  (epoch=0, startOffset=0)
             (epoch=1, startOffset=120)   <- 第一次切主发生在 offset 120
             (epoch=2, startOffset=345)

follower 重启恢复流程 (新):
  1. 向 leader 发 OffsetsForLeaderEpoch(自己最后的 epoch)
  2. leader 返回该 epoch 的合法结束位置
  3. follower 只截断超出该位置的部分  -- 精确, 不再依赖滞后的 HW
```

效果：即使连续故障切换，副本间也能收敛到一致的日志，不误删已提交数据。这是面试高频题"HW 会导致什么问题、怎么解决"的标准答案。

## 5. unclean.leader.election：可用性与一致性的抉择

如果 ISR 全空（所有同步副本都挂了），只剩 OSR 里落后的副本，怎么办？

```properties
unclean.leader.election.enable=false   # 默认
```

| 取值 | 行为 | 后果 |
|---|---|---|
| false（默认） | 等 ISR 副本活过来 | 分区不可用一段时间，但**不丢已确认数据** |
| true | 让落后的 OSR 副本当 leader | 立刻恢复可用，但落后部分的**已确认消息永久丢失** |

金融、订单类系统坚决保持 false；纯日志、可容忍丢失的场景可以权衡开 true。

## 6. 配置与排查

黄金组合回顾（与第 6 章呼应）：

```properties
# topic 级
replication.factor=3
min.insync.replicas=2
# producer 级
acks=all
enable.idempotence=true
```

这个组合的容错边界：**挂任意 1 台 broker，不丢数据、不停服务**；挂 2 台时拒绝写入（保数据不保可用）。

排查命令：

```bash
# 查看 ISR 状态
bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders
# Isr 列少于 Replicas 列 => 有副本掉队

# 全集群找 under-replicated 分区 (ISR < 副本数)
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --under-replicated-partitions

# 找不满足 min.insync.replicas 的分区
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --under-min-isr-partitions
```

<Callout type="warn" title="UnderReplicatedPartitions 是最重要的告警指标">
JMX 指标 kafka.server ReplicaManager UnderReplicatedPartitions 长期大于 0，说明有 follower 持续追不上——可能是磁盘 IO 瓶颈、网络带宽不足或某 broker 过载。它是集群健康的第一哨兵，必须配告警。偶发的短暂非零（重启、流量尖峰）可以接受，持续非零必须处理。
</Callout>

<Callout type="info" title="为什么 Kafka 不用多数派写入">
不同于 Raft 的 quorum 写（3 副本必须写成功 2 个），Kafka 用 ISR 模型：写入等待 ISR 全体确认，而 ISR 大小动态收缩。这让 Kafka 在同样容错能力下只需更少副本（Raft 容忍 1 台故障要 3 副本且每次等 2 个确认；Kafka 3 副本 + min.isr=2 正常时等 3 个、降级时等 2 个）。代价是依赖 controller 维护 ISR 的正确性——这正是元数据用 Raft（KRaft）而数据面用 ISR 的原因：各取所长。
</Callout>

## 小结

- follower 主动 Fetch 拉取同步；ISR = 跟得上的副本集合，按 replica.lag.time.max.ms 判定
- HW = ISR 最小 LEO，消费者只能读 HW 之前；acks=all 确认过的消息必在所有 ISR 副本上
- Leader Epoch 取代 HW 作为截断依据，解决切主丢数据与副本分歧
- unclean 选举默认关闭：宁可短暂不可用，不丢已确认数据
- 黄金组合容错边界：3 副本 + min.isr=2 + acks=all，挂 1 台无感，挂 2 台停写保数据

**参考答案：**

**第 1 题 · 观察 ISR 的收缩与扩张**

```bash
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic isr-watch --partitions 1 --replication-factor 3

bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic isr-watch
# Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
```

开一个终端持续观察，另一个终端做操作：

```bash
# 终端 A：每秒刷新 ISR 状态
watch -n1 'bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --topic isr-watch'

# 终端 B：持续写入，让 LEO 一直增长（这样掉队才看得出来）
while true; do echo "msg-$(date +%s%N)"; sleep 0.1; done | \
  bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic isr-watch

# 终端 C：干掉一个 follower（假设 leader 是 1，那就杀 2）
docker stop kafka2
```

**收缩过程**：

```text
T+0s    Isr: 1,2,3         <- 刚 kill，还没被发现
T+10s   Isr: 1,2,3         <- 仍在容忍窗口内
T+30s   Isr: 1,3           <- broker 2 掉出 ISR
```

从 kill 到 ISR 收缩的延迟由 **`replica.lag.time.max.ms`（默认 30000ms）** 决定：leader 记录每个 follower 最后一次"追上 LEO"的时间，超过这个阈值没追上就把它移出 ISR。

服务端日志会打印：

```text
INFO [Partition isr-watch-0 broker=1] Shrinking ISR from 1,2,3 to 1,3.
     Leader: (highWatermark: 1042, endOffset: 1043).
     Out of sync replicas: (brokerId: 2, endOffset: 1010, ...)
```

**扩张过程**：

```bash
docker start kafka2
```

```text
T+0s    Isr: 1,3           <- broker 2 刚起来，正在追数据
T+8s    Isr: 1,3           <- 还在 catch-up
T+15s   Isr: 1,2,3         <- 追平，重新加入
```

```text
INFO [Partition isr-watch-0 broker=1] Expanding ISR from 1,3 to 1,3,2
```

**恢复耗时取决于落后的数据量**：follower 重启后作为 fetcher 从 leader 批量拉取缺失数据，追平（LEO 达到 leader 的 LEO 且在 `replica.lag.time.max.ms` 内保持跟随）后才重新加入 ISR。停机时间越长、写入速率越高，恢复越慢。可以用 `--time -1` 对比 LEO 的追赶过程。

**这个实验要建立的三个认知：**

1. **Replicas 是静态的，ISR 是动态的。** `Replicas: 1,2,3` 是建 topic 时确定的副本分配，机器挂了也不变；`Isr` 反映的是"此刻谁跟得上"，是实时健康状态。
2. **ISR 收缩不是立即的**，有 `replica.lag.time.max.ms` 的容忍窗口。这个设计是为了容忍 GC、网络抖动等短暂波动，避免 ISR 频繁震荡。
3. **`Isr` 列长度 < `Replicas` 列长度 = under-replicated**，这是集群健康的第一警报。可以用专门的命令全集群扫描：

```bash
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --under-replicated-partitions
```

对应的 JMX 指标 `kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions` **必须配告警**。偶发短暂非零（滚动重启、流量尖峰）可接受，持续非零说明有 follower 长期追不上，要查磁盘 IO、网络带宽或 broker 过载。

**第 2 题 · acks=all 被拒绝而 acks=1 仍能写入**

```bash
bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --alter --entity-type topics --entity-name isr-watch \
  --add-config min.insync.replicas=2

# 杀掉两个，只剩 leader
docker stop kafka2 kafka3
sleep 35
bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic isr-watch
# Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1        <- ISR 只剩 1
```

对照实验：

```bash
# acks=all -> 被拒绝
echo "with-acks-all" | bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic isr-watch --request-required-acks all
```

```text
ERROR Error when sending message to topic isr-watch with key: null, value: 13 bytes
org.apache.kafka.common.errors.NotEnoughReplicasException: Messages are rejected
since there are fewer in-sync replicas than required.
```

```bash
# acks=1 -> 写入成功，毫无提示
echo "with-acks-1" | bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic isr-watch --request-required-acks 1
# 静默成功
```

**为什么 acks=1 危险——这是本章最需要理解透的一点：**

```text
acks=1 的语义：leader 把消息写进自己的本地日志（PageCache）就返回成功
              ↑ 不等任何 follower，甚至不等 fsync 到磁盘

此刻 ISR 只有 leader 一个，也就是说：
  这条消息在【全世界只有一份副本】，还躺在内存的 PageCache 里

如果 broker 1 现在宕机（进程崩溃 / 断电 / 磁盘损坏）：
  - 断电：PageCache 里未落盘的数据直接消失
  - 磁盘损坏：数据永久丢失，且没有任何副本可恢复
  - 而 Producer 早已收到 "成功" 响应，业务侧认为消息已可靠送达
  => 【静默丢失】：数据没了，但没有任何人知道
```

`min.insync.replicas` **只对 `acks=all` 生效**，这是一个极其常见的误解。它的检查逻辑是"当 `acks=all` 时，若 ISR 大小 < `min.insync.replicas` 则拒绝写入"。配了 `acks=0` 或 `acks=1` 的 Producer 完全绕过这道门槛。

**两种失败模式的本质区别：**

| 配置 | ISR 只剩 1 时的行为 | 性质 |
|---|---|---|
| `acks=all` + `min.isr=2` | 抛 `NotEnoughReplicasException` | **显式失败**：上游能感知，可重试、可降级、可告警 |
| `acks=1` | 静默成功 | **隐性风险**：出事时才发现，且无法追溯丢了什么 |

工程上，**显式失败永远优于静默成功**。失败了业务可以重试、可以写降级队列、可以报警人工介入；静默丢失则是在事故发生后才被发现，而且往往无从查起丢了哪些数据。

**还有一个更隐蔽的坑**：`acks=all` 单独使用而**不配** `min.insync.replicas`（默认值是 1）时，ISR 缩到 1 后 `acks=all` 会**静默退化成 `acks=1`**——你以为配了最高可靠性，实际和 `acks=1` 没区别，而且完全无感知。所以这两个参数**必须成对出现**。

**正确的组合与容错边界：**

```properties
# topic 级
replication.factor=3
min.insync.replicas=2
# producer 级
acks=all
enable.idempotence=true
```

```text
挂 0 台：正常，ISR=3，写入等 3 个确认
挂 1 台：ISR=2 ≥ min.isr=2，写入正常，不丢数据    <- 关键的容错能力
挂 2 台：ISR=1 < min.isr=2，拒绝写入（保数据不保可用）
```

**为什么不用 3 副本 + min.isr=3**：那样任意一台机器重启（哪怕是计划内的滚动升级）都会让 topic 不可写。`3 + 2` 是可用性与可靠性的最佳平衡点。

**第 3 题 · HW=10、LEO=12 时 leader 宕机**

先画出宕机前的状态：

```text
                LEO   HW    说明
  Leader   B1   12    10    offset 10、11 只有 leader 有，follower 还没拉走
  Follower B2   10    10
  Follower B3   10    10

日志内容：
  B1: [0..9][10][11]     <- 10、11 是"已写入但未提交"的消息
  B2: [0..9]
  B3: [0..9]

HW = ISR 中最小的 LEO = min(12, 10, 10) = 10
消费者只能读到 offset 0..9（HW 之前的才算已提交、才可见）
```

**B1 宕机后：**

```text
1. Controller 从 ISR 中选出新 leader，假设是 B2
2. B2 的 LEO = 10，成为新 leader，新 HW = 10
3. offset 10、11 在新 leader 上【根本不存在】—— 消息丢失

  Leader   B2   10    10    [0..9]
  Follower B3   10    10    [0..9]

4. B1 重启回归后作为 follower，发现自己的日志比 leader 长：
   - 老机制：按 HW 截断
   - 新机制（0.11+）：发 OffsetsForLeaderEpoch 请求，leader 告知
     旧 epoch 的合法结束位置是 10，B1 精确截断掉 10、11
  Follower B1   10    10    [0..9]     <- 10、11 被彻底丢弃
```

**offset 10、11 的最终命运：被截断丢弃，永久消失。**

**关键在于：Producer 端会不会知道？** 这完全取决于 acks 配置：

| Producer 配置 | 结果 | 是否静默 |
|---|---|---|
| `acks=0` | 早就返回成功了，消息丢了毫不知情 | **静默丢失** |
| `acks=1` | leader 写完本地就返回成功，消息丢了也不知情 | **静默丢失** |
| `acks=all` + `min.isr=2` | **根本不会返回成功**——因为要等 ISR 全体确认，而 B2、B3 从未确认过 10、11。Producer 侧表现为超时或异常，并自动重试到新 leader | **显式失败，不丢** |

**这就是本题的核心结论**：`acks=all` 的真正含义是 **"等到 ISR 中所有副本都拿到这条消息（即 HW 推进到它之后）才返回成功"**。换句话说，**Producer 收到成功响应的消息，一定已经存在于当时所有 ISR 副本上，因此任何一个 ISR 副本当选新 leader 都不会丢它。** 而 offset 10、11 这种"只在 leader 上、HW 还没推进过去"的消息，Producer 从来没收到过成功响应，所以它会重试——重试到新 leader 上，消息以新的 offset 重新写入，业务上没有丢失。

**保证不静默丢失的完整配置：**

```properties
# Producer 端
acks=all
enable.idempotence=true        # 3.x 默认开启；防止重试造成重复与乱序
retries=2147483647             # 幂等开启时的默认值
delivery.timeout.ms=120000     # send() 到最终成败的总时限
max.in.flight.requests.per.connection=5   # 幂等下 <=5 均可保序
```

```properties
# topic 端
replication.factor=3
min.insync.replicas=2
unclean.leader.election.enable=false
```

其中 `enable.idempotence=true` 在这个场景下尤为重要：重试会导致同一条消息被写入两次（第一次写到了老 leader 但没提交，重试写到新 leader），幂等机制用 PID + 序列号在 broker 侧去重，避免重复。

**`unclean.leader.election.enable=false` 的作用**在这里也值得强调：如果它是 `true`，当 ISR 全空时 Kafka 会让 OSR 中一个严重落后的副本（比如 LEO 只有 5）当 leader，那么 offset 5..9 这些**已经被 `acks=all` 确认过的消息也会丢失**——这是比本题严重得多的数据丢失。默认 `false` 意味着 Kafka 宁可让分区暂时不可用，也不牺牲已确认的数据。金融、订单类系统必须保持 `false`。

**最后补充 HW 与 Leader Epoch 的关系**：老版本用 HW 做截断依据存在缺陷——follower 的 HW 更新总是滞后 leader 一轮 Fetch，连续故障切换时可能把已提交消息也截断掉，甚至造成副本间数据分歧。Leader Epoch 机制通过记录"每个 epoch 从哪个 offset 开始"，让 follower 能向 leader 精确查询"我这个 epoch 的合法结束位置在哪"，从而只截断真正多余的部分。本题第 4 步用的就是这个新机制。
