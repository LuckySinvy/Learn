# Cluster：16384 槽的数据分片

哨兵架构里所有数据仍在一台主库上——内存超过单机、写 QPS 超过单主时就到头了。Redis Cluster 把数据**分片**到多个主库：每个主库负责一部分数据，各配从库做故障转移，容量与写吞吐都能水平扩展。

## 1. 哈希槽：数据怎么分

Cluster 把整个键空间划分为 **16384 个槽（slot）**，每个 key 通过 CRC16 映射到一个槽，每个主节点负责一段槽区间：

```text
slot = CRC16(key) mod 16384

+-----------------+  +-----------------+  +------------------+
| 节点 A           |  | 节点 B          |  | 节点 C            |
| slots 0~5460    |  | slots 5461~10922|  | slots 10923~16383|
|   + 从节点 A1    |  |   + 从节点 B1    |  |   + 从节点 C1     |
+-----------------+  +-----------------+  +------------------+

key "user:1001" -> CRC16 -> slot 8123 -> 节点 B
```

为什么引入"槽"这个中间层，而不是直接 `hash(key) mod 节点数`？因为**节点数会变**。直接取模时加一台机器，几乎所有 key 的归属都变了，等于全量迁移。有了槽，扩容只需要把**一部分槽**（连同槽里的 key）搬到新节点，其余数据纹丝不动。

为什么是 16384 而不是 65536？节点间心跳包里要携带自己负责的槽位图，16384 bit = 2 KB，65536 bit = 8 KB——心跳是高频消息，作者选择了够用且更省带宽的值（官方建议集群不超过 1000 节点，16384 个槽足够分）。



## 3. MOVED 与 ASK 重定向

Cluster 的客户端路由是"去中心化"的：任何节点都能告诉你 key 在哪。

### 3.1 MOVED：槽不归我管

```bash
# 不带 -c 连接节点 A, 访问属于节点 B 的 key:
127.0.0.1:7001> GET user:1001
(error) MOVED 8123 10.0.0.2:7002
# 带 -c 时客户端自动跳转:
127.0.0.1:7001> GET user:1001
-> Redirected to slot [8123] located at 10.0.0.2:7002
"Ada"
```

MOVED 表示"槽 8123 **永久**归 7002 管"。智能客户端（Jedis/Lettuce/redis-py-cluster）收到后会更新本地的"槽到节点"映射表，后续同槽请求直达正确节点，不再多跳。

### 3.2 ASK：槽正在搬家

槽迁移进行到一半时，槽里的 key 一部分在源节点、一部分已到目标节点：

```text
slot 8123 迁移中: 源节点 B (MIGRATING) -> 目标节点 D (IMPORTING)

客户端 GET k1 -> 节点 B:
  ├─ k1 还在 B  -> 正常返回
  └─ k1 已搬走  -> (error) ASK 8123 10.0.0.4:7007
       客户端 -> 节点 D: 先发 ASKING, 再 GET k1

ASK  = 临时重定向, 只对本次请求有效, 不更新槽映射
MOVED = 永久重定向, 更新槽映射
```

迁移完成后源节点开始对该槽返回 MOVED，客户端更新映射，世界恢复平静。

## 4. hash tag 与跨槽限制

### 4.1 多 key 命令的限制

MSET、SINTERSTORE、事务、Lua 脚本里的多个 key，**必须落在同一个槽**，否则报错：

```bash
127.0.0.1:7001> MSET user:1 a user:2 b
(error) CROSSSLOT Keys in request don't hash to the same slot
```

### 4.2 hash tag：把相关 key 钉进同一个槽

key 中出现花括号时，**只有花括号内的部分**参与 CRC16 计算。把用户相关的 key 都写成 `user:{1001}:xxx` 的形式：

```bash
127.0.0.1:7001> MSET {user:1001}:name Ada {user:1001}:age 30
OK                      # 两个 key 的 hash tag 都是 user:1001, 同槽, 成功
127.0.0.1:7001> EVAL "return redis.call('GET', KEYS[1])" 1 {user:1001}:name
"Ada"                   # 同理, Lua 多 key 也能用
```

代价是数据倾斜风险：所有 `{hot}` 前缀的 key 都挤在一个槽、一个节点。hash tag 只用于**确实需要原子多 key 操作**的一小撮 key，别全库滥用。

其他限制：Cluster 只支持 0 号库（SELECT 无效）；Pub/Sub 建议用分片版 SSUBSCRIBE（第 13 章）；KEYS/SCAN 只扫当前节点，全集群遍历要逐节点执行。

## 5. 故障转移

Cluster 内置了类似哨兵的机制，不需要单独部署哨兵：

```text
1. 节点间通过 gossip 协议交换状态 (PING/PONG 心跳)
2. 主节点 B 失联超过 cluster-node-timeout -> 标记 PFAIL (疑似下线)
3. 多数主节点都认为 B PFAIL -> 升级为 FAIL (确定下线), 广播
4. B 的从节点发起选举, 由其余主节点投票 (每纪元一票, 多数当选)
5. 当选从节点执行切换: 接管 B 的槽, 广播自己成为新主
```

注意：**多数主节点存活**是集群运作的前提。3 主集群同时挂 2 个主（且从库也没顶上）时，整个集群拒绝服务（`cluster_state:fail`）。默认 `cluster-require-full-coverage yes` 时，任何槽无人负责都会让全集群停止服务，可按业务改为 no（缺槽部分报错，其余照常）。

## 6. 扩容与缩容

### 6.1 扩容：加节点 + 迁槽

```bash
# 1. 新主节点加入集群
$ redis-cli --cluster add-node 10.0.0.4:7007 10.0.0.1:7001
# 2. 从现有节点匀一些槽过去（交互式选择迁多少、从谁迁）
$ redis-cli --cluster reshard 10.0.0.1:7001
How many slots do you want to move? 4096
What is the receiving node ID? <7007 的 node id>
Source node: all
# 3. 给新主配从库
$ redis-cli --cluster add-node 10.0.0.4:7008 10.0.0.1:7001 \
  --cluster-slave --cluster-master-id <7007 的 node id>
```

槽迁移是**在线**的：逐个 key 用 MIGRATE 命令原子搬运，期间靠 ASK 重定向保证读写正确。大 key 会让单次 MIGRATE 阻塞两边节点——又一个要治理大 key 的理由。

### 6.2 缩容：先清空槽再摘节点

```bash
# 1. 把待下线节点的槽全部 reshard 给其他节点
$ redis-cli --cluster reshard 10.0.0.1:7001   # source 填待下线节点
# 2. 摘除节点
$ redis-cli --cluster del-node 10.0.0.1:7001 <待下线 node id>
```

```bash
# 迁移后检查均衡度
$ redis-cli --cluster check 10.0.0.1:7001
$ redis-cli --cluster rebalance 10.0.0.1:7001    # 自动均衡槽分布
```

<Callout type="warn" title="Cluster 不是银弹">
上 Cluster 前想清楚：1）多 key 原子操作要 hash tag 迁就；2）Lua/事务受同槽限制，很多单机玩法失效；3）客户端、监控、运维复杂度全面上升；4）它仍是异步复制，故障转移仍可能丢尾部写入。**数据量与吞吐没到单机瓶颈时，主从 + 哨兵是更省心的选择。**
</Callout>

## 小结

- 16384 个槽是 key 与节点之间的间接层，扩缩容只搬槽不重分布全量数据
- MOVED 永久重定向（更新路由表），ASK 临时重定向（迁移中）
- 多 key 命令须同槽，hash tag `{...}` 定向控制槽位，慎防倾斜
- 故障转移内置：gossip 探测 + 多数主投票 + 从库接管槽
- 下一章回到应用层：分布式锁 →

**核心区别**：

| | 不带 `-c` | 带 `-c` |
|---|---|---|
| 收到 MOVED | 原样打印错误，**命令失败** | 自动连到目标节点重试 |
| 连接行为 | 始终连着原节点 | **切换到目标节点**（提示符会变） |
| 使用场景 | 运维排查、只操作本节点数据 | 日常使用 |

**重要认知：MOVED 不是"服务端帮你转发"，而是"服务端告诉你走错了"。** Redis Cluster 采用**客户端直连 + 重定向纠错**的架构，没有代理层。真正的重定向工作由客户端完成。

**redis-cli 的 `-c` 是"笨"实现**：每次收到 MOVED 才重连一次，多一个 RTT。而生产级客户端（JedisCluster、Lettuce、go-redis 的 ClusterClient）会**在启动时拉取完整的槽映射表并缓存在本地**，之后直接把命令发到正确的节点，**零重定向开销**。只有在集群拓扑变更（扩缩容、故障转移）时才会收到 MOVED，此时客户端顺便刷新本地路由表。

```bash
# 客户端启动时会执行这个命令获取路由表
$ redis-cli -p 7001 CLUSTER SLOTS
1) 1) (integer) 0
   2) (integer) 5460
   3) 1) "127.0.0.1"
      2) (integer) 7001
   4) 1) "127.0.0.1"          # 从节点信息
      2) (integer) 7005
...

# Redis 7 推荐用信息更丰富的 CLUSTER SHARDS
$ redis-cli -p 7001 CLUSTER SHARDS
```

**MOVED 与 ASK 的区别（面试高频）**：

| | MOVED | ASK |
|---|---|---|
| 含义 | 槽**已经**归属别的节点 | 槽**正在迁移中**，这个 key 已经过去了 |
| 持续性 | **永久** | **临时**，仅针对这一次请求 |
| 客户端动作 | **更新本地路由表** | **不更新**路由表，只这一次跳过去 |
| 前置命令 | 无 | 必须先发 `ASKING` |

```bash
# 迁移中访问某个 key 的完整流程：
#   1. 客户端 → 源节点：GET foo
#   2. 源节点检查：槽在迁移中，且 foo 已经不在本地了
#   3. 源节点 → 客户端：ASK 12182 127.0.0.1:7004
#   4. 客户端 → 目标节点：ASKING
#   5. 客户端 → 目标节点：GET foo
#   6. 目标节点返回结果
#
# 为什么需要 ASKING？
#   目标节点还没正式拥有这个槽，直接请求会被它用 MOVED 打回去，
#   造成客户端在两个节点之间无限跳转。ASKING 相当于说
#   "我知道你还没接管，但源节点让我来的，这一次请你破例处理"
```

**2. CLUSTER KEYSLOT 验证 hash tag**

```bash
$ redis-cli -p 7001 CLUSTER KEYSLOT "user:1001"
(integer) 5474

$ redis-cli -p 7001 CLUSTER KEYSLOT "{user:1001}:name"
(integer) 5474                    # 与上面【相同】

$ redis-cli -p 7001 CLUSTER KEYSLOT "{user:1001}:cart"
(integer) 5474                    # 也【相同】

# 对照：不加 hash tag 的话会散开
$ redis-cli -p 7001 CLUSTER KEYSLOT "user:1001:name"
(integer) 14039                   # 完全不同的槽
$ redis-cli -p 7001 CLUSTER KEYSLOT "user:1001:cart"
(integer) 2887                    # 又是另一个槽
```

（具体槽号以你本机执行结果为准，关键在于**前三者相同、后两者各不相同**。）

**回答三个问题**：

- **`user:1001` 与 `{user:1001}:name`：槽相同。** 前者不含花括号，对整个 key 算 CRC16；后者含花括号，只对花括号内的 `user:1001` 算 CRC16。两次计算的输入字符串完全一致，结果自然相同。
- **`{user:1001}:cart`：槽同样相同。** 理由一样——花括号内的内容还是 `user:1001`。

**槽计算规则**：

```bash
# slot = CRC16(hash_key) mod 16384
#
# hash_key 的确定规则（按顺序判断）：
#   1. 找第一个 '{'
#   2. 从它之后找第一个 '}'
#   3. 如果两者都存在，且【中间内容非空】
#        → hash_key = 花括号之间的内容
#      否则
#        → hash_key = 整个 key
```

**边界情况**：

```bash
$ redis-cli -p 7001 CLUSTER KEYSLOT "{}user:1001"
# 花括号内为空 → 规则不生效，对整个字符串 "{}user:1001" 计算

$ redis-cli -p 7001 CLUSTER KEYSLOT "{user}:{1001}"
# 只认【第一对】有效花括号 → hash_key = "user"，第二对被当普通字符

$ redis-cli -p 7001 CLUSTER KEYSLOT "{user:1001"
# 只有左括号没有右括号 → 规则不生效，对整个字符串计算

$ redis-cli -p 7001 CLUSTER KEYSLOT "a{b}c{d}e"
# hash_key = "b"
```

**hash tag 的用途：让相关的 key 落在同一节点，从而支持多 key 操作。**

```bash
# ---- 不加 hash tag：多 key 命令报错 ----
127.0.0.1:7001> MGET user:1001:name user:1001:age
(error) CROSSSLOT Keys in request don't hash to the same slot

127.0.0.1:7001> SINTERSTORE dst user:1001:tags user:1002:tags
(error) CROSSSLOT Keys in request don't hash to the same slot

# ---- 加了 hash tag：正常工作 ----
127.0.0.1:7001> MSET {user:1001}:name "Tom" {user:1001}:age "28"
-> Redirected to slot [5474] located at 127.0.0.1:7002
OK
127.0.0.1:7002> MGET {user:1001}:name {user:1001}:age
1) "Tom"
2) "28"

# ---- 事务和 Lua 同样受此约束 ----
127.0.0.1:7002> EVAL "return redis.call('GET', KEYS[1]) .. redis.call('GET', KEYS[2])" 2 {user:1001}:name {user:1001}:age
"Tom28"
```

**必须警惕数据倾斜（hash tag 的最大陷阱）**：

```bash
# 灾难性用法：把所有 key 塞进同一个 tag
# {global}:user:1  {global}:user:2  ...  {global}:user:10000000
#
# 后果：
#   - 全部落在同一个槽 → 同一个节点
#   - 该节点内存爆掉，其他节点闲置
#   - 分片完全失效，集群退化成单机
#   - 这个槽无法拆分，扩容也救不了
```

**正确用法：tag 的粒度要小、数量要多。**

```bash
# ✓ 按用户 ID：几百万个不同的 tag，天然分散
{user:1001}:profile   {user:1001}:cart   {user:1001}:orders

# ✓ 按订单 ID
{order:20260802001}:items   {order:20260802001}:payment

# ✗ 按业务模块：只有几个 tag，严重倾斜
{cart}:u1001   {cart}:u1002   ...   # 全部挤在一个槽

# ✗ 按城市：城市数量有限，且大城市数据量远超小城市
{beijing}:shop:1   {beijing}:shop:2  ...
```

**检查倾斜情况**：

```bash
# 查看各节点的 key 数量分布
$ redis-cli --cluster call 127.0.0.1:7001 DBSIZE

# 找出最大的槽（Redis 7 的 --cluster-only-masters 更方便）
$ redis-cli -p 7001 --cluster check 127.0.0.1:7001

# 查看某个槽有多少 key
$ redis-cli -p 7002 CLUSTER COUNTKEYSINSLOT 5474
(integer) 3

# 列出某个槽里的 key
$ redis-cli -p 7002 CLUSTER GETKEYSINSLOT 5474 10
1) "user:1001"
2) "{user:1001}:name"
3) "{user:1001}:age"
```

**3. 扩容演练：加入第 4 个主节点并迁移 4096 个槽**


**在另一个终端启动持续读写，用于验证业务无感**：

```bash
# 持续写入并校验（迁移期间一直跑着）
while true; do
  n=$((RANDOM % 100000))
  redis-cli -c -p 7001 SET "mig:test:$n" "value-$n" > /dev/null
  v=$(redis-cli -c -p 7001 GET "mig:test:$n")
  if [ "$v" != "value-$n" ]; then
    echo "$(date +%T) 数据不一致! key=mig:test:$n got=$v"
  fi
  sleep 0.01
done

# 或者用 redis-benchmark 施加持续压力
redis-benchmark --cluster -h 127.0.0.1 -p 7001 -t set,get -n 1000000 -c 50
```

**执行 reshard 迁移 4096 个槽**：

**为什么业务无感？** 上面那个 while 循环全程不会打印任何"数据不一致"。原因是**每个槽的迁移都是原子切换**的，Redis 用一套精细的协议保证了迁移期间的正确性：

```bash
# 单个槽的迁移流程：
#   1. 目标节点：CLUSTER SETSLOT <slot> IMPORTING <源节点ID>
#   2. 源节点：  CLUSTER SETSLOT <slot> MIGRATING <目标节点ID>
#   3. 循环：源节点 CLUSTER GETKEYSINSLOT 取一批 key
#            → MIGRATE 命令逐批搬到目标节点（原子的"删源+写目标"）
#   4. 搬完后，两个节点都执行：CLUSTER SETSLOT <slot> NODE <目标节点ID>
#   5. 通过 gossip 协议扩散给全集群
#
# 迁移期间访问这个槽的 key：
#   - key 还在源节点 → 源节点【正常处理】，客户端毫无感知
#   - key 已搬走     → 源节点返回 ASK，客户端跳到目标节点，多一个 RTT
#   - 新写入的 key   → 源节点仍然接收（它还是槽的所有者），后续会被搬过去
```

**关键点：任何时刻这个槽都有明确的负责人，不存在"两边都不管"或"数据丢失"的窗口。** 客户端最坏只是多一次网络往返。

**扩容的运维注意事项**：

```bash
# 1. 给新主节点配从库，否则它是单点
$ redis-cli --cluster add-node 127.0.0.1:7008 127.0.0.1:7001 \
    --cluster-slave --cluster-master-id f7g8...

# 2. 迁移速度与 key 数量、value 大小相关，避开业务高峰
#    大 key 迁移时 MIGRATE 会【阻塞双方主线程】—— 这是最大的风险点
#    迁移前务必先用 --bigkeys 排查并拆分大 key
$ redis-cli -p 7001 --bigkeys

# 3. 迁移超时（大 key 可能需要调大）
$ redis-cli --cluster reshard ... --cluster-timeout 60000

# 4. 中断后可以恢复
$ redis-cli --cluster fix 127.0.0.1:7001      # 修复处于中间态的槽

# 5. 用 rebalance 自动均衡（比手动算槽数方便）
$ redis-cli --cluster rebalance 127.0.0.1:7001 --cluster-use-empty-masters
```

**缩容的顺序正好相反（容易搞反导致数据丢失）**：

```bash
# 1. 先把槽全部迁走
$ redis-cli --cluster reshard 127.0.0.1:7001 \
    --cluster-from <要删除的节点ID> --cluster-to <接收节点ID> \
    --cluster-slots <该节点的槽数> --cluster-yes

# 2. 确认该节点槽数为 0
$ redis-cli -p 7001 CLUSTER NODES | grep <要删除的节点ID>

# 3. 再删除节点（先删从库，再删主库）
$ redis-cli --cluster del-node 127.0.0.1:7001 <节点ID>

# ⚠️ 顺序反了会怎样：直接 del-node 一个还持有槽的节点，
#    这些槽会变成【无人负责】，cluster_state 变成 fail，整个集群拒绝服务
```

**最后提醒一个 Cluster 的常见误区**：Cluster 模式下**只能使用 0 号数据库**，`SELECT 1` 会直接报错。如果你的代码里用了多 DB 做业务隔离，迁移到 Cluster 前必须先改造成用 key 前缀区分。
