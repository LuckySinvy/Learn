# 主从复制：读写分离与数据冗余

单实例有两个致命问题：挂了服务就停（可用性），盘坏了数据就没（冗余）。主从复制是解决这两个问题的第一步：**主库写，从库实时同步并提供读能力**。它也是后面哨兵和 Cluster 的地基——两者的故障转移本质都是"把某个从库提升为主库"。

## 1. 搭建主从

从库只需一条配置或命令：

```bash
# 方式一: 配置文件
# replica.conf
replicaof 192.168.1.10 6379
masterauth Your_Strong_Pass123     # 主库有密码时需要

# 方式二: 运行时命令（重启失效）
127.0.0.1:6380> REPLICAOF 192.168.1.10 6379
OK
# 取消复制, 恢复为独立主库:
127.0.0.1:6380> REPLICAOF NO ONE
OK
```

验证：

```bash
# 主库视角
127.0.0.1:6379> INFO replication
role:master
connected_slaves:1
slave0:ip=192.168.1.11,port=6380,state=online,offset=4213,lag=0
master_repl_offset:4213

# 从库视角
127.0.0.1:6380> INFO replication
role:slave
master_host:192.168.1.10
master_link_status:up
slave_read_only:1
slave_repl_offset:4213      # 与主库 offset 一致 = 无延迟
```

## 2. 同步机制：全量与部分重同步

### 2.1 首次连接：全量同步

```text
从库                                主库
 |--- PSYNC ? -1 ------------------->|   (第一次, 不知道任何上下文)
 |<-- +FULLRESYNC replid offset -----|   (主库: 做全量吧)
 |                                   |-- BGSAVE 生成 RDB
 |<-- RDB 文件 ----------------------|   (期间新写命令暂存 replication buffer)
 |-- 清空自身, 加载 RDB               |
 |<-- 缓冲的增量命令 -----------------|
 |<== 此后持续接收写命令流 ===========|   (命令传播阶段)
```

全量同步很昂贵：主库 fork + 生成 RDB + 网络传输，从库清空 + 加载。10 GB 的实例做一次全量同步，网络和磁盘都要抖一阵。

### 2.2 断线重连：部分重同步与 repl_backlog

从库断线几秒重连，重新全量太浪费。主库维护一个**环形缓冲区** `repl_backlog`（默认 1 MB），记录最近的写命令流：

```text
repl_backlog（环形, 固定大小, 新数据覆盖最老数据）:

        写入位置(master_repl_offset)
              |
   +----------v-----------+
   |  ...旧命令 | 新命令... |
   +----------------------+
        ^
   从库断线时的 offset

重连: PSYNC replid offset
  ├─ offset 还在 backlog 范围内 -> +CONTINUE, 只补发缺的命令 (部分重同步)
  └─ offset 已被覆盖 / replid 不匹配 -> +FULLRESYNC, 重来全量
```

关键配置：

```conf
repl-backlog-size 64mb        # 默认 1mb 太小! 按"断线时长 × 写入速率"估算
repl-backlog-ttl 3600         # 无从库连接后 backlog 保留时间
```

写入 1 MB/s 的主库，默认 backlog 只够 1 秒的断线容忍——网络闪断 5 秒就得全量重来。**调大 backlog 是主从架构第一个该动的参数**。

replid 是主库的"血统标识"：从库晋升为新主库后会换 replid，但保留旧 replid（replid2），让其他从库在故障转移后仍可能走部分重同步。

### 2.3 无盘复制

主库磁盘慢时，可以不落盘直接把 RDB 写进 socket：

```conf
repl-diskless-sync yes           # 7.x 默认开启
repl-diskless-sync-delay 5       # 等 5 秒攒多个从库一起同步
```

## 3. 从库只读与读写分离

```conf
replica-read-only yes    # 默认: 从库拒绝写命令
```

```bash
127.0.0.1:6380> SET k v
(error) READONLY You can't write against a read only replica.
```

**不要**把从库改成可写：写入的数据不会同步回主库，且下次全量同步会被清掉，纯粹制造数据不一致。读写分离的正确姿势是应用层（或客户端库/代理）把读请求路由到从库：

```text
            写                      读
  应用 ------------> 主库   应用 ---------> 从库1
                      |            \------> 从库2
                      +--复制流--> 从库1, 从库2
```

## 4. 复制延迟与一致性

Redis 复制是**异步**的：主库执行完写命令立即返回客户端，然后才把命令传播给从库。这意味着：

### 4.1 读到旧数据

```text
t0: 客户端 SET x 2 -> 主库返回 OK（此时从库还是 x=1）
t1: 客户端从从库 GET x -> 得到 1   <- 写后读不一致
t2: 复制流到达, 从库 x=2
```

正常情况下延迟是毫秒级，但这些场景会放大：从库执行慢查询阻塞了复制流应用、主库写入洪峰、网络拥塞、从库正在加载全量 RDB。监控指标：

```bash
127.0.0.1:6379> INFO replication
master_repl_offset:100230
slave0:...,offset=100180,lag=0     # 主从 offset 差 = 积压字节数
```

应对策略按业务分级：

- 能容忍（商品详情、文章内容）：直接读从库；
- 写后立即读自己的数据（发帖后跳详情页）：**读主库**，或会话粘滞（该用户短时间内读主库）；
- 完全不能容忍：这个数据别用读写分离。

### 4.2 主库可以要求"最少从库在线"

```conf
min-replicas-to-write 1       # 至少 1 个从库
min-replicas-max-lag 10       # 且延迟不超过 10 秒, 否则主库拒绝写入
```

这不是强一致（复制仍是异步的），只是降低"主库裸奔写入然后宕机全丢"的风险窗口。

<Callout type="warn" title="主从切换丢数据是设计内行为">
异步复制决定了：主库宕机瞬间，尚未传播到从库的写入**必然丢失**（哪怕配了 AOF always——那只保住主库本机的盘）。哨兵/Cluster 的故障转移同样如此。Redis 的定位是 AP 系统，需要"不丢一条"的场景请把 Redis 当缓存、把真相放数据库，或用 WAIT 命令确认复制（性能代价大且仍非绝对）。
</Callout>

<Callout type="info" title="复制风暴">
一主多从（如 1 主 8 从）同时断线重连（比如主库机房网络闪断恢复），8 个从库同时请求全量同步，主库要 fork 并传 8 份 RDB，可能直接被打死。缓解：树状复制拓扑（从库再挂从库，从库也能当同步源）、调大 backlog 让重连走部分重同步、repl-diskless-sync-delay 合并同步请求。
</Callout>

## 5. 常用运维检查

```bash
# 从库落后多少
127.0.0.1:6380> INFO replication
master_link_status:up            # down 说明复制断了
slave_repl_offset:100180

# 主库上看所有从库状态与延迟
127.0.0.1:6379> INFO replication

# 复制相关事件都会写日志:
# "Full resync requested by replica"    <- 全量, 该警惕频率
# "Partial resynchronization accepted"  <- 部分, 健康
```

## 小结

- REPLICAOF 一条命令建立复制：首次全量（RDB），断线重连尽量部分重同步（repl_backlog）
- repl-backlog-size 默认 1 MB 远远不够，按写入速率 × 容忍断线时长调大
- 从库保持只读；读写分离在应用层路由，注意写后读一致性问题
- 复制是异步的：主从切换必然可能丢尾部写入，架构设计要接受这个前提

**关于 `replica-read-only`**：

```bash
# 默认开启，强烈建议保持
127.0.0.1:6380> CONFIG GET replica-read-only
1) "replica-read-only"
2) "yes"

# 关掉后从库可写（不要这么做）
127.0.0.1:6380> CONFIG SET replica-read-only no
OK
127.0.0.1:6380> SET local:only "danger"
OK                               # 写成功了，但这是个陷阱
```

关掉只读的三个恶果：

- **数据会被静默覆盖**：从库上写的数据不会同步给主库，而下次主库同步过来同名 key 时会直接覆盖，写入凭空消失
- **全量重同步会清空一切**：从库触发 full resync 时会 `FLUSHALL` 再加载主库 RDB，所有本地写入瞬间蒸发
- **主从数据永久分叉**：故障转移后这个从库升为主库，脏数据就成了"正式数据"，且无从追溯

**关于"写后立刻读"的一致性问题**：

```bash
# 主库写入后，从库需要一小段时间才能收到（异步复制）
# 本机 Docker 环境延迟约 0.1ms，跨机房可能 10~100ms
#
# 危险场景：用户提交表单 → 写主库 → 立刻跳转到详情页 → 读从库 → 读到旧数据
```

应对手段：

```bash
# 方案一：关键读走主库（最简单可靠）
#         "写后立刻读"的场景直接路由到主库，牺牲一点主库压力换正确性

# 方案二：WAIT 命令等待复制完成
127.0.0.1:6379> SET important "value"
OK
127.0.0.1:6379> WAIT 1 100       # 等待至少 1 个从库确认，最多等 100 毫秒
(integer) 1                       # 返回实际确认的从库数

# 注意：WAIT 只保证"从库收到了"，不保证"从库落盘了"，也【不是】强一致
#      返回值小于期望值时业务要自己决定怎么办

# 方案三：会话粘性
#         同一用户写操作后的 N 秒内，所有读都路由到主库

# 方案四：比对复制偏移量
127.0.0.1:6379> INFO replication | grep master_repl_offset
master_repl_offset:1204
127.0.0.1:6380> INFO replication | grep slave_repl_offset
slave_repl_offset:1204            # 相等说明已追平
```

**2. 从库重启后的部分重同步 vs 全量同步**

**实验 A：backlog 足够大 → 部分重同步**

```bash
# ---- 确认 backlog 配置 ----
127.0.0.1:6379> CONFIG GET repl-backlog-size
1) "repl-backlog-size"
2) "33554432"                     # 32 MB

# ---- 关掉从库 ----
$ docker stop redis-replica

# ---- 主库继续写入少量数据（远少于 32MB）----
for i in $(seq 1 1000); do echo "set k$i v$i"; done | redis-cli --pipe

# ---- 30 秒后重启从库 ----
$ docker start redis-replica

# ---- 查看主库日志 ----
$ docker logs redis-master --tail 20
* Replica 172.17.0.3:6379 asks for synchronization
* Partial resynchronization request from 172.17.0.3:6379 accepted.
  Sending 24580 bytes of backlog starting from offset 1205.

# ---- 从库日志 ----
$ docker logs redis-replica --tail 20
* Trying a partial resynchronization (request 8f3ac1e5b2d7...:1205).
* Successful partial resynchronization with master.
* MASTER <-> REPLICA sync: Master accepted a Partial Resynchronization.

# ---- 统计验证 ----
127.0.0.1:6379> INFO stats | grep sync
sync_full:1                       # 只有最初建立时的那 1 次全量
sync_partial_ok:1                 # 部分重同步成功 1 次
sync_partial_err:0
```

**实验 B：backlog 太小 → 退化为全量同步**

```bash
# ---- 把 backlog 调到 16 KB ----
127.0.0.1:6379> CONFIG SET repl-backlog-size 16kb
OK

# ---- 关掉从库 ----
$ docker stop redis-replica

# ---- 灌入远超 16KB 的写入 ----
for i in $(seq 1 100000); do echo "set big:$i $(printf 'x%.0s' {1..100})"; done | redis-cli --pipe

# ---- 重启从库 ----
$ docker start redis-replica

# ---- 主库日志：变成全量了 ----
$ docker logs redis-master --tail 20
* Partial resynchronization not accepted: Requested offset for second replica
  ID was 1205, but I can reply up to 10245780
* Starting BGSAVE for SYNC with target: disk
* Background saving started by pid 47
* Background saving terminated with success
* Synchronization with replica 172.17.0.3:6379 succeeded

# ---- 从库日志 ----
$ docker logs redis-replica --tail 20
* Full resync from master: 8f3ac1e5b2d7...:10245780
* MASTER <-> REPLICA sync: Flushing old data      # 【注意】先清空自己的数据
* MASTER <-> REPLICA sync: Loading DB in memory
* MASTER <-> REPLICA sync: Finished with success

# ---- 统计验证 ----
127.0.0.1:6379> INFO stats | grep sync
sync_full:2                       # 全量次数 +1
sync_partial_ok:1
sync_partial_err:1                # 部分重同步失败 +1
```

**判定逻辑**：

```bash
# 从库重连时发送 PSYNC <replid> <offset>
# 主库检查两个条件：
#   1. replid 是否匹配（主库没换过身份）
#   2. 请求的 offset 是否还在 backlog 缓冲区里
#
# backlog 是一个【环形缓冲区】，新数据不断覆盖旧数据
# 断线期间的写入量 > backlog 大小  →  历史被覆盖  →  只能全量
```

**全量同步的代价（这就是要调大 backlog 的原因）**：

| 环节 | 影响 |
|---|---|
| 主库 fork | 阻塞主线程，32GB 实例约 0.3~0.6 秒 |
| 生成 RDB | 磁盘 IO 飙升（`repl-diskless-sync yes` 可改为直接走 socket） |
| 传输 RDB | 占满网络带宽，可能影响正常业务流量 |
| 从库加载 | **加载期间从库不可用**，读流量全部打回主库 |
| 从库清空 | `Flushing old data` 会先删掉已有数据，期间从库数据为空 |

在读写分离架构下，一次全量同步意味着**该从库的读流量全部转移到主库**，很容易引发连锁的雪崩。所以调大 `repl-backlog-size` 是性价比极高的优化——花几十 MB 内存，换掉大部分全量同步。

**两个相关配置**：

```bash
# backlog 保留时长：所有从库都断开后，backlog 保留多久才释放
127.0.0.1:6379> CONFIG GET repl-backlog-ttl
1) "repl-backlog-ttl"
2) "3600"                         # 默认 1 小时，0 表示永不释放

# 无盘复制：RDB 不落盘，直接通过 socket 发给从库
127.0.0.1:6379> CONFIG SET repl-diskless-sync yes
OK
127.0.0.1:6379> CONFIG SET repl-diskless-sync-delay 5    # 等 5 秒，攒多个从库一起发
OK
# 磁盘慢、网络快的环境下（尤其云主机）建议开启，Redis 7 已默认 yes
```

**Redis 4.0+ 的 replid2 机制**：主从切换后，新主库会保留旧主库的 replication ID（存为 `master_replid2`），这样其他从库连过来时**仍然可以做部分重同步**，不必因为换了主库就全部全量。这个改进极大降低了故障转移的冲击。

```bash
127.0.0.1:6379> INFO replication | grep replid
master_replid:8f3ac1e5b2d7...
master_replid2:0000000000000000000000000000000000000000
second_repl_offset:-1
```

**3. backlog 大小估算**

**计算公式**：

```bash
repl-backlog-size >= 写入速率(bytes/s) × 可容忍断线时长(s)

# 本题：
#   写入峰值    = 5 MB/s
#   容忍断线    = 2 分钟 = 120 秒
#
#   理论最小值 = 5 MB/s × 120 s = 600 MB
```

**加上安全余量**：

```bash
# 理论值只是刚好够用，实际要留冗余，原因：
#   1. "峰值"往往是监控采样的平均峰值，瞬时可能更高
#   2. 断线恢复本身要花时间（重连、握手、PSYNC 协商）
#   3. 复制流里除了写命令还有 PING 心跳、SELECT 等开销
#   4. 从库追赶期间主库仍在持续写入，追赶需要时间
#
# 建议系数 1.5 ~ 2 倍：
#   保守方案：600 MB × 1.5 = 900 MB  →  取整 1 GB
#   充裕方案：600 MB × 2   = 1.2 GB  →  取整 1.5 GB
```

```bash
# 配置（运行时生效，注意会立即重新分配内存）
```

**但 1 GB 是个很大的数字，需要重新审视这个需求：**

```bash
# backlog 是【常驻内存】的，直接占用 maxmemory 之外的空间
# 1 GB backlog 意味着：
#   - 机器需要额外 1 GB 内存
#   - 如果主库本身只有 8 GB 数据，backlog 占了 12.5%，性价比存疑
```

**更划算的做法是重新评估"2 分钟"这个目标**：

| 容忍断线 | 所需 backlog | 评价 |
|---|---|---|
| 10 秒 | ~100 MB | 覆盖网络抖动、短暂丢包 |
| 30 秒 | ~256 MB | **推荐**，覆盖绝大多数瞬时故障 |
| 60 秒 | ~512 MB | 覆盖从库快速重启 |
| 120 秒 | ~1 GB | 成本偏高，收益递减 |

**关键判断**：断线超过 30 秒通常已经不是"网络抖动"，而是真正的故障（机器宕机、进程崩溃、机房网络中断）。这种情况下从库往往需要较长时间才能恢复，即便 backlog 撑住了，追赶大量积压数据本身也会给主库带来压力。**为极低概率的长断线付出 1 GB 常驻内存，不如把钱花在把 backlog 设成 256 MB + 完善监控告警上。**

**实际建议**：

```bash
# 第一步：先按 30 秒容忍度配置
repl-backlog-size 256mb

# 第二步：上线后观察真实数据，用统计指标驱动调整
127.0.0.1:6379> INFO stats | grep sync
sync_full:2
sync_partial_ok:47
sync_partial_err:1

# 判断标准：
#   sync_partial_err 长期为 0        → 配置合适，甚至可以调小
#   sync_partial_err 偶尔 +1         → 可接受
#   sync_full 频繁增长               → backlog 不够，翻倍调大
```

**同时监控实际写入速率**，验证 5 MB/s 这个估算是否准确：

```bash
# 方法一：观察复制偏移量的增长速度（最准确）
127.0.0.1:6379> INFO replication | grep master_repl_offset
master_repl_offset:1048576000
# 等 10 秒
127.0.0.1:6379> INFO replication | grep master_repl_offset
master_repl_offset:1099517440
# 速率 = (1099517440 - 1048576000) / 10 = 5094144 B/s ≈ 4.86 MB/s
# 与估算的 5 MB/s 吻合

# 方法二：看网络出口流量
127.0.0.1:6379> INFO stats | grep total_net_output_bytes
```

**顺带提醒**：5 MB/s 的持续写入对单个 Redis 实例来说已经不低了。如果这是常态而非瞬时峰值，还应该同步检查：

- **AOF 磁盘压力**：5 MB/s 写入意味着 AOF 每秒也要写 5 MB+，注意 `aof_delayed_fsync` 是否增长
- **主从网络带宽**：跨机房复制时 5 MB/s = 40 Mbps，专线带宽要留足
- **是否该分片**：单实例写入压力持续偏高时，Cluster 分片能把压力摊薄，同时每个分片的 backlog 也可以设得更小
