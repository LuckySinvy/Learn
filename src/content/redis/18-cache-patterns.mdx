# 缓存模式与穿透、击穿、雪崩

缓存是 Redis 最普遍的用途，也是事故最高发的领域。本章先讲清读写模式（数据在缓存与数据库之间怎么流动），再逐个拆解三大经典问题——穿透、击穿、雪崩，最后直面最缠人的"双写一致性"。

## 1. 三种缓存读写模式

### 1.1 Cache-Aside（旁路缓存，事实标准）

应用自己管理缓存与数据库：

```text
读: 查缓存 --命中--> 返回
        \--未命中--> 查数据库 -> 写入缓存(带 TTL) -> 返回

写: 更新数据库 -> 删除缓存   (注意: 是删除, 不是更新)
```

```python
def get_user(uid):
    data = redis.get(f"cache:user:{uid}")
    if data is not None:
        return json.loads(data)
    user = db.query("SELECT ... WHERE id = %s", uid)
    redis.set(f"cache:user:{uid}", json.dumps(user), ex=600)
    return user

def update_user(uid, fields):
    db.execute("UPDATE ... WHERE id = %s", uid)
    redis.delete(f"cache:user:{uid}")     # 删缓存, 下次读时重建
```

写时为什么删缓存而不是更新缓存？1）更新的值可能被并发写覆盖出错，删除天然幂等；2）缓存的可能是多表拼装结果，更新成本高；3）写多读少的字段更新了也未必被读，浪费。

### 1.2 Read/Write-Through（读写穿透）

应用只和"缓存服务"交互，由缓存层负责与数据库同步。应用代码更干净，但需要一个能挂钩数据库的缓存中间层，Redis 本身不提供，通常由公司内部平台或框架（如带 CacheLoader 的组件）实现。

### 1.3 Write-Behind（异步写回）

写只写缓存，由异步任务批量刷数据库。写性能极高（合并大量写），代价是**缓存宕机会丢数据**、一致性最弱。适合点赞数、浏览量这类容忍丢失的高频计数，不适合交易数据。

| 模式 | 读路径 | 写路径 | 一致性 | 复杂度 |
|---|---|---|---|---|
| Cache-Aside | 应用查缓存/DB | 写 DB, 删缓存 | 较好 | 低（推荐默认） |
| Read/Write-Through | 只查缓存层 | 缓存层同步写 DB | 较好 | 需中间层 |
| Write-Behind | 只查缓存层 | 只写缓存, 异步刷 DB | 弱 | 高 |

## 2. 缓存穿透：查"根本不存在"的数据

```text
请求 key=user:-1 (恶意构造/已删除的 ID)
  -> 缓存无 (不存在的东西当然没缓存)
  -> 打到数据库, 也查不到
  -> 没有结果可缓存, 下一次同样请求原样再来
  => 缓存形同虚设, 数据库被海量无效请求打穿
```

### 2.1 解法一：缓存空值

<Playground
  language="redis"
  title="缓存空值挡住穿透"
  id="redis-18-1"
  code={`# 第一次查: 缓存里没有, 只能去查数据库（也查不到）
GET cache:user:404
# 把"确认不存在"这件事也缓存起来, 空字符串占位, TTL 要短
SET cache:user:404 "" EX 60
# 之后同样的请求: 拿到空串就直接返回"不存在", 不再打数据库
GET cache:user:404
# 注意区分: EXISTS 是 1（有这个 key）, 值才是空的
EXISTS cache:user:404
TTL cache:user:404`}
/>

查到空值直接返回"不存在"。简单有效，但海量随机不存在的 key 会占内存，且 TTL 内新插入的数据会被误判——所以空值 TTL 要短（30~120 秒）。

### 2.2 解法二：布隆过滤器

把**全量存在的 ID** 预先放进布隆过滤器，请求先问过滤器：

```text
布隆过滤器: m 位的 bit 数组 + k 个哈希函数
写入 x: k 个哈希各算一个位置, 全部置 1
查询 y: k 个位置都是 1?
   ├─ 有任何一位是 0 -> y 一定不存在 (直接拒绝, 不打 DB)
   └─ 全是 1        -> y 可能存在 (有误判率, 放行去查)
特性: 不存在的判断 100% 准; 存在的判断有小概率误判; 不支持删除
```

用 RedisBloom 模块（redis-stack 自带）：

```bash
127.0.0.1:6379> BF.RESERVE bf:users 0.01 1000000    # 误判率 1%, 容量 100 万
OK
127.0.0.1:6379> BF.ADD bf:users 1001
(integer) 1
127.0.0.1:6379> BF.EXISTS bf:users 1001
(integer) 1
127.0.0.1:6379> BF.EXISTS bf:users 999999999
(integer) 0             # 一定不存在, 直接返回, 不查库
```

没有模块时可以用 Bitmap 手搓，或在应用内用 Guava BloomFilter。此外，接口层的参数校验（ID 格式、范围）能挡掉大部分低级恶意流量，永远是第一道防线。

## 3. 缓存击穿：热点 key 过期的瞬间

```text
热点 key (如首页 banner) 每秒 1 万次读
t0: TTL 到期, 缓存消失
t0+1ms: 1 万个并发请求同时未命中 -> 1 万个请求同时打向数据库重建
  => 数据库瞬间被打爆; 且 1 万次重建是重复劳动
```

### 3.1 解法一：互斥锁重建

只允许一个请求去重建，其余等待：

```python
def get_hot(key):
    data = redis.get(key)
    if data is not None:
        return data
    # 抢重建锁 (就是上一章的分布式锁)
    if redis.set(f"lock:rebuild:{key}", uuid, nx=True, ex=10):
        try:
            data = db.load()
            redis.set(key, data, ex=600)
        finally:
            release_lock(f"lock:rebuild:{key}", uuid)   # Lua 校验释放
        return data
    else:
        time.sleep(0.05)          # 没抢到: 短暂等待后重读缓存
        return get_hot(key)
```

代价：重建期间其他请求在等待（可能堆积线程）。

### 3.2 解法二：逻辑过期

key **不设 TTL**，把过期时间放进 value 里：

```text
value = { data: {...}, expire_at: 1722310600 }

读到后检查 expire_at:
  ├─ 未过期 -> 直接用
  └─ 已过期 -> 返回旧数据 + 异步触发一个任务去重建(带互斥)
  => 永远不会有"缓存消失"的瞬间, 请求永不阻塞
```

代价：过期后到重建完成之间，读到的是旧数据。适合"热点榜单、活动页"这类允许分钟级陈旧的场景。两种解法的取舍就是**一致性 vs 可用性**。

## 4. 缓存雪崩：大面积同时失效

两种成因，两套药方：

**成因一：大批 key 同一时刻过期**（比如凌晨批量预热时统一设了 3600 秒）。

```python
ttl = 3600 + random.randint(0, 600)     # TTL 加随机抖动, 摊平过期时刻
redis.set(key, value, ex=ttl)
```

效果就是同一批预热的 key 各自散落在不同时刻过期：

**成因二：Redis 实例整体宕机**，所有请求穿到数据库。

- 事前：主从 + 哨兵/Cluster 高可用（第 14~16 章）；
- 事中：应用层**限流与熔断**（数据库前面加信号量/线程池隔离，超载直接快速失败降级）；
- 兜底：多级缓存（进程内缓存扛一部分）、静态化兜底页。

三大问题速查表：

| 问题 | 本质 | 首选解法 |
|---|---|---|
| 穿透 | 查不存在的数据，缓存永远无法命中 | 布隆过滤器 + 空值缓存 + 参数校验 |
| 击穿 | 单个热点 key 过期瞬间并发重建 | 互斥锁重建 或 逻辑过期 |
| 雪崩 | 大量 key 同时失效 / 实例宕机 | TTL 随机抖动 + 高可用 + 限流熔断 |

## 5. 双写一致性与延迟双删

Cache-Aside 的"先更新库，再删缓存"仍有不一致窗口：

```text
经典竞态 (概率低但存在):
 读请求 R: 缓存未命中 -> 查 DB 得到旧值 v1 -> (卡了一下)
 写请求 W: 更新 DB 为 v2 -> 删除缓存 (此时缓存本来就空, 删了个寂寞)
 读请求 R: 恢复执行 -> 把旧值 v1 写进缓存
 => 缓存里是 v1, 数据库是 v2, 直到 TTL 到期都不一致
```

**延迟双删**：写请求删完缓存后，隔一小段时间**再删一次**，把上述竞态写进去的脏值清掉：

```python
def update_user(uid, fields):
    redis.delete(f"cache:user:{uid}")         # 第一次删
    db.execute("UPDATE ...", fields)
    time.sleep_async(0.5)                     # 睡过"读请求回填"的窗口(异步做)
    redis.delete(f"cache:user:{uid}")         # 第二次删
```

延迟时间取"一次读请求的 P99 耗时 + 余量"，通常几百毫秒。更彻底的方案是**订阅数据库 binlog**（Canal/Debezium），由独立服务在数据变更后删缓存，将删除与业务代码解耦，还能重试。

<Callout type="warn" title="接受最终一致，别追求强一致">
只要用缓存，缓存与数据库之间就不存在无成本的强一致（除非引入分布式事务，那缓存就失去意义了）。工程目标是：**不一致窗口足够短 + TTL 兜底**。所有缓存必须设 TTL——它是一切一致性方案失灵后的最后防线。
</Callout>

## 小结

- 默认用 Cache-Aside：读时回填，写时"更新库 + 删缓存"
- 穿透防"不存在"（布隆过滤器/空值），击穿防"热点过期"（互斥锁/逻辑过期），雪崩防"集体失效"（TTL 抖动/高可用/熔断）
- 双写不一致的兜底三板斧：延迟双删、binlog 驱动删除、必设 TTL

**四个关键设计点**：

**① 为什么写操作是"删缓存"而不是"更新缓存"？**

```bash
# 更新缓存的并发问题：
#   T1: 请求 A 更新 DB 为 price=100
#   T2: 请求 B 更新 DB 为 price=200
#   T3: 请求 B 更新缓存为 200
#   T4: 请求 A 更新缓存为 100     ← 网络延迟导致乱序
#   结果：DB 是 200，缓存是 100，【永久不一致】直到 TTL 过期
#
# 删缓存不存在这个问题：无论谁先删，结果都是"缓存为空"，
# 下次读取时会从 DB 加载到最新值
```

另外，删除是**惰性加载**思想：如果这个数据写完之后压根没人读，更新缓存就是白白浪费一次序列化和网络开销。写多读少的数据尤其明显。

**② 为什么是"先更新库，后删缓存"而不是反过来？**

```bash
# 先删缓存、后更新库的问题：
#   T1: 请求 A（写）删除缓存
#   T2: 请求 B（读）缓存未命中，查 DB 读到【旧值】
#   T3: 请求 B 把旧值回填到缓存
#   T4: 请求 A 更新 DB 为新值
#   结果：DB 是新值，缓存是旧值，【长期不一致】
#
# 这个窗口是"一次 DB 写入的耗时"（毫秒~几十毫秒），命中概率不低
```

先更新库的方案也有不一致窗口，但小得多——见第 3 题的分析。

**③ 空值缓存的注意事项**

```bash
# 用一个不可能与真实数据冲突的特殊标记
127.0.0.1:6379> SET cache:product:99999 "__NULL__" EX 60

# 三个要点：
#   1. TTL 必须【明显短于】正常数据（60秒 vs 3600秒）
#      否则数据真的被创建出来后，用户要等很久才能看到
#   2. 数据被创建时要主动删除对应的空值缓存
#   3. 空值也会占内存，恶意攻击构造海量随机 ID 时仍会撑爆
#      → 大流量场景要叠加布隆过滤器
```

**布隆过滤器方案**（更彻底的防穿透）：

```bash
# 需要 RedisBloom 模块
127.0.0.1:6379> BF.RESERVE product:filter 0.01 10000000
OK                                 # 误判率 1%，容量 1000 万
127.0.0.1:6379> BF.ADD product:filter 2001
(integer) 1
127.0.0.1:6379> BF.EXISTS product:filter 2001
(integer) 1                        # 可能存在 → 继续查缓存和 DB
127.0.0.1:6379> BF.EXISTS product:filter 99999
(integer) 0                        # 【一定】不存在 → 直接返回，不查 DB

# 布隆过滤器的特性：
#   - 说"不存在" → 100% 准确
#   - 说"存在"   → 可能误判（概率 = 设定的误判率）
#   - 【不支持删除】元素，数据下架后需要定期重建
```

**④ TTL 随机抖动为什么必要？**

```bash
# 无抖动：批量预热的 10 万个 key 全部 3600 秒过期
#         → 3600 秒后同一秒内集体失效
#         → 10 万请求瞬间打到数据库 → 【缓存雪崩】
#
# 有抖动：3600 + rand(0, 600)，失效时间分散在 10 分钟窗口内
#         → 数据库压力被摊平

# 抖动幅度建议：基础 TTL 的 10% ~ 20%
```

**准备一个"数据库查询"计数器**：

```bash

(integer) 1

wait

127.0.0.1:6379> GET db:query:count
"87"                               # 87 次！几乎所有请求都打到了 DB
```

**这就是缓存击穿**：单个热点 key 失效的瞬间，所有并发请求同时发现缓存为空，一窝蜂涌向数据库。和雪崩的区别是——**雪崩是大量 key 同时失效，击穿是单个热点 key 失效**。

**方案 B：互斥锁重建**

```bash
127.0.0.1:6379> DEL db:query:count cache:hot:item lock:rebuild:hot:item
(integer) 2

for i in $(seq 1 100); do
  (
    v=$(redis-cli GET cache:hot:item)
    if [ -z "$v" ]; then
      # 尝试抢重建锁
      got=$(redis-cli SET lock:rebuild:hot:item "$$" NX EX 10)
      if [ "$got" = "OK" ]; then
        # 抢到锁：我来查库重建
        redis-cli INCR db:query:count > /dev/null
        sleep 0.05
        redis-cli SET cache:hot:item "hot-value" EX 3600 > /dev/null
        redis-cli DEL lock:rebuild:hot:item > /dev/null
      else
        # 没抢到：短暂等待后重试读缓存
        sleep 0.1
        redis-cli GET cache:hot:item > /dev/null
      fi
    fi
  ) &
done
wait

127.0.0.1:6379> GET db:query:count
"1"                                # ✓ 只有 1 次！其余 99 个请求等待后读到了缓存
```

```bash
#         # 没抢到锁，短暂休眠后重试（注意设置最大重试次数）
#         sleep(50 ~ 100 ms)
#         return getWithMutex(key)      # 递归重试
```

**注意 `finally` 里的释放和"双重检查"**——这两点漏掉会导致死锁或重复查库，是手写实现最常见的两个 bug。

**方案 C：逻辑过期（永不过期 + 异步重建）**

```bash
# key 本身【不设 TTL】，把过期时间写进 value 里
127.0.0.1:6379> SET cache:hot:item2 "{\"data\":\"hot-value\",\"expireAt\":1785003600}"
OK
# 注意：没有 EX 参数，这个 key 永远不会被自动删除

# 读取逻辑（伪代码）：
# function getWithLogicalExpire(key):
#     obj = redis.GET(key)
#     if obj == nil:
#         return loadAndSet(key)           # 冷启动，同步加载
#
#     if obj.expireAt > now():
#         return obj.data                   # 逻辑上未过期，直接返回
#
#     # 逻辑上已过期：先返回旧数据，同时异步重建
#     if tryLock(key):
#         asyncExecute:
#             try:
#                 newData = db.query(key)
#                 redis.SET(key, {data: newData, expireAt: now() + 3600})
#             finally:
#                 releaseLock(key)
#
#     return obj.data                       # ← 返回【旧数据】，不阻塞
```

**三种方案对比**：

| 方案 | DB 压力 | 用户体验 | 数据新鲜度 | 复杂度 |
|---|---|---|---|---|
| 无保护 | ❌ 100 次查询 | 快但可能压垮 DB | 最新 | 最低 |
| 互斥锁 | ✓ 1 次查询 | **部分请求要等待** | 最新 | 中 |
| 逻辑过期 | ✓ 1 次查询 | **零等待**，始终有数据返回 | **可能返回旧数据** | 高 |

**选型建议**：

- **互斥锁**：通用方案，能接受少量请求短暂等待时首选。注意等待的请求会占用连接和线程，极端并发下要设置最大等待时间和降级逻辑
- **逻辑过期**：秒杀商品详情、首页推荐这类**绝对不能有等待**的场景。代价是要接受几百毫秒的数据陈旧，且需要额外的 key 永不过期（内存不会自动回收，要有清理机制）
- **热点数据永不过期 + 主动更新**：对于数量可枚举的超级热点（如首页 Banner），干脆不设 TTL，由后台任务或 binlog 监听主动刷新，从源头消除击穿

**3. 延迟双删时序图**

**先看不用双删时的问题**：

```bash
#  时间轴 ───────────────────────────────────────────────────────►
#
#  写请求 W:  ①更新DB(v2) ────────────── ②删缓存
#                  │                          │
#  读请求 R:       │  ③读缓存(miss)           │
#                  │       │                  │
#                  │  ④查DB → 读到 v1 或 v2 ？ │
#                  │            │             │
#                  │       ⑤回填缓存 ─────────┼──► 可能写入【旧值 v1】
#                  │                          │
#                  ▼                          ▼
#             DB = v2                    缓存被删
#
# 危险时序（W 的 ② 发生在 R 的 ⑤ 之前）：
#   T1: R 读缓存 miss
#   T2: R 查 DB，读到旧值 v1（W 还没提交，或 R 走了 DB 从库）
#   T3: W 更新 DB 为 v2
#   T4: W 删除缓存（此时缓存本来就是空的，删了个寂寞）
#   T5: R 把 v1 回填进缓存        ← 💥 脏数据产生，且【永久存在】
#
#   最终：DB = v2，缓存 = v1，直到 TTL 到期才会被纠正
```

**这个时序要成立需要同时满足**：读请求恰好在 W 更新 DB 之前查库、又恰好在 W 删缓存之后回填。窗口很窄，但在高并发下必然会出现。

**延迟双删的时序**：

```bash
#  时间轴 ───────────────────────────────────────────────────────────────►
#
#           T1         T2         T3         T4              T5
#            │          │          │          │               │
#  写 W:  ①更新DB(v2) ②删缓存 ─────┼──────────┼──►(等待 500ms)──③再删缓存
#            │          │          │          │               │
#  读 R:     │          │      ③读缓存(miss)  │               │
#            │          │          │          │               │
#            │          │      ④查DB(可能读到v1)               │
#            │          │          │          │               │
#            │          │          │      ⑤回填 v1 ──► 脏数据  │
#            │          │          │          │               │
#            │          │          │          │          ⑥【第二次删除】
#            │          │          │          │           清掉脏数据 ✓
#            ▼          ▼          ▼          ▼               ▼
#         DB=v2     缓存空     缓存空      缓存=v1(脏)      缓存空
#
#                          ┌───────────────────────┐
#                          │  第二次删除覆盖的窗口   │
#                          │  T2 ~ T5 之间的所有    │
#                          │  脏数据回填都会被清掉   │
#                          └───────────────────────┘
#
#  T5 之后：缓存为空 → 下一次读请求从 DB 加载 v2 → ✓ 一致
```

**双删能清掉的窗口**：**第一次删除之后、第二次删除之前**这段时间内，任何并发读回填的脏数据都会被第二次删除清掉。

**延迟时长怎么定？**

```bash
# 延迟时间 > (读请求查 DB 耗时 + 回填缓存耗时) 的 P99
#
# 典型取值：300 ~ 1000 毫秒
#   - 太短：脏数据还没回填就删了，第二次删除白做
#   - 太长：不一致窗口被人为拉长，且占用异步资源
#
# 如果读 DB 走从库，还要加上【DB 主从延迟】：
#   延迟时间 > DB主从延迟 + 查询耗时 + 回填耗时
```

**延迟双删仍然无法覆盖的场景**：

**① 第二次删除之后的 DB 主从延迟（题目提示的重点）**

```bash
#  时间轴 ─────────────────────────────────────────────────────────────►
#
#  W:  ①更新DB主库(v2)  ②删缓存 ──────────── ③延迟500ms后再删缓存
#            │                                        │
#  DB主从:   └─── 复制延迟 800ms ────────────────────────────► ④从库同步到 v2
#                                                     │              │
#  R:                                              ⑤读缓存(miss)     │
#                                                     │              │
#                                                  ⑥查DB【从库】     │
#                                                     │              │
#                                                  读到【旧值 v1】   │
#                                                     │              │
#                                                  ⑦回填 v1  ← 💥 脏数据
#                                                                    │
#                                                          （没有第三次删除）
#
#  结果：缓存 = v1，DB = v2，脏数据【长期存在】直到 TTL 过期
```

**根因**：延迟双删的延迟时间是按"读请求耗时"估算的，但如果 **DB 主从延迟 > 双删的延迟时间**，第二次删除发生时从库还没同步到新值，之后的读请求依然会从从库读到旧数据并回填。

**缓解手段**：

```bash
# 方案一：延迟时间 > DB 主从延迟的 P99（但主从延迟本身不稳定，可能突然飙到几秒）
# 方案二：写操作后的一段时间内，强制读走【主库】
# 方案三：改用 binlog 驱动删除（见下方，最推荐）
```

**② 第二次删除失败**

```bash
# 异步任务所在的进程崩溃、Redis 短暂不可用、消息队列丢消息
# → 第二次删除根本没执行 → 脏数据保留到 TTL 过期
#
# 缓解：删除操作进消息队列并配置重试；监控删除失败率
```

**③ 更新 DB 成功但删缓存失败**

```bash
# 第一次删除就失败了（Redis 抖动、网络超时）
# → 缓存中是完整的旧值，比"回填脏数据"的情况更糟
#
# 缓解：删除失败进重试队列；这也是必须设 TTL 的原因
```

**④ 主从架构的 Redis 本身的延迟**

```bash
# 应用删的是 Redis 主库，但读请求走 Redis 从库
# → Redis 主从复制延迟期间，从库上的旧缓存仍然可读
#
# 缓解：缓存的读写都走主库（缓存场景通常不做读写分离）
```

**⑤ 两次删除之间的时间窗口本身**

```bash
# T2（第一次删除）到 T5（第二次删除）之间，缓存里可能就是脏数据 v1
# 这 500 毫秒内的所有读请求都会读到旧值
#
# 延迟双删【不能消除】不一致，只能【缩短】不一致的持续时间：
#   从"直到 TTL 过期"（可能 1 小时）缩短为"最多 500 毫秒"
```

**更可靠的方案：binlog 驱动删除**

```bash
#  应用 ──更新──► MySQL 主库
#                    │
#                    │ binlog
#                    ▼
#                 Canal / Debezium
#                    │
#                    ▼
#                 消息队列（Kafka/RocketMQ）
#                    │
#                    ▼
#               缓存删除消费者 ──DEL──► Redis
```

**优势**：

| 维度 | 延迟双删 | binlog 驱动 |
|---|---|---|
| 触发时机 | 应用代码里手动调用 | **DB 实际提交后**，时序天然正确 |
| 遗漏风险 | 某处代码忘了删就漏了 | **所有写入都会被捕获**，包括手工 SQL、定时脚本 |
| 可靠性 | 进程崩溃就丢 | MQ 持久化 + 消费重试 |
| 业务侵入 | 每个写方法都要加删除逻辑 | **零侵入**，业务代码只管写库 |
| 主从延迟 | 无法解决 | 监听主库 binlog，不受影响 |
| 复杂度 | 低 | 高（要部署 Canal + MQ + 消费者） |

**"所有写入都会被捕获"这一点尤其重要**：延迟双删依赖开发者在每个写入路径上都记得删缓存，而实际项目里总会有人通过运维脚本、数据修复 SQL、第三方系统直接改库——这些路径的缓存永远不会被清理。binlog 方案从数据源头捕获，不存在遗漏。

**最终结论：TTL 是最后防线，永远不能省。**

```bash
# 无论用哪种一致性方案，都必须给缓存设 TTL
#
# 因为上面列举的所有失败场景（删除失败、消息丢失、主从延迟、
# 代码遗漏、Redis 抖动）最终都由 TTL 兜底：
#   脏数据最多存活一个 TTL 周期，然后自动消失
#
# 没有 TTL 的缓存 = 一旦出现脏数据就【永久不一致】，
# 只能靠人工发现和手动清理 —— 这在生产上是不可接受的
```

**工程上的正确心态**：**缓存与数据库之间不存在无成本的强一致**。想要强一致就得引入分布式事务（2PC/TCC），那样缓存的性能优势荡然无存，还不如直接读库。所以务实的目标是——**把不一致窗口压到业务可接受的范围内，并用 TTL 保证它一定会收敛**。

先和业务方确认"能容忍多久的数据延迟"，再据此选择方案：

- 能容忍分钟级 → **只设 TTL**，最简单，什么都不用做
- 能容忍秒级 → **Cache-Aside + 删缓存 + TTL**，覆盖 99% 的场景
- 能容忍百毫秒级 → **加延迟双删**
- 要求近实时 → **binlog 驱动删除**
- 要求强一致 → **别用缓存**，或者接受分布式事务的代价
