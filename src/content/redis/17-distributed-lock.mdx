# 分布式锁：从 SET NX 到 Redlock

多个服务实例同时处理同一个订单、同时刷新同一份缓存——跨进程的互斥需要分布式锁。Redis 因为快、原子命令丰富，成了最流行的分布式锁载体。但"能用"和"正确"之间隔着好几个坑，本章一个一个填。

## 1. 第一版：SET NX EX

<Playground
  language="redis"
  title="第一版：SET NX EX 加锁与释放"
  id="redis-17-1"
  code={`# 进程 A 加锁: key 不存在才能设置成功, 同时带 30 秒过期
SET lock:order:8801 "1" NX EX 30
# 进程 B 来抢同一把锁: 返回 nil, 抢锁失败, 等待重试
SET lock:order:8801 "1" NX EX 30
# 锁会自动过期, 持有者崩溃也不会死锁
TTL lock:order:8801
# A 业务完成, 释放锁
DEL lock:order:8801
# 现在 B 可以抢到了
SET lock:order:8801 "1" NX EX 30`}
/>

三个设计点缺一不可：

- **NX**：不存在才设置 = 互斥；
- **EX 30**：过期时间 = 持有者崩溃后锁自动释放，不死锁；
- **一条命令完成**：NX 和 EX 必须在同一条 SET 里（原子），分成 SETNX + EXPIRE 两步，中间崩溃就死锁。

## 2. 第二个坑：锁被别人释放

场景推演：

```text
t0: 进程 A 拿到锁, TTL 30 秒
t1: A 执行业务, 遇到长 GC / 慢 SQL, 耗时 35 秒
t2: 锁在 30 秒时过期, 进程 B 拿到了锁
t3: A 终于干完活, 执行 DEL —— 删掉的是 B 的锁!
t4: 进程 C 又拿到了锁。现在 B 和 C 同时在临界区里
```

问题根源：DEL 不分青红皂白。解法：**value 存唯一标识（UUID），释放前先验证是自己的锁**。

```bash
# 加锁时 value 用本次请求的唯一 ID
127.0.0.1:6379> SET lock:order:8801 "a1b2c3-uuid-of-A" NX EX 30
OK
```

但"GET 判断 + DEL"是两步，判断完、删除前锁恰好过期易主，还是会误删。必须用 Lua 保证原子：

```lua
-- unlock.lua: 是自己的锁才删
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
else
  return 0
end
```

压成一行运行，对比"拿错 uuid"与"拿对 uuid"两种结果：

<Playground
  language="redis"
  title="Lua 原子释放：只删自己的锁"
  id="redis-17-2"
  code={`# A 加锁, value 是 A 的唯一标识
SET lock:order:8801 "uuid-of-A" NX EX 30
# B 拿着自己的 uuid 来释放: 校验不通过, 返回 0, 锁纹丝不动
EVAL "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end" 1 lock:order:8801 uuid-of-B

# A 用自己的 uuid 释放: 返回 1, 释放成功
EVAL "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end" 1 lock:order:8801 uuid-of-A
EXISTS lock:order:8801`}
/>

到这里，一个**基本正确**的单机 Redis 锁已经成型：`SET key uuid NX EX ttl` 加锁 + Lua 校验释放。

## 3. 第三个坑：业务没干完锁先过期

TTL 设多长？太短业务没完锁就飞了，太长持有者崩溃后别人干等。工程解法是**看门狗（watchdog）续期**：

```text
加锁成功, TTL 30 秒
   |
   +--> 启动后台线程: 每 10 秒 (TTL/3) 检查
             业务还在执行? --是--> PEXPIRE 锁 重置为 30 秒
                           --否/进程已死--> 不续期, 锁自然过期
```

续期同样要校验身份（Lua）：

```lua
-- renew.lua: 是自己的锁才续期
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('PEXPIRE', KEYS[1], ARGV[2])
else
  return 0
end
```

<Playground

  title="看门狗续期：校验身份后 PEXPIRE"
  id="redis-17-3"
  code={`SET lock:order:8801 "uuid-of-A" NX EX 30
TTL lock:order:8801
# A 的看门狗续期: 校验通过, TTL 重置为 60 秒
EVAL "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('PEXPIRE', KEYS[1], ARGV[2]) else return 0 end" 1 lock:order:8801 uuid-of-A 60000
TTL lock:order:8801
# 别人的看门狗想续期: 返回 0, 续不了
EVAL "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('PEXPIRE', KEYS[1], ARGV[2]) else return 0 end" 1 lock:order:8801 uuid-of-B 60000
TTL lock:order:8801`}
/>

Java 的 Redisson 内置了这一整套（默认 TTL 30 秒、每 10 秒续期），还提供可重入、公平锁、读写锁：

```java
RLock lock = redisson.getLock("lock:order:8801");
try {
    // 不带 leaseTime 参数 => 自动启用看门狗续期
    if (lock.tryLock(5, TimeUnit.SECONDS)) {
        doBusiness();
    }
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

自己手写客户端时，别忘了看门狗的反面：**业务线程卡死但进程没死**，看门狗会无限续期，锁永不释放。所以续期要有最大次数上限。

## 4. 第四个坑：主从切换丢锁

单机 Redis 锁的天花板：

```text
t0: A 在主库上加锁成功
t1: 主库宕机, 锁的写入还没复制到从库 (异步复制!)
t2: 哨兵切换, 从库升主 —— 新主库上没有这把锁
t3: B 在新主库加锁成功
    => A 和 B 同时持有"同一把锁"
```

这不是实现 bug，是异步复制的固有窗口。两条路：

1. **接受它**：概率低、业务有兜底（数据库唯一约束、幂等设计）时，单实例锁足够——这是大多数业务的选择；
2. **Redlock**：官方提出的多实例方案。

## 5. Redlock 及其争议

思路：部署 5 个**完全独立**的 Redis（不是主从，是 5 个孤立单机），加锁时：

```text
1. 记录起始时间
2. 依次向 5 个实例发 SET key uuid NX PX 30000 (每个有很短的超时)
3. 在多数派 (>=3) 实例上成功, 且总耗时 < 锁有效期
   => 加锁成功, 实际有效期 = 30000 - 加锁耗时
4. 失败 => 向所有实例发释放脚本, 稍后重试
```

单实例宕机不影响多数派，主从切换问题不存在（没有主从）。

但分布式系统专家 Martin Kleinmann 在著名的辩论中指出它的软肋：

- **时钟跳变**：某实例的系统时钟被 NTP 大幅回拨/前调，锁提前过期，多数派被破坏；
- **进程暂停**：客户端拿到锁后陷入长 GC，醒来时锁早过期了，它却不知道自己已无锁——任何带 TTL 的锁都有这个问题，Redlock 没解决；
- 结论：Redis 锁适合**效率场景**（防止重复干活，偶尔失效代价可控）；**正确性场景**（绝不允许两个进程同时进临界区，否则钱就错了）应该用有 fencing token 的系统（ZooKeeper/etcd），或者在资源端做防护（数据库乐观锁版本号）。

Redis 作者 antirez 也做了回应与反驳，这场辩论本身就是最好的教材。工程上的务实结论：

| 场景 | 方案 |
|---|---|
| 防缓存重复重建、定时任务防重跑 | 单实例 SET NX EX + Lua 释放，足够 |
| 一般业务互斥（有幂等兜底） | 单实例或主从 + 哨兵，接受极小窗口 |
| 涉及资金等强正确性 | 锁只做优化，最终正确性靠数据库约束/版本号 |

<Callout type="warn" title="分布式锁自查清单">
1）NX 与 EX 是否在一条 SET 里？2）value 是否为唯一标识？3）释放是否用 Lua 校验身份？4）TTL 是否大于业务 P99 耗时，或有看门狗？5）获取锁失败的重试是否有退避与上限？6）Cluster 环境锁 key 是否考虑了 hash tag（锁与相关数据同槽以便 Lua 操作）？7）临界区内的操作是否幂等（锁失效的兜底）？
</Callout>

<Callout type="info" title="锁的粒度决定并发度">
锁 key 要尽量细：锁"订单 8801"（lock:order:8801）而不是锁"所有订单"（lock:orders）。粒度粗一档，并发能力就掉一个量级。
</Callout>

## 小结

- 正确的单机锁 = SET key uuid NX EX ttl 加锁 + Lua 校验身份释放
- 锁过期与业务超时的矛盾用看门狗续期解决（注意续期上限）
- 主从异步复制导致切换丢锁；Redlock 用 5 个独立实例的多数派规避，但有时钟与进程暂停的理论争议
- 务实原则：效率场景 Redis 锁随便用；正确性场景必须在资源端加最后防线

```bash
127.0.0.1:6379> EVAL "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end" 1 lock:order:1001 "A-uuid"
(integer) 1

# ========== 终端 B：重试成功 ==========
127.0.0.1:6379> SET lock:order:1001 "B-7a9d4c2f-8e1b-11f0-b5d7-0242ac120003" NX EX 30
OK                                # 这次抢到了
```

**加锁命令的每个部分都不可省略**：

| 部分 | 作用 | 省略的后果 |
|---|---|---|
| `NX` | 只在 key 不存在时设置 | 会覆盖别人的锁，互斥完全失效 |
| `EX 30` | 自动过期 | 持有者宕机 → **永久死锁** |
| UUID 作为 value | 标识持有者 | 无法区分是谁的锁 → 误删 |
| Lua 释放 | 校验+删除原子化 | 校验和删除之间有窗口 → 误删 |

**为什么不能用 `SETNX` + `EXPIRE` 两条命令？**

```bash
# 危险写法
127.0.0.1:6379> SETNX lock:x "uuid"
(integer) 1
# ↑↓ 如果客户端在这两条命令之间崩溃/网络中断...
127.0.0.1:6379> EXPIRE lock:x 30

# 结果：锁被创建但【永远不会过期】，所有后续请求永久阻塞
# 只能人工介入 DEL，这在生产上是 P0 事故
```

`SET key value NX EX ttl` 把两个操作合成了一条原子命令，从根本上消除了这个窗口。

**2. 复现误删，再验证 Lua 版本安全**

```bash
# ========== 复现误删（危险写法）==========

# ---- T0：A 加锁，TTL 只有 5 秒 ----
127.0.0.1:6379> SET lock:job "A-uuid-aaa" NX EX 5
OK

# ---- A 的业务执行很慢，超过了 5 秒 ----
# ---- T5：锁自动过期，A 完全不知情 ----
127.0.0.1:6379> TTL lock:job
(integer) -2                      # 锁已消失

# ---- T5+：B 抢到了这把"空出来"的锁 ----
127.0.0.1:6379> SET lock:job "B-uuid-bbb" NX EX 30
OK
127.0.0.1:6379> GET lock:job
"B-uuid-bbb"                      # 现在锁属于 B

# ---- T6：A 的业务终于跑完了，直接 DEL 释放 ----
127.0.0.1:6379> DEL lock:job
(integer) 1                       # 💥 删掉的是 B 的锁！

127.0.0.1:6379> EXISTS lock:job
(integer) 0                       # B 还在执行业务，锁却没了

# ---- T7：C 也能抢到锁了 ----
127.0.0.1:6379> SET lock:job "C-uuid-ccc" NX EX 30
OK
# 现在 B 和 C 【同时】在执行临界区代码 —— 互斥彻底失效
```

```bash
# ========== Lua 校验版：不会误删 ==========

# ---- 重现同样的时序 ----
127.0.0.1:6379> SET lock:job2 "A-uuid-aaa" NX EX 5
OK
# 等待 6 秒，锁过期
127.0.0.1:6379> SET lock:job2 "B-uuid-bbb" NX EX 30
OK                                # B 抢到锁

# ---- A 用 Lua 尝试释放 ----
127.0.0.1:6379> EVAL "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end" 1 lock:job2 "A-uuid-aaa"
(integer) 0                       # ✓ 返回 0，拒绝删除

127.0.0.1:6379> GET lock:job2
"B-uuid-bbb"                      # ✓ B 的锁完好无损

# ---- B 释放自己的锁：正常成功 ----
127.0.0.1:6379> EVAL "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end" 1 lock:job2 "B-uuid-bbb"
(integer) 1
```

**为什么必须用 Lua 而不是"GET 判断 + DEL"两步？**

```bash
# 看似安全的写法：
#   value = GET lock:job
#   if value == myUuid:
#       DEL lock:job
#
# 竞态时序：
#   T1: A 执行 GET，返回 "A-uuid"，判断相符 ✓
#   T2: 【就在这一瞬间】锁过期了
#   T3: B 抢到锁，写入 "B-uuid"
#   T4: A 执行 DEL  → 删掉了 B 的锁 💥
#
# 窗口虽然只有几毫秒，但在高并发下必然会命中
```

Lua 脚本在服务端原子执行，"读取 → 比较 → 删除"三步之间**不可能插入任何其他命令**，从根本上消除了这个窗口。

**但 Lua 只解决了"误删"，没解决"锁过期时业务还在跑"这个更本质的问题。** 上面的例子里，即使 A 没有误删，**B 和 A 在 T5~T6 之间也是同时在执行临界区的**。这才是分布式锁最难的部分。

**解法一：看门狗自动续期**

```bash
# 加锁时启动一个后台线程，每隔 TTL/3 检查一次：
#   如果锁还是我的 → 续期
#
# 续期脚本（同样要校验身份）
127.0.0.1:6379> EVAL "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('EXPIRE', KEYS[1], ARGV[2]) else return 0 end" 1 lock:job "A-uuid-aaa" 30
(integer) 1                       # 续期成功

# 业务结束时停止看门狗并释放锁
```

Redisson 的 `RLock` 默认就带看门狗（`lockWatchdogTimeout` 默认 30 秒，每 10 秒续一次）。**注意必须设置续期上限或最大持有时间**，否则业务代码死循环时锁会被无限续期，变成永久死锁——这比锁提前过期更难排查。

**解法二：Fencing Token（唯一能真正解决问题的方案）**

```bash
# 加锁时同时获取一个单调递增的令牌
127.0.0.1:6379> INCR lock:job:fence
(integer) 42
127.0.0.1:6379> SET lock:job "A-uuid:42" NX EX 30
OK

# 操作共享资源时【带上令牌】，由资源端做校验
#   UPDATE orders SET status='paid', fence=42
#   WHERE id=1001 AND fence < 42
#
# 效果：即使 A 的锁已过期、B 拿着令牌 43 先完成了操作，
#      A 后到的请求会因为 fence 42 < 43 被资源端拒绝
```

**这是唯一能应对"进程暂停 / GC 停顿 / 网络延迟"的方案**，因为它把最终的正确性判断放在了**资源端**，而不是依赖锁本身。代价是需要资源端（数据库、文件系统）配合支持版本号校验。

**3. 业务场景自查**

**场景示例：订单支付回调的幂等处理**

第三方支付平台会对同一笔订单**重复推送回调**（网络重试、平台补偿机制），必须保证只处理一次，否则会重复发货、重复加积分。

```bash
# 加锁
127.0.0.1:6379> SET lock:pay:callback:20260802001 "worker-3:uuid-xyz" NX EX 30
OK

# 处理逻辑：
#   1. 查订单状态，如果已是 paid 则直接返回成功（幂等短路）
#   2. 更新订单状态为 paid
#   3. 发货 / 加积分 / 发通知
#   4. Lua 释放锁
```

**自查清单逐项过**：

| 检查项 | 本场景的回答 |
|---|---|
| **1. 锁的粒度是否足够细？** | ✓ 按订单号加锁，不同订单互不阻塞，并发度高 |
| **2. 临界区耗时可控吗？** | ⚠️ 涉及发货等外部调用，最坏可能几十秒 → **需要看门狗续期** |
| **3. 加锁是否带 TTL？** | ✓ EX 30，配合看门狗 |
| **4. 释放是否校验身份？** | ✓ Lua 校验 UUID |

**第 7 项是本场景成立的关键**：

```bash
# 数据库层面的最后防线
#   UPDATE orders SET status = 'paid', paid_at = NOW()
#   WHERE order_no = '20260802001' AND status = 'unpaid';
#
# 只有影响行数 = 1 才继续执行发货
# 影响行数 = 0 说明已被其他请求处理过，直接返回
```

有了这道防线，**即使 Redis 锁完全失效**（主从切换丢锁、锁提前过期、网络分区），数据库的条件更新也能保证只有一个请求能把状态从 `unpaid` 改成 `paid`。Redis 锁在这里的作用退化为"**性能优化**"——挡掉 99.9% 的重复请求，避免它们白白打到数据库上，而不是承担最终的正确性保证。

**为什么不需要 Redlock？**

```bash
# Redlock 的代价：
#   - 需要 5 个【完全独立】的 Redis 实例（不是主从，是各自独立的 master）
#   - 每次加锁要向 5 个实例发请求，延迟是单实例的数倍
#   - 运维复杂度陡增：5 套实例的部署、监控、扩容
#   - 依赖各节点时钟不能大幅漂移（Martin Kleppmann 的核心质疑点）
#   - 遇到 GC 停顿、进程暂停时【依然不安全】—— 这是理论上无解的
#
# 而本场景已经有数据库兜底，Redlock 带来的边际收益几乎为零
```

**核心决策原则**：

> **效率场景**（锁失效只造成重复劳动，如定时任务重复执行、缓存重复重建）→ 单实例 Redis 锁足够，简单可靠。
>
> **正确性场景**（锁失效造成数据错误或资损）→ **必须在资源端加最后防线**（唯一索引、条件更新、fencing token）。有了这道防线，Redis 锁用单实例就够了；没有这道防线，用 Redlock 也不安全。

这个原则的深层逻辑是：**任何基于超时的分布式锁都无法应对进程暂停**。因为持有锁的进程可能在任意时刻被 GC 或 OS 调度暂停任意长时间，等它醒来时锁早已过期并被他人获取，而它自己毫不知情。Redlock 也逃不过这一点——Martin Kleppmann 那篇著名批评文章的核心论点正在于此。

所以结论是：**不要试图用更复杂的锁算法来获得绝对安全，那是徒劳的。把最终的正确性保证放在资源端，锁只负责减少冲突。**

**其他常见场景的判断**：

| 场景 | 类型 | 建议 |
|---|---|---|
| 定时任务防重复执行 | 效率 | 单实例锁足够，失效了最多多跑一次 |
| 缓存重建防击穿 | 效率 | 单实例锁足够，失效了最多多查几次库 |
| 库存扣减 / 秒杀 | 正确性 | **不要用锁**，用 Lua 原子扣减（第 20 章） |
| 账户余额变更 | 正确性 | 数据库事务 + 行锁，Redis 锁只做前置削峰 |
| 订单状态流转 | 正确性 | Redis 锁 + 数据库条件更新兜底 |
| 分布式 ID 生成 | 正确性 | **不要用锁**，用 `INCRBY` 取号段 |
| 文件上传去重 | 正确性 | Redis 锁 + 存储层唯一约束 |

注意表格里有两项写的是"**不要用锁**"——这是很重要的提醒：**很多以为需要分布式锁的场景，其实用 Redis 的原子命令（`INCR`、`SET NX`、Lua 脚本）就能直接解决，而且更快更可靠。** 加锁是最后手段，不是第一选择。
