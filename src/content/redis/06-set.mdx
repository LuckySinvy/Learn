# Set：去重、标签与随机抽取

Set 是**无序、去重**的字符串集合。它的两大杀手锏：O(1) 判断"存在不存在"，以及服务端直接完成交集、并集、差集运算——共同好友、共同关注这类需求一条命令搞定。

## 1. 核心命令实操

### 1.1 增删查

<Playground
  language="redis"
  title="Set 增删查"
  id="redis-06-1"
  code={`SADD tags:article:1 "redis" "cache" "database"
# 已存在，自动去重，返回实际新增数 0
SADD tags:article:1 "redis"
SISMEMBER tags:article:1 "redis"
# 6.2+ 批量判断
SMISMEMBER tags:article:1 "redis" "mysql"
# 集合大小
SCARD tags:article:1
SREM tags:article:1 "database"
SMEMBERS tags:article:1`}
/>

`SMEMBERS` 返回全部成员，大集合上等同于 KEYS 的危险性，改用 `SSCAN`：

```bash
127.0.0.1:6379> SSCAN tags:article:1 0 COUNT 100
1) "0"
2) 1) "cache"
   2) "redis"
```

### 1.2 随机抽取：SPOP 与 SRANDMEMBER

```bash
127.0.0.1:6379> SADD lottery:users u1 u2 u3 u4 u5
(integer) 5
127.0.0.1:6379> SRANDMEMBER lottery:users 2
1) "u3"
2) "u1"                 # 只随机读取，不删除
127.0.0.1:6379> SPOP lottery:users 2
1) "u5"
2) "u2"                 # 随机弹出并删除
127.0.0.1:6379> SCARD lottery:users
(integer) 3
```

两者的区别决定了抽奖用法：

- **一等奖不能重复中**：用 `SPOP`，中奖者移出奖池；
- **每轮独立、可重复参与**：用 `SRANDMEMBER`。

`SRANDMEMBER` 的 count 为负数时允许返回重复成员（如 `-5` 可能返回同一人多次）。

### 1.3 集合运算：交、并、差

<Playground
  language="redis"
  title="交集、并集、差集"
  id="redis-06-2"
  code={`SADD follow:ada u2 u3 u4
SADD follow:bob u3 u4 u5
# 交集：共同关注
SINTER follow:ada follow:bob
# 并集
SUNION follow:ada follow:bob
# 差集：ada 关注而 bob 没关注的
SDIFF follow:ada follow:bob
# STORE 版本把结果存成新 key，便于缓存复用
SINTERSTORE common:ada:bob follow:ada follow:bob
EXPIRE common:ada:bob 300
SMEMBERS common:ada:bob
# 7.0+ 只要交集数量，不要成员，更省
SINTERCARD 2 follow:ada follow:bob`}
/>

带 STORE 后缀的版本把结果存进新 key，配合 EXPIRE 就是一个"交集结果缓存 5 分钟"的实现；`SINTERCARD`（7.0+）只返回交集大小，省掉传输成员的开销。

复杂度注意：SINTER 是 O(N*M)（最小集合大小 × 集合个数），SUNION/SDIFF 是 O(N)（全部元素之和）。对两个百万级集合求并集是重操作，必要时放到从库或离线做。

## 2. 底层编码：intset 与 listpack 与 hashtable

<Playground
  language="redis"
  title="intset / listpack / hashtable"
  id="redis-06-3"
  code={`SADD nums 1 2 3
OBJECT ENCODING nums
SADD strs "a" "b"
OBJECT ENCODING strs
SADD strs "this-is-a-long-member-over-sixty-four-bytes-xxxxxxxxxxxxxxxxxxxxxxx"
OBJECT ENCODING strs`}
/>

| 编码 | 条件 | 结构 |
|---|---|---|
| `intset` | 全部成员是整数，且个数 ≤ 512 | 有序整数数组，二分查找 |
| `listpack` | 成员含字符串，个数 ≤ 128 且都 ≤ 64 字节（7.2+） | 紧凑连续内存 |
| `hashtable` | 超出上述条件 | 哈希表，value 为空 |

```text
intset（升级机制）:
  [1, 2, 3]           全是 int16 -> 每个成员 2 字节
  SADD nums 100000    需要 int32 -> 整个数组升级为 4 字节/成员
  SADD nums 10^12     需要 int64 -> 再升级为 8 字节/成员
  （只升不降）
```

相关配置：

```conf
set-max-intset-entries 512
set-max-listpack-entries 128
set-max-listpack-value 64
```

存纯数字 ID 的集合（用户 ID、商品 ID）时 intset 极其省内存：512 个 int32 只占约 2 KB。

## 3. 典型场景

### 3.1 标签系统

```bash
# 双向存储: 文章的标签 + 标签下的文章
127.0.0.1:6379> SADD article:1:tags "redis" "cache"
(integer) 2
127.0.0.1:6379> SADD tag:redis:articles 1 5 9
(integer) 3
127.0.0.1:6379> SADD tag:cache:articles 1 7
(integer) 2
# 同时含 redis 和 cache 标签的文章:
127.0.0.1:6379> SINTER tag:redis:articles tag:cache:articles
1) "1"
```

### 3.2 抽奖去重

```bash
# 报名: SADD 天然防重复报名
127.0.0.1:6379> SADD raffle:20260801 u1001
(integer) 1
127.0.0.1:6379> SADD raffle:20260801 u1001
(integer) 0             # 重复报名无效
# 开奖: 抽 3 个三等奖（不放回）
127.0.0.1:6379> SPOP raffle:20260801 3
1) "u1017"
2) "u1001"
3) "u1093"
```

### 3.3 点赞与已读去重

<Playground
  language="redis"
  title="点赞去重：用返回值判断首次"
  id="redis-06-4"
  code={`# 返回 1 = 点赞成功
SADD like:post:42 u1
# 返回 0 = 已点过（可提示或执行取消逻辑）
SADD like:post:42 u1
SADD like:post:42 u2 u3

SISMEMBER like:post:42 u9`}
/>

<Callout type="tip" title="用返回值代替先查后写">
判断"是否已点赞"不需要先 SISMEMBER 再 SADD——直接 SADD，看返回值是 1 还是 0。一次网络往返，而且原子，不存在并发下的先查后写竞态。
</Callout>

<Callout type="warn" title="大集合的三个雷区">
1）SMEMBERS 百万成员集合会阻塞并产生巨大响应，遍历用 SSCAN；2）SINTERSTORE 大集合会在主线程做大量计算；3）海量 UV 去重场景（千万级）用 Set 太耗内存——每天几千万 ID 可能吃掉数 GB，这种"只要数量不要成员"的需求应该用 HyperLogLog（第 8 章），12 KB 搞定。
</Callout>

## 小结

- Set 提供 O(1) 存在性判断与自动去重，SADD 返回值可直接当"是否首次"用
- SPOP 不放回抽取（抽奖），SRANDMEMBER 只读随机（可重复）
- SINTER/SUNION/SDIFF 服务端集合运算，STORE 版本可缓存结果
- 编码三态：纯整数 intset，小字符串集合 listpack，大集合 hashtable

**参考答案：**

**1. 关注集合的交并差运算**

```bash
# 构造两个各含 10 个成员的关注集合
127.0.0.1:6379> SADD follow:alice u1 u2 u3 u4 u5 u6 u7 u8 u9 u10
(integer) 10
127.0.0.1:6379> SADD follow:bob u5 u6 u7 u8 u11 u12 u13 u14 u15 u16
(integer) 10

# ---- 共同关注（交集）----
127.0.0.1:6379> SINTER follow:alice follow:bob
1) "u5"
2) "u6"
3) "u7"
4) "u8"

# ---- 全部关注（并集，自动去重）----
127.0.0.1:6379> SUNION follow:alice follow:bob
 1) "u1"
 2) "u2"
 ...                      # 共 16 个，u5~u8 不重复
127.0.0.1:6379> SCARD follow:alice
(integer) 10

# ---- alice 独有的关注（差集，注意顺序敏感）----
127.0.0.1:6379> SDIFF follow:alice follow:bob
1) "u1"
2) "u2"
3) "u3"
4) "u4"
5) "u9"
6) "u10"

# ---- bob 独有的关注：交换顺序 ----
127.0.0.1:6379> SDIFF follow:bob follow:alice
1) "u11"
...                       # u11~u16

# ---- 用 SINTERSTORE 缓存交集结果 60 秒 ----
127.0.0.1:6379> SINTERSTORE cache:common:alice:bob 2 follow:alice follow:bob
(error) ERR value is not an integer or out of range
# 注意：SINTERSTORE 不需要 numkeys 参数，直接跟 key 列表
127.0.0.1:6379> SINTERSTORE cache:common:alice:bob follow:alice follow:bob
(integer) 4               # 返回结果集的元素个数
127.0.0.1:6379> EXPIRE cache:common:alice:bob 60
(integer) 1
127.0.0.1:6379> SMEMBERS cache:common:alice:bob
1) "u5"
2) "u6"
3) "u7"
4) "u8"
127.0.0.1:6379> TTL cache:common:alice:bob
(integer) 57
```

几个要点：

- **`SDIFF` 顺序敏感**：`SDIFF A B` 是"A 有 B 没有"，交换顺序结果完全不同。`SINTER` 和 `SUNION` 则与顺序无关
- **STORE 版本返回的是元素个数，不是集合内容**：想看内容要再 `SMEMBERS`
- **STORE 会覆盖目标 key**，且**不保留目标 key 原有的 TTL**，所以 `EXPIRE` 必须在 `SINTERSTORE` 之后执行。这个顺序搞反是缓存不过期的常见原因
- **结果为空时目标 key 会被删除**：如果交集为空，`SINTERSTORE` 返回 0 且不会创建 key，此时 `EXPIRE` 返回 0
- **STORE 的价值**：把"共同关注"这种昂贵计算的结果落成一个 key，60 秒内的重复请求直接 `SMEMBERS` 读缓存。但要警惕两个大集合求交会在主线程做大量计算，`SINTERCARD`（Redis 7.0+）可以在只需要数量时提前终止：`SINTERCARD 2 follow:alice follow:bob LIMIT 10`

**2. 抽奖流程**

```bash
# ---- 1. 100 人报名，SADD 天然防重复 ----
for i in $(seq 1 100); do redis-cli sadd lottery:2026:signup "u$i"; done
127.0.0.1:6379> SCARD lottery:2026:signup
(integer) 100

# 重复报名不会增加人数
127.0.0.1:6379> SADD lottery:2026:signup u50
(integer) 0               # 返回 0 = 已报名，业务侧可提示"你已参与"

# ---- 2. 抽 1 个一等奖：SPOP 不放回 ----
127.0.0.1:6379> SPOP lottery:2026:signup 1
1) "u73"
127.0.0.1:6379> SCARD lottery:2026:signup
(integer) 99              # 人数减少，u73 不会再被抽到

# 记录中奖名单
127.0.0.1:6379> SADD lottery:2026:winner:first u73
(integer) 1

# ---- 3. 从剩余 99 人中抽 5 个参与奖 ----
127.0.0.1:6379> SPOP lottery:2026:signup 5
1) "u12"
2) "u88"
3) "u41"
4) "u5"
5) "u60"
127.0.0.1:6379> SCARD lottery:2026:signup
(integer) 94

127.0.0.1:6379> SADD lottery:2026:winner:join u12 u88 u41 u5 u60
(integer) 5

# ---- 验证：一等奖不在参与奖名单里 ----
127.0.0.1:6379> SISMEMBER lottery:2026:winner:join u73
(integer) 0
127.0.0.1:6379> SINTER lottery:2026:winner:first lottery:2026:winner:join
(empty array)             # 交集为空，证明没有重复中奖
```

**为什么用 `SPOP` 而不是 `SRANDMEMBER`？**

| 命令 | 是否移除 | 是否可能重复 | 适用场景 |
|---|---|---|---|
| `SPOP key N` | 是（不放回） | 不会 | 抽奖、发号、任务分配 |
| `SRANDMEMBER key N` | 否（只读） | N 为正数时不重复；**N 为负数时可重复** | 随机推荐、随机展示 |

抽奖必须用 `SPOP`：它把"随机选取"和"移除"做成了一个原子操作。如果用"`SRANDMEMBER` 选人 + `SREM` 移除"两步，并发抽奖时两个请求可能选中同一个人。

`SRANDMEMBER key -5` 传负数会返回 5 个**可能重复**的成员（且个数一定是 5，即使集合里只有 2 个人），这个特性在"随机展示 N 个广告位"时有用，但抽奖场景绝对不能用。

**注意抽奖的原子性边界**：上面 `SPOP` + `SADD` 记录名单是两条命令，如果中间宕机会丢失中奖记录。严格场景应该用 Lua 把两步合成原子操作。

**3. 观察 intset 到 hashtable 的两次编码状态**

```bash
127.0.0.1:6379> DEL nums
(integer) 1

# ---- 状态一：加入 500 个小整数 ----
for i in $(seq 1 500); do redis-cli sadd nums $i; done
127.0.0.1:6379> SCARD nums
(integer) 500
127.0.0.1:6379> OBJECT ENCODING nums
"intset"                  # 全是整数 → intset

# ---- 状态二：加入 1 个字符串 ----
127.0.0.1:6379> SADD nums "hello"
(integer) 1
127.0.0.1:6379> OBJECT ENCODING nums
"hashtable"               # 出现非整数 → 直接跳到 hashtable

# ---- 验证不可逆 ----
127.0.0.1:6379> SREM nums "hello"
(integer) 1
127.0.0.1:6379> OBJECT ENCODING nums
"hashtable"               # 即使又变回纯整数，也不会转回 intset
```

**为什么是 hashtable 而不是 listpack？** Set 有三种编码，选择逻辑是：

```bash
# 决策顺序：
# 1. 全是整数 且 元素数 <= set-max-intset-entries(512)  → intset
# 2. 有非整数 且 元素数 <= set-max-listpack-entries(128)
#    且 每个元素 <= set-max-listpack-value(64)          → listpack
# 3. 其他所有情况                                        → hashtable
```

本题因为已经有 500 个元素（远超 listpack 的 128 上限），加入字符串后第 2 条不满足，所以**跳过 listpack 直接变成 hashtable**。

对比实验，如果元素少就会落到 listpack：

```bash
127.0.0.1:6379> DEL small
127.0.0.1:6379> SADD small 1 2 3
(integer) 3
127.0.0.1:6379> OBJECT ENCODING small
"intset"
127.0.0.1:6379> SADD small "hello"
(integer) 1
127.0.0.1:6379> OBJECT ENCODING small
"listpack"                # 元素少 → 中间态 listpack

# 再加到超过 128 个元素
for i in $(seq 1 200); do redis-cli sadd small "s$i"; done
127.0.0.1:6379> OBJECT ENCODING small
"hashtable"
```

另一条触发路径：纯整数但数量超过 512，也会转（Redis 7 会转成 listpack 或 hashtable，取决于是否同时满足 listpack 条件）：

```bash
127.0.0.1:6379> DEL bignums
for i in $(seq 1 600); do redis-cli sadd bignums $i; done
127.0.0.1:6379> OBJECT ENCODING bignums
"hashtable"               # 600 > 512，且 600 > 128，所以是 hashtable
```

**intset 的特点**：底层是一个**有序的整数数组**，用二分查找定位，所以 `SISMEMBER` 是 O(log N) 而不是 O(1)。它还会根据最大值自动升级编码宽度（int16 → int32 → int64），且升级同样不可逆——存入一个大整数后，即使删掉它，数组也不会降回 int16。这也是为什么 intset 极省内存：500 个小整数用 int16 只要约 1 KB，换成 hashtable 至少要几十 KB。
