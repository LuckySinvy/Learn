# 哨兵：自动故障转移

主从复制解决了数据冗余，但主库挂了仍需人工执行 `REPLICAOF NO ONE` 切换——凌晨三点的告警电话不是高可用。**Sentinel（哨兵）** 是 Redis 官方的自动故障转移方案：一组哨兵进程持续监控主从，主库故障时自动选出新主库并通知客户端。

## 1. 架构

哨兵本身是特殊模式的 Redis 进程，**必须部署至少 3 个、奇数个、分布在不同机器**：

```text
   +----------+   +----------+   +----------+
   | Sentinel1|   | Sentinel2|   | Sentinel3|     互相通信, 交换对节点的看法
   +----+-----+   +----+-----+   +----+-----+
        |  \        /  |  \        /  |
        |   监控主库+从库（PING、INFO）  |
        v              v              v
    +-------+      +-------+      +-------+
    | Master| ---> |Replica| ---> |Replica|
    +-------+      +-------+      +-------+
```

为什么至少 3 个？故障判定和选举都需要**多数派**投票——2 个哨兵挂 1 个就凑不齐多数，1 个哨兵则自身就是单点，还容易因网络分区误判。

### 1.1 配置与启动

```conf
# sentinel.conf
port 26379
# 监控名为 mymaster 的主库, quorum=2 (2 个哨兵认为它挂了才算真挂)
sentinel monitor mymaster 192.168.1.10 6379 2
sentinel auth-pass mymaster Your_Strong_Pass123
sentinel down-after-milliseconds mymaster 5000    # 5 秒无响应视为主观下线
sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1     # 切换后同时向新主同步的从库数
```

```bash
redis-sentinel /etc/redis/sentinel.conf
# 或 redis-server /etc/redis/sentinel.conf --sentinel
```

只需配置主库地址：哨兵通过 `INFO replication` 自动发现从库，通过主库上的 `__sentinel__:hello` 频道自动发现其他哨兵。

```bash
# 哨兵管理命令
$ redis-cli -p 26379
127.0.0.1:26379> SENTINEL get-master-addr-by-name mymaster
1) "192.168.1.10"
2) "6379"
127.0.0.1:26379> SENTINEL replicas mymaster
...
127.0.0.1:26379> SENTINEL sentinels mymaster
...
```

## 2. 故障判定：主观下线与客观下线

### 2.1 主观下线（SDOWN）

每个哨兵每秒 PING 所有被监控节点。某哨兵在 `down-after-milliseconds` 内收不到有效回复，就**单方面**标记该节点主观下线（Subjectively Down）——"我觉得它挂了"。

### 2.2 客观下线（ODOWN）

主观下线可能是这个哨兵自己网络不好。于是它询问其他哨兵：

```text
Sentinel1: "你们看 master 挂了吗?"  (SENTINEL is-master-down-by-addr)
Sentinel2: "挂了+1"
Sentinel3: "挂了+1"

同意数 >= quorum (2)  =>  客观下线 (Objectively Down)
                          可以启动故障转移了
```

只有**主库**才有客观下线的概念（从库和哨兵 SDOWN 即可，不触发转移）。quorum 设为"哨兵总数的多数"（3 个哨兵设 2）是常规做法。

## 3. 领导者选举：谁来执行切换

多个哨兵同时发起切换会打架，必须选一个**领导者**独自执行。选举是 Raft 风格：

```text
1. 发现 ODOWN 的哨兵把自己的"纪元(epoch)"+1, 请求其他哨兵投票给自己
2. 每个哨兵在每个纪元里只有一票, 先到先得
3. 拿到 多数派(超过半数) 且 >= quorum 票的哨兵当选
4. 平票/超时? 纪元再+1, 随机延迟后重新拉票
```

这就是"哨兵要奇数个"的原因：偶数个更容易平票，且 4 个哨兵的容错能力（可挂 1 个）和 3 个一样，纯浪费。

## 4. 故障转移四步流程

领导者哨兵按以下顺序执行：

```text
第 1 步: 挑选新主库。从库候选按优先级过滤与排序:
         ① 剔除: 已下线/断连时间过长的
         ② 比较 replica-priority (配置项, 越小越优先, 0 = 永不当选)
         ③ 比较复制偏移量 offset (数据最全的赢)
         ④ 比较 runid (最后的平局裁决)

第 2 步: 对选中的从库执行 REPLICAOF NO ONE, 使其成为主库

第 3 步: 对其余从库执行 REPLICAOF 新主库地址
         (parallel-syncs 控制同时切几个, 防止新主库被同步请求打垮)

第 4 步: 把旧主库标记为新主库的从库
         (它恢复后, 哨兵会命令它 REPLICAOF 新主库, 自动归队)
```

```bash
# 手动触发一次故障转移（演练/维护时用）
127.0.0.1:26379> SENTINEL failover mymaster
OK
```

## 5. 客户端如何感知新主库

主库地址变了，应用怎么知道？**客户端不能写死主库 IP**，正确姿势是"问哨兵"：

```text
应用启动/重连时:
  1. 连任意一个哨兵
  2. SENTINEL get-master-addr-by-name mymaster -> 得到当前主库地址
  3. 连接主库, 校验其 role 确实是 master
运行中:
  订阅哨兵的 +switch-master 事件频道, 收到即重建连接
```

主流客户端库都内置了 Sentinel 支持，只需配置哨兵地址列表：

```python
# Python redis-py
from redis.sentinel import Sentinel
sentinel = Sentinel([('10.0.0.1', 26379), ('10.0.0.2', 26379), ('10.0.0.3', 26379)],
                    socket_timeout=0.5)
master = sentinel.master_for('mymaster', password='xxx')   # 写走主库
replica = sentinel.slave_for('mymaster', password='xxx')   # 读走从库
master.set('k', 'v')
```

```java
// Java Jedis
Set<String> sentinels = Set.of("10.0.0.1:26379", "10.0.0.2:26379", "10.0.0.3:26379");
JedisSentinelPool pool = new JedisSentinelPool("mymaster", sentinels, "xxx");
try (Jedis jedis = pool.getResource()) {
    jedis.set("k", "v");    // 池自动指向当前主库, 切换后自动更新
}
```

<Callout type="warn" title="脑裂：切换后旧主库还在收写入">
网络分区时可能出现：哨兵和多数从库在 A 侧，选出了新主库；旧主库孤零零在 B 侧**还活着**，不知情的客户端继续往它写。分区恢复后旧主库被降级为从库、清空重新同步——**B 侧期间的写入全部丢失**。缓解手段：主库配置 `min-replicas-to-write 1` + `min-replicas-max-lag 10`，孤立的旧主库因为连不上任何从库会自动拒绝写入，把丢失窗口压缩到 10 秒左右。
</Callout>

<Callout type="info" title="哨兵不做数据分片">
哨兵集群管理的是"一主多从"的单份数据，解决的是**可用性**。数据量超过单机内存、写入吞吐超过单主上限时，哨兵无能为力——那是 Cluster 的领域（下一章）。经验：数据 10 GB 以内、写 QPS 单机可承载，用哨兵（架构简单）；超出则上 Cluster。
</Callout>

## 6. 部署清单

- 3 或 5 个哨兵，跨机器/机架/可用区部署，绝不与主库同机全灭；
- `down-after-milliseconds`：太短容易误判（网络抖动就切换），太长故障恢复慢，常用 5~30 秒；
- 所有哨兵的配置保持一致；哨兵会自动改写自己的配置文件（记录纪元、发现的节点），这是正常现象；
- 定期演练 `SENTINEL failover` ，验证客户端能自动跟随切换——**没演练过的高可用等于没有高可用**。

## 小结

- 哨兵 = 监控 + 多数派故障判定（SDOWN 到 ODOWN）+ Raft 式领导者选举 + 自动切换
- 至少 3 个、奇数个、跨机器部署；quorum 通常设为多数
- 新主库按"优先级、复制偏移量、runid"三级挑选，数据最全者优先
- 客户端通过哨兵发现主库地址，切换事件驱动重连；防脑裂靠 min-replicas-to-write
- 数据超单机容量？下一章 Cluster 分片 →

日志会依次出现以下事件：

```bash
# ---- 阶段 1：SDOWN（主观下线）----
# 单个哨兵在 down-after-milliseconds(5秒) 内 PING 不通主库
+sdown master mymaster 172.20.0.2 6379

# ---- 阶段 2：ODOWN（客观下线）----
# 哨兵之间通过 SENTINEL is-master-down-by-addr 互相询问
# 确认下线的哨兵数达到 quorum(2) → 判定客观下线
+odown master mymaster 172.20.0.2 6379 #quorum 2/2

# ---- 阶段 3：领导者选举（Raft 式）----
+new-epoch 1                                    # 纪元 +1
+try-failover master mymaster 172.20.0.2 6379   # 尝试发起故障转移
+vote-for-leader 4f8c2a1e... 1                  # 投票给某个哨兵
# 其他哨兵的投票也会到达
+elected-leader master mymaster 172.20.0.2 6379 # 当选为领导者

# ---- 阶段 4：选择新主库 ----
+failover-state-select-slave master mymaster 172.20.0.2 6379
+selected-slave slave 172.20.0.3:6379 ...       # 选中 replica1
+failover-state-send-slaveof-noone slave 172.20.0.3:6379 ...
+failover-state-wait-promotion slave 172.20.0.3:6379 ...
+promoted-slave slave 172.20.0.3:6379 ...       # 提升为主库

# ---- 阶段 5：重新配置其他从库 ----
+failover-state-reconf-slaves master mymaster 172.20.0.2 6379
+slave-reconf-sent slave 172.20.0.4:6379 ...    # 通知 replica2
+slave-reconf-inprog slave 172.20.0.4:6379 ...
+slave-reconf-done slave 172.20.0.4:6379 ...

# ---- 阶段 6：切换完成 ----
+failover-end master mymaster 172.20.0.2 6379
+switch-master mymaster 172.20.0.2 6379 172.20.0.3 6379
#              ^^^^^^^^ 旧主库地址        ^^^^^^^^ 新主库地址

# ---- 阶段 7：旧主库被标记为从库（仍处于 sdown 状态）----
+slave slave 172.20.0.2:6379 ... @ mymaster 172.20.0.3 6379
+sdown slave 172.20.0.2:6379 ...
```

**`+switch-master` 是最关键的事件**——客户端库正是订阅这个频道来感知主库变更并重连的。

```bash
# 验证新主库
$ docker compose exec replica1 redis-cli INFO replication
role:master
connected_slaves:1
slave0:ip=172.20.0.4,port=6379,state=online,offset=15420,lag=0
```

**SDOWN 与 ODOWN 的区别（面试高频）**：

| | SDOWN（主观下线） | ODOWN（客观下线） |
|---|---|---|
| 判定者 | **单个**哨兵独立判断 | **多个**哨兵达成共识 |
| 依据 | 自己 PING 超时 | 认同 SDOWN 的哨兵数 ≥ quorum |
| 后果 | 仅内部标记，**不触发切换** | 触发领导者选举和故障转移 |
| 适用对象 | 主库和从库都可能 | **只对主库有意义** |

这个两阶段设计是为了防止**单个哨兵的网络问题**误判主库宕机。如果只有哨兵 A 到主库的网络断了，A 会标记 SDOWN，但 B 和 C 说"主库好好的"，达不到 quorum，就不会有 ODOWN，也就不会误切换。

**2. 旧主库重启后自动降级为从库**

```bash
# ---- 重启旧主库 ----
$ docker compose start master

# ---- 等几秒后查看它的角色 ----
$ docker compose exec master redis-cli INFO replication
# Replication
role:slave                       # 已经自动变成从库了
master_host:172.20.0.3           # 指向新主库（原 replica1）
master_port:6379
master_link_status:up
slave_read_only:1
slave_repl_offset:15680

# ---- 哨兵日志 ----
$ docker compose logs sentinel1 --tail 10
-sdown slave 172.20.0.2:6379 ...                # 恢复在线
* Sending SLAVEOF command to a replica ...      # 哨兵下发 REPLICAOF
+convert-to-slave slave 172.20.0.2:6379 ...     # 转为从库

# ---- 现在的拓扑：新主库 + 2 从库 ----
$ docker compose exec sentinel1 redis-cli -p 26379 SENTINEL master mymaster | head -6
1) "name"
2) "mymaster"
3) "ip"
4) "172.20.0.3"                  # 主库已是新地址
```

**这个自动降级是哨兵最重要的能力之一**。哨兵持续监控所有节点，一旦发现某个节点声称自己是 master 但和当前记录的主库不符，就会给它发 `REPLICAOF <新主库>` 命令，强制它归位。

**这里隐藏着数据丢失风险（必须理解）**：

```bash
# 时间线：
#   T1: 客户端向旧主库写入 x=100，主库返回 OK
#   T2: 复制是【异步】的，x=100 还没发给从库
#   T3: 旧主库宕机
#   T4: 哨兵切换，replica1 升为新主库（它没有 x=100）
#   T5: 旧主库重启，变成从库
#   T6: 从库执行全量或部分重同步，【x=100 被覆盖丢失】
#
# 结果：客户端收到过 OK，但数据永久消失
```

这是**异步复制的固有代价，无法通过配置完全消除**。缓解手段：

```bash
# 主库配置：从库不足时拒绝写入
127.0.0.1:6379> CONFIG SET min-replicas-to-write 1      # 至少 1 个从库在线
OK
127.0.0.1:6379> CONFIG SET min-replicas-max-lag 10      # 且延迟不超过 10 秒
OK

# 效果：不满足条件时主库直接报错，宁可写失败也不"假装成功"
127.0.0.1:6379> SET k v
(error) NOREPLICAS Not enough good replicas to write.
```

这个配置也是**防脑裂的核心手段**：网络分区时，被隔离的旧主库因为看不到足够的从库而拒绝写入，避免产生"两个主库各自接收写入"的分叉数据。

**要真正的零丢失只能上 WAIT 或换方案**：

```bash
# WAIT 让写入等待从库确认（牺牲延迟换安全）
127.0.0.1:6379> SET important "value"
OK
127.0.0.1:6379> WAIT 1 500
(integer) 1
# 但 WAIT 只保证"从库收到"不保证"从库落盘"，且超时后仍会返回，不是强一致
```

**运维提醒**：`+switch-master` 之后，`sentinel monitor` 的配置会被哨兵自动改写到配置文件里。如果你用配置管理工具（Ansible/Puppet）强制覆盖 sentinel.conf，会把哨兵的状态搞乱——**哨兵配置文件必须排除在配置管理之外**。

**3. 为什么 quorum=1 危险，2 个哨兵为什么不可靠**

**先厘清两个容易混淆的概念**：

| 概念 | 作用 | 取值 |
|---|---|---|
| **quorum** | 判定 ODOWN 需要多少个哨兵同意 | 配置项，可自定义 |
| **majority** | 执行故障转移需要多少票当选领导者 | **固定为 `哨兵总数/2 + 1`，不可配置** |

关键点：**这是两道独立的门槛，必须同时通过。** 很多人只调 quorum 就以为控制了整个流程，其实 majority 这一关是硬编码的。

```bash
# 3 个哨兵：quorum 可配 1~3，majority 固定为 2
# 5 个哨兵：quorum 可配 1~5，majority 固定为 3
```

**为什么 quorum=1 很危险？**

`quorum=1` 意味着**任何单个哨兵都能独自判定主库客观下线**，两阶段判定退化成一阶段。

```bash
# 危险场景：哨兵 A 到主库的网络出问题（主库本身完全健康）
#
#   T1: 哨兵 A ping 主库超时 → 标记 SDOWN
#   T2: quorum=1，A 自己就够了 → 立刻判定 ODOWN
#   T3: A 发起选举，向 B、C 拉票
#   T4: B、C 虽然认为主库是健康的，但【投票阶段不校验主库状态】，
#       它们只判断"这个 epoch 我还没投过票"，于是投给了 A
#   T5: A 获得 2 票（含自己），达到 majority=2，当选领导者
#   T6: A 执行故障转移，把一个健康的主库换掉了
```

**后果**：

- **无谓的服务抖动**：切换过程中主库地址变更，所有客户端要重连，期间写入失败
- **可能丢数据**：切换瞬间未同步的写入全部丢失
- **可能真脑裂**：旧主库网络恢复后，如果客户端还连着它（未及时收到切换通知），就会出现两个主库同时接收写入
- **反复横跳**：如果网络问题持续存在，哨兵可能不断触发切换，系统永无宁日

**根本问题**：`quorum` 的设计初衷就是**用多数派共识过滤单点误判**。设成 1 等于主动放弃这个保护机制，把整个集群的稳定性押在"每个哨兵的网络都不会出问题"这个不成立的假设上。

**正确配置**：

```bash
# 3 个哨兵 → quorum = 2
sentinel monitor mymaster 127.0.0.1 6379 2

# 5 个哨兵 → quorum = 3
sentinel monitor mymaster 127.0.0.1 6379 3

# 通用原则：quorum = 哨兵总数 / 2 + 1（即 majority）
```

**为什么 2 个哨兵不可靠？**

2 个哨兵时：`majority = 2/2 + 1 = 2`，即**必须两个哨兵都活着并互相投票才能完成故障转移**。

**场景一：哨兵和主库同机部署，机器整体宕机**

```bash
# 部署：机器1 = 主库 + 哨兵A，机器2 = 从库 + 哨兵B
#
# 机器1 整机宕机（这恰恰是最需要故障转移的场景）：
#   - 主库挂了
#   - 哨兵 A 也挂了
#   - 只剩哨兵 B
#   - B 标记 SDOWN，quorum=2 但只有 B 一个 → 【永远达不到 ODOWN】
#   - 故障转移完全无法触发
#
# 结果：高可用系统在最关键的时刻失效了
```

即使把 quorum 调成 1 让 B 能判定 ODOWN，它也拿不到 `majority=2` 的票数，选举失败，照样无法切换。

**场景二：两个哨兵之间网络分区**

```bash
# 主库和从库都健康，只是哨兵 A 和 B 互相看不见对方
#
#   A 认为 B 挂了，B 认为 A 挂了
#   假设主库此时也真的挂了：
#     - A 想切换，但拿不到 B 的票，只有自票 1 张 < majority 2 → 失败
#     - B 同理 → 失败
#   两边都在无限重试，谁也切不成
#
# 更糟的情况（如果 quorum=1）：
#   A 和 B 各自认为对方挂了，可能在不同 epoch 中反复尝试，
#   系统陷入选举风暴，日志刷屏，始终无法收敛
```

**核心矛盾**：分布式共识需要**奇数个节点**才能在任意单点故障下仍然形成多数派。

```bash
# 容错能力对照表（N = 哨兵总数，majority = N/2 + 1）
#
# N=1: majority=1, 容忍 0 个故障   → 单点，无意义
# N=2: majority=2, 容忍 0 个故障   → 【比 1 个还差：多了一个故障源，容错却没提升】
# N=3: majority=2, 容忍 1 个故障   → ✓ 最小可用配置
# N=4: majority=3, 容忍 1 个故障   → 和 3 个一样，白白多花一台机器
# N=5: majority=3, 容忍 2 个故障   → ✓ 更高可靠性
# N=6: majority=4, 容忍 2 个故障   → 和 5 个一样，浪费
# N=7: majority=4, 容忍 3 个故障   → ✓
```

**"2 个比 1 个还差"这个反直觉的结论值得强调**：单哨兵至少在自己健康时能完成切换（majority=1，自己投自己就够了）；而 2 个哨兵一旦挂掉任意一个，剩下那个**什么都做不了**。多部署一个节点反而降低了可用性——因为故障源变多了，容错能力却纹丝不动。

**偶数节点全都浪费**：4 个的容错能力等于 3 个，6 个等于 5 个。多出来的那台机器只增加了成本和故障概率，对可靠性零贡献。所以**哨兵数量必须是奇数**。

**生产部署清单**：

```bash
# 1. 至少 3 个哨兵，奇数个
# 2. 分散在【不同的物理机】上（虚拟机要确认不在同一宿主机）
# 3. 不要和 Redis 主库同机 —— 主库所在机器宕机会同时带走哨兵
# 4. 跨机架 / 跨可用区部署，避免机架级、机房级单点

# 三机房部署示例（推荐）：
#   机房 A：主库    + 哨兵1
#   机房 B：从库1   + 哨兵2
#   机房 C：从库2   + 哨兵3
#
# 任意一个机房整体失联，剩下两个机房的 2 个哨兵仍能形成多数派

# 双机房部署的问题（不推荐）：
#   机房 A：主库 + 从库1 + 哨兵1 + 哨兵2
#   机房 B：从库2 + 哨兵3
#
#   机房 A 整体故障 → 只剩哨兵3，majority=2 达不到 → 无法切换
#   这就是为什么高可用需要【三个】故障域，两个是不够的
```

**其他关键配置**：

```bash
# down-after-milliseconds：判定 SDOWN 的超时
# 太小 → 网络抖动误判，频繁切换
# 太大 → 故障发现慢，服务中断时间长
# 建议 5000 ~ 30000，必须【大于最坏 fork 耗时】（否则 BGSAVE 会被误判为宕机）
sentinel down-after-milliseconds mymaster 30000

# parallel-syncs：切换后同时向新主库同步的从库数
# 设为 1：从库逐个同步，任一时刻只有 1 个从库不可用（推荐）
# 设大：切换快，但多个从库同时全量同步会打爆新主库带宽
sentinel parallel-syncs mymaster 1

# failover-timeout：故障转移各阶段的超时，超时后允许其他哨兵重新尝试
sentinel failover-timeout mymaster 180000
```

**最后一条最重要的建议**：**定期做故障演练**。

```bash
# 手动触发故障转移（不需要真的杀主库）
$ redis-cli -p 26379 SENTINEL failover mymaster
OK

# 演练时要验证的事项：
#   1. 切换是否在预期时间内完成
#   2. 应用日志里有多少请求失败，业务是否有感知
#   3. 客户端是否自动重连到新主库（有些客户端配置不对会一直连旧地址）
#   4. 监控告警是否正常触发
#   5. 旧主库恢复后是否自动降级
```

配置得再完美，**没演练过的高可用等于没有高可用**。生产上最常见的翻车不是哨兵不工作，而是**客户端没配 Sentinel 模式**——业务代码里硬编码了主库 IP，切换后哨兵这边一切正常，应用却全线连不上。这种问题只有演练才能提前暴露。
