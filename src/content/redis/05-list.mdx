# List：队列、栈与时间线

List 是一个**双端链表**语义的有序集合：两端都能推入弹出，中间可按下标访问。它是 Redis 里最简单的消息队列载体，也是"最新 N 条"类需求（时间线、操作日志）的标准答案。

## 1. 数据模型

```text
          LPUSH 从左进                RPUSH 从右进
              |                           |
              v                           v
  左(头) <- [ e4 | e3 | e2 | e1 | e0 ] -> 右(尾)
              ^                           ^
              |                           |
          LPOP 从左出                  RPOP 从右出
```

- `LPUSH` + `RPOP`（或反向）= 队列（FIFO）
- `LPUSH` + `LPOP` = 栈（LIFO）

### 2.2 范围读取与裁剪

<Playground
  language="redis"
  title="范围读取与 LTRIM 裁剪"
  id="redis-05-2"
  code={`RPUSH timeline p1 p2 p3 p4 p5
LRANGE timeline 0 2
# 负下标从尾部数

/>

`LPUSH` + `LTRIM` 组合是"定长时间线"的标准姿势：

```bash
# 用户动态流: 新动态插头部，只保留最新 100 条
127.0.0.1:6379> LPUSH feed:u1001 "post:9527"
(integer) 101
127.0.0.1:6379> LTRIM feed:u1001 0 99
OK
```

### 2.3 按下标与按值操作

<Playground
  language="redis"
  title="按下标与按值操作"
  id="redis-05-3"
  code={`RPUSH timeline p1 p2 p3
LINDEX timeline 0

注意 `LINDEX`/`LSET`/`LINSERT` 都是 O(n)，长列表上慎用。

### 2.4 阻塞弹出：BLPOP / BRPOP

消费者轮询空队列既浪费 CPU 又有延迟。阻塞版本让连接挂起等待，有数据立刻返回：

```bash
# 消费者窗口: 阻塞等待，最长 30 秒（0 表示无限等待）
127.0.0.1:6379> BLPOP queue:email 30
（挂起中...）

# 另一个窗口的生产者:
127.0.0.1:6379> RPUSH queue:email "to:ada@example.com"
(integer) 1

# 消费者立刻返回:
1) "queue:email"        # 哪个 key 有数据（BLPOP 可同时监听多个 key）
2) "to:ada@example.com"
(3.62s)
```

### 2.5 LMOVE：可靠队列的雏形

`RPOPLPUSH` 已废弃，Redis 6.2+ 用 `LMOVE`：原子地把元素从一个列表转移到另一个列表。

<Playground
  language="redis"
  title="LMOVE 双队列可靠消费"
  id="redis-05-4"
  code={`RPUSH pending "task-1" "task-2"
# 从 pending 左端取出，放入 processing 右端
LMOVE pending processing LEFT RIGHT
LRANGE pending 0 -1
LRANGE processing 0 -1
# 处理成功后从 processing 删除
# 消费者崩溃则 task 还留在 processing，可被恢复重投
LREM processing 1 "task-1"
LLEN processing`}
/>

这个"工作队列 + 处理中队列"模式让消息在消费者崩溃时不丢失，也有阻塞版 `BLMOVE`。

## 3. 底层编码：quicklist

Redis 7 中 List 的编码是 listpack 或 quicklist：

```bash
127.0.0.1:6379> OBJECT ENCODING timeline
"listpack"              # 元素少且短时
```

元素超过 128 个或单元素超 64 字节后转为 quicklist——一个**由多个 listpack 节点组成的双向链表**：

```text
quicklist:
 head                                              tail
  |                                                 |
  v                                                 v
+---------+     +---------+     +---------+     +---------+
| listpack| <-> | listpack| <-> | listpack| <-> | listpack|
| e1..e64 |     | e65..   |     |  ...    |     | ..eN    |
+---------+     +---------+     +---------+     +---------+
```

设计动机：纯双向链表每个节点都有前后指针（16 字节开销）且内存碎片化；纯 listpack 大了以后插入删除要整体挪动。quicklist 折中：**链表串起一段段小 listpack**，两端操作 O(1)，内存又紧凑。相关配置：

```conf
list-max-listpack-size 128   # 每个 listpack 节点的元素上限
list-compress-depth 0        # 两端各保留几个节点不压缩（中间节点可 LZF 压缩）
```

复杂度速查：LPUSH/RPUSH/LPOP/RPOP 为 O(1)；LRANGE 为 O(s+n)；LINDEX/LREM/LINSERT 为 O(n)。

## 4. List 做消息队列的局限

List 是入门级队列，但相比专业方案缺了不少东西：

| 能力 | List | Stream（第 9 章） |
|---|---|---|
| 阻塞消费 | BLPOP 支持 | XREAD BLOCK 支持 |
| 消息确认 ACK | 无（弹出即删除） | XACK 支持 |
| 消费组（多消费者分摊） | 无，弹出即抢占 | XGROUP 支持 |
| 重复消费/回溯 | 不可能 | 消息保留可回溯 |
| 广播（一条消息多方消费） | 不支持 | 多个消费组各自独立消费 |

<Callout type="warn" title="BLPOP 弹出即删除，崩溃就丢消息">
消费者 BLPOP 拿到消息后、处理完成前如果崩溃，这条消息就永久丢失了。要可靠性就用 LMOVE 双队列模式，或者直接上 Stream。另外注意：BLPOP 阻塞期间连接被占用，使用连接池的客户端要为阻塞命令使用独立连接。
</Callout>

<Callout type="info" title="时间线场景的局限">
LPUSH + LTRIM 的时间线只能"按插入顺序"排列。如果需要按分数排序（热度榜）、按时间范围查询、去重插入，应该用 ZSet。List 适合"只追加、只看最新 N 条"的简单场景。
</Callout>

## 小结

- List 双端 O(1) 操作：LPUSH/RPUSH/LPOP/RPOP 组合出队列与栈
- LPUSH + LTRIM 实现定长时间线；BLPOP 实现无轮询消费
- LMOVE 双队列模式给消息加上"处理中"状态，防消费者崩溃丢消息
- 编码：小列表 listpack，大列表 quicklist（listpack 节点组成的链表）
- 需要 ACK、消费组、消息回溯时，升级到 Stream →（第 9 章）
- 下一章 Set：无序去重集合 →

127.0.0.1:6379> BLPOP task:queue 0        # 0 = 永久阻塞，直到有数据

三个关键观察：

- **耗时标记 `(23.47s)`**：redis-cli 只在命令耗时超过 0.5 秒时才显示。这个数字证明连接是真的被挂起了，不是在轮询
- **返回值是两元素数组**：因为 `BLPOP` 可以同时监听多个队列（`BLPOP q1 q2 q3 0`），所以必须告诉你数据来自哪个队列。这一点写代码时很容易忘，直接取返回值当数据会拿到队列名
- **阻塞不消耗 CPU**：客户端被挂到该 key 的阻塞链表上，`RPUSH` 时由服务端主动唤醒。对比"每秒 `LPOP` 一次"的轮询方案，既省 CPU 又零延迟

```bash
# 设置超时，避免连接永久占用
127.0.0.1:6379> BLPOP task:queue 5
(nil)
(5.02s)                                   # 5 秒无数据，返回 nil

# 多个消费者时先阻塞的先拿到数据（FIFO 公平唤醒）
# 窗口 A 先 BLPOP，窗口 C 后 BLPOP，此时 RPUSH 一条 → A 拿到
```

**重要提醒**：`BLPOP` 阻塞期间这条连接完全被占用，无法执行其他命令。用连接池的客户端（Jedis、Lettuce、go-redis）必须为阻塞命令**单独分配连接**，否则会把整个池耗尽导致其他业务卡死。

**2. 最近浏览记录（去重 + 定长）**

```bash
# 用户浏览商品 3001
127.0.0.1:6379> LREM history:u1001 0 3001      # 先删掉已存在的（0 = 删除全部匹配项）
(integer) 0
127.0.0.1:6379> LPUSH history:u1001 3001       # 再从头部插入
(integer) 1
127.0.0.1:6379> LTRIM history:u1001 0 9        # 只保留前 10 条（下标 0~9）
OK

# 又浏览 3002
127.0.0.1:6379> LREM history:u1001 0 3002
(integer) 0
127.0.0.1:6379> LPUSH history:u1001 3002
(integer) 2
127.0.0.1:6379> LTRIM history:u1001 0 9
OK

# 重新浏览 3001（已存在，验证去重 + 置顶效果）
127.0.0.1:6379> LREM history:u1001 0 3001
(integer) 1                                     # 返回 1，说明确实删掉了旧记录
127.0.0.1:6379> LPUSH history:u1001 3001
(integer) 2
127.0.0.1:6379> LTRIM history:u1001 0 9
OK

# 查看结果：3001 跑到了最前面，且只出现一次
127.0.0.1:6379> LRANGE history:u1001 0 -1

127.0.0.1:6379> EXPIRE history:u1001 2592000

```

**必须用事务或 Lua 保证原子性**，否则并发浏览时可能出现重复项：

```bash
# 方式一：MULTI/EXEC 打包（三条命令连续执行，中间不插入其他客户端命令）
127.0.0.1:6379> MULTI
OK
127.0.0.1:6379> LREM history:u1001 0 3005
QUEUED
127.0.0.1:6379> LPUSH history:u1001 3005
QUEUED
127.0.0.1:6379> LTRIM history:u1001 0 9
QUEUED
127.0.0.1:6379> EXEC
1) (integer) 0
2) (integer) 3
3) OK

# 方式二：Lua 脚本（可复用，只传参数）
127.0.0.1:6379> EVAL "redis.call('LREM', KEYS[1], 0, ARGV[1]); redis.call('LPUSH', KEYS[1], ARGV[1]); redis.call('LTRIM', KEYS[1], 0, tonumber(ARGV[2]) - 1); return redis.call('LLEN', KEYS[1])" 1 history:u1001 3006 10
(integer) 4
```

三条命令的分工：

| 命令 | 作用 | 复杂度 |
|---|---|---|
| `LREM key 0 v` | 去重：删除所有等于 v 的元素 | O(N) |
| `LPUSH key v` | 置顶：从头部插入 | O(1) |
| `LTRIM key 0 9` | 定长：截断到 10 条 | O(N) |

因为 `LTRIM` 保证了长度始终 ≤ 10，`LREM` 的 O(N) 里 N 最大只有 10，所以整体性能没有问题。**但如果没有 `LTRIM`，`LREM` 会随列表增长越来越慢**——这是这个模式必须三条命令配套使用的原因。

`LREM` 的第二个参数含义：正数 = 从头开始删 N 个，负数 = 从尾开始删 N 个，`0` = 删除全部匹配项。去重场景固定用 `0`。

**3. 观察 listpack 到 quicklist 的转换**

```bash
127.0.0.1:6379> DEL mylist
(integer) 1

# 先加 100 个元素（未超过 list-max-listpack-size 128）
for i in $(seq 1 100); do redis-cli rpush mylist "item$i"; done
127.0.0.1:6379> LLEN mylist
(integer) 100
127.0.0.1:6379> OBJECT ENCODING mylist
"listpack"

# 继续加到 200 个，突破 128
for i in $(seq 101 200); do redis-cli rpush mylist "item$i"; done
127.0.0.1:6379> LLEN mylist
(integer) 200
127.0.0.1:6379> OBJECT ENCODING mylist
"quicklist"

# 验证不可逆：删到只剩 10 个，编码依然是 quicklist
127.0.0.1:6379> LTRIM mylist 0 9
OK
127.0.0.1:6379> LLEN mylist
(integer) 10
127.0.0.1:6379> OBJECT ENCODING mylist
"quicklist"

# 另一条触发路径：单个元素过大（默认单元素超 64 字节也会转）
127.0.0.1:6379> DEL big
127.0.0.1:6379> RPUSH big "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
(integer) 1
127.0.0.1:6379> OBJECT ENCODING big
"quicklist"
```

**两种编码的取舍**：

- **listpack**：一整块连续内存，无指针开销，缓存命中率高。缺点是插入/删除要 memmove 整块数据，元素多了会很慢，还可能触发连锁更新
- **quicklist**：多个 listpack 节点串成的双向链表。每个节点内部仍然紧凑，节点之间用指针连接。这样既避免了单块内存过大导致的 memmove 成本，又比纯双向链表（每个元素两个指针，64 位下 16 字节纯开销）省内存

`list-compress-depth` 配置可以让**中间节点做 LZF 压缩**（两端各保留 N 个节点不压缩）。这对"只操作两端"的队列场景很划算：中间的数据反正不访问，压缩后能省一半以上内存。设为 `1` 表示首尾各留 1 个节点不压缩。

和 Hash 一样，List 的编码转换也是**单向**的，原因同样是避免阈值边界的反复抖动。
