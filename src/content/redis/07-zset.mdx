# ZSet：排行榜背后的跳表

ZSet（Sorted Set）给每个成员绑定一个 double 类型的 **score**，集合始终按 score 排序。它同时具备三种能力：按分数排序、按排名取段、按成员查分——这让它成为排行榜、延时队列、滑动窗口限流的首选结构。

## 1. 数据模型

```text
key: rank:game
score      member
------     --------
 98.0  <-> "ada"       按 score 升序排列
 95.5  <-> "bob"       score 相同时按 member 字典序
 95.5  <-> "carol"
 80.0  <-> "dave"
```

成员唯一（再次 ZADD 同名成员是更新分数），score 可重复。

## 2. 核心命令实操

### 2.1 写入与更新

ZADD 的条件参数：`NX` 只增不改、`XX` 只改不增、`GT`/`LT` 只在新分数更大/更小时更新（做"历史最高分"极方便）。

## 3. 底层实现：skiplist + hashtable 双结构

小 ZSet 用 listpack（≤128 个成员且都 ≤64 字节）；超过阈值后用 **skiplist + hashtable 的组合**：

```bash
127.0.0.1:6379> OBJECT ENCODING rank:game
"listpack"
```

```conf
zset-max-listpack-entries 128
zset-max-listpack-value 64
```

为什么要两个结构一起用？因为 ZSet 要同时满足两类查询：

- `ZSCORE member` —— 按成员查分数，需要 **hashtable**：O(1)；
- `ZRANGE`/`ZRANK` —— 按分数/排名的有序操作，需要 **skiplist**：O(log n)。

两个结构共享成员与分数（通过指针），内存不双倍。

### 3.1 跳表长什么样

跳表是"带多层快速通道的有序链表"。每个节点随机决定层数（每升一层概率 1/4），高层是低层的"高速公路"：

```text
L3:  head ----------------------------> 50 ------------------> NULL
L2:  head ----------> 20 ------------> 50 ------------------> NULL
L1:  head --> 10 --> 20 -----> 35 --> 50 --> 70 ------------> NULL
L0:  head --> 10 --> 20 --> 30 --> 35 --> 50 --> 60 --> 70 --> NULL

查找 60: L3 到 50 (下一个是 NULL, 降层)
         L2 从 50 (下一个 NULL, 降层)
         L1 从 50 -> 70 超了, 降层
         L0 从 50 -> 60 命中。 跳过了大部分节点。
```

平均查找/插入/删除都是 O(log n)。每层节点还记录了到下一节点的**跨度（span）**，把沿途跨度累加就得到排名——这是 ZRANK 也能 O(log n) 的原因。

为什么不用红黑树？作者的理由：跳表实现简单得多；范围查询（ZRANGE）沿底层链表顺序走即可，比树的中序遍历更直接；调整概率参数即可权衡内存与速度。

## 4. 典型场景

### 4.1 排行榜

```bash
# 玩家得分更新（累加制）
127.0.0.1:6379> ZINCRBY lb:weekly 150 "player:1001"
"150"
# 取 Top 10
127.0.0.1:6379> ZRANGE lb:weekly 0 9 REV WITHSCORES
1) "player:1001"
2) "150"
# 查自己的名次与分数（两条命令可用 pipeline 合并）
127.0.0.1:6379> ZREVRANK lb:weekly "player:1001"
(integer) 0
127.0.0.1:6379> ZSCORE lb:weekly "player:1001"
"150"
```

周榜按周分 key（`lb:2026w31`），过期自动清理。同分排名问题：score 相同按成员字典序，若业务要求"先到先得排前面"，可以把时间戳编进小数位：`score = 分数 * 10^10 + (10^10 - 时间戳)`。

### 4.2 延时队列

score 存"应执行的时间戳"，消费者轮询取"到期任务"：

<Playground
  language="redis"
  title="ZSet 延时队列"
  id="redis-07-4"
  code={`# 生产：把"应执行时间戳"当作 score
ZADD delay:close-order 1722312000 "order:8801"
ZADD delay:close-order 1722315600 "order:8802"
# 消费：取一批到期任务（当前时间之前的）
ZRANGEBYSCORE delay:close-order -inf 1722312000 LIMIT 0 10
# 取到后用 ZREM 抢占，返回 1 才算抢到，防多个消费者重复处理
ZREM delay:close-order "order:8801"
# 未到期的任务仍留在队列里
ZRANGE delay:close-order 0 -1 WITHSCORES`}
/>

"ZRANGEBYSCORE 再 ZREM"两步之间存在竞态，严格场景用 Lua 脚本把"取+删"做成原子操作（第 12 章），或用 Redis 7 的 `ZMPOP`。

### 4.3 滑动窗口限流

member 存唯一请求 ID，score 存时间戳；统计窗口内的请求数：

```bash
# 判断 user:1 最近 60 秒是否超过 100 次请求
127.0.0.1:6379> ZREMRANGEBYSCORE rate:u1 -inf 1722311940   # 清掉窗口外
(integer) 3
127.0.0.1:6379> ZCARD rate:u1
(integer) 97            # 未超限, 放行并记录本次
127.0.0.1:6379> ZADD rate:u1 1722312000 "req-uuid-x"
(integer) 1
```

完整原子版本在第 20 章用 Lua 实现。

<Callout type="warn" title="ZSet 的成本意识">
ZSet 是所有结构里单元素内存开销最大的（skiplist 节点 + hashtable 项 + 分数）。百万级成员的 ZSet 内存可观且 ZRANGEBYSCORE 大范围扫描是 O(log n + m)。排行榜只保留 Top N（定期 ZREMRANGEBYRANK 裁剪），限流 key 记得设 TTL。
</Callout>

## 小结

- ZSet = 排序 + 去重 + 按成员查分，三种查询一个结构全包
- ZADD 的 GT/LT/NX/XX 参数优雅解决"历史最高分""只增不改"类需求
- 底层 skiplist（有序、范围、排名）+ hashtable（O(1) 查分）双结构配合
- 三大场景：排行榜（ZINCRBY + ZRANGE REV）、延时队列（score=执行时间）、滑动窗口限流

**2. ZSet 实现延时队列**

核心思路：**score = 任务的执行时间戳**，消费者轮询取出所有 score ≤ 当前时间的任务。

```bash
# ---- 加入 3 个不同到期时间的任务 ----
# 假设当前时间戳为 1785000000
127.0.0.1:6379> ZADD delay:queue 1785000010 "order:1001:cancel"   # 10 秒后
(integer) 1
127.0.0.1:6379> ZADD delay:queue 1785000060 "order:1002:cancel"   # 60 秒后
(integer) 1
127.0.0.1:6379> ZADD delay:queue 1785000300 "coupon:88:expire"    # 5 分钟后
(integer) 1

127.0.0.1:6379> ZRANGE delay:queue 0 -1 WITHSCORES
1) "order:1001:cancel"
2) "1785000010"
3) "order:1002:cancel"
4) "1785000060"
5) "coupon:88:expire"
6) "1785000300"

# ---- 消费者：取出"当前已到期"的任务 ----
# 假设现在时间走到了 1785000070
127.0.0.1:6379> ZRANGEBYSCORE delay:queue 0 1785000070 LIMIT 0 10
1) "order:1001:cancel"
2) "order:1002:cancel"

# 逐个删除（删除成功才处理，靠返回值抢占）
127.0.0.1:6379> ZREM delay:queue "order:1001:cancel"
(integer) 1               # 返回 1 = 我抢到了这个任务，可以处理
127.0.0.1:6379> ZREM delay:queue "order:1002:cancel"
(integer) 1

127.0.0.1:6379> ZCARD delay:queue
(integer) 1               # 只剩未到期的那个
```

**多消费者下必须保证原子性**，否则"查询 + 删除"两步之间会被别的消费者插入，导致同一任务被重复处理：

```bash
# 方式一：Lua 脚本，取出并删除做成一步
127.0.0.1:6379> EVAL "local t = redis.call('ZRANGEBYSCORE', KEYS[1], 0, ARGV[1], 'LIMIT', 0, tonumber(ARGV[2])); if #t > 0 then redis.call('ZREM', KEYS[1], unpack(t)) end; return t" 1 delay:queue 1785000070 10
1) "order:1001:cancel"
2) "order:1002:cancel"

# 方式二：Redis 5.0+ 的 ZPOPMIN，原子弹出最小分数的成员
127.0.0.1:6379> ZPOPMIN delay:queue 1
1) "coupon:88:expire"
2) "1785000300"
# 但 ZPOPMIN 不管有没有到期都会弹出，需要业务侧判断 score
# 如果没到期，得再 ZADD 放回去，有竞态风险，所以延时队列还是推荐 Lua

# 方式三：靠 ZREM 返回值抢占（简单但会多一次网络往返）
# 查到任务后，谁 ZREM 返回 1 谁处理，返回 0 说明被别人抢走了
```

**消费者的典型循环**（伪代码）：

```bash
# while true:
#   now = 当前秒级时间戳
#   tasks = EVAL(上面的Lua脚本, delay:queue, now, 100)
#   if tasks 为空:
#       sleep(1)          # 空转时休眠，避免打爆 Redis
#   else:
#       for t in tasks: 处理任务(t)
```

**和 List 队列的区别**：List 只能 FIFO，先进先出；ZSet 延时队列可以**按时间乱序插入、按时间顺序取出**，天然支持"30 分钟后取消未支付订单""7 天后自动确认收货"这类需求。

**生产注意事项**：

- **必须处理失败重试**：任务取出后如果处理失败，应该重新 `ZADD` 回队列（score 设为"当前时间 + 退避间隔"），否则任务就丢了。更稳妥的做法是先移到一个"处理中"的 ZSet，处理成功后再删，超时未完成的自动捞回
- **轮询间隔是延迟下限**：sleep 1 秒意味着任务最多晚 1 秒执行，对精度敏感的场景要缩短间隔
- **注意时间单位统一**：秒和毫秒混用是这个模式最常见的 bug，建议全用毫秒时间戳
- **ZSet 会无限增长**：如果生产快于消费，队列积压会变成大 key，要做监控告警

**3. 验证 listpack 到 skiplist 的转换**

```bash
127.0.0.1:6379> DEL z
(integer) 1

# 先写 120 个成员（未超过 zset-max-listpack-entries 128）
for i in $(seq 1 120); do redis-cli zadd z $i "m$i"; done
127.0.0.1:6379> ZCARD z
(integer) 120
127.0.0.1:6379> OBJECT ENCODING z
"listpack"

# 加到 130 个，突破 128
for i in $(seq 121 130); do redis-cli zadd z $i "m$i"; done
127.0.0.1:6379> ZCARD z
(integer) 130
127.0.0.1:6379> OBJECT ENCODING z
"skiplist"

# 验证不可逆
127.0.0.1:6379> ZREMRANGEBYRANK z 0 -11
(integer) 120
127.0.0.1:6379> ZCARD z
(integer) 10
127.0.0.1:6379> OBJECT ENCODING z
"skiplist"                # 只剩 10 个也不会转回 listpack

# 另一条触发路径：单个成员名超过 zset-max-listpack-value（默认 64 字节）
127.0.0.1:6379> DEL z2
127.0.0.1:6379> ZADD z2 1 "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
(integer) 1
127.0.0.1:6379> OBJECT ENCODING z2
"skiplist"                # 只有 1 个成员，但名字太长
```

相关配置：

```bash
# redis.conf
zset-max-listpack-entries 128    # 成员数上限
zset-max-listpack-value 64       # 单个成员名的字节数上限
```

**两种编码的差异**：

- **listpack**：连续内存，成员和分数交替存放，按分数排序。查找靠**线性扫描** O(N)，但因为元素少（≤128）且缓存友好，实际比 skiplist 更快，内存也省得多
- **skiplist**：实际是 **skiplist + hashtable 双结构**。skiplist 负责按分数排序、范围查询、排名计算（O(log N)）；hashtable 负责"给成员查分数"（O(1)）。两份结构存同一批数据，所以 ZSet 是所有类型里单元素内存开销最大的

这也解释了为什么 `ZSCORE` 是 O(1) 而 `ZRANK` 是 O(log N)——前者走 hashtable，后者要在 skiplist 上边走边累加跨度。

排行榜场景要控制 ZSet 规模：只保留 Top N（用上面的 `ZREMRANGEBYRANK`），历史全量数据落到数据库里，Redis 只做热榜。
