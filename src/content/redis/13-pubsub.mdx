# 发布订阅：即发即失的消息广播

Pub/Sub 是 Redis 里最轻量的消息机制：发布者往频道扔消息，**当前在线**的订阅者立刻收到——没有存储、没有确认、没有回放。它是广播喇叭，不是收件箱。理解这个定位，就知道它该用在哪、绝不能用在哪。

## 1. 基本使用

### 1.1 订阅与发布

```bash
# 终端 A: 订阅频道（可同时订阅多个）
127.0.0.1:6379> SUBSCRIBE news:tech news:sport
1) "subscribe"
2) "news:tech"
3) (integer) 1          # 当前已订阅 1 个频道
1) "subscribe"
2) "news:sport"
3) (integer) 2
（进入订阅态, 等待消息...）
```

```bash
# 终端 B: 发布
127.0.0.1:6379> PUBLISH news:tech "Redis 8 released"
(integer) 1             # 返回收到消息的订阅者数量
```

```bash
# 终端 A 立即收到:
1) "message"            # 消息类型
2) "news:tech"          # 来源频道
3) "Redis 8 released"   # 内容
```

`PUBLISH` 的返回值很有用：0 表示当前没人订阅，**这条消息已经凭空消失了**。

### 1.2 模式订阅：PSUBSCRIBE

用 glob 通配符订阅一批频道：

```bash
127.0.0.1:6379> PSUBSCRIBE news:*
1) "psubscribe"
2) "news:*"
3) (integer) 1
# 任何 news: 前缀频道的消息都会送达:
1) "pmessage"
2) "news:*"             # 匹配的模式
3) "news:finance"       # 实际频道
4) "CPI data out"
```

注意：一个客户端同时用 SUBSCRIBE news:tech 和 PSUBSCRIBE news:* 时，一条发到 news:tech 的消息会**收到两次**（一次 message 一次 pmessage）。

### 1.3 观察命令

```bash
127.0.0.1:6379> PUBSUB CHANNELS          # 有订阅者的频道列表
1) "news:tech"
127.0.0.1:6379> PUBSUB NUMSUB news:tech
1) "news:tech"
2) (integer) 3          # 3 个订阅者
127.0.0.1:6379> PUBSUB NUMPAT
(integer) 1             # 模式订阅的数量
```

下面这段可以直接运行：**没有订阅者时发布，消息就地蒸发**——这就是"即发即失"最直观的证据。

<Callout type="info" title="为什么这里没法在线演示 SUBSCRIBE">
SUBSCRIBE 会让连接进入订阅态并**一直挂着等消息**，需要两个终端、两条长连接一收一发。本页沙箱每行命令各自建连、执行完即断开，演示不了收发过程，所以订阅侧保留静态示例，请在本机开两个 redis-cli 窗口演练。
</Callout>

进入订阅态的连接只能执行 SUBSCRIBE/UNSUBSCRIBE/PING/QUIT 等少数命令，**业务里必须用独立连接做订阅**，不能复用普通命令的连接池连接。

## 2. 消息为什么会丢

Pub/Sub 的投递模型是**纯内存转发**：

```text
PUBLISH ch msg
     |
     v
遍历 ch 的订阅者连接 -> 把消息写进各连接的输出缓冲区 -> 完事
     |
     +-- 没有订阅者?      消息直接丢弃
     +-- 订阅者断线中?    收不到, 重连后也没有
     +-- 订阅者处理太慢?  输出缓冲区超限, 连接被强制断开
```

三种丢消息的姿势：

1. **离线即丢**：订阅者网络抖动重连的几秒里，所有消息永久错过；
2. **无确认**：消息写进 socket 就算送达，订阅者崩在处理中也无从得知；
3. **慢消费者被踢**：输出缓冲区超过 `client-output-buffer-limit pubsub 32mb 8mb 60` 的限制，Redis 直接断开该订阅者连接（防止内存被慢客户端拖爆）。

此外主从切换时，订阅关系不会迁移，客户端必须自己重新 SUBSCRIBE。

<Callout type="warn" title="绝不能用 Pub/Sub 传业务关键消息">
订单支付成功通知、库存变更事件这类"丢一条就出事故"的消息，用 Pub/Sub 等于埋雷。它只适合**丢了无所谓**的场景：实时弹幕、在线状态广播、配置刷新通知（丢了还有下次全量兜底）、多实例本地缓存失效通知（配合定期全量校验）。
</Callout>

## 3. Cluster 下的分片订阅：SSUBSCRIBE

普通 Pub/Sub 在 Cluster 里的实现是**广播到所有节点**——任何节点收到 PUBLISH 都要转发给集群其他节点，因为订阅者可能连在任何节点上。节点越多，内部广播流量越大，严重制约扩展性。

Redis 7 引入 **Sharded Pub/Sub**：频道按 key 的槽位规则归属某个分片，发布与订阅都必须发生在该分片上，不再全集群广播：

```bash
# 分片订阅（客户端会被路由/重定向到该频道所属分片）
127.0.0.1:6379> SSUBSCRIBE orders:events
1) "ssubscribe"
2) "orders:events"
3) (integer) 1

# 分片发布
127.0.0.1:6379> SPUBLISH orders:events "order 8801 paid"
(integer) 1
```

```text
普通 Pub/Sub in Cluster:        Sharded Pub/Sub:
PUBLISH 到节点 A                 SPUBLISH 到频道所属分片 B
  A -> 广播给 B, C, D...           只有 B 处理, 无跨节点广播
  订阅者连哪都行                    订阅者必须连 B（或其副本）
```

代价是客户端需要感知路由（智能客户端处理 MOVED），收益是集群水平扩展时 Pub/Sub 流量不再爆炸。

## 4. Pub/Sub、Stream、List 终极对比

| 维度 | Pub/Sub | Stream | List |
|---|---|---|---|
| 消息存储 | 无 | 持久保留 | 保留到弹出 |
| 离线补收 | 不可能 | 可以（按 ID 续读） | 可以 |
| 广播（多方全量收） | 天然支持 | 多消费组支持 | 不支持 |
| 分摊（多方分工收） | 不支持 | 消费组支持 | 天然支持 |
| ACK / 重试 | 无 | 有 | 无 |
| 延迟 | 最低（直接转发） | 低 | 低 |
| 内存压力 | 几乎无 | 需 MAXLEN 控制 | 需消费及时 |

决策树：

```text
消息丢了会出业务事故吗?
├── 会  -> Stream（要广播就开多个消费组）
└── 不会 -> 需要最低延迟的纯实时广播?
          ├── 是 -> Pub/Sub（Cluster 上用 SSUBSCRIBE）
          └── 否 -> 简单任务分发用 List, 否则仍建议 Stream
```

一个常见的组合拳：**Stream 存事件 + Pub/Sub 发"有新事件"的信号**——订阅者收到信号后去 Stream 拉取，即使信号丢了，定时轮询 Stream 也能兜底。

## 5. 实战：多实例本地缓存失效

微服务多实例各自有进程内缓存（Caffeine/本地 map），某实例更新数据后要通知所有实例清掉本地缓存：

```bash
# 更新方:
127.0.0.1:6379> DEL cache:user:1001            # 先删 Redis 缓存
(integer) 1
127.0.0.1:6379> PUBLISH cache:invalidate "user:1001"
(integer) 4             # 4 个实例在线收到

# 每个实例启动时:
127.0.0.1:6379> SUBSCRIBE cache:invalidate
# 收到消息 -> 删除本地缓存中的 user:1001
```

这是 Pub/Sub 的舒适区：消息偶尔丢失的后果只是"本地缓存多存活一会"，配合较短的本地 TTL 即可兜底。

## 小结

- Pub/Sub 是即发即失的广播：无存储、无 ACK、离线即丢、慢消费者会被断开
- PSUBSCRIBE 模式订阅注意与普通订阅叠加时的重复投递
- Cluster 用 SSUBSCRIBE/SPUBLISH 分片订阅，避免全集群广播
- 只用于"丢了无所谓"的场景；关键消息一律 Stream
- 下一章开始高可用三部曲：主从复制 →

| 维度 | SUBSCRIBE | PSUBSCRIBE |
|---|---|---|
| 消息类型字段 | `message` | `pmessage` |
| 数组长度 | **3 个元素** | **4 个元素** |
| 第 2 个元素 | 频道名 | **匹配的模式** |
| 第 3 个元素 | 消息内容 | **实际频道名** |

**这个差异是写客户端代码时的高频 bug 点**：如果按固定下标 `msg[2]` 取消息内容，普通订阅是对的，模式订阅拿到的却是频道名。正确做法是先判断 `msg[0]` 的类型再决定取哪个下标。多数客户端库（如 go-redis、Lettuce）已经封装好了，但用底层 API 时要小心。

**叠加订阅会导致重复投递**：

```bash
# 同一个客户端同时用两种方式订阅同一频道
127.0.0.1:6379> SUBSCRIBE news:tech
127.0.0.1:6379> PSUBSCRIBE news:*
# 发布一条 news:tech 消息，这个客户端会收到【两次】：
#   一次 message（来自普通订阅）
#   一次 pmessage（来自模式订阅）

# 多个模式重叠也会重复
127.0.0.1:6379> PSUBSCRIBE news:*
127.0.0.1:6379> PSUBSCRIBE news:te*
# 一条 news:tech 消息会触发两次 pmessage
```

**PUBLISH 的返回值把两种订阅都算进去了**，所以看到返回 2 不代表有 2 个不同的客户端。业务上要做幂等处理，或者干脆避免叠加订阅。

**模式匹配的性能代价**：普通订阅走的是**哈希表精确查找**，O(1)；模式订阅要**遍历所有已注册的模式**逐个做 glob 匹配，是 O(N)。模式数量多时 `PUBLISH` 会变慢，且这个开销发生在主线程上。所以不要滥用 `PSUBSCRIBE`，尤其避免 `PSUBSCRIBE *` 这种全匹配。

```bash
# 查看订阅状态
127.0.0.1:6379> PUBSUB CHANNELS              # 列出所有活跃频道（有订阅者的）
1) "news:tech"
127.0.0.1:6379> PUBSUB CHANNELS "news:*"     # 按模式过滤
127.0.0.1:6379> PUBSUB NUMSUB news:tech      # 某频道的普通订阅者数
1) "news:tech"
2) (integer) 1
127.0.0.1:6379> PUBSUB NUMPAT                # 模式订阅的总数
(integer) 1
```

注意 `PUBSUB CHANNELS` **只统计普通订阅**，模式订阅的频道不会出现在里面——排查"为什么没人收到消息"时容易被这一点误导。

**2. 验证"离线即丢"**

```bash
# ---- 终端 A：订阅 ----
127.0.0.1:6379> SUBSCRIBE alerts
Reading messages... (press Ctrl-C to quit)
1) "subscribe"
2) "alerts"
3) (integer) 1

# ---- 终端 B：发一条，A 能收到 ----
127.0.0.1:6379> PUBLISH alerts "msg-0"
(integer) 1                        # 返回 1：有 1 个订阅者

# 终端 A 显示：
1) "message"
2) "alerts"
3) "msg-0"

# ---- 终端 A：Ctrl+C 断开 ----
^C

# ---- 终端 B：离线期间发 3 条 ----
127.0.0.1:6379> PUBLISH alerts "msg-1"
(integer) 0                        # 返回 0：没有订阅者，消息【直接丢弃】
127.0.0.1:6379> PUBLISH alerts "msg-2"
(integer) 0
127.0.0.1:6379> PUBLISH alerts "msg-3"
(integer) 0

# ---- 终端 A：重新订阅 ----
127.0.0.1:6379> SUBSCRIBE alerts
1) "subscribe"
2) "alerts"
3) (integer) 1
# 一直等待... 什么都收不到，msg-1/2/3 永久丢失

# ---- 终端 B：再发一条新的，这次能收到 ----
127.0.0.1:6379> PUBLISH alerts "msg-4"
(integer) 1
# 终端 A 收到 msg-4，但之前 3 条永远找不回来
```

**`PUBLISH` 的返回值就是最直接的证据**：它返回的是"消息被投递给了几个订阅者"。返回 0 意味着这条消息**被服务端直接丢弃了**，不写内存、不写磁盘、不排队，什么痕迹都不留。

**Redis 服务端不为 Pub/Sub 保存任何状态**：没有消息存储、没有消费位点、没有确认机制。`PUBLISH` 的实现就是"遍历该频道的订阅者列表，逐个把消息写进它们的输出缓冲区"——找不到订阅者，遍历零次，函数返回。

**除了离线，还有两种丢消息的情况**：

```bash
# ---- 情况一：慢消费者被强制断开 ----
# 订阅者处理不过来时，消息堆积在服务端为它分配的输出缓冲区里
# 超过限制后 Redis 会【主动断开】这个客户端，堆积的消息全部丢弃
127.0.0.1:6379> CONFIG GET client-output-buffer-limit
1) "client-output-buffer-limit"
2) "normal 0 0 0 slave 268435456 67108864 60 pubsub 33554432 8388608 60"
#                                                    ^^^^^^^^ ^^^^^^^ ^^
#                                                    硬限制32MB 软限制8MB 持续60秒

# 含义：pubsub 客户端缓冲区超过 32MB 立即断开；
#       或超过 8MB 并持续 60 秒也断开

# 观察是否发生过
127.0.0.1:6379> INFO stats | grep client_output_buffer
client_output_buffer_limit_disconnections:3    # 非 0 说明有客户端被踢过

# ---- 情况二：网络抖动导致的瞬时断连 ----
# 客户端库自动重连需要时间（通常几百毫秒到几秒），这期间的消息全丢
# 而且重连后没有任何机制能感知"我错过了几条"
```

**关键结论**：Pub/Sub 的投递语义是 **at-most-once（至多一次）**——消息要么送达一次，要么丢失，永远不会重复。这是它和 Stream（at-least-once，至少一次）的本质区别。

**3. 本地缓存失效广播方案**

**场景背景**：为了扛住极高的读 QPS，应用进程内部维护一层本地缓存（Caffeine / Guava Cache / sync.Map），避免每次都走 Redis 网络往返。问题是数据更新后，**各个应用实例的本地缓存都是脏的**，必须有机制通知它们清理。

**架构**：

```bash
# 数据更新时：
#   写库 → 删 Redis 缓存 → PUBLISH 失效通知
#                              ↓
#            ┌─────────────────┼─────────────────┐
#            ↓                 ↓                 ↓
#        实例 A            实例 B            实例 C
#     清本地缓存         清本地缓存         清本地缓存
```

**发布方命令流程**（数据更新时）：

```bash
# 1. 先更新数据库（略）
#    UPDATE product SET price = 99 WHERE id = 2001;

# 2. 删除 Redis 中的分布式缓存
127.0.0.1:6379> DEL cache:product:2001
(integer) 1

# 3. 广播失效消息，通知所有实例清理本地缓存
127.0.0.1:6379> PUBLISH cache:invalidate "product:2001"
(integer) 3                        # 3 个应用实例收到

# 批量失效（比如刷新整个分类）
127.0.0.1:6379> DEL cache:product:2001 cache:product:2002 cache:product:2003
(integer) 3
127.0.0.1:6379> PUBLISH cache:invalidate "product:2001,product:2002,product:2003"
(integer) 3

# 清空某一类缓存
127.0.0.1:6379> PUBLISH cache:invalidate "product:*"
(integer) 3
```

**消息体建议用 JSON**，携带更多元信息便于排查和处理：

```bash
127.0.0.1:6379> PUBLISH cache:invalidate "{\"keys\":[\"product:2001\"],\"ts\":1785000000,\"source\":\"instance-A\",\"op\":\"update\"}"
(integer) 3
```

`source` 字段有个实际用途：**发布方自己也订阅了这个频道，收到自己发的消息时可以跳过**（虽然多清一次本地缓存无害，但能省一点开销，也便于日志区分）。

**订阅方命令流程**（应用启动时）：

```bash
# 每个应用实例启动时订阅
127.0.0.1:6379> SUBSCRIBE cache:invalidate
1) "subscribe"
2) "cache:invalidate"
3) (integer) 1

# 收到消息后的处理（伪代码）：
# on_message(channel, payload):
#     data = json.parse(payload)
#     if data.source == MY_INSTANCE_ID:
#         return                        # 跳过自己发的
#     for key in data.keys:
#         if key.endswith("*"):
#             localCache.invalidateByPrefix(key[:-1])
#         else:
#             localCache.invalidate(key)
#     metrics.increment("cache.invalidate.received")
```

**读取时的三级缓存逻辑**：

```bash
# get(productId):
#     1. 查本地缓存 → 命中直接返回（纳秒级）
#     2. 查 Redis    → 命中则回填本地缓存，返回（毫秒级）
#     3. 查数据库    → 回填 Redis 和本地缓存，返回（十毫秒级）
```

**兜底方案（这是本题的重点）**

Pub/Sub 会丢消息，所以**绝对不能把它当作唯一的一致性保障**。必须叠加多层兜底：

**兜底一：本地缓存设置短 TTL（最重要，必做）**

```bash
# 本地缓存 TTL 设为 30 ~ 60 秒
# Redis 缓存 TTL 设为 5 ~ 30 分钟
#
# 效果：即使广播 100% 失效，脏数据最多存活 30 秒后自动过期
#      这是整个方案的【安全底线】，其他所有措施都是在这个底线之上做优化
```

这一条的意义在于：它把"不确定的、可能永久的不一致"变成了"确定的、有上界的不一致"。业务方只需要回答一个问题——"能否接受最多 30 秒的数据延迟"。能接受，方案就成立；不能接受，就说明本地缓存这个架构本身不适用，应该直接读 Redis。

```bash
# 不同数据的 TTL 分档
# 商品价格、库存等敏感数据     → 本地 10 秒
# 商品标题、描述等一般数据     → 本地 60 秒
# 分类树、配置项等极少变更数据 → 本地 300 秒
```

**兜底二：本地缓存容量上限 + LRU**

```bash
# 限制本地缓存最大条目数（如 10000）
# 超出后按 LRU 淘汰，防止内存泄漏，也让冷数据自然消失
```

**兜底三：订阅断线检测与全量清空**

```bash
# 客户端库通常提供连接状态回调
# on_disconnect():
#     log.warn("Pub/Sub 连接断开，本地缓存进入不可信状态")
#     metrics.increment("cache.pubsub.disconnect")
#
# on_reconnect():
#     localCache.invalidateAll()      # 【关键】断线期间的失效通知全丢了，
#                                     #  无法知道哪些 key 脏了，只能全清
#     log.info("Pub/Sub 重连成功，已清空本地缓存")
```

这一步经常被忽略，但它非常关键：**断线重连后，你无法知道自己错过了什么**。唯一安全的做法就是把本地缓存整个丢掉重建。全清会带来一次缓存穿透的小尖峰，但比长期提供脏数据好得多。

**兜底四：版本号校验（强一致要求时）**

```bash
# 在 Redis 里维护一个全局版本号
127.0.0.1:6379> INCR cache:version:product:2001
(integer) 5

# 本地缓存除了存数据，也存写入时的版本号
# 读取时（可以降低频率，比如每 5 秒才校验一次）：
127.0.0.1:6379> GET cache:version:product:2001
"5"
# 与本地记录的版本号比对，不一致就丢弃本地缓存重新加载
```

这个方案能把不一致窗口压到很小，代价是每次（或每隔几秒）多一次 Redis 往返，**削弱了本地缓存的性能优势**。只在关键数据上使用。

**兜底五：定期全量刷新**

```bash
# 后台定时任务，每 5 分钟清空一次本地缓存
# 作为最后的保险，防止任何未预料到的不一致状态长期存在
# 注意错开各实例的执行时间，避免同时清空造成回源尖峰
```

**兜底六：监控告警**

```bash
# 关键指标
127.0.0.1:6379> PUBSUB NUMSUB cache:invalidate
1) "cache:invalidate"
2) (integer) 3                     # 订阅者数应该等于应用实例数
                                   # 少了说明有实例掉线，需要告警

127.0.0.1:6379> INFO stats | grep client_output_buffer_limit_disconnections
client_output_buffer_limit_disconnections:0    # 非 0 说明有慢消费者被踢

# 应用侧指标
#   - 发布的消息数 vs 各实例接收的消息数（差值即丢失量）
#   - 本地缓存命中率（突然升高可能意味着失效通知没生效）
#   - Pub/Sub 连接断开次数
```

**为什么不用 Stream 替代？**

理论上 Stream 不丢消息，看起来更可靠。但在这个场景下 Pub/Sub 反而更合适：

| 维度 | Pub/Sub | Stream |
|---|---|---|
| 广播语义 | 天然广播，新实例订阅即可 | 每个实例要建独立消费组，实例扩缩容时要管理组的生命周期 |
| 延迟 | 服务端直接推送，最低 | 需要 XREADGROUP 拉取（阻塞读也有唤醒开销） |
| 服务端开销 | 零存储 | 消息持久化，要配 MAXLEN 和 XTRIM |
| 运维复杂度 | 极低 | 要清理下线实例的消费组，否则 PEL 无限堆积 |
| 丢消息后果 | **本地缓存多脏 30 秒**（有 TTL 兜底） | —— |

**决策依据是"丢消息的后果可以接受"**。缓存失效通知丢了，最坏结果是某个实例多返回 30 秒的旧数据——配合短 TTL，这个损失是有界且可控的。为此引入 Stream 的复杂度不划算。

反过来说，如果业务要求"价格变更必须 1 秒内全网生效，否则会有资损"，那本地缓存这个架构本身就不该用，应该直接读 Redis（毫秒级且强一致），而不是纠结用 Pub/Sub 还是 Stream。

**Cluster 环境的额外注意**：

```bash
# 普通 PUBLISH 在 Cluster 中会向【所有节点】广播，节点多时是可观的内部流量
127.0.0.1:6379> PUBLISH cache:invalidate "product:2001"

# Redis 7.0+ 提供分片 Pub/Sub，消息只在 key 所属 slot 的节点组内传播
127.0.0.1:6379> SPUBLISH cache:invalidate "product:2001"
127.0.0.1:6379> SSUBSCRIBE cache:invalidate
```

但要注意：**分片订阅意味着只有连到对应节点的订阅者才能收到**。用于"全实例广播"场景时需要保证所有实例订阅的是同一个 slot 对应的频道，否则会漏掉部分实例。缓存失效广播这种需要全网触达的场景，用普通 `PUBLISH` 反而更稳妥。

**最后提一句 Redis 6 的客户端缓存（Client-side Caching / Tracking）**：它是 Redis 原生提供的本地缓存失效方案，服务端会追踪每个客户端读过哪些 key，key 变更时**自动**发送失效通知，不需要你手动 `PUBLISH`。

```bash
127.0.0.1:6379> CLIENT TRACKING ON REDIRECT 42
OK
```

优点是无需业务代码维护失效逻辑，缺点是服务端要维护追踪表（有内存开销）、客户端库支持参差不齐、broadcast 模式下同样可能丢通知。如果你的客户端库支持得好（如 Lettuce），值得评估；否则手写 Pub/Sub 方案更可控。
