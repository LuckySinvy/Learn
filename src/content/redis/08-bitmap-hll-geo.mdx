# Bitmap、HyperLogLog 与 GEO

这三个不是独立的数据类型，而是构建在 String 和 ZSet 之上的**特殊用途结构**：Bitmap 用 1 个 bit 记录一个布尔状态，HyperLogLog 用 12 KB 估算亿级基数，GEO 把经纬度编码进 ZSet 做半径搜索。它们的共同主题是：**用极小的空间解决特定问题**。

## 1. Bitmap：一个 bit 记一个状态

Bitmap 本质是 String，把它当作 bit 数组来操作。一个 512 MB 的 String 可容纳 2^32 个 bit。

### 1.1 基本操作

<Playground
  language="redis"
  title="Bitmap 实现月签到"
  id="redis-08-1"
  code={`# 7 月 1 日（偏移 0）签到，返回该位的旧值
SETBIT sign:u1001:202607 0 1
# 7 月 2 日签到
SETBIT sign:u1001:202607 1 1
# 7 月 30 日签到
SETBIT sign:u1001:202607 29 1
# 7 月 2 日签过
GETBIT sign:u1001:202607 1
# 7 月 3 日没签
GETBIT sign:u1001:202607 2
# 本月共签到几天
BITCOUNT sign:u1001:202607
# 第一个 1 的位置：首次签到日
BITPOS sign:u1001:202607 1`}
/>

一个用户一个月的签到只占 31 bit ≈ 4 字节；1 亿用户的月签到约 400 MB，而用 Set 存"签到用户 ID"要几十 GB。

### 1.2 位运算：BITOP

<Playground
  language="redis"
  title="BITOP 算连续活跃与总活跃"
  id="redis-08-2"
  code={`# day1 / day2 分别是两天的活跃用户位图（偏移即用户 ID）
SETBIT active:day1 1001 1
SETBIT active:day1 1002 1
SETBIT active:day2 1002 1
# AND：连续两天都活跃的用户位图
BITOP AND active:both active:day1 active:day2
BITCOUNT active:both
# OR：两天内活跃过的总人数（精确去重）
BITOP OR active:any active:day1 active:day2
BITCOUNT active:any`}
/>

`BITOP` 支持 AND/OR/XOR/NOT，连续 N 天活跃、留存率计算都是几条位运算的事。

<Callout type="warn" title="偏移量决定内存，别用离散大 ID">
`SETBIT key 4000000000 1` 会立即分配 500 MB 内存——Bitmap 按最大偏移量分配空间。用户 ID 作偏移的前提是 ID 连续自增；如果 ID 是雪花 ID 这种 64 位大数，直接用会撑爆内存，需要先映射成连续编号。
</Callout>

## 2. HyperLogLog：12 KB 数亿级 UV

需求："统计页面今天有多少**不同**用户访问"（UV）。用 Set 精确去重，1 亿个 ID 要几 GB；如果能接受 0.81% 的标准误差，HyperLogLog 只要 **12 KB**。

### 2.1 使用

<Playground
  language="redis"
  title="HyperLogLog 估算 UV"
  id="redis-08-3"
  code={`# 返回 1 表示估算值发生了变化
PFADD uv:20260730 u1 u2 u3
# 重复元素不影响，返回 0
PFADD uv:20260730 u2
PFCOUNT uv:20260730
PFADD uv:20260729 u3 u4
# 合并多天得到周 UV：去重合并，不是相加
PFMERGE uv:week1 uv:20260729 uv:20260730
PFCOUNT uv:week1
# HLL 底层就是 String，看一眼类型
TYPE uv:week1`}
/>

只有三个命令：PFADD 添加、PFCOUNT 估算基数、PFMERGE 合并。注意 **HLL 只能给出数量，无法回答"某个用户来过没有"**——它根本不存储元素本身。

### 2.2 误差从哪来：概率估计的直觉

HLL 的核心思想类似"抛硬币"：一个均匀哈希值的二进制表示中，**前导零的个数**服从几何分布——见过"前导 20 个零"的哈希，说明大约见过 2^20 个不同元素。单次估计方差很大，HLL 的改进是：

```text
元素 -> hash 64bit -> 前 14 bit 选桶(共 16384 个桶)
                      剩余 bit 统计前导零个数, 桶内只保留最大值

  桶0   桶1   桶2  ...  桶16383
 [ 5 ] [ 3 ] [ 7 ] ... [ 4 ]      每桶 6 bit, 16384 * 6bit = 12KB

 基数估算 = 常数 * 桶数^2 / sum(2^-桶值)   (调和平均抗离群值)
 标准误差 = 1.04 / sqrt(16384) ≈ 0.81%
```

16384 个桶各自独立估计再取调和平均，把误差压到 0.81%。这就是"12 KB 固定内存、亿级基数、误差不到 1%"的数学来源。

## 3. GEO：附近的人

GEO 把经纬度通过 **GeoHash 编码成 52 bit 整数存进 ZSet 的 score**——所以 GEO 的 key 用 TYPE 查看是 zset，可以直接用 ZSet 命令操作。

### 3.1 写入与查询

<Playground
  language="redis"
  title="GEO 写入与半径搜索"
  id="redis-08-4"
  code={`GEOADD riders 121.4737 31.2304 "rider:1"
GEOADD riders 121.4837 31.2404 "rider:2" 121.5037 31.2104 "rider:3"
# 编码解码有厘米级精度损失
GEOPOS riders rider:1
# 两点距离，单位 km
GEODIST riders rider:1 rider:2 km
# 以坐标为圆心找 3 公里内的骑手，按距离升序
GEOSEARCH riders FROMLONLAT 121.4737 31.2304 BYRADIUS 3 km ASC WITHDIST
# GEO 底层就是 ZSet
TYPE riders`}
/>

### 3.2 半径搜索：GEOSEARCH（6.2+，替代 GEORADIUS）

```bash
# 以某坐标为圆心找 3 公里内的骑手，按距离升序
127.0.0.1:6379> GEOSEARCH riders FROMLONLAT 121.4737 31.2304 BYRADIUS 3 km ASC WITHCOORD WITHDIST
1) 1) "rider:1"
   2) "0.0001"
   3) 1) "121.47370249032974243"
      2) "31.23039901743481792"
2) 1) "rider:2"
   2) "1.4453"
   3) 1) "121.48369997739791870"
      2) "31.24039987621843541"
# 以某成员为中心, 矩形范围搜索
127.0.0.1:6379> GEOSEARCH riders FROMMEMBER rider:1 BYBOX 4 4 km ASC COUNT 10
1) "rider:1"
2) "rider:2"
```

GeoHash 的原理是经纬度二分交替编码：把地球反复对半切，落在左/下记 0、右/上记 1，交织成一个整数——**编码相近的点空间上也相近**（Z 序曲线），因此 ZSet 的按 score 范围查找能转化为空间邻近查找，再对候选点精确算距离过滤。

骑手位置更新就是重复 GEOADD（同名成员覆盖坐标）；下线用 `ZREM riders rider:1` 删除。

<Callout type="tip" title="三个结构的选型口诀">
要"每个个体的状态"（签了没签、活跃没活跃）用 Bitmap；只要"去重后的数量"且量极大用 HyperLogLog；要"位置与距离"用 GEO。共同前提：都是单 key 结构，注意配合 TTL 与按时间分 key。
</Callout>

<Callout type="warn" title="GEO 大 key 与 Cluster 注意">
全城骑手放一个 GEO key，量大后是典型大 key，且在 Cluster 中无法分片。实践中按城市或网格分 key（如 `riders:sh:grid:105`）。另外 GEOSEARCH 半径越大扫描的候选越多，避免动辄"50 公里内"的全城搜索。
</Callout>

## 小结

- Bitmap：bit 级布尔数组，签到、活跃、留存的空间效率之王；注意偏移量与内存的关系
- HyperLogLog：12 KB 估算亿级基数，误差 0.81%，只有数量没有成员
- GEO：GeoHash 进 ZSet，GEOADD 写入、GEOSEARCH 半径/矩形搜索
- 三者都是"特化工具"：先确认业务能否接受各自的限制（精确性、可查性、精度）

```bash

127.0.0.1:6379> SETBIT signin:u1001:202608 0 1      # 8月1日
(integer) 0                                          # 返回值是该位的"旧值"
127.0.0.1:6379> SETBIT signin:u1001:202608 2 1      # 8月3日
(integer) 0
127.0.0.1:6379> SETBIT signin:u1001:202608 3 1      # 8月4日
(integer) 0
127.0.0.1:6379> SETBIT signin:u1001:202608 9 1      # 8月10日
(integer) 0
127.0.0.1:6379> SETBIT signin:u1001:202608 15 1     # 8月16日
(integer) 0

127.0.0.1:6379> SETBIT signin:u1001:202608 0 1

# ---- 统计本月总签到天数 ----
127.0.0.1:6379> BITCOUNT signin:u1001:202608

127.0.0.1:6379> GETBIT signin:u1001:202608 2       # 8月3日
(integer) 1               # 1 = 已签到
127.0.0.1:6379> GETBIT signin:u1001:202608 4       # 8月5日
(integer) 0               # 0 = 未签到

# ---- 找出首次签到日：BITPOS 找第一个值为 1 的位 ----
127.0.0.1:6379> BITPOS signin:u1001:202608 1

# 没有任何签到时返回 -1
127.0.0.1:6379> BITPOS signin:u9999:202608 1
(integer) -1

127.0.0.1:6379> STRLEN signin:u1001:202608
(integer) 2               # 只要 2 字节就存下了 16 天的状态

# ---- 设置过期，保留 1 年 ----
127.0.0.1:6379> EXPIRE signin:u1001:202608 31536000
(integer) 1
```

**扩展玩法**：

```bash
# 统计前 10 天签到几次（BITCOUNT 的 BIT 索引，Redis 7.0+）
127.0.0.1:6379> BITCOUNT signin:u1001:202608 0 9 BIT
(integer) 4

# 找出第一个"未签到"的日子（断签日）
127.0.0.1:6379> BITPOS signin:u1001:202608 0
(integer) 1               # offset 1 → 8月2日没签

# 连续两个月都签到的用户（BITOP AND 求交集）
127.0.0.1:6379> BITOP AND result signin:u1001:202607 signin:u1001:202608
(integer) 4
```

**为什么 Bitmap 这么省？** 一个月 31 天只需要 31 bit = 4 字节。存 1000 万用户一个月的签到数据，总共约 40 MB。如果用 Set 存每天的签到用户，每个用户 ID 至少几十字节，一个月下来是几 GB 量级——差了两个数量级。

**使用注意**：

- **offset 决定内存**：`SETBIT key 100000000 1` 会立刻分配 12.5 MB 内存（Redis 会把中间所有位补 0）。所以 offset 一定要是"从 0 开始的紧凑序号"，绝对不能直接拿用户 ID 当 offset——用户 ID 是 20 位数的话，一个 key 就能吃掉你所有内存
- **按月分 key**：key 里带上年月，配合 TTL 自动清理，也避免单 key 无限增长
- **Bitmap 本质是 String**：所以 `STRLEN`、`GETRANGE`、`SETRANGE` 都能用，`OBJECT ENCODING` 返回 `raw`

**2. HyperLogLog 的误差验证**

```bash
127.0.0.1:6379> DEL hll:test
(integer) 1

# ---- 写入 1 万个不同元素 ----
# 用 pipe 模式批量写入，比循环调用快几十倍
for i in $(seq 1 10000); do echo "pfadd hll:test elem$i"; done | redis-cli --pipe
All data transferred. Waiting for the last reply...
Last reply received from server.
errors: 0, replies: 10000

# ---- 对比估算值与真实值 ----
127.0.0.1:6379> PFCOUNT hll:test
(integer) 10023           # 真实值 10000，估算值 10023

# 误差 = |10023 - 10000| / 10000 = 0.23%

# ---- 对照：用 Set 存同样的数据，看内存差距 ----
for i in $(seq 1 10000); do echo "sadd set:test elem$i"; done | redis-cli --pipe
127.0.0.1:6379> SCARD set:test
(integer) 10000           # Set 是精确值

127.0.0.1:6379> MEMORY USAGE hll:test
(integer) 12304           # 约 12 KB，固定不变
127.0.0.1:6379> MEMORY USAGE set:test
(integer) 622160          # 约 608 KB，是 HLL 的 50 倍
```

不同数据量下的误差表现（实测值会略有波动）：

| 真实基数 | PFCOUNT 估算 | 误差 | HLL 内存 | Set 内存 |
|---|---|---|---|---|
| 100 | 100 | 0% | ~200 B（稀疏编码） | ~7 KB |
| 1,000 | 1,000 | 0% | ~1.5 KB | ~60 KB |
| 10,000 | ~10,023 | ~0.2% | 12 KB | ~600 KB |
| 1,000,000 | ~997,240 | ~0.28% | 12 KB | ~60 MB |
| 100,000,000 | ~99,5xx,xxx | `<1%` | 12 KB | ~6 GB |

关键观察：

- **小基数时通常完全精确**：HLL 有稀疏（sparse）和稠密（dense）两种编码。元素少时用稀疏编码，实际是精确记录，内存也远小于 12 KB。超过 `hll-sparse-max-bytes`（默认 3000 字节）才转成稠密编码开始估算
- **12 KB 是上限不是固定值**：稠密编码固定 12 KB（16384 个寄存器 × 6 bit），此后无论存 1 万还是 1 亿都不再增长
- **标准误差 0.81%**：这是统计意义上的标准差，单次测量可能更准也可能更差，多做几次实验会看到误差在 0 到 2% 之间波动

**合并多个 HLL（PFMERGE）**：

```bash
# 每天一个 HLL，合并出周 UV —— 这是 HLL 最有价值的能力
127.0.0.1:6379> PFADD uv:20260801 u1 u2 u3
(integer) 1
127.0.0.1:6379> PFADD uv:20260802 u2 u3 u4
(integer) 1
127.0.0.1:6379> PFMERGE uv:week uv:20260801 uv:20260802
OK
127.0.0.1:6379> PFCOUNT uv:week
(integer) 4               # 自动去重，u2/u3 只算一次

# 也可以直接对多个 key 求并集基数，不落地中间结果
127.0.0.1:6379> PFCOUNT uv:20260801 uv:20260802
(integer) 4
```

用 Set 做同样的事需要 `SUNIONSTORE` 一个巨大的集合，内存和 CPU 都扛不住；HLL 合并永远只是 12 KB 对 12 KB 的位运算。

**HLL 的硬限制**：**只能得到数量，无法列出成员，也无法判断某个元素是否存在**。如果业务上哪天需要"把昨天的 UV 用户捞出来发券"，HLL 就完全无能为力了。选型前一定要确认这个需求永远不会出现，否则要么用 Set，要么 HLL 和明细数据（如 Hive/ClickHouse）配合使用。

**3. GEO 门店查询**

```bash
# ---- 写入 5 个门店坐标（经度 纬度 名称，注意经度在前）----
127.0.0.1:6379> GEOADD shops:sh 121.4737 31.2304 "人民广场店" \
                                121.5054 31.2453 "陆家嘴店" \
                                121.4581 31.2222 "静安寺店" \
                                121.4869 31.2397 "外滩店" \
                                121.4214 31.1937 "徐家汇店"
(integer) 5

# ---- 查找我 2 公里内最近的 3 家门店，返回距离 ----
# 假设我在 121.4700 31.2300（人民广场附近）
127.0.0.1:6379> GEOSEARCH shops:sh FROMLONLAT 121.4700 31.2300 \
                BYRADIUS 2 km ASC COUNT 3 WITHDIST
1) 1) "人民广场店"
   2) "0.3546"            # 距离，单位与 BYRADIUS 一致（km）
2) 1) "外滩店"
   2) "1.8123"
3) 1) "静安寺店"
   2) "1.9876"

# 同时返回坐标
127.0.0.1:6379> GEOSEARCH shops:sh FROMLONLAT 121.4700 31.2300 \
                BYRADIUS 2 km ASC COUNT 3 WITHDIST WITHCOORD
1) 1) "人民广场店"
   2) "0.3546"
   3) 1) "121.47370100021362"
      2) "31.23040001"

# ---- 以某个已有成员为中心搜索（比如"陆家嘴店附近还有哪些店"）----
127.0.0.1:6379> GEOSEARCH shops:sh FROMMEMBER "陆家嘴店" BYRADIUS 3 km ASC WITHDIST
1) 1) "陆家嘴店"
   2) "0.0000"            # 自己也会被返回，业务侧要过滤掉
2) 1) "外滩店"
   2) "1.8654"

# ---- 矩形范围搜索（适合地图视口内的门店）----
127.0.0.1:6379> GEOSEARCH shops:sh FROMLONLAT 121.4700 31.2300 \
                BYBOX 4 4 km ASC WITHDIST

# ---- 其他常用命令 ----
127.0.0.1:6379> GEODIST shops:sh "人民广场店" "陆家嘴店" km
"3.2145"                  # 两点直线距离

127.0.0.1:6379> GEOPOS shops:sh "外滩店"
1) 1) "121.48690104484558"
   2) "31.23970002"

127.0.0.1:6379> GEOHASH shops:sh "外滩店"
1) "wtw3sm0y0k0"          # 标准 GeoHash 字符串，可用于外部系统对接
```

关键参数说明：

| 参数 | 作用 |
|---|---|
| `FROMLONLAT lon lat` | 以指定经纬度为中心 |
| `FROMMEMBER m` | 以集合中某个成员为中心 |
| `BYRADIUS r unit` | 圆形范围，unit 可为 `m`/`km`/`mi`/`ft` |
| `BYBOX w h unit` | 矩形范围 |
| `ASC` / `DESC` | 按距离由近到远 / 由远到近 |
| `COUNT n` | 只返回前 n 个 |
| `WITHDIST` | 返回距离 |
| `WITHCOORD` | 返回经纬度 |
| `WITHHASH` | 返回 52 位整数形式的 GeoHash |

**必须注意的几点**：

- **经度在前、纬度在后**：这是最容易搞错的地方。经度范围 ±180，纬度范围 ±85.05（墨卡托投影限制）。写反了会报 `invalid longitude,latitude pair` 或者查出完全错误的结果
- **`ASC` + `COUNT` 才等于"最近的 N 个"**：只写 `COUNT 3` 不加 `ASC`，Redis 为了性能会在找到 3 个后就提前返回，这 3 个**不保证是最近的**。加了 `ASC` 后 Redis 会完整搜索再排序
- **中心点自己会被返回**：用 `FROMMEMBER` 时距离为 0 的那条就是中心点本身，业务代码要过滤
- **GEO 底层就是 ZSet**：`ZRANGE shops:sh 0 -1` 能看到所有成员，`ZREM` 可以删除门店（GEO 没有专门的删除命令）。`OBJECT ENCODING` 返回 `skiplist` 或 `listpack`
- **`GEORADIUS` 已废弃**：Redis 6.2 起用 `GEOSEARCH` 替代，新代码不要再用旧命令
- **精度约 0.5 米**：GeoHash 编码有损，对精度要求极高的场景（如高精地图）不适用

**大 key 与分片问题**：全城几十万骑手放一个 GEO key 是典型大 key，且 Cluster 下无法拆分。实践中按城市或网格分 key（如 `riders:sh:grid:105`），查询时根据用户位置算出所在网格及相邻网格，并发查几个 key 再合并结果。同时避免大半径搜索——半径越大候选点越多，`GEOSEARCH` 在主线程做的计算量就越大。
