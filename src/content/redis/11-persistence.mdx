# 持久化：RDB 与 AOF

Redis 数据在内存里，进程一退全部蒸发。持久化回答一个问题：**重启之后，数据还能剩多少？** RDB 和 AOF 是两种答案，各自的丢失窗口、性能代价、恢复速度截然不同——理解机制才能按业务的容忍度做选择。

## 1. RDB：某一时刻的全量快照

RDB 把某个时间点的**全部数据**序列化成一个紧凑的二进制文件（dump.rdb）。

### 1.1 触发方式

```conf
# redis.conf: 满足任一条件即自动触发 bgsave
save 3600 1        # 3600 秒内至少 1 次修改
save 300 100       # 300 秒内至少 100 次修改
save 60 10000      # 60 秒内至少 10000 次修改
dir /var/lib/redis
dbfilename dump.rdb
```

```bash
127.0.0.1:6379> BGSAVE          # 手动触发, 后台执行（生产用这个）
Background saving started
127.0.0.1:6379> SAVE            # 同步执行, 阻塞所有请求, 生产禁用
OK
127.0.0.1:6379> LASTSAVE        # 上次成功快照的时间戳
(integer) 1722310000
```

持久化策略是**运行时可查**的，先看看当前实例被配置成了什么样：

### 1.2 fork + 写时复制（COW）

BGSAVE 时主进程 fork 出一个子进程，由子进程遍历内存写文件。关键问题：**子进程写文件要几十秒，期间主进程还在改数据，快照会不会脏？**

答案是不会，靠操作系统的写时复制（Copy-On-Write）：

```text
fork 瞬间: 父子进程共享同一批内存页(只读标记), 不复制数据
+--------+          +--------+
| 父进程 | -共享页-> | 子进程 |     fork 本身只复制页表, 毫秒级
+--------+          +--------+

父进程随后修改某页数据时:
  内核先把该页复制一份 -> 父进程改"新页", 子进程仍看到"旧页"
  => 子进程眼中的数据永远定格在 fork 那一刻, 快照是一致的
```

代价：

- fork 复制页表的耗时与内存量成正比，10 GB 实例的 fork 可能卡主线程上百毫秒（`INFO stats` 里的 `latest_fork_usec`）；
- 快照期间写入越多，被复制的页越多，**极端情况下内存翻倍**——这是"Redis 内存别超过物理内存一半"说法的来源。

### 1.3 RDB 的优缺点

- 优点：文件紧凑、恢复快（直接加载二进制）、对主进程性能影响集中在 fork 一瞬；适合定期备份、主从全量同步。
- 缺点：**两次快照之间的数据全部会丢**。按默认配置，宕机可能丢几分钟数据。

## 2. AOF：记录每一条写命令

AOF（Append Only File）把每条写命令追加到日志文件，重启时**重放**所有命令恢复数据。

```conf
appendonly yes
appendfsync everysec      # fsync 策略, 见下
# Redis 7: AOF 拆分为多文件, 放在 appenddirname 目录下
appenddirname "appendonlydir"
```

### 2.1 三种 fsync 策略：性能与丢失窗口的权衡

写命令先进 AOF 内存缓冲区，何时刷到磁盘由 `appendfsync` 决定：

| 策略 | 行为 | 丢失窗口 | 性能 |
|---|---|---|---|
| `always` | 每条命令都 fsync | 最多丢 1 条命令 | 差，受磁盘 IOPS 限制 |
| `everysec` | 后台线程每秒 fsync 一次 | 最多丢约 1 秒 | 好（默认，推荐） |
| `no` | 交给操作系统（约 30 秒） | 最多丢几十秒 | 最好 |

```text
写命令 -> AOF 缓冲区(内存) --fsync--> 磁盘
              ^                        ^
        这一步永远很快          everysec: 每秒刷一次
                               宕机时缓冲区里未刷的部分 = 丢失窗口
```

`everysec` 是绝大多数场景的正确选择：性能接近无持久化，最坏丢 1~2 秒数据。

### 2.2 AOF 重写：文件会无限膨胀

对同一个 key 执行 1 万次 INCR，AOF 里就有 1 万条记录，但其实一条 `SET counter 10000` 就够。AOF 重写（rewrite）生成一份**等价但最小**的新 AOF：

```bash
127.0.0.1:6379> BGREWRITEAOF
Background append only file rewriting started
```

```conf
auto-aof-rewrite-percentage 100    # 比上次重写后大 100% 时自动触发
auto-aof-rewrite-min-size 64mb     # 且至少 64MB
```

重写也走 fork + COW：子进程按当前内存数据生成新 AOF；期间新的写命令由主进程写入增量缓冲。Redis 7 的 Multi-Part AOF 把文件拆成"1 个基础文件 + N 个增量文件 + manifest 清单"，重写不再需要旧版"重写缓冲区拷贝"的复杂逻辑，内存开销更小。

```text
appendonlydir/
├── appendonly.aof.1.base.rdb    # 基础文件(重写产物)
├── appendonly.aof.1.incr.aof    # 增量命令
└── appendonly.aof.manifest      # 清单
```

## 3. 混合持久化：两全其美

纯 AOF 恢复慢（逐条重放命令），纯 RDB 丢得多。Redis 4 起的混合模式（7.x 默认开启）：

```conf
aof-use-rdb-preamble yes
```

AOF 重写时，基础文件直接存 **RDB 格式**（紧凑、加载快），此后的增量仍是 AOF 命令格式：

```text
恢复流程: 先加载 base.rdb (快) -> 再重放 incr.aof (少量) 
        = RDB 的恢复速度 + AOF 的低丢失窗口
```

## 4. 方案选型与丢失窗口对照

| 方案 | 宕机丢失窗口 | 恢复速度 | 适用 |
|---|---|---|---|
| 不持久化 | 全部 | - | 纯缓存，可全量重建 |
| 仅 RDB | 上次快照以来（分钟级） | 快 | 能容忍分钟级丢失、要低开销 |
| AOF everysec | 约 1 秒 | 慢 | - |
| RDB + AOF 混合（推荐） | 约 1 秒 | 较快 | 大多数持久化需求 |
| AOF always | 最多 1 条 | 慢 | 极端要求（性能损失大） |

<Callout type="info" title="持久化不能替代备份与高可用">
持久化解决"本机重启不丢（多）"；磁盘损坏要靠**异地备份**（定期把 RDB 传到对象存储）；机器宕机期间的可用性要靠**主从 + 哨兵/Cluster**（后续章节）。三者是三个层次的问题。
</Callout>

<Callout type="warn" title="生产常见的持久化事故">
1）**fork 失败**：内存超物理内存一半且 `vm.overcommit_memory=0` 时 BGSAVE 报 Cannot allocate memory，需设置 `sysctl vm.overcommit_memory=1`；2）**RDB 失败阻断写入**：默认 `stop-writes-on-bgsave-error yes`，快照失败后所有写命令报错——监控必须盯住 `rdb_last_bgsave_status`；3）**AOF 重写风暴**：大实例重写时磁盘 IO 打满影响 everysec 的 fsync，出现 `aof_delayed_fsync` 增长，主线程可能被拖住。
</Callout>

```bash
# 持久化状态巡检

aof_last_write_status:ok
aof_delayed_fsync:0             # fsync 被延迟的次数, 增长说明磁盘顶不住
```

## 小结

- RDB：fork + COW 的全量快照，紧凑恢复快，丢失窗口是"两次快照之间"
- AOF：追加写命令，everysec 策略把丢失窗口压到约 1 秒；重写解决膨胀
- 混合持久化 = RDB 格式的基础 + AOF 增量，7.x 的默认最优解
- fork 的代价与内存量成正比：控制单实例内存，盯住 latest_fork_usec
- 持久化、备份、高可用是三件事；下一章讲事务与 Lua →

**2. always 与 everysec 在崩溃下的差异**

```bash
# ========== 实验组 A：appendfsync always ==========
127.0.0.1:6379> CONFIG SET appendonly yes
OK
127.0.0.1:6379> CONFIG SET appendfsync always
OK
127.0.0.1:6379> SET sync:always "test-value"
OK
# 立刻强杀，不留任何缓冲时间
$ kill -9 $(pgrep redis-server)
$ redis-server /etc/redis/redis.conf
127.0.0.1:6379> GET sync:always
"test-value"                      # 幸存！

# ========== 实验组 B：appendfsync everysec ==========
127.0.0.1:6379> CONFIG SET appendfsync everysec
OK
127.0.0.1:6379> SET sync:everysec "test-value"
OK
$ kill -9 $(pgrep redis-server)   # 必须在 1 秒内执行才能复现丢失
$ redis-server /etc/redis/redis.conf
127.0.0.1:6379> GET sync:everysec
(nil)                             # 可能丢失（取决于 kill 的时机）
```

**注意实验的时机敏感性**：`everysec` 下如果你手敲命令，从 `SET` 到 `kill` 往往超过 1 秒，后台线程已经 fsync 过了，数据反而幸存。要稳定复现丢失，用脚本把两步连起来：

```bash
# 写入后立刻杀进程
redis-cli SET sync:test "value" && kill -9 $(pgrep -f "redis-server.*6379")
```

**为什么会有这个差异？** 关键在于 `write()` 和 `fsync()` 是两回事：

```bash
# write() ：把数据从 Redis 进程的 AOF 缓冲区写到内核的 page cache
#           很快（微秒级），但数据还在内存里，掉电就没了
# fsync() ：命令内核把 page cache 刷到物理磁盘
#           慢（毫秒级，机械盘更慢），但数据真正落盘
```

`kill -9` 只杀死进程，**内核的 page cache 不受影响**，操作系统之后仍会把它刷到磁盘。所以严格来说，`kill -9` 测试的是"进程崩溃"，不是"断电"。要真正验证 `fsync` 的作用，需要物理断电或者用虚拟机强制断电。

不过在 `everysec` 下 `kill -9` 依然可能丢数据，原因是 Redis 自己的 **AOF 缓冲区**（`aof_buf`）里还有没执行 `write()` 的内容——这部分在进程内存里，进程死了就没了。

三种策略的完整对比：

| 策略 | write 时机 | fsync 时机 | 进程崩溃丢失 | 断电丢失 | 性能 |
|---|---|---|---|---|---|
| `always` | 每条命令 | **每条命令** | 0 | 0 | 最慢，QPS 掉到几千~几万 |
| `everysec` | 每条命令 | 后台线程每秒 | 最多 1 秒 | 最多 2 秒 | 接近不开 AOF |
| `no` | 每条命令 | 交给操作系统（约 30 秒） | 不确定 | 最多 30 秒 | 最快 |

**为什么 `everysec` 断电最多丢 2 秒而不是 1 秒？** 因为后台 fsync 线程如果上一次 fsync 还没做完（磁盘慢），主线程这一秒的 write 会被推迟，累积起来最坏是 2 秒。

**生产选型**：

- **`everysec` 是 99% 场景的答案**：1 秒丢失窗口 + 几乎无性能损失，性价比最高
- **`always` 只在金融级场景考虑**：每条命令都要等磁盘 fsync 返回，SSD 上 QPS 也就几万，机械盘直接崩到几千。而且这个损失换来的"零丢失"其实并不完整——单机 fsync 成功不代表数据安全，机器整体故障（磁盘损坏、机房断网）照样丢。真正的高可靠要靠**多副本 + 跨机房**，而不是死磕单机 fsync
- **`no` 基本不用**：丢失窗口不可控，还不如直接关掉 AOF 用 RDB

```bash
# 监控 fsync 是否顶得住
127.0.0.1:6379> INFO persistence | grep aof_delayed_fsync
aof_delayed_fsync:0               # 持续增长说明磁盘 IO 跟不上，要么换 SSD 要么降低写入量
```

`aof_delayed_fsync` 增长意味着后台 fsync 超过 1 秒还没完成，主线程被迫等待——这时 Redis 的延迟会明显抖动，是磁盘瓶颈的强信号。

**3. latest_fork_usec 与数据量的关系**

```bash
127.0.0.1:6379> INFO persistence | grep fork
latest_fork_usec:18234            # 最近一次 fork 耗时（微秒）
total_forks:47

127.0.0.1:6379> INFO memory | grep used_memory_human
used_memory_human:2.05G
```

**估算公式**：

```bash
# fork 耗时 ≈ 内存量 / 页表复制速度
#
# fork 本身并不复制数据，但要复制【页表】（page table）
# 页表大小 = 内存量 / 4KB页大小 × 8字节每个页表项
#          = 内存量 / 512
#
# 经验值（普通 x86 服务器，未开大页）：
#   每 GB 内存 → fork 耗时约 10 ~ 20 毫秒
#
# 上面的例子验证：2.05 GB → 18234 微秒 = 18.2 毫秒 ≈ 8.9 ms/GB，符合经验范围
```

**32 GB 实例的 fork 耗时估算**：

```bash
# 保守估计：32 GB × 10 ms/GB  = 320 毫秒
# 典型估计：32 GB × 15 ms/GB  = 480 毫秒
# 悲观估计：32 GB × 20 ms/GB  = 640 毫秒
#
# 结论：约 0.3 ~ 0.6 秒
```

**这 0.3~0.6 秒意味着什么？** fork 期间**主线程完全阻塞**，无法处理任何命令：

- 按 10 万 QPS 算，0.5 秒会积压 5 万个请求
- 所有客户端看到 500 毫秒的延迟尖刺，超时时间设得紧的直接报错
- 上游服务可能触发熔断
- 如果这时正好有 Sentinel 在做健康检查，`down-after-milliseconds` 设得小于 500ms 的话，**会误判主节点宕机并触发主从切换**

**影响 fork 耗时的因素**：

| 因素 | 影响 |
|---|---|
| 内存总量 | **线性正相关**，这是最主要因素 |
| 虚拟化环境 | 云主机（尤其 Xen）比物理机慢 2~5 倍 |
| 透明大页 THP | 开启后 fork 更快，但**写时复制的粒度从 4KB 变成 2MB**，导致内存暴涨和延迟飙升，**必须关闭** |
| 写入速率 | 不影响 fork 本身，但影响 fork 之后 COW 的内存开销 |

```bash
# 必须关闭 THP（Redis 启动时会警告）
$ echo never > /sys/kernel/mm/transparent_hugepage/enabled
# 永久生效：写进 /etc/rc.local 或用 systemd tuned

# 检查当前状态
$ cat /sys/kernel/mm/transparent_hugepage/enabled
always [madvise] never
```

**控制 fork 影响的实践建议**：

```bash
# 1. 单实例内存控制在 8 GB 以内（fork 约 100ms，可接受）
#    更大的数据量用 Cluster 分片，而不是堆单实例内存
127.0.0.1:6379> CONFIG SET maxmemory 8gb

# 2. 在从节点做持久化，主节点关掉 RDB
#    主库 redis.conf：
save ""
appendonly no
#    从库 redis.conf：
save 900 1
appendonly yes

# 3. 避开业务高峰做 BGSAVE / BGREWRITEAOF
#    关掉自动触发，改用凌晨的定时任务
127.0.0.1:6379> CONFIG SET save ""
$ crontab -e
0 3 * * * redis-cli BGSAVE

# 4. 控制 AOF 自动重写的触发频率
127.0.0.1:6379> CONFIG SET auto-aof-rewrite-percentage 100   # 增长 100% 才重写
127.0.0.1:6379> CONFIG SET auto-aof-rewrite-min-size 512mb   # 且至少 512MB

# 5. Sentinel 的 down-after-milliseconds 要大于最坏 fork 耗时
#    sentinel.conf：
sentinel down-after-milliseconds mymaster 30000
```

**COW 的内存放大风险**（比 fork 耗时更容易出事）：

fork 之后父子进程共享物理内存页，但**父进程每修改一个页，内核就要复制一份**。极端情况下（fork 期间所有数据都被改了一遍），内存占用会翻倍。

```bash
# 32 GB 实例做 BGSAVE，最坏需要 64 GB 内存
# 如果机器只有 40 GB，就会触发 OOM Killer 杀掉 Redis

# 缓解措施：
# 1. 机器内存至少是 maxmemory 的 1.5 ~ 2 倍
# 2. 开启 overcommit_memory，避免 fork 因为内存检查失败而报错
$ echo 1 > /proc/sys/vm/overcommit_memory
$ sysctl -w vm.overcommit_memory=1     # 临时
# 永久：写入 /etc/sysctl.conf

# 3. 监控 fork 期间的内存增长
127.0.0.1:6379> INFO memory | grep -E "used_memory_rss|used_memory_peak"
```

`vm.overcommit_memory=1` 是 Redis 官方强烈建议的配置。默认值 0 时，内核会在 fork 时检查"剩余内存是否够复制整个进程"，即使实际上因为 COW 根本用不了那么多。这会导致 `Can't save in background: fork: Cannot allocate memory` 错误，持久化直接失败。

**最后一个提醒**：`latest_fork_usec` 应该纳入常规监控。它突然变大通常意味着两件事之一——内存涨了，或者宿主机被其他租户挤占了资源。两种情况都值得立刻排查。
