# 权限与团队协作

Dify 不是一个人的玩具。当团队一起建应用、接知识库、调模型，就需要**成员角色、权限边界与协作流程**。本章讲清团队怎么安全地玩转 Dify。

## 1. 工作区与成员

回顾第 3 章：工作区是隔离单元。把「同一个业务线的人」放进一个工作区，共享应用、知识库与工具。

邀请成员方式：

- 「设置 → 成员 → 邀请」，填邮箱发送邀请
- 企业版支持 **SSO（单点登录）** 与 **LDAP/SCIM** 批量同步账号

<Callout type="info" title="一个账号多工作区">
成员可同时属于多个工作区，在右上角切换。不同工作区数据互不可见，天然隔离各业务线。
</Callout>

## 2. 角色与权限

Dify 内置角色（具体随版本，常见如下）：

| 角色 | 能力 |
|---|---|
| **管理员（Admin）** | 管理成员、模型密钥、工作区设置 |
| **编辑者（Editor）** | 创建/编辑应用、知识库、工具 |
| **使用者（User/Viewer）** | 使用已发布应用、查看日志（受限） |

```text
典型分工：
  管理员 → 管密钥、管成员、管合规
  算法/开发 → 搭应用、调工作流、接模型
  业务/运营 → 写知识库文档、看日志反馈
```

<Callout type="warn" title="API Key 与密钥权限收紧">
模型供应商 Key、后端 API Key 属于高敏感信息。只给管理员/必要人员可见，避免普通成员误用或泄露导致额度被盗刷。
</Callout>

## 3. 应用协作流程

推荐一个安全的协作节奏：

```text
草稿开发（编辑者）
  → 内部预览自测
  → 发布到「仅团队可见」灰度
  → 收集日志与标注
  → 确认稳定后发布为公开/嵌入
```

- 用**版本管理**留存每次发布快照，出问题可回滚（第 6 章）
- 重大改动先在小流量验证，再全量

## 4. 数据安全与合规

- 知识库文档谁可上传、谁可删，按角色控制
- 日志可能含用户隐私，限制查看权限并定期清理
- 自部署版（第 2 章）数据完全不出内网，满足合规

<Callout type="tip" title="把「谁负责什么」写进文档">
团队初期人少容易全员 Admin，随着人数增长务必分权。建一份简单的「职责说明」：谁管密钥、谁管发布、谁看日志，能省很多扯皮。
</Callout>

## 5. 与研发流程结合

- 知识库文档变更可走 Git/同步（如 Notion 同步）
- 关键应用配置建议评审后再发布
- 用第 15 章的标注集做回归，保障协作不破坏质量

**关键分界线在哪**

对照表里加粗的四行就是答案的核心：

1. **编辑者 vs 管理员的分界 = 密钥与成员**。编辑者能把应用从头搭到发布，但**碰不到模型供应商的 API Key**，也不能拉人进来。这个设计很合理——搭应用是日常高频操作，管密钥是低频高危操作，两者必须分开。
2. **普通成员 vs 编辑者的分界 = 读写**。普通成员是「消费者」，只能用别人做好的应用，看不到编排页，也看不到日志。

**验证脚本：让编辑者账号依次尝试**

```text
✅ 应该成功：
   1. 新建一个对话型应用 → 成功
   2. 改提示词、加知识库、点发布 → 成功
   3. 上传文档到知识库 → 成功
   4. 查看日志、写标注 → 成功
   5. 创建应用 API Key → 成功

❌ 应该被拒：
   6. 设置 → 模型供应商 → 尝试修改 OpenAI Key
      → 入口置灰 / 提示「需要管理员权限」
   7. 设置 → 成员 → 尝试邀请新成员
      → 「邀请」按钮不可见
   8. 尝试删除整个工作区
      → 入口不存在
```

用普通成员账号再跑一遍，会发现连第 1 步就进不去。

**一个容易被忽略的重点：WebApp 的访问权限是独立的**

这是本练习最有价值的发现——**工作区角色 ≠ WebApp 访问权限**。应用发布后，在「访问设置」里单独控制谁能打开这个网页：

```text
应用 → 发布 → WebApp 设置 → 访问权限
  ○ 仅自己可访问
  ○ 工作区成员可访问        ← 内部工具选这个
  ○ 指定成员可访问
  ○ 任何人可访问（公开链接） ← 对外产品选这个
```

也就是说，一个**完全不在工作区里的外部用户**，也可以通过公开链接使用你的应用。所以「谁能改应用」（工作区角色）和「谁能用应用」（WebApp 访问设置）是两套独立的机制，别混为一谈。

**实践中的分权建议**

```text
Owner（1 人）      → 通常是团队负责人，只保留一个
Admin（1–2 人）    → 平台管理者：管密钥、管成员、管合规
Editor（核心开发） → 搭应用、调工作流、维护知识库
Normal（业务方）   → 用应用、提反馈；配合 WebApp 权限精细控制
```

配套一份简单的职责文档（正文那条 tip）：

```text
| 事项              | 负责人 | 备份人 | 说明                     |
|-------------------|--------|--------|--------------------------|
| 模型 API Key 管理 | 张三   | 李四   | 季度轮换一次             |
| 生产应用发布      | 李四   | 张三   | 需 1 人 review           |
| 知识库文档维护    | 王五   | -      | 每月同步一次源文档       |
| 日志巡检与标注    | 赵六   | -      | 每周挑 10 条差回答标注   |
| 新成员权限审批    | 张三   | -      | 默认给 Normal，按需升级  |
```

**为什么初期就要分权**

正文说「人少容易全员 Admin」，这确实是常态，但有两个具体风险：

- **密钥泄露面扩大**：每多一个 Admin，模型 Key 就多一个泄露渠道。Key 被盗刷是真实发生过的事故，云端模型账单可以在几小时内跑到很高。
- **误操作不可逆**：Admin 能删应用、删知识库。知识库删了要重新上传文档 + 重新索引，几千个片段的重建既费时又费钱。

**进阶：企业级能力**

- **SSO 单点登录**（OIDC / SAML）：接入公司 IdP，员工离职自动失效，不用手动清理
- **SCIM 同步**：从 AD/LDAP 自动同步成员与部门，角色可按组映射
- **审计日志**：记录谁在什么时候改了什么，合规场景必需

这些属于企业版能力，社区版没有。如果是自部署社区版又需要审计，一个务实的替代方案是：**关键配置走版本管理 + 发布前评审**，用流程弥补工具缺口。

**和数据安全的联系**

日志里可能包含用户提交的隐私内容（手机号、订单信息、甚至身份证号）。这意味着「谁能看日志」实际上是一个**数据合规问题**，不只是权限问题。建议：

- 日志查看权限只给必要人员
- 配置日志保留期，定期清理（自部署可写定时任务清理数据库）
- 在应用提示词或 WebApp 说明里提醒用户不要输入敏感个人信息
- 涉及个人信息的场景，优先走自部署，数据不出内网

## 小结

- 工作区隔离业务线；成员多工作区可切换
- 角色分管理员/编辑者/使用者，密钥权限收紧
- 协作走「草稿→灰度→全量」+ 版本回滚
- 合规场景优先自部署；下一步两个端到端实战 →
