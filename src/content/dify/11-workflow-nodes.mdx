# 工作流节点详解

节点是工作流的「积木」。本章拆解最常用的几类节点，并给出组合思路。掌握它们，你能拼出绝大多数业务流水线。

## 1. LLM 节点

调用大模型生成内容。配置项：

- **模型**：选具体模型与温度
- **提示词**：可引用上游变量，如 `{{#start.query#}}`
- **记忆**：是否带会话历史（对话型工作流可用）
- **输出**：默认 `text` 字段供下游引用

```text
提示词示例：
你是翻译助手。把下面文本译成英文：
{{#start.text#}}
```

## 2. 知识检索节点

关联知识库，按输入检索片段。

```text
输入：{{#start.query#}}
输出：{{#retrieve.result#}}  (数组，含多个片段)
```

常与 LLM 节点串联做 RAG。

<Callout type="tip" title="检索结果先筛再喂">
检索返回多个片段，可直接全喂给 LLM；若片段很长，可在中间插一个「代码/条件」节点截取 Top 片段或拼接，控制 token 成本。
</Callout>

## 3. 代码节点（Code）

用 Python/JavaScript 写轻量逻辑：数据清洗、格式转换、简单计算。

```python
# 代码节点示例：把检索片段拼接成一段上下文
def main(retrieve_result: list) -> dict:
    context = "\n".join([r["content"] for r in retrieve_result[:3]])
    return {"context": context}
```

<Callout type="warn" title="代码节点别写重逻辑">
它适合「胶水代码」：切片、拼接、解析。重业务逻辑、需要依赖库或联网的，应放到你的后端服务，由 API 工具调用（第 9 章）。
</Callout>

## 4. 条件节点（IF / 分支）

根据表达式走不同分支。

```text
IF  {{#start.lang#}} == "en"
   → 走「英文回答」分支
ELSE
   → 走「中文回答」分支
```

支持比较、包含、为空等判断，是流程分流的关键。

## 5. 迭代节点（Iteration）

对**数组**逐元素执行子流程，类似编程里的 `for` 循环。

```text
输入：检索结果数组 [片段1, 片段2, 片段3]
子流程：对每个片段调用 LLM 抽取关键信息
输出：抽取结果数组
```

适合「批量处理多条记录」场景，如批量摘要多篇文章。

## 6. 典型组合示例

```text
Start(问题)
  → 知识检索 → 代码节点(拼接Top3)
  → 条件节点(是否含敏感词)
       是 → 直接返回「无法回答」
       否 → LLM(生成答案) → End
```

**第一部分：代码节点**

代码节点的输入变量要先在节点面板里声明，再在 `main()` 的参数中同名接收。

```python
def main(retrieve_result: list) -> dict:
    """把检索结果拼接成一段带编号的上下文文本。"""
    if not retrieve_result:
        return {"context": "（未检索到相关资料）", "hit_count": 0}

    parts = []
    for i, item in enumerate(retrieve_result[:3], start=1):
        content = (item.get("content") or "").strip()
        title = item.get("title") or "未知来源"
        score = item.get("score", 0)
        # 单段截断，防止某个超长片段吃光 token 预算
        if len(content) > 800:
            content = content[:800] + "……"
        parts.append(
            f"【资料{i}｜来源：{title}｜相关度：{score:.2f}】\n{content}"
        )

    return {
        "context": "\n\n".join(parts),
        "hit_count": len(parts),
    }
```

节点面板配置：

```yaml
输入变量:
  - 变量名: retrieve_result
    赋值: retrieve.result        # 从上游知识检索节点选取
输出变量:
  - 名称: context   类型: String
  - 名称: hit_count 类型: Number
```

**为什么要自己拼而不用 `{{#context#}}`**

| 场景 | 用 `{{#context#}}` | 用代码节点自拼 |
|---|---|---|
| 只想要标准 RAG | ✅ 更省事，自带引用归属 | 没必要 |
| 要控制 token（截断长片段） | ❌ 做不到 | ✅ |
| 要加来源标注、相关度、编号 | ❌ 格式固定 | ✅ 完全自定义 |
| 要按分数二次过滤 | ❌ | ✅ |
| 要统计命中数供下游判断 | ❌ | ✅ 输出 `hit_count` |

代码节点的价值就在于**可控**。但请遵守正文那条 warn：它只做「胶水」——拼接、截断、格式化。不要在里面写业务规则、连数据库、发 HTTP 请求（沙箱环境也不允许）。

**LLM 节点改为引用代码节点输出**

```text
USER 提示词：
参考资料：
{{#code.context#}}

问题：{{#start.query#}}

要求：严格依据上述资料回答，并在句末用【资料N】标注依据。
资料中没有的信息，回答「资料中未找到相关信息」。
```

**第二部分：条件节点（长问题先摘要）**

条件节点无法直接算字符串长度，有两种常见做法：

**做法 A（推荐）：先用代码节点算长度，再判断**

```python
def main(query: str) -> dict:
    q = (query or "").strip()
    return {
        "length": len(q),
        "is_long": len(q) > 200,   # 布尔值也可直接给 IF 用
    }
```

然后 IF 节点配置：

```yaml
条件: len_check.length  >  200
  true  分支 → LLM 摘要节点
  false 分支 → 直接进入知识检索
```

**做法 B：直接用 IF 节点的「长度」运算符**

新版 Dify 的条件节点对字符串类型提供了长度比较，可直接选：

```yaml
变量: start.query
条件: 长度大于（length >）
值: 200
```

有这个选项就用它，能省掉一个节点。

**摘要 LLM 节点的配置**

```text
模型: gpt-4o-mini（温度 0.2，摘要要稳定不发挥）
SYSTEM:
你是问题精简助手。用户的提问过长，请提炼成一句不超过 50 字的
检索查询语句，只保留核心诉求与关键实体（产品名、编号、动作）。
只输出精简后的问题本身，不要任何解释、前缀或引号。

USER:
{{#start.query#}}
```

**关键点：两条分支要合流**

这是本练习最容易卡住的地方。true 分支产出 `summarize.text`，false 分支产出 `start.query`，下游的知识检索节点只能绑定一个变量。解决办法是插入**变量聚合器（Variable Aggregator）** 节点：

```yaml
节点: 变量聚合器
输出变量名: final_query
分组赋值:
  - summarize.text     # 来自 true 分支
  - start.query        # 来自 false 分支
```

聚合器会取**实际执行到的那条分支**的值。之后知识检索节点的查询变量绑定 `aggregator.final_query` 即可。

没有聚合器的话，你会遇到「另一条分支的变量为 null」或者干脆连不上线的问题。

**运行验证**

```text
用例 1：短问题（约 20 字）
  query = "如何退款？"
  → IF 判定 false，跳过摘要
  → 聚合器 final_query = "如何退款？"
  → 检索命中 3 段 → 代码拼接 context（约 900 字）
  → LLM 输出答案
  耗时约 2.1s，节点执行 6 个（摘要节点显示为「跳过」）

用例 2：超长问题（约 350 字的吐槽式提问）
  query = "我上周买了你们的企业版，然后发现导出功能……（略）"
  → IF 判定 true
  → 摘要节点输出 "企业版导出功能异常如何处理"
  → 聚合器 final_query = 摘要结果
  → 检索命中质量明显好于直接拿原文去检索
  耗时约 3.4s，多了一次 LLM 调用
```

**用例 2 揭示的原理**：超长口语化提问直接拿去做向量检索，噪音词会稀释语义，召回质量下降。先摘要成一句检索友好的短句，召回准确率通常有可观提升。这就是所谓的 **Query Rewriting（查询改写）**，是 RAG 里性价比很高的一个优化点。

**常见坑**

| 问题 | 原因 | 解决 |
|---|---|---|
| 代码节点报 `KeyError: 'content'` | 检索结果字段名不符预期 | 用 `item.get("content")` 而非 `item["content"]` |
| 代码节点报变量未定义 | 面板里没声明输入变量 | 输入变量名必须与 `main()` 形参完全同名 |
| 分支合流后下游拿到 null | 缺少变量聚合器 | 插入聚合器节点 |
| 摘要节点输出带引号或「摘要：」前缀 | 提示词没约束死 | 加「只输出问题本身，不要任何前缀」 |
| 代码节点超时 | 写了循环调用或大量计算 | 代码节点有执行时长限制，只做轻量处理 |

**延伸思考**

跑通后可以想想：如果检索完全没命中（`hit_count == 0`），现在的流程会把「（未检索到相关资料）」喂给 LLM，仍然要花一次模型调用。更优的做法是在代码节点后再加一个 IF，`hit_count == 0` 时直接走固定话术到 End——既省钱又杜绝幻觉。

## 小结

- LLM 节点生成、知识检索做 RAG、代码节点做胶水处理
- 条件节点分流、迭代节点批量处理数组
- 组合思路：检索→清洗→判断→生成→输出
