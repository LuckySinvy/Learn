# 工作流基础

当需求从「聊聊天」变成「按固定步骤处理一件事」，**工作流（Workflow）** 就该登场了。它用**节点画布**把处理逻辑可视化，比让模型自由发挥更可控、可调试、可复现。

## 1. 什么时候用工作流

- 流程固定：先 A 再 B 再 C，顺序明确
- 需要分支判断：满足条件走这条、否则走那条
- 要调用多个工具/知识库并拼装结果
- 对输出格式、步骤有强约束

<Callout type="tip" title="工作流 vs Agent">
流程你说了算、要稳定可预期 → 工作流。流程连你都不确定、要模型自己想办法 → Agent（第 12 章）。很多生产系统用「工作流为主 + 局部 Agent」的混合。
</Callout>

## 2. 画布与节点

创建工作流应用后进入画布，核心要素：

- **Start（开始）节点**：接收输入变量（如用户问题、文件）
- **中间节点**：LLM、知识检索、代码、条件、迭代等（第 11 章）
- **End（结束）节点**：输出最终结果
- **连线**：定义节点执行顺序与数据流向

```text
[Start] --用户输入--> [知识检索] --> [LLM 生成] --> [End]
                                  ↘ [条件判断] --> [代码处理] --> [End]
```

## 3. 第一个工作流：问答流水线

我们搭一个「检索增强问答」最小流程：

1. 添加 **Start**，定义变量 `query`（用户输入）
2. 添加 **知识检索** 节点，关联你的知识库，输入 `query`
3. 添加 **LLM** 节点，提示词引用检索结果：`根据以下资料回答：{{#knowledge#}} 问题：{{#query#}}`
4. 添加 **End**，输出 LLM 的结果

<Callout type="warn" title="连线方向要对">
节点连线错乱会导致「数据没传过去」。每个节点的输入来自上游哪个节点的哪个输出，画布上要能一眼看清。调试报错先看连线。
</Callout>

## 4. 运行与调试

- 点「**运行**」输入测试值，画布会**高亮每个节点**并展示中间结果
- 某个节点输出异常 → 单独改它，不必重跑全部
- 支持查看每一次运行的完整链路与变量快照

```text
运行 #12
  Start.query = "如何退款？"
  知识检索 → 命中 3 段
  LLM → 生成答案 128 字
  End → 输出成功
```

## 5. 变量在节点间传递

工作流的本质是**数据流动**。上游节点的输出以 `{{#节点ID.字段#}}` 形式被下游引用。

```text
{{#start.query#}}        ← Start 节点的 query 变量
{{#retrieve.result#}}    ← 知识检索节点的 result
{{#llm.text#}}           ← LLM 节点的 text
```

**运行与观察**

点右上角「运行」，填入 `query = 如何退款？`，然后**逐个点开节点查看详情**：

```text
运行 #1  总耗时 2.4s  消耗 1,203 tokens

├─ Start          0.01s
│    输出: { "query": "如何退款？" }
│
├─ 知识检索        0.35s
│    输入: { "query": "如何退款？" }
│    输出: result = [
│      { "content": "退款需在收货后 7 日内...", "score": 0.83 },
│      { "content": "退款将原路返回...",       "score": 0.79 },
│      { "content": "特殊商品不支持退款...",   "score": 0.71 }
│    ]
│
├─ LLM            1.98s
│    输入 prompt（可展开看完整拼装结果）
│    输出: text = "退款流程如下：1. 进入订单详情页..."
│    tokens: prompt 1,050 / completion 153
│
└─ End            0.01s
     输出: { "answer": "退款流程如下：..." }
```

**这里要确认的三件事**

1. **知识检索节点的 `result` 不为空数组**——空了说明检索没命中，往下走再好的 LLM 也没用。
2. **LLM 节点的输入 prompt 里真的出现了检索到的文本**——展开看完整 prompt，如果 `{{#context#}}` 位置是空的，说明「上下文变量」没挂对。
3. **End 的输出等于 LLM 的 text**——变量选错会导致输出为空或是上游某个中间值。

**两种引用上下文的方式（容易混淆）**

| 写法 | 前提 | 效果 |
|---|---|---|
| `{{#context#}}` | LLM 节点的「上下文变量」必须挂上检索节点的 result | Dify 自动格式化片段，并生成**引用与归属**信息 |
| `{{#retrieve.result#}}` | 无需挂上下文变量 | 直接插入原始数组文本，**不会有引用标注** |

**推荐用前者**，因为能在最终回答里看到来源片段，便于溯源和调试。很多人用了后者，然后困惑「为什么没有引用信息」。

**变量引用的正确姿势**

不要手敲 `{{#start.query#}}`，在提示词框里输入 `/` 或点「+」会弹出变量选择器，从列表里选。手敲极易出现：

```text
{{#Start.query#}}     ← 节点 ID 大小写错误
{{#start.qeury#}}     ← 字段名拼错
{{start.query}}       ← 少了井号，工作流内不认这种写法
```

这三种写法都会让占位符原样出现在 prompt 里，模型收到一串花括号，回答就会莫名其妙。

**常见报错与排查**

| 报错 / 现象 | 原因 | 解决 |
|---|---|---|
| `Node not connected` | 有节点没连线，成了孤岛 | 检查每个节点都在 Start→End 的通路上 |
| 检索节点 result 为空 | 阈值太高 / 知识库还在索引 / 查询变量选错 | 降阈值到 0.4 试；确认知识库状态为「可用」 |
| LLM 回答与资料无关 | 上下文变量没挂，prompt 里没有资料 | 展开 LLM 输入 prompt 确认 |
| End 输出为空 | 输出变量没绑定或绑错节点 | 重新从选择器里选 `llm.text` |
| 整体很慢（>10s） | 模型慢或 TopK 太大导致 prompt 过长 | 换快模型；TopK 降到 3–4 |

**进阶：加一个「无召回」分支**

跑通四节点后，可以试着在检索和 LLM 之间插一个**条件分支（IF/ELSE）** 节点：

```text
[Start] → [知识检索] → [IF: retrieve.result 长度 > 0]
                          ├─ true  → [LLM 生成] → [End]
                          └─ false → [直接回复固定话术] → [End]
```

这样在完全没召回时，直接返回「未找到相关资料，请联系人工客服」，既省了一次模型调用的钱，又杜绝了幻觉。这是生产环境里非常常见的做法，第 11 章会详细讲条件节点。
</Answer>
</Callout>

## 小结

- 工作流用节点画布把固定流程可视化，比自由对话更可控
- Start 收输入、End 出结果、连线定顺序，中间是各类节点
- 运行可逐步高亮、查看中间结果，便于调试
- 节点间靠 `{{#节点.字段#}}` 传递数据；下一步详解各节点 →
