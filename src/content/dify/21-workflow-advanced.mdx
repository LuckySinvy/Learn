# 工作流条件分支与迭代进阶

第 10、11 章介绍了工作流画布与常用节点。当业务出现「多条路径」或「一批数据逐项处理」时，就需要**条件分支（IF/ELSE）** 与 **迭代（Iteration）** 节点。本章讲清它们的实战用法。

## 1. 条件分支：让流程「看情况走」

条件节点依据变量判断，把执行导向不同分支。例如按用户意图分流：

```text
[Start]
  → [分类 LLM] 输出 intent
  → [IF] intent == "退款"
        → 走「退款处理」分支
  → [ELSE]
        → 走「通用问答」分支
  → [End]
```

```yaml
# 条件节点配置示意
if_node:
  variable: "{{#classify.intent#}}"
  conditions:
    - op: equals
      value: "退款"
      goto: refund_branch
  else:
    goto: general_branch
```

<Callout type="tip" title="条件变量先用 LLM 规整">
自由文本难直接判断，先用一个 LLM 节点把用户输入归类为固定枚举（退款/咨询/投诉），再交给 IF 判断，流程更稳、分支更清晰。
</Callout>

## 2. 迭代节点：批量处理列表

当输入是一组条目（如一批订单、一组文件），用**迭代节点**逐项执行子流程并聚合结果。

```text
输入：订单列表 [O1, O2, O3]
迭代节点：
  对每一项：查状态 → 判断是否超时 → 拼成一行摘要
输出：["O1 已发货", "O2 超时待处理", "O3 已签收"]
```

## 3. 变量聚合与下游消费

迭代结果通常是数组，下游 LLM 或代码节点需把它**聚合为可读文本**再使用：

```text
{{#iteration.output#}} 是一个数组
用代码节点 join 为换行字符串，再喂给总结节点：
O1 已发货
O2 超时待处理
O3 已签收
```

<Callout type="warn" title="留意迭代的 token 成本">
列表越长，迭代次数越多，每次都可能调用 LLM。处理上百条数据时，考虑先在代码节点做过滤，只把需要模型判断的条目送入迭代，控住成本。
</Callout>

## 4. 嵌套与断路

复杂流程可在分支内再套迭代。但要避免「分支永远不汇合」——确保各路径最终都连到 End，否则运行会卡住或结果缺失。

**节点 1：分类 LLM（关键——必须输出纯枚举）**

```text
模型: gpt-4o-mini
温度: 0            # 分类任务必须用 0，要的是确定性不是创造力

SYSTEM:
你是工单分类器。将用户输入归入且仅归入以下三类之一：
A = 退款、退货、账单争议、要求赔偿
B = 故障、报错、无法使用、功能异常、性能问题
C = 以上都不是（功能咨询、使用方法、售前问题、闲聊）

规则：
- 只输出单个大写字母 A、B 或 C，不要输出任何其他字符。
- 不要输出解释、标点、引号、换行以外的内容。
- 若同时涉及多类，按 A > B > C 的优先级取其一。
- 无法判断时输出 C。

USER:
{{#start.user_input#}}
```

正文那条 tip 的落地就在这里。**为什么必须归到固定枚举**：IF 节点做的是精确字符串比较，如果 LLM 输出「A 类」「退款」「A（退款）」，条件判断就全部落空，流程直接掉进 ELSE。

**加固技巧**：在 IF 之前插一个代码节点做清洗，比只靠提示词可靠得多：

```python
def main(raw: str) -> dict:
    """把 LLM 输出规整为严格的 A/B/C，防止格式抖动导致分支失效。"""
    s = (raw or "").strip().upper()
    for ch in s:
        if ch in ("A", "B", "C"):
            return {"intent": ch}
    return {"intent": "C"}   # 兜底，绝不返回意外值
```

**节点 2：三分支 IF/ELSE**

```yaml
IF:    normalize.intent == "A"   → 退款分支
ELIF:  normalize.intent == "B"   → 报修分支
ELSE:                            → 其他分支
```

Dify 的条件节点支持添加 ELIF 形成多分支，不必嵌套两层 IF。

**节点 3：拆分故障点（为迭代准备数组）**

迭代节点的输入必须是**数组**，所以要先把自由文本拆成列表：

```python
import re

def main(text: str) -> dict:
    """从用户描述中拆出故障点列表，保证返回 1-5 个元素。"""
    t = (text or "").strip()
    # 按序号、分号、句号、换行切分
    parts = re.split(r"[；;。\n]|(?:\d+[、.)])", t)
    items = [p.strip() for p in parts if p and len(p.strip()) >= 4]
    if not items:
        items = [t or "未描述具体问题"]
    return {"issues": items[:5]}   # 限制上限，控制迭代成本
```

`items[:5]` 这个上限很重要——它就是正文那条 warn 说的「先过滤再迭代」。用户可能粘贴一大段日志，不设上限的话迭代 50 次，token 和耗时都会失控。

**节点 4：迭代节点**

```yaml
迭代节点:
  输入数组: split_issues.issues
  子流程:
    - LLM 节点:
        模型: gpt-4o-mini（温度 0.3）
        SYSTEM: |
          你是技术支持工程师。针对用户提到的单个故障点，
          给出一条不超过 40 字的排查建议。
          只输出建议本身，不要编号、不要前缀、不要客套话。
        USER: |
          故障点：{{#iteration.item#}}
  输出: output    # 数组，每项是子流程的 LLM 输出
```

子流程内用 `{{#iteration.item#}}` 引用当前元素，用 `{{#iteration.index#}}` 引用下标（从 0 开始）。

**节点 5：数组转文本（下游 LLM 不能直接吃数组）**

```python
def main(results: list, issues: list) -> dict:
    """把迭代结果与原故障点配对，拼成带编号的可读文本。"""
    lines = []
    for i, (issue, advice) in enumerate(zip(issues, results), start=1):
        lines.append(f"{i}. 问题：{issue}\n   建议：{str(advice).strip()}")
    return {
        "report": "\n".join(lines),
        "count": len(lines),
    }
```

这一步是正文第 3 节的重点：**迭代输出是数组，必须聚合成文本才能喂给下游 LLM**。直接把数组塞进提示词，会得到一串带引号和方括号的 Python 字面量，模型读起来很别扭。

**节点 6：汇总 LLM**

```text
SYSTEM:
你是客服主管。根据下面的逐项排查报告，用一句不超过 50 字的话
向用户总结整体情况与下一步动作。不要罗列细节，只给结论性建议。

USER:
共发现 {{#join.count#}} 个问题：
{{#join.report#}}
```

**节点 7：变量聚合器（三条分支必须合流）**

```yaml
变量聚合器:
  输出变量: final_answer
  分组赋值:
    - refund_llm.text      # A 分支
    - summary_llm.text     # B 分支
    - general_llm.text     # C 分支
```

**这是本练习最容易出错的地方**，也是正文第 4 节「避免分支永远不汇合」的具体解法。没有聚合器时，End 节点只能绑定某一条分支的输出变量，另外两条分支执行完就到不了 End，表现为「运行成功但输出为空」。

**测试用例**

```text
用例 A：「我要退款，这个月的订阅费退给我」
  → 分类 A → 退款分支 → 输出退款话术
  → 迭代节点显示「跳过」，耗时约 1.8s

用例 B：「登录页面打不开；上传文件一直转圈；导出的 PDF 是乱码」
  → 分类 B → 拆出 3 个故障点
  → 迭代 3 次，每次一个 LLM 调用
  → 拼接报告 → 汇总成一句
  → 耗时约 5.2s，是 A 分支的 3 倍——迭代的成本代价一目了然

用例 C：「你们支持导出 Excel 吗？」
  → 分类 C → 知识检索 → 通用问答

用例 D（边界）：「随便说点什么」
  → 分类应落到 C，验证兜底逻辑

用例 E（边界）：故障描述里塞 20 个问题
  → 验证 items[:5] 截断生效，迭代次数不失控
```

**用例 B 是本练习的核心观察点**：打开运行详情，迭代节点可以展开看到**每一轮的独立输入输出**，这是调试迭代逻辑的唯一手段。如果某一轮输出异常，能精确定位是哪个元素出的问题。

**成本对照（用例 B）**

```text
分类 LLM      ×1  = 约 120 tokens
迭代内 LLM    ×3  = 约 450 tokens
汇总 LLM      ×1  = 约 280 tokens
合计             ≈ 850 tokens，5 次模型调用

若不设 items[:5] 上限，用户粘贴 20 个问题：
             ≈ 3500+ tokens，22 次调用，耗时 30s+
```

这就是为什么要在迭代前过滤。**迭代节点是工作流里最容易失控的成本黑洞**。

**常见坑汇总**

| 现象 | 原因 | 解决 |
|---|---|---|
| 所有输入都走 ELSE 分支 | LLM 输出带了多余字符 | 加规整代码节点；分类温度设 0 |
| 迭代节点报「输入不是数组」 | 上游给的是字符串 | 用代码节点转成 list |
| 迭代只跑了一次 | 数组实际只有 1 个元素 | 检查拆分逻辑的分隔符 |
| End 输出为空 | 缺变量聚合器 | 补上聚合器节点 |
| 下游 LLM 收到一串方括号 | 直接引用了数组变量 | 先 join 成字符串 |
| 迭代内引用不到外部变量 | 子流程作用域限制 | 需要的外部值先通过迭代节点的入参传入 |
| 运行很久不结束 | 迭代次数过多 | 加数量上限；考虑并行迭代（新版支持并行模式） |

**进阶：并行迭代**

新版 Dify 的迭代节点支持**并行模式**，可设置并发数（如 3）。3 个故障点串行要 3×1.5s，并行只需约 1.5s。适合各元素之间**互不依赖**的场景。如果后一项处理需要用到前一项的结果（累加、递推），就必须保持串行。

## 小结

- 条件分支用「先归类、再判断」最稳
- 迭代节点逐项处理列表，结果需聚合后再用
- 大数据量先过滤再迭代，控制成本
- 所有分支必须汇到 End；下一步用 API 把流程接进外部系统 →
