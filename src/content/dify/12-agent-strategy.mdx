# Agent 策略与推理

**Agent（智能体）** 与工作流相反：你**不规定步骤**，而是给模型目标、工具和推理框架，让它自己决定「先做什么、调哪个工具、下一步怎么办」。本章讲清它的原理与配置。

## 1. 什么是 Agent

- 工作流：你画好流程图，机器照走
- Agent：你给目标 + 工具箱，模型自己规划路径

Agent 适合**开放、路径不确定**的任务：订机票、排查故障、跨系统办事。

<Callout type="info" title="Agent 不是魔法">
Agent 的可靠性高度依赖「工具质量 + 提示词约束 + 推理策略」。工具描述不清、目标模糊，Agent 就会乱来或陷入循环。
</Callout>

## 2. ReAct 推理范式

Dify 的 Agent 多基于 **ReAct（Reason + Act）** 循环：

```text
Thought（思考）：我需要先查订单状态
Action（行动）：调用 query_order(ORD-123)
Observation（观察）：返回「已发货」
Thought：用户还问了预计到货，我调用物流查询
Action：call_logistics(ORD-123)
Observation：预计明天
Thought：信息齐了，可以回答了
Final Answer：您的订单已发货，预计明天送达。
```

模型在「思考—行动—观察」间循环，直到认为能给出最终答案。

## 3. 推理模式与策略

Dify 提供不同 Agent 策略（随版本演进）：

- **Function Calling（工具调用）**：模型直接输出结构化工具调用，稳定高效（主流推荐）
- **ReAct**：以自然语言 Thought/Action 循环，兼容性强
- 可在 Agent 设置中选择策略并配置**最大迭代次数**（防死循环）

```text
Agent 设置：
  推理策略：Function Calling
  最大迭代轮数：5
  失败重试：2
```

<Callout type="warn" title="务必设最大迭代">
不设上限，Agent 可能在「调工具→不满意→再调」里无限循环，既慢又烧 token。5–10 轮通常足够，超限就让它诚实说「无法完成」。
</Callout>

## 4. 给 Agent 配工具

Agent 的能力 = 你挂载的工具集合。常见组合：

- 搜索工具（获取实时信息）
- 内部 API 工具（查/办业务）
- 代码工具（计算、解析）
- 知识库检索（基于私有资料）

工具的 `description` 越清楚，Agent 选得越准（回看第 9 章）。

## 5. 提示词约束 Agent

用系统提示框定边界：

```text
你是一个运维助手。可以调用查询类工具，但禁止执行任何写操作。
每步先说明你要做什么，再调用工具。
若两次尝试仍无结果，停止并说明原因。
```

<Callout type="tip" title="Agent + 工作流混合">
复杂系统常这样设计：外层 Agent 负责「理解意图、拆解任务」，把确定性的子任务交给工作流/工具执行。兼顾灵活与可控。
</Callout>

```text

你是产品对比顾问，帮助客户在我司产品之间做选择。

# 工具使用规则
1. 我司产品的价格与特性，一律用 get_product_info 查询，一次只查一个产品。

- 表格下方给出一句选型建议，说明「什么情况下选哪个」。
- 若某项信息工具查不到，在表格中标注「暂无数据」，不要编造。
- 若 5 轮内仍无法收集齐信息，如实说明已获得什么、缺什么。
```

**预期的推理轨迹**

问：「对比一下专业版和企业版的价格与特性」

```text

Action: get_product_info(product_name="企业版")
Observation: {"price": "¥999/月", "features": ["不限成员", "1TB 存储",

Final Answer:

|---|---|---|

```

**观察轨迹时的四个重点**

1. **工具选择是否正确**——问我方产品时用了 `get_product_info` 而非 `web_search`。如果它跑去网上搜自家价格，说明两个工具的 description 边界没划清（回看第 9 章）。
2. **是否串行拆解**——Agent 把「对比两个产品」自动拆成了两次单产品查询。这正是 Agent 相对工作流的价值：**你没规定要查两次，它自己想到的**。
3. **何时停止**——迭代 3 判断信息已足够就收手，没有继续瞎调。这依赖模型判断力和清晰的输出要求。
4. **最终答案是否只用了工具返回的数据**——检查表格里的价格数字是否与 Observation 一致。如果出现工具没返回过的数字，就是幻觉，需要加强提示词第 3 条。

**故意制造异常，观察边界行为**

这才是本练习最有价值的部分：

```text
实验 A：问一个不存在的产品
  问：「对比一下旗舰版和企业版」
  期望：get_product_info("旗舰版") 返回 404 / 空
        → Agent 应告知「未找到旗舰版」，而不是编造参数
  若它自动改查「企业版、专业版」并假装那就是答案 → 提示词需加约束

实验 B：把最大迭代降到 1，重新提问
  期望：只来得及查一个产品，然后应当如实说明
        「已获取专业版信息，因步数限制未能查询企业版」
  若它凭空补出企业版数据 → 典型幻觉，说明约束不足

实验 C：把 get_product_info 的 description 改成只写「查询产品」
  期望：Agent 开始误用工具，或该调不调、改用 web_search
  这直观验证了正文「工具描述决定调用准确率」
```

**Function Calling vs ReAct 的实测差异**

同一个问题分别用两种策略跑：

| 维度 | Function Calling | ReAct |
|---|---|---|
| 参数准确性 | 高（结构化输出，模型侧保证格式） | 中（靠文本解析，偶尔参数格式出错） |
| Token 消耗 | 较低 | 较高（Thought 是自然语言，很啰嗦） |
| 速度 | 快 | 慢 |
| 可读性 | 轨迹较简洁 | 推理过程更易懂，适合调试和教学 |
| 模型要求 | 必须原生支持 | 任何模型都能跑 |

**结论**：生产环境优先 Function Calling；本地小模型或调试阶段用 ReAct。

**常见问题排查**

| 现象 | 原因 | 解决 |
|---|---|---|
| Agent 一轮工具都不调 | 模型不支持 FC / 工具未勾选 / 提示词没提工具 | 换模型或改 ReAct；确认工具已启用 |
| 反复调同一个工具直到超限 | 工具返回为空或报错，模型不断重试 | 提示词加「同参数不重复调用」；修好工具本身 |
| 触发最大迭代仍无答案 | 任务太复杂，或工具粒度太细 | 提高上限到 8–10，或合并工具减少调用次数 |
| 参数传错（如传了「企业」而非「企业版」） | 参数 description 没写清取值范围 | 在参数描述里枚举合法值 |
| 回答里价格与工具返回不符 | 幻觉 | 温度调低；提示词强调「数字必须来自工具」 |

**回到正文的那句话**

「Agent 不是魔法」——本练习跑下来你会发现，Agent 表现好坏几乎完全取决于三件事：**工具 description 写得清不清楚、系统提示词约束够不够硬、模型本身的推理能力**。这三样都到位，Agent 很聪明；缺一样，它就开始胡来。所以生产系统才普遍采用「工作流为主 + 局部 Agent」的混合架构——把确定的部分固化，只把真正需要临场判断的部分交给 Agent。

## 小结

- Agent 自主规划步骤，适合开放不确定任务
- ReAct / Function Calling 是主流推理范式
- 必须设最大迭代防死循环；工具描述决定调用准确率
- 用提示词约束边界；常与工作流混合使用
