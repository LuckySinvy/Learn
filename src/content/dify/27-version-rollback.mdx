# 应用版本管理与回滚

前面讲了提示词、工作流、模型路由的优化。但优化有风险——一次「看似更好」的改动可能让线上效果翻车。Dify 提供**应用版本快照**机制，让你可以放心试错、一键回退。本章讲怎么用好它。

## 1. 版本是什么

每次「发布（Publish）」都会生成一个**版本快照**，记录那一刻的提示词、变量、工作流、模型配置。快照不可变，可随时切回。

```text
发布历史：
  v3  2026-07-28  调整退款分支逻辑   ← 当前线上
  v2  2026-07-20  接入重排模型
  v1  2026-07-10  初始版本
```

<Callout type="tip" title="每次有意义的改动都发布一版">
不要把多次不相关改动堆在一个版本里。语义清晰的版本（『接入重排』『调整退款分支』）回滚时你才知道切到哪一版。
</Callout>

## 2. 回滚操作

当新版本效果变差或报错：

1. 进入「应用 → 发布 → 版本历史」
2. 找到稳定的旧版本（如 v2）
3. 点「**恢复此版本**」→ 系统把当前草稿与线上都切回 v2 的配置
4. 确认后重新发布生效

```yaml
# 回滚策略示意
rollback_policy:
  trigger: gpt_score_drop > 0.3  # 配合第 26 章评估
  target: last_stable_version    # 上一个达标版本
  action: restore_and_republish
```

## 3. 草稿与线上的隔离

Dify 区分**草稿（Draft）** 与**已发布（Published）**：你在草稿里随便改，不影响线上用户；确认无误再发布成新版本。回滚也是把线上切到旧快照，草稿不受影响。

<Callout type="warn" title="回滚不自动恢复知识库">
应用版本只存提示词/工作流/配置，**不存知识库内容**。若问题出在知识库（如误删文档），需配合知识库的备份单独恢复。
</Callout>

## 4. 与评估联动

最稳的节奏：改一版 → 跑第 26 章的评估 → 分数达标才发布 → 否则丢弃草稿。把版本、评估、回滚串成一条「安全迭代流水线」。

<Callout type="exercise" title="动手做">
在测试应用里故意发布一个「会答错」的版本，然后用版本历史恢复回上一版，确认线上行为恢复正常，体验完整回滚流程。
</Callout>

## 小结

- 每次发布生成不可变版本快照，可随时回退
- 回滚恢复的是提示词/工作流配置，不含知识库
- 草稿隔离线上，确认后再发布
- 版本 + 评估 + 回滚构成安全迭代闭环
