# 应用版本管理与回滚

前面讲了提示词、工作流、模型路由的优化。但优化有风险——一次「看似更好」的改动可能让线上效果翻车。Dify 提供**应用版本快照**机制，让你可以放心试错、一键回退。本章讲怎么用好它。

## 1. 版本是什么

每次「发布（Publish）」都会生成一个**版本快照**，记录那一刻的提示词、变量、工作流、模型配置。快照不可变，可随时切回。

```text
发布历史：
  v3  2026-07-28  调整退款分支逻辑   ← 当前线上
  v2  2026-07-20  接入重排模型
  v1  2026-07-10  初始版本
```

<Callout type="tip" title="每次有意义的改动都发布一版">
不要把多次不相关改动堆在一个版本里。语义清晰的版本（『接入重排』『调整退款分支』）回滚时你才知道切到哪一版。
</Callout>

## 2. 回滚操作

当新版本效果变差或报错：

1. 进入「应用 → 发布 → 版本历史」
2. 找到稳定的旧版本（如 v2）
3. 点「**恢复此版本**」→ 系统把当前草稿与线上都切回 v2 的配置
4. 确认后重新发布生效

```yaml
# 回滚策略示意
rollback_policy:
  trigger: gpt_score_drop > 0.3  # 配合第 26 章评估
  target: last_stable_version    # 上一个达标版本
  action: restore_and_republish
```

## 3. 草稿与线上的隔离

Dify 区分**草稿（Draft）** 与**已发布（Published）**：你在草稿里随便改，不影响线上用户；确认无误再发布成新版本。回滚也是把线上切到旧快照，草稿不受影响。

<Callout type="warn" title="回滚不自动恢复知识库">
应用版本只存提示词/工作流/配置，**不存知识库内容**。若问题出在知识库（如误删文档），需配合知识库的备份单独恢复。
</Callout>

## 4. 与评估联动

最稳的节奏：改一版 → 跑第 26 章的评估 → 分数达标才发布 → 否则丢弃草稿。把版本、评估、回滚串成一条「安全迭代流水线」。

<Callout type="exercise" title="动手做">
在测试应用里故意发布一个「会答错」的版本，然后用版本历史恢复回上一版，确认线上行为恢复正常，体验完整回滚流程。

**第 3 步：回滚**

```text

2. 版本列表：

     v1  2026-08-02 14:10  基线版本
3. 在 v1 上点「更多」→「恢复此版本」
4. 系统提示「恢复后当前草稿将被覆盖」→ 确认
5. 此时草稿已变回 v1 的配置，但线上还是 v2
6. 点「发布更新」，备注：v3 回滚至 v1 配置（v2 存在幻觉问题）
```

**第 5 步是最容易踩的坑**：「恢复此版本」只是把**草稿**还原成旧配置，**线上并不会自动变**。必须再点一次「发布」才真正生效。很多人恢复完就以为搞定了，结果用户看到的还是坏版本。

```bash
# 输出恢复为：抱歉，我在资料中没有找到相关信息…… ✅
```

再跑一次评测集确认指标回到基线：

```text
gpt_score 2.8 → 4.2   幻觉数 3 → 0   ✅ 已恢复
```

**回滚后的版本历史长什么样**

```text
v3  2026-08-02 15:52  回滚至 v1 配置（v2 存在幻觉问题）  ← 当前线上
v2  2026-08-02 15:30  提升亲和力
v1  2026-08-02 14:10  基线版本
```

**注意回滚产生的是一个新版本 v3，而不是删除 v2**。这是好事——历史是完整、可追溯的，v2 还留在那里，将来想分析「当时到底改坏了什么」随时能对比。

**演练要验证的几个关键认知**

| 问题 | 答案 |
|---|---|
| 恢复版本会立刻影响线上吗？ | ❌ 不会，必须再发布一次 |
| 恢复会覆盖当前草稿吗？ | ✅ 会。草稿里未发布的改动**会丢失** |
| 回滚会恢复知识库内容吗？ | ❌ 不会（正文 warn） |
| 回滚会恢复模型供应商配置吗？ | ❌ 不会，那是工作区级设置 |
| 回滚会影响正在进行的会话吗？ | 新消息用新配置，已有会话历史不变 |
| API Key 需要更换吗？ | ❌ 不需要，Key 与版本无关 |

**第二项要特别小心**：如果你正在草稿里写一个新功能，写到一半线上出事需要回滚，「恢复此版本」会把你的草稿覆盖掉。正确做法是**先把当前草稿发布成一个版本**（哪怕备注写「WIP 暂存」），再执行恢复。

**版本快照包含什么、不包含什么**

```text
✅ 包含（回滚能恢复）
   提示词、开场白、建议问题
   变量定义
   工作流画布结构与所有节点配置
   模型选择与参数（温度、max tokens）
   关联的知识库「引用关系」与检索参数
   工具挂载配置
   Agent 策略与迭代次数

❌ 不包含（回滚恢复不了）
   知识库里的文档与向量数据      ← 最常见的误解
   模型供应商的 API Key
   工作区成员与权限
   会话日志与标注数据
   应用的 API Key
```

**正文那条 warn 的完整含义**

假设线上出问题的原因是「有人误删了知识库里的 20 篇文档」，那么无论你怎么回滚应用版本都没用——应用配置本来就是对的，坏的是数据。这时候需要的是第 23 章的**知识库/数据库备份恢复**。

所以排障时第一件事是**判断问题出在配置还是数据**：

```text
用户反馈「答不上来了」
   │
   ├─ 展开引用与归属，有召回吗？
   │   ├─ 有召回但答得不对 → 配置问题 → 回滚应用版本
   │   └─ 完全没召回      → 数据问题 → 查知识库文档是否还在、索引状态是否正常
   │                                   → 需要恢复数据备份，回滚应用版本无用
   └─ 直接报错 → 查模型供应商是否正常（Key 过期、余额不足、服务商故障）
                 → 这也不是回滚能解决的
```

**给生产环境的版本管理规范**

```text
□ 版本备注写「改了什么 + 为什么」，不要写「更新」「优化」这种废话
□ 一个版本只做一类改动（正文 tip），便于二分定位问题
□ 发布前必跑第 26 章评测集，不达标不发布
□ 维护一个「已知稳定版本」标记，出事直接回它，不用现场判断
□ 重大改动先灰度：WebApp 权限设为「指定成员」，小范围验证后再放开
□ 回滚决策要快：线上出现幻觉或报错，先回滚止血，再慢慢查原因
□ 回滚后补一条评测用例，防止同类问题复发
```

**最后一条是闭环的关键**。这次 v2 因为删了拒答约束而翻车，回滚之后应该往评测集里加一条专门检验拒答的用例。这样下次再有人想「提升亲和力」时，评测会立刻拦住他。

这就把第 15 章（日志发现问题）、第 26 章（评估量化）、第 27 章（版本回滚）串成了完整的安全迭代闭环：

```text
上线 → 日志/告警发现问题 → 回滚止血 → 定位根因
  → 补充评测用例 → 修复 → 评估达标 → 重新发布
  → 该用例永久留在回归集里，防止复发
```

## 小结

- 每次发布生成不可变版本快照，可随时回退
- 回滚恢复的是提示词/工作流配置，不含知识库
- 草稿隔离线上，确认后再发布
- 版本 + 评估 + 回滚构成安全迭代闭环
