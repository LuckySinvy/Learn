# 知识库索引进阶

第 4、5 章讲了基础切片与检索参数。但真实文档往往很长、层级很多：用固定长度切片会把一个完整流程「切断」，召回时只拿到半截。本章讲两个进阶武器——**父子分段**与**检索调优**。

## 1. 为什么普通分段会丢上下文

固定长度分段（如每段 500 字）存在两难：

- 段太长 → 噪音多、向量被稀释
- 段太短 → 缺少前后文，模型看不懂

文档天然有「章节 → 小节 → 段落」的层级。**父子分段（Parent-Child Chunking）** 利用这层结构解决矛盾。

## 2. 父子分段的原理

- **父片段**：按文档逻辑结构（标题、段落）切出较大的块，保留完整语义
- **子片段**：在父块内再细切成小块用于**向量检索**（更易命中）
- 检索时先用子片段匹配，命中后**返回对应的父片段**给模型

```yaml
# 父子分段配置示意
indexing_technique: "parent_child"
parent:
  chunk_size: 1000
  separator: ["\n## ", "\n### "]
child:
  chunk_size: 200
  overlap: 20
retrieve: child_match_then_return_parent
```

<Callout type="tip" title="父子分段适合手册类文档">
产品手册、政策制度、API 文档这类「层级清晰、单点问题对应大段说明」的资料，父子分段能同时保证召回精度与上下文完整，强烈推荐。
</Callout>

## 3. 混合检索权重调优

开启混合检索后，向量得分与关键词得分需要融合。语义问法多 → 调高向量权重；编号、专有名词多 → 调高关键词权重。

```yaml
retrieval_mode: hybrid
weights:
  semantic: 0.7
  fulltext: 0.3
rerank:
  enabled: true
  model: bge-reranker-v2-m3
  top_n: 5
```

## 4. 重排与阈值联动调优

粗召回一批候选（如 20 个）→ 重排模型精排 → 取 TopN → 再按相似度阈值过滤。三步联动，常见基线：粗召回 20、重排取 5、阈值 0.5。

<Callout type="warn" title="不要同时卡死重排和阈值">
重排已把最相关的顶到前面，若再设很高阈值，可能把本应召回的答案过滤掉。重排开启时阈值宜放宽（0.4–0.5）。
</Callout>

**问题设计：什么叫「跨小节问题」**

这是本实验的关键。跨小节问题指的是**答案的完整性依赖上下文，而不是某一句话**：

| 类型 | 示例 | 为什么能区分两种分段 |
|---|---|---|
| 完整流程类 | 「报销的完整流程是什么？」 | 流程步骤分布在多个段落，固定分段会切断 |
| 前提依赖类 | 「什么情况下需要总监审批？」 | 条件在小节开头，具体规则在后面 |
| 例外条款类 | 「有哪些不能报销的情形？」 | 「但以下情形除外」后面跟一串列表 |
| 表格类 | 「不同职级的差旅标准？」 | 表头与数据行常被切散 |
| 指代类 | 「上述材料需要几份？」 | 「上述」指代前文，切断后完全无法理解 |

反例：「公司名称是什么？」这种单点事实问题，两种分段都能答对，测不出差异。

**记录表**

```text
| # | 问题             | 库A完整度 | 库A片段可读 | 库B完整度 | 库B片段可读 | 说明 |
|---|------------------|-----------|-------------|-----------|-------------|------|
| 1 | 报销完整流程     | 2/5 缺后半| 否，断在第3步| 5/5      | 是          | 典型差异 |
| 2 | 何时需总监审批   | 3/5       | 部分        | 5/5       | 是          | 前提被切走 |
| 3 | 不可报销情形     | 2/5 只列3条| 否         | 4/5 列7条 | 是          | 列表被截断 |
```

「片段可读性」的判断方法：展开「引用与归属」，**把召回的片段单独读一遍**，问自己「不看原文，这段话能看懂吗」。这是父子分段最直观的收益点。

**预期结果**

| 指标 | 固定分段 | 父子分段 |
|---|---|---|
| 答案完整度（10 题均分） | 约 2.5–3.5 | 约 4.0–4.8 |
| 片段自洽率 | 低，常见半句话、孤立列表项 | 高，基本是完整小节 |
| 流程/列表类问题 | 差异最大，经常只给出前半截 | 明显更好 |
| 单点事实问题 | 与父子分段基本持平 | 无明显优势 |
| 送入模型的 token | 较少 | **明显更多**（返回的是父块） |
| 索引耗时与存储 | 基准 | 略高（子块数量更多） |

**父子分段为什么有效——一句话原理**

```text
检索用小块（200 字）  → 语义聚焦，向量不被稀释，容易精准命中
送模型用大块（1000 字）→ 上下文完整，模型能看懂前因后果

即：用「小块的检索精度」换到「大块的上下文完整度」，
    而普通分段只能在这两者之间二选一。
```

这正是正文开头那个「段太长噪音多、段太短没上下文」两难的解法。

**注意父子分段的代价**

不是没有成本，实测中你会明显感觉到：

1. **Token 消耗上升明显**。TopK=4 时，固定分段送 4×500=2000 字，父子分段送 4×1000=4000 字，直接翻倍。所以**开启父子分段后，TopK 应当调小**，从 4 降到 2–3 通常就够了。
2. **可能出现父块重复**。多个子块命中同一个父块时，若系统不去重，同一段内容会被送两遍，白白浪费 token。检查「引用与归属」里有没有重复内容，有的话就把 TopK 调更小。
3. **父块过大会稀释重点**。父块设 2000+ 字时，模型可能在长文里「迷失中间」（lost in the middle），关键信息在中段反而容易被忽略。父块建议控制在 1000–1500 字。

**推荐配置组合**

```yaml
# 父子分段的配套检索参数
分段:
  父块: 1000-1200 字（按 "\n## " 或段落切）
  子块: 200-250 字，重叠 20-30
检索:
  模式: 混合检索
  TopK: 3            # 比固定分段时小
  相似度阈值: 0.4     # 开 rerank 时放宽，见正文 warn
  Rerank: bge-reranker-v2-m3
```

**什么时候不要用父子分段**

| 场景 | 原因 | 更好的选择 |
|---|---|---|
| FAQ 库（一问一答，本身就短） | 每条已经自洽，父块没意义 | 固定分段，一条一段 |
| 文档无标题、无段落结构 | 父块切不出有意义的边界 | 固定分段 + 大重叠 |
| 上下文窗口紧张 / 成本敏感 | 父块 token 翻倍 | 固定分段 + rerank |
| 只做关键词精确查找 | 语义完整性不重要 | 经济索引即可 |

**延伸：还有一种做法叫 Q&A 分段**

Dify 还提供「Q&A 模式」分段——用 LLM 把每段文档自动转成若干「问题-答案」对，用问题去做向量匹配。

```text
原文：报销需在费用发生后 30 日内提交，逾期需部门总监审批。

自动生成：
  Q: 报销的时限是多久？        A: 费用发生后 30 日内提交。
  Q: 超过报销时限怎么办？      A: 需要部门总监审批。
```

优势是**问题与问题的向量匹配度远高于问题与陈述句**，FAQ 类场景召回率很高。代价是建库时要对每个片段调用一次 LLM，**成本和耗时都显著增加**，且质量取决于生成问题的模型。

三种策略的选择：

```text
文档层级清晰、内容较长  → 父子分段
FAQ / 客服知识库        → Q&A 分段
结构松散 / 成本敏感     → 固定分段 + 混合检索 + rerank
```

**实验之外的建议**

分段策略是**建库时决定**的，改了就得**重新索引整个知识库**（耗时且花钱）。所以务必按第 4 章那条 tip——先用一份 10–20 页的小文档把策略试对了，再批量导入几百份文档。在小样本上多花半小时，能省下大规模返工的几个小时。

## 小结

- 父子分段：子片段检索、父片段送模型，兼顾精度与上下文
- 混合检索靠权重平衡语义与关键词
- 重排 + 阈值联动，重排开时阈值宜放宽
