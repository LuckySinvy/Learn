# 多模型路由与负载

第 13 章讲了如何接入多种模型供应商。但「接进来」只是第一步——生产里你希望**不同任务用最合适的模型**，并且在某个供应商抖动能自动切换。本章讲路由与容灾。

## 1. 为什么需要路由

- **成本**：简单分类用便宜小模型，复杂生成才用大模型
- **质量**：中文问答用本土模型，代码用强推理模型
- **可用**：单一供应商限流/故障时，有备用通道不中断

## 2. 按任务类型路由

用工作流的「分类节点 + 条件分支」实现：先判断任务类型，再选模型。

```text
[Start] → [分类 LLM] 输出 task_type
  → IF task_type == "分类"  → 用 小模型A（便宜）
  → IF task_type == "创作"  → 用 大模型B（强）
  → ELSE                    → 用 默认模型C
```

```yaml
# 路由策略示意
routing:
  - match: "简单分类"
    model: gpt-3.5-equivalent
  - match: "长文创作"
    model: flagship-large
  - match: default
    model: flagship-mid
```

<Callout type="tip" title="给每条路由设成本画像">
在配置里记录每个模型的单价与延迟，路由时不仅看「能不能做」，也看「划不划算」。高频简单任务尽量下沉到小模型，成本能降一截。
</Callout>

## 3. 故障转移（Fallback）

主模型调用失败或超时时，自动切到备用模型，对用户无感知。

```yaml
fallback_chain:
  primary: model-b
  on_error: [model-c, model-a]
  timeout_ms: 8000
  retry: 1
```

<Callout type="warn" title="Fallback 要验证输出兼容">
不同模型的输出格式、语气可能不同。若下游依赖固定结构（如 JSON），切换到备用模型后仍需走同一套解析与兜底，避免格式突变导致流程崩。
</Callout>

## 4. 负载与限速

多应用共用模型配额时，用中间代理做统一限速与排队，避免互相踩踏：

```text
请求 → 模型网关（限流/排队）→ 具体供应商
            ↑ 监控各供应商剩余配额，超阈值则优先走有额度的通道
```

<Callout type="exercise" title="动手做">
在你的工作流里加一个分类节点，把输入分为「简单/复杂」两类，分别接不同模型节点，运行几条样例，观察是否按预期走了不同模型。

**关键设计：分类器必须用便宜模型**

这是整个路由方案成立的前提。如果用 GPT-4o 做分类，那「省钱」就无从谈起了——分类本身的成本会吃掉路由带来的节省。

```text
分类节点配置：
  模型: qwen2.5:7b（本地，边际成本近零）或 gpt-4o-mini
  温度: 0
  最大 tokens: 5        # 只输出一个词，卡死上限防止啰嗦

SYSTEM:
你是任务复杂度分类器。判断用户输入属于哪一类，只输出一个英文单词。

simple  = 事实查询、简单问答、格式转换、翻译、闭合式问题
          （答案明确、无需多步推理、不需要查阅资料）
complex = 多步推理、方案设计、代码生成与调试、需要检索公司资料、
          涉及权衡取舍或多条件判断

规则：
- 只输出 simple 或 complex，全小写，不要标点、不要解释。
- 无法判断时输出 complex（宁可贵一点，也不要答错）。

USER:
{{#start.user_input#}}
```

**「无法判断时输出 complex」这条规则很重要**：路由的失败方向应该是「多花点钱」而不是「答得不好」。用便宜模型答错一个复杂问题，用户流失的成本远高于省下的那几分钱。这是路由策略的**默认安全方向**。

**加固：规整分类结果**

和第 21 章一样，加一个代码节点防止 LLM 输出格式抖动：

```python
def main(raw: str) -> dict:
    s = (raw or "").strip().lower()
    if "simple" in s:
        return {"route": "simple"}
    return {"route": "complex"}   # 兜底走贵的，安全方向
```

**两个分支的模型配置**

```yaml
# simple 分支
模型: qwen2.5:7b（本地 Ollama）
温度: 0.3
上下文: 不接知识库
SYSTEM: 简明扼要回答用户问题，不超过 100 字。

# complex 分支
模型: gpt-4o
温度: 0.3
上下文: 接知识库（TopK=4，混合检索）
SYSTEM: 依据【上下文】详细回答，需要时分步骤说明，标注资料来源。
```

**测试样例（要包含边界用例）**

```text
预期 simple：
  1. 「你们的客服电话是多少？」
  2. 「把『你好』翻译成英文」
  3. 「今天星期几？」

预期 complex：
  4. 「我们团队 30 人，需要 SSO 和私有化部署，该选哪个版本？为什么？」
  5. 「这段 Python 报 KeyError，帮我分析原因并给修复方案」
  6. 「对比一下你们的退款政策和行业惯例有什么差异」

边界用例（观察分类器怎么判）：
  7. 「你们支持导出 PDF 吗？」   ← 看似简单，但需要查知识库
  8. 「在吗？」                  ← 闲聊
```

**用例 7 是最有价值的观察点**。它字面上是个闭合式问题（像 simple），但答案在知识库里（需要 complex 分支的检索）。如果分类器把它判成 simple，小模型没有知识库就只能瞎猜。

这暴露了一个设计问题：**「复杂度」和「是否需要检索」是两个不同的维度**，不该用一个分类器混着判。改进方案是分两级：

```text
第一级：是否需要检索知识库？（need_retrieval: yes/no）
第二级：推理复杂度如何？    （complexity: simple/complex）

组合成四种路由：
  no  + simple  → 小模型，不检索        （闲聊、翻译）
  yes + simple  → 小模型 + 检索          （事实查询，最常见）
  no  + complex → 大模型，不检索         （代码生成、方案设计）
  yes + complex → 大模型 + 检索          （最贵，但也最少）
```

这个改进能进一步降本——「事实查询」占了客服场景的大头，它需要检索但不需要强推理，用小模型 + 检索完全够用。

**成本测算（这才是路由的意义）**

假设日均 1000 次请求，实测分布 simple 占 70%、complex 占 30%：

```text
方案一：全部用 gpt-4o
  1000 × 约 1500 tokens = 150 万 tokens/天

方案二：路由
  分类开销   1000 ×   80 tokens =   8 万（本地模型，成本≈0）
  simple 700 ×  200 tokens =  14 万（本地模型，成本≈0）
  complex 300 × 1500 tokens =  45 万（gpt-4o）
  → 付费 token 从 150 万降到 45 万，约降 70%

同时平均延迟也从 3.5s 降到约 1.6s
（70% 的请求走本地小模型，快得多）
```

**路由不只省钱，还降延迟**——这点经常被忽略。大部分简单请求不再排队等大模型，整体体验反而更好。

**故障转移（Fallback）怎么在 Dify 里做**

Dify 的 LLM 节点本身有重试配置，但跨模型的 fallback 需要手动搭：

```text
[LLM-主模型 gpt-4o]
      │
      ├─ 成功 ──────────────────────┐
      └─ 异常分支（节点右侧红点）    │
             │                       │
             ▼                       │
      [LLM-备用 qwen-max] ───────────┤
                                     ▼
                          [变量聚合器: answer]
```

在 LLM 节点的「异常处理」里选择「失败时继续」，就会多出一条异常分支线，把它连到备用模型节点即可。

配套配置：

```yaml
主模型节点:
  超时: 8000ms          # 不能太长，否则用户等不及
  重试次数: 1            # 瞬时抖动重试一次
  失败处理: 走异常分支    # 而非中断整个工作流
备用模型: 选择不同供应商   # 关键！同一供应商挂了，切它家的另一个模型没用
```

**最后一点尤其重要**：fallback 的备用模型必须来自**不同供应商**。OpenAI 挂了，你 fallback 到 `gpt-4o-mini` 一样调不通。正确的做法是 OpenAI → 通义 / DeepSeek，或者云端 → 本地。

**正文那条 warn 的实践**

不同模型的输出风格差异很大，如果下游要解析 JSON，切换模型后可能格式就变了。两个应对手段：

```python
# 1. 统一的容错解析，两条分支共用
import json
import re


def main(raw: str) -> dict:
    s = (raw or "").strip()
    # 剥离 markdown 代码围栏和前缀说明
    m = re.search(r"\{.*\}", s, re.S)
    if not m:
        return {"ok": False, "data": {}, "raw": s}
    try:
        return {"ok": True, "data": json.loads(m.group(0)), "raw": s}
    except json.JSONDecodeError:
        return {"ok": False, "data": {}, "raw": s}
```

```text
# 2. 备用模型的提示词要更啰嗦
主模型（能力强）：以 JSON 返回，格式：{...}
备用模型（能力弱）：
  只输出 JSON，不要 markdown 代码块，不要任何前缀说明，
  不要解释。第一个字符必须是 {，最后一个字符必须是 }。
  格式严格如下：{...}
```

**常见坑**

| 现象 | 原因 | 解决 |
|---|---|---|
| 所有请求都判成 complex | 分类提示词偏保守 / 温度不是 0 | 温度设 0，补充 simple 的正例 |
| 分类节点输出「simple。」带标点 | 没限制输出格式 | 加规整代码节点 |
| 省钱效果不明显 | 分类器本身用了贵模型 | 分类必须用最便宜的模型 |
| simple 分支答案质量差 | 把需要检索的问题分错了 | 改用「是否需检索 + 复杂度」二维路由 |
| fallback 没生效 | LLM 节点没开「失败时继续」 | 在节点的异常处理里配置 |
| 两条分支输出汇不到 End | 缺变量聚合器 | 补聚合器节点 |
</Answer>
</Callout>

## 小结

- 路由按任务类型选模型，兼顾质量与成本
- Fallback 链提供故障转移，但要保证输出兼容
- 用模型网关统一限流与配额管理
