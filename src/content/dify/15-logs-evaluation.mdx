# 日志、标注与评估

上线不是终点。**会话日志 + 用户标注 + 效果评估** 才是 Dify 持续迭代的飞轮。本章讲怎么用数据驱动优化。

## 1. 会话日志

「**日志**」页记录每一次真实对话：

- 用户输入、模型完整输出
- 实际注入的上下文（知识库片段）
- 使用的模型、耗时、token 消耗
- 调用了哪些工具、返回什么

```text
会话 #204
  用户：退款要几天？
  检索命中：[退款政策 §3, 退款政策 §5]
  模型：一般 3–5 个工作日……
  耗时：1.8s  token：820
```

<Callout type="tip" title="从日志里找失败模式">
定期翻日志，专门找「答非所问 / 答错 / 没用到知识库」的会话。它们是最有价值的优化线索，比拍脑袋改提示词管用得多。
</Callout>

## 2. 用户标注（Annotation）

Dify 支持「标注」机制：当模型答错或不够好，人工给出**标准答案**。

```text
原回答：……
标注正确回答：「退款通常在 3 个工作日内原路退回。」
状态：已标注（待用于评估/训练）
```

标注数据有两个用途：

- 作为**评估基准**：新版本回答是否接近标注
- 作为**改进素材**：反馈给提示词优化或知识库补充

## 3. 效果评估

Dify 提供评估能力，用标注集或自动指标衡量质量：

| 维度 | 说明 |
|---|---|
| **命中率** | 知识库是否召回了相关片段 |
| **回答相关性** | 输出是否贴合问题 |
| **标注一致性** | 与人工标准答案的吻合度 |
| **成本/延迟** | token 与响应时间 |

<Callout type="warn" title="没有评估别乱改">
每次只改一个变量（提示词 / 检索参数 / 模型），用同一批标注问题跑评估对比。同时改多处，你永远不知道是哪个改动起了作用。
</Callout>

## 4. 迭代闭环

```text
上线 → 收集日志/标注 → 发现失败模式
  → 改提示词/补知识库/调检索
  → 用标注集评估对比
  → 效果好则发布，不好则回滚
```

这是一个持续循环，让应用随真实使用越来越准。

## 5. 导出与复用

- 日志可导出，用于离线分析或构建评测集
- 标注可沉淀为回归测试集，每次大改前先跑一遍
- 好的知识库补充（文档更新）应同步回第 4 章的知识库

| # | 失败类型 | 在日志里怎么识别 | 根因通常在哪 |
|---|---|---|---|
| 1 | **检索未命中** | 展开日志看「引用与归属」为空，或分数都很低 | 知识库/检索参数（第 4、5 章） |
| 2 | **召回了但没用上** | 命中片段里明明有答案，回答却答非所问 | 提示词没强调「依据上下文」 |
| 3 | **幻觉编造** | 回答里的数字/路径在任何片段中都找不到 | 温度过高 + 缺少拒答约束 |
| 4 | **格式跑偏** | 要求列表却输出长段落，或 JSON 带前缀 | 输出格式约束太弱 |
| 5 | **多轮指代丢失** | 第二轮反问「您指的是什么」 | 记忆窗口太小或被截断 |

「日志 → 筛选 → 用户反馈为『踩』」是最快的入口；没有用户反馈时，就按耗时异常、token 异常高、或对话轮次特别多（用户反复追问 = 没答好）来筛。

**第二步：写标注答案**

日志里点开某条消息 → 右侧「添加标注」→ 填写你认为正确的回答。

标注答案要写成**理想输出的完整样子**，而不是简单一句对错评价：

```text
问题：退款一般几天到账？

退款时间因情况而异，建议您联系客服了解具体进度。   ← 正确的废话

标注答案：
退款将在审核通过后 3 个工作日内原路退回。
1. 微信/支付宝：1-3 个工作日
2. 银行卡：3-5 个工作日
若超过 7 个工作日未到账，请联系客服并提供订单号。
依据：《售后政策》第 3 条

失败类型：检索命中但未采用（类型 2）
```

给每条都标上「失败类型」，这是后面判断优化是否对症的关键。

**第三步：整理成可复用的评估集**

标注会存在 Dify 的标注库里（可开启「标注回复」直接命中同类问题），但做回归测试建议**另外维护一份结构化文件**：

```json
{
  "version": "v1",
  "created_at": "2026-08-01",
  "cases": [
    {
      "id": "E01",
      "query": "退款一般几天到账？",
      "expected_points": ["3 个工作日", "原路退回", "超时联系客服"],
      "must_not_contain": ["无法确定", "请联系客服了解"],
      "failure_type": "检索命中但未采用",
      "baseline_score": 2
    },
    {
      "id": "E02",
      "query": "你们支持比特币支付吗？",
      "expected_points": ["资料中未提及", "建议联系人工"],
      "must_not_contain": ["支持", "可以使用"],
      "failure_type": "幻觉编造",
      "baseline_score": 1
    }
  ]
}
```

**为什么用 `expected_points` 而不是「标准答案全文」**：模型每次措辞都不同，逐字比对必然全挂。判断标准应该是「**关键信息点是否都覆盖了**」+「**是否出现了不该出现的内容**」。这两条加起来足够客观，也能自动化。

**第四步：打分与对比**

每条按 0–5 打分，建议用这个量表（人工打分时保持一致性很重要）：

```text
5 = 信息点全覆盖，格式正确，无多余内容
4 = 信息点全覆盖，格式或措辞略有瑕疵
3 = 覆盖主要信息点，遗漏次要细节
2 = 只答对一部分，或答了但用户仍需追问
1 = 基本没答对，但至少没编造
0 = 编造了错误信息（最严重，比不回答更糟）
```

**注意 0 分的定义**：幻觉比拒答危害大得多。一个说「我不知道」的助手用户还能接受，一个自信地给出错误退款时效的助手会引发投诉。打分时要体现这个权重差异。

**第五步：改一次，跑一次**

严格遵守正文那条 warn——**一次只改一个变量**：

```text
| 轮次 | 改动内容              | E01 | E02 | E03 | E04 | E05 | 均分 |
|------|-----------------------|-----|-----|-----|-----|-----|------|
| 基线 | （未改动）            |  2  |  1  |  2  |  3  |  1  | 1.8  |
| v1   | 提示词加「依据上下文」|  5  |  4  |  2  |  3  |  1  | 3.0  |
| v2   | v1 + 温度 0.7→0.3     |  5  |  5  |  2  |  4  |  1  | 3.4  |
| v3   | v2 + 检索改混合+TopK5 |  5  |  5  |  5  |  4  |  1  | 4.0  |
| v4   | v3 + 记忆窗口 3→8     |  5  |  5  |  5  |  4  |  5  | 4.8  |
```

从这张表能读出很多信息：

- E01/E02 在 v1 就修好了 → 确认是提示词问题
- E03 直到 v3 改检索才好 → 确认是检索问题，改提示词是白费力气
- E05 直到 v4 才好 → 确认是记忆问题
- **如果 v2 改了温度但分数没动**，说明温度不是瓶颈，可以回滚这个改动

这就是「一次一个变量」的价值：**每一格都在告诉你根因在哪**。如果一次性把提示词、温度、检索、记忆全改了，最后分数从 1.8 涨到 4.8，你依然不知道哪个改动有用，也不知道有没有某个改动其实在拖后腿。

**第六步：让它变成常态**

- 评估集**只增不减**。每次线上发现新的失败模式，就补一条进去，慢慢从 5 条长到 50 条。
- 每次**发布前必跑**，分数不低于上一版才允许发布。这就是回归测试。
- 定期回看：某条 case 连续 10 个版本都满分，说明这个问题已经彻底解决，可以标记为「稳定」降低跑测频率。

**规模化：从人工打分到自动评估**

5 条可以人工看，50 条就受不了了。两条路径：

```python
# 路径 A：规则校验（快、免费、适合信息点明确的场景）
def evaluate(answer: str, case: dict) -> dict:
    hits = [p for p in case["expected_points"] if p in answer]
    bad = [p for p in case["must_not_contain"] if p in answer]
    return {
        "id": case["id"],
        "coverage": len(hits) / len(case["expected_points"]),
        "violated": bad,
        "passed": len(hits) == len(case["expected_points"]) and not bad,
    }
```

```text
# 路径 B：LLM-as-a-Judge（灵活、适合开放式回答）
用一个更强的模型当裁判：

你是答案评审员。请对比【标准要点】与【实际回答】，按 0–5 打分。
评分规则：
  5 = 要点全覆盖且无错误信息
  3 = 覆盖主要要点
  0 = 包含标准要点中不存在的事实性内容（幻觉）
只输出 JSON：{"score": 数字, "missing": [...], "hallucination": [...]}

【标准要点】{{expected_points}}
【实际回答】{{actual_answer}}
```

裁判模型要选**比被测模型更强的**，否则裁判自己就判不准。另外裁判本身也要抽样人工校验，别盲信。

**一个容易忽略的点：标注回复功能**

Dify 的标注除了当评估基准，还能直接开启「**标注回复**」——当用户问到相似问题时，直接返回你标注的答案，绕过模型。适合高频、答案固定、绝对不能出错的问题（如退款政策、营业时间）。相似度阈值建议设高一些（0.9+），避免误命中。

这相当于给 AI 加了一层「人工兜底缓存」，是很实用的生产技巧。

## 小结

- 日志揭示真实失败模式；标注沉淀标准答案
- 评估用命中率、相关性、一致性、成本多维度衡量
- 一次只改一个变量 + 固定评测集，避免盲目调参
- 形成「上线→标注→优化→评估」迭代飞轮
