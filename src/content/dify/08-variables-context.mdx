# 变量与上下文

静态提示词只能「一招鲜」。真实应用需要根据**用户输入、会话历史、外部数据**动态调整——这就要靠**变量（Variables）** 与**上下文（Context）**。本章把它们讲透。

## 1. 输入变量（Input Variables）

在编排页「变量」区定义变量，运行时由用户填写或由上游传入。

| 字段 | 说明 |
|---|---|
| 变量名 | 英文字符，如 `user_name` |
| 类型 | 文本 / 段落 / 下拉选择 / 数字 等 |
| 必填 | 是否必须提供 |
| 默认值 | 未填时使用 |

定义后在提示词中以 `{{user_name}}` 引用：

```text
欢迎你，{{user_name}}！我是你的 {{product_name}} 助手。
```

对话型应用里，变量可在开场时通过表单收集；文本生成型应用里，变量直接作为生成入参。

<Callout type="tip" title="用下拉减少无效输入">
像「语言偏好」这类有限枚举，用「下拉选择」变量比自由文本更可控，也能避免模型收到千奇百怪的值。
</Callout>

## 2. 会话上下文（Conversation Context）

对话型应用自带**会话记忆**，模型能记住本轮对话前文。Dify 把上下文管理能力可视化：

- **记忆窗口（Memory）**：保留最近 N 轮，避免无限增长撑爆上下文
- **对话角色前缀**：可定制「用户/助手」标签
- **上下文引用**：在提示词里可用特殊标记引用历史

```text
# 典型多轮效果
用户：帮我查订单 ORD-123
助手：该订单状态为「已发货」。
用户：那什么时候到？        ← 模型借助上下文理解「那」指上一单
助手：预计 2 天内送达。
```

<Callout type="warn" title="记忆窗口别设太大">
保留轮数过多会拉长每次请求的 token、增加成本与延迟；设太小又「忘性大」。一般 5–10 轮是平衡点，长文档场景优先靠知识库而非长记忆。
</Callout>

## 3. 上下文来源：知识库与外部

除了会话记忆，「上下文」还包括：

- **知识库片段**：第 5 章配置，检索后注入
- **变量注入**：用户/外部传入的结构化数据
- **工具返回**：工具调用结果（第 9、12 章）

它们共同组成模型「当前能看到的信息」。

## 4. 变量与上下文的配合示例

```text
系统提示：
你服务于 {{company}} 的 {{department}} 部门。
参考以下资料回答：
{{#context#}}     ← 知识库检索结果占位
历史对话已自动包含在上下文中。
```

这里 `{{company}}` 是输入变量，`{{#context#}}` 是知识库上下文占位，二者合一形成动态提示。

## 5. 调试与排错

- 预览窗口会显示「当前变量值」，确认替换是否正确
- 变量为空导致怪异输出 → 检查必填与默认值
- 上下文不相关 → 回到第 5 章调检索参数

<Callout type="exercise" title="动手做">
为第 6 章的应用增加两个变量：`user_name`（文本，必填）、`language`（下拉：中文/英文）。改提示词引用它们，验证不同输入产生不同问候。

<Answer>
**参考答案：**

**第一步：定义两个变量**

编排页「变量」区点「+ 添加」：

```yaml
# 变量 1
变量名（Key）: user_name
显示名称: 你的称呼
字段类型: 文本（Text）
必填: 是
最大长度: 20

# 变量 2
变量名（Key）: language
显示名称: 回复语言
字段类型: 下拉选择（Select）
必填: 是
选项:
  - 中文
  - 英文
默认值: 中文
```

**为什么 `language` 用下拉而不是文本**：枚举值固定时，下拉能杜绝用户输入「中文吧」「Chinese」「zh-CN」这类五花八门的值，模型收到的永远是两个确定字符串之一，行为才稳定。这正是正文那条 tip 的实践。

**第二步：在提示词中引用**

```text
# 角色
你是 Acme 公司的产品小助手，正在为用户 {{user_name}} 提供一对一服务。

# 语言规则
本次会话的回复语言为：{{language}}。
- 若为「中文」，全程使用简体中文回答。
- 若为「英文」，全程使用英文回答（English only），
  包括标题、列表项和提示语，不要中英混排。
- 无论哪种语言，专有名词（产品名、菜单名）保持原文不翻译。

# 称呼规则
- 首轮回答开头用一句话问候 {{user_name}}，之后不再重复问候。
- 若 {{user_name}} 未提供，则使用「您」，不要输出空白或花括号。

# 任务
依据【上下文】中的资料回答用户关于产品的问题；
资料中没有的内容，如实告知并建议联系人工客服。
```

**第三步：验证（四组用例）**

```text
用例 1：user_name=张三, language=中文
问：怎么导出数据？
期望：张三你好！可在「设置 → 导出」中完成……（简体中文）

用例 2：user_name=Alice, language=英文
问：怎么导出数据？
期望：Hi Alice! You can export via Settings → Export...（纯英文）

用例 3：user_name=张三, language=英文
问：怎么导出数据？
期望：Hi 张三! ...（人名保留原文，正文英文）

用例 4：user_name 留空
期望：表单直接拦截，提示「此项为必填」——根本进不到模型
```

**用例 4 是重点**：它验证的是「必填」在 UI 层就生效了，模型不会收到空值。这也解释了一个常见困惑——既然必填能拦住，为什么提示词里还要写兜底规则？因为**通过 API 调用时可以绕过前端表单**（第 14 章），`inputs` 里少传一个字段是完全可能的，所以双重保险仍有必要。

**观察点：变量到底怎么进入模型的**

在预览窗口右上角可以看到「**当前变量值**」面板；开启后每次对话下方也能展开查看实际拼装后的提示词。你会发现：

```text
渲染前：你正在为 {{user_name}} 提供服务，回复语言：{{language}}
渲染后：你正在为 张三 提供服务，回复语言：中文
```

变量替换发生在**提示词送进模型之前**，是纯字符串替换——模型并不知道有「变量」这回事，它只看到最终那段文本。理解这一点，很多问题就能自己排查了。

**变量、上下文、记忆的关系**

```text
最终送给模型的内容 = 系统提示（变量已替换）
                   + 知识库检索结果（{{#context#}} 位置）
                   + 最近 N 轮会话记忆
                   + 本轮用户输入
```

四者共同构成「模型当前能看到的信息」，也共同消耗上下文窗口。这就是正文警告「记忆窗口别设太大」的原因——记忆占得多，留给知识库片段的空间就少了。

**进阶：用变量控制记忆行为**

变量不只能用于问候语，还能驱动逻辑分支：

```text
若 {{language}} 为「英文」，在检索知识库时优先使用英文表述理解问题，
但引用资料时保留原文，并在回答中给出英文说明。
```

**常见坑**

| 现象 | 原因 | 解决 |
|---|---|---|
| 回答里原样出现 `{{user_name}}` | 变量名拼写不一致（大小写、下划线） | 核对「变量」区的 Key 与提示词完全一致 |
| 选了「英文」还是回中文 | 约束太弱，模型跟随用户提问语言 | 加「English only」「不要中英混排」等强指令 |
| 第二轮之后问候语重复出现 | 没写「之后不再重复问候」 | 补上轮次约束 |
| 变量改了但预览没变化 | 未点「保存」，或预览会话未重置 | 保存后点「重新开始」清空会话再测 |
</Answer>
</Callout>

## 小结

- 输入变量让提示词参数化；类型与默认值要设好
- 会话记忆靠记忆窗口控制，别无限拉长
- 上下文 = 记忆 + 知识库 + 变量 + 工具返回
