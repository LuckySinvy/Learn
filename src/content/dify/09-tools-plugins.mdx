# 工具与插件

纯靠模型「凭记忆回答」有限。给它**工具（Tools）**，它就能查天气、调内部接口、算数据——从「嘴炮」变成「能办事」。本章讲 Dify 的工具体系。

## 1. 工具是什么

工具是模型在回答时可**调用**的能力单元。Dify 在检测到需要时会自动（或在 Agent 模式下主动）调用工具，把结果拿回来继续推理。

工具的常见类型：

- **内置工具**：网页搜索、计算器、维基、当前时间等开箱即用
- **自定义 API 工具**：你自己的 HTTP 接口
- **插件（Plugins）**：社区/官方发布的扩展包，一键安装

<Callout type="info" title="对话型 vs Agent 的工具调用">
对话型应用：工具按你编排的「显式节点」触发。Agent 应用：模型根据情况**自主决定**是否调用、调哪个（第 12 章详述）。
</Callout>

## 2. 启用内置工具

在编排页「工具」区添加，例如「Web 搜索」：

```text
配置：
  工具：Web 搜索（如 Bing / SerpAPI）
  API Key：在对应服务商获取后填入
```

添加后，当用户问「今天天气怎么样」，模型会自动调用搜索并返回实时结果。

## 3. 自定义 API 工具

把你自己的后端能力暴露成工具。Dify 支持通过 **OpenAPI/Swagger 规范** 导入，或手动配置。

```yaml
# 自定义工具示例：查询订单状态
name: query_order
description: 根据订单号查询物流状态
method: GET
endpoint: https://api.internal.example.com/orders/{order_id}
headers:
  Authorization: Bearer {{api_token}}
parameters:
  - name: order_id
    in: path
    required: true
    type: string
```

配置后，Dify 会把它当作一个可调用的工具，模型/工作流即可引用 `query_order`。

<Callout type="warn" title="给工具写清楚 description">
模型的工具选择依赖你写的 `description`。描述含糊，模型就可能调错或漏调。写明「什么时候用、输入什么、返回什么」最关键。
</Callout>

## 4. 插件市场

Dify 的**插件（Plugins）** 生态提供现成能力：

- 各类模型服务商接入
- 第三方服务（如飞书、Slack 通知）
- 专用工具包（文档解析、图像生成等）

在「插件」页搜索安装，安装后即可在应用中启用，无需自己写封装。

## 5. 工具权限与安全

- 工具可配置**是否需审批**（高权限操作先人工确认）
- 内部 API 工具建议走**白名单 IP / 鉴权**，不要暴露公网
- 敏感工具（发邮件、改数据）优先放在 Agent 的受控流程里

<Callout type="tip" title="从小工具开始">
先接一个只读的查询类工具（如查订单）跑通调用链路，再考虑写操作类工具。写操作务必加审批与鉴权。
</Callout>

<Callout type="exercise" title="动手做">
给你的应用添加一个内置「Web 搜索」工具，问一个需要实时信息的问题（如「今天最新的 AI 新闻」），观察模型是否自动调用工具并引用结果。

<Answer>
**参考答案：**

**第一步：准备搜索服务的 API Key**

内置 Web 搜索工具本身不含搜索引擎，需要接一个搜索服务商。常见选择：

| 工具 | 免费额度 | 说明 |
|---|---|---|
| **Tavily Search** | 每月 1000 次 | 专为 LLM 设计，返回已清洗的摘要，最省事 |
| **SearXNG** | 无限（自建） | 开源元搜索，可 Docker 自部署，数据不出内网 |
| **SerpAPI** | 每月 100 次 | 结果最接近真实 Google |
| **Bing Search** | 需 Azure 订阅 | 企业环境常用 |

**第二步：授权工具**

「工具 → 找到对应工具 → 去授权」，填入 API Key 并保存。授权是**工作区级**的，配一次所有应用都能用。

**第三步：在应用中启用**

注意这里有个容易踩的坑——**对话型应用（Chatbot）默认不会自动调用工具**。要让模型自主决定调用，需要把应用切到 **Agent 模式**（编排页顶部有「聊天助手 / Agent」切换），或者直接用工作流编排显式调用。

```text
编排页 → 切换为 Agent → 「工具」区点「+ 添加」→ 选中已授权的搜索工具
Agent 策略：Function Calling（模型支持则优先选）或 ReAct
最大迭代次数：3–5
```

**第四步：提问并观察**

```text
问：今天最新的 AI 新闻有哪些？

预览窗口会依次展示：
  🔧 正在使用工具 tavily_search
     输入参数：{"query": "最新 AI 新闻 2026", "max_results": 5}
  ✅ 工具返回（可展开查看原始 JSON）
     [{"title": "...", "url": "...", "content": "..."}, ...]
  💬 模型基于返回结果生成的最终回答（含链接引用）
```

**这就是本练习的核心观察点**：回答上方多出了「**工具调用轨迹**」，能看到模型传了什么参数、工具返回了什么。这是排查工具类问题的唯一依据。

**必须做的对比实验**

再问一个**不需要实时信息**的问题，例如「什么是向量数据库？」

预期表现：模型**不调用工具**，直接凭内部知识回答。

这个对比说明了工具的调用机制——模型是根据工具的 `description` 和当前问题**自行判断该不该调**，而不是每轮都调。如果发现该调不调、或不该调也调，问题几乎都出在 description 上，这正是正文那条 warn 的含义。

**description 好坏对照**

```yaml
# 差：模型不知道什么时候该用
name: search
description: 搜索

# 好：说清「何时用、输入什么、返回什么、什么时候别用」
name: web_search
description: >
  当用户询问实时信息（今日新闻、当前股价、天气、最新版本号）
  或询问训练数据截止之后发生的事件时，使用本工具联网搜索。
  输入：query（中文或英文检索关键词，尽量具体）。
  返回：最多 5 条结果，每条含 title、url、content 摘要。
  注意：产品自身的功能与政策问题请优先查询知识库，不要用本工具。
```

最后那句「什么时候**别**用」经常被忽略，但它对减少误调用非常有效——尤其在同时挂载了知识库和搜索工具时，能避免模型放着现成资料不用、跑去联网。

**排查表：工具没被调用怎么办**

```text
1. 应用是否是 Agent 模式？普通聊天助手不会自主调用
   └─ 切到 Agent，或改用工作流显式编排

2. 模型是否支持 Function Calling？
   └─ 部分小参数量的本地模型不支持，会「假装」调用但实际没调
   └─ 换支持的模型，或把 Agent 策略改为 ReAct

3. 工具是否已授权且已在本应用中勾选？
   └─ 工作区里授权 ≠ 应用里启用，两步都要做

4. description 是否写清了触发条件？
   └─ 参考上面的「好」版本重写

5. 提示词是否明确允许使用工具？
   └─ 可加一句：「涉及实时信息时，请使用 web_search 工具查证后再回答」

6. 看工具调用轨迹里的报错
   ├─ 401/403 → API Key 无效或额度用尽
   ├─ 超时    → 网络不通（自部署环境常见，检查容器能否出网）
   └─ 参数错误 → 模型传的参数不符合工具定义，需细化参数 description
```

**安全提醒**

本练习用的是**只读查询类**工具，风险可控。若后续要接「发邮件」「改数据」这类写操作工具，务必按正文第 5 节：开启审批、走鉴权、限制在受控流程内。一个能自主发邮件却没有审批的 Agent，是很容易出事的。
</Answer>
</Callout>

- 插件市场扩展生态；工具的 description 决定调用准确率
