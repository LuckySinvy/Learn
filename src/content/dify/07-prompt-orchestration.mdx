# 提示词编排

提示词是应用的「灵魂」。Dify 把提示词工程变成可视化、可变量化的配置。本章讲清系统提示、角色设定与占位符三大件。

## 1. 系统提示（System Prompt）

系统提示定义模型的**身份、目标与约束**，出现在每轮对话最前面，对整体行为影响最大。

一个好的系统提示通常包含：

- **角色**：你是谁（如「资深技术支持工程师」）
- **目标**：要帮用户做什么
- **风格/约束**：语气、长度、禁忌（如「不知道就明说」）
- **输出格式**：是否用列表、是否带步骤

```text
你是一名严谨的「IT 支持助手」。
目标：帮助员工解决常见的电脑与账号问题。
要求：
1. 用中文，分步骤说明，必要时给出命令示例。
2. 涉及密码等敏感操作，提醒用户通过官方渠道处理。
3. 无法确认时，明确告知并建议提交工单。
```

<Callout type="tip" title="把约束写具体">
「回答要专业」太模糊。改成「用中文、分步骤、每条不超过 3 行、敏感操作给官方渠道」——越具体，模型越稳定。
</Callout>

## 2. 对话角色与多角色设定

对话型应用默认是「系统 + 用户 + 助手」三角色。Dify 支持在编排里指定：

- **开场白（Opening）**：首条助手消息，引导用户
- **建议问题（Suggested Questions）**：提供快捷提问按钮
- 可通过提示词让模型扮演特定人格或遵循特定应答模板

## 3. 变量占位符

提示词里可以用 `{{变量名}}` 引用**变量**，让同一段提示词适配不同输入。

```text
你正在为 {{user_name}} 提供服务。
他/她是 {{department}} 部门的员工。
请结合其部门特点，回答关于 {{topic}} 的问题。
```

运行时 `{{user_name}}` 等会被实际值替换（变量如何定义见第 8 章）。这让提示词从「写死」变为「参数化、可复用」。

<Callout type="warn" title="变量要兜底">
如果变量可能为空（如用户未填部门），在提示词里加一句「若未提供部门，按通用情况回答」，避免模型因空值产生奇怪输出。
</Callout>

## 4. 提示词模板进阶

- **Few-shot 示例**：在提示里放 1–3 个「问→答」样例，引导格式
- **结构化指令**：用编号、关键词（必须/禁止）强化约束
- **条件分支**：结合工作流（第 10 章）实现「不同输入走不同提示」

```text
示例：
问：怎么重置密码？
答：请访问 account.example.com/reset，用企业邮箱验证后设置新密码。
（遵循此格式回答类似问题）
```

## 5. 调试技巧

- 在预览窗口逐条测试边界问题（空输入、超长输入、敏感词）
- 用「**对话日志**」（第 15 章）回看模型实际收到的完整提示词
- 提示词改动后**保存再发布**，草稿态不影响线上

3. 涉及删除、重置、支付等不可逆操作时，先提示风险再给步骤。

2. 点击「导出」

**变量配置**

在编排页「变量」区新增：

```yaml
变量名: product_name
类型: 文本（Text）
标签: 产品名称
必填: 是
默认值: Acme Cloud     # 兜底，避免为空时提示词出现空洞
最大长度: 30
```

**为什么四段式有效**

| 段落 | 作用 | 少了会怎样 |
|---|---|---|
| **角色** | 锁定语气与专业深度 | 回答忽而口语忽而学术 |
| **目标** | 明确「做成什么算好」 | 模型自说自话、答非所问 |
| **约束** | 划定边界，防止编造与越权 | 出现幻觉、乱承诺 |
| **格式** | 固定输出结构，便于前端渲染 | 有时列表有时长段落，UI 难处理 |

**对比测试方法**

用同一批问题（≥5 条，含 1 条知识库外的边界问题）分别跑两版提示词，从四个维度打分：

```text
| 维度       | 改写前 | 改写后 | 说明                         |
|------------|--------|--------|------------------------------|
| 格式一致性 | 2/5    | 5/5    | 改写后步骤类问题一律有序列表 |
| 长度稳定性 | 2/5    | 5/5    | 200 字上限被严格遵守         |
| 拒答准确性 | 3/5    | 5/5    | 边界问题不再编造             |
| 信息密度   | 3/5    | 4/5    | 去掉了「很高兴为您服务」等废话 |
```

**关键结论**

- **提升最大的是「可预期性」而不是「聪明程度」**。模型本身没变，但输出从「每次都不一样」变成「基本可预测」——这对下游要解析结果的程序至关重要。
- **数字化的约束最有效**：「不超过 200 字」「不超过 6 步」「每步不超过 20 字」远胜于「简洁」。
- **Few-shot 示例是格式的最后一道保险**：即使前面的格式描述模型没完全理解，看到示例也能照猫画虎。1–3 个示例足够，放多了徒增 Token。

**变量的兜底写法**

正文提到变量要兜底。除了在变量配置里设默认值，也可以在提示词内加一句：

```text
若 {{product_name}} 为空或未提供，则统称「本产品」，不要输出空白或占位符。
```

**常见坑**

- 变量名写错大小写或拼写（`{{productName}}` vs `{{product_name}}`）→ 占位符原样输出到回答里，用户会看到一串花括号。改完务必在预览里确认替换成功。
- 约束之间**互相矛盾**（如既要求「详细展开」又限制「不超过 50 字」）→ 模型会随机挑一个遵守，表现为不稳定。写完通读一遍检查冲突。
- 提示词改了没点「保存」就去预览 → 测的还是旧配置。

## 小结

- 系统提示定义角色/目标/约束，是行为总开关
- 用 `{{变量}}` 让提示词参数化、可复用
- 具体约束 + Few-shot 示例能显著提升稳定性
