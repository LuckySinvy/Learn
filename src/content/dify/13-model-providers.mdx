# 接入大模型

Dify 把「用哪家模型」抽象成**模型供应商（Model Provider）**。接入后，所有应用都能像下拉菜单一样切换模型，无需改业务代码。本章覆盖主流接入方式。

## 1. 模型分类

Dify 区分三类模型，分别在不同的地方被使用：

| 类型 | 用途 | 例子 |
|---|---|---|
| **LLM（生成模型）** | 对话、生成 | GPT-4o、Claude、Qwen、本地模型 |
| **Embedding** | 知识库向量化 | text-embedding-3、bge-large-zh |
| **Rerank** | 检索重排 | bge-reranker |

<Callout type="info" title="三者可能来自不同供应商">
为了省钱，常见组合：生成用云端 GPT/通义，Embedding 与 Rerank 用本地中文模型。Dify 允许混搭，互不影响。
</Callout>

## 2. 接入 OpenAI

「设置 → 模型供应商 → OpenAI → 设置 API Key」：

```bash
# 环境变量方式（docker/.env），避免在前端明文
OPENAI_API_KEY=sk-xxx
OPENAI_API_BASE=https://api.openai.com/v1
```

添加后即可在应用中选择 `gpt-4o`、`gpt-4o-mini` 等，并配置温度、最大 token。

<Callout type="warn" title="密钥走环境变量更安全">
把 API Key 写进 `.env` 或部署 Secret，而不是在多人可见的 UI 里反复粘贴。轮换密钥时只改环境变量、重启即可。
</Callout>

## 3. 接入 Azure OpenAI

企业常用 Azure 以获得合规与区域部署：

```bash
AZURE_OPENAI_API_KEY=xxx
AZURE_OPENAI_ENDPOINT=https://your-resource.openai.azure.com
AZURE_OPENAI_API_VERSION=2024-02-01
# 还需在 UI 配置 Deployment 名称映射
```

Azure 的优势是数据留在指定区域、可走企业协议，适合合规要求高的场景。

## 4. 接入本地模型（Ollama / vLLM）

不想把数据出网？用本地推理：

```bash
# Ollama 启动一个模型
ollama pull qwen2.5:7b
ollama serve   # 默认 http://localhost:11434
```

在 Dify 选择「Ollama」供应商，填入 base URL：

```bash
OLLAMA_API_BASE=http://host.docker.internal:11434
# 若 Dify 与 Ollama 同主机 docker，用宿主机地址而非 127.0.0.1
```

```bash
# vLLM 提供 OpenAI 兼容接口
vllm serve Qwen/Qwen2.5-7B-Instruct --port 8000
# 在 Dify 以「OpenAI 兼容」类型接入，base 指向 http://host:8000/v1
```

<Callout type="tip" title="本地模型选型建议">
中文场景优先 Qwen2.5、ChatGLM、InternLM 等中文友好模型；Embedding 用 bge/m3e。注意本地模型对显存有要求，7B 模型约需 8–16GB 显存。
</Callout>

## 5. 验证与切换

- 接入后在编排页「模型」下拉应能看到新模型
- 用预览窗口发一条消息，确认调用成功
- 多模型对比：同一提示词切不同模型，观察质量/速度/成本

<Callout type="exercise" title="动手做">
分别接入一个云端模型（如 OpenAI）和一个本地模型（Ollama），在同一个应用里切换，对比回答质量与响应速度，选出你的默认模型。

<Answer>
**参考答案：**

**第一步：接入云端模型**

「设置 → 模型供应商 → OpenAI（或通义千问 / DeepSeek）→ 设置 API Key」。国内网络环境下，DeepSeek、通义、智谱通常比 OpenAI 更容易跑通，也更便宜，作为练习完全够用。

```bash
# 推荐写进 docker/.env 而非 UI 明文粘贴
OPENAI_API_KEY=sk-xxx
OPENAI_API_BASE=https://api.openai.com/v1
```

**第二步：接入本地 Ollama**

```bash
ollama pull qwen2.5:7b
ollama serve                      # 默认监听 11434
curl http://localhost:11434/api/tags   # 先在宿主机确认服务正常
```

在 Dify 中「模型供应商 → Ollama → 添加模型」：

```yaml
模型类型: LLM
模型名称: qwen2.5:7b              # 必须与 ollama list 显示的完全一致
基础 URL: http://host.docker.internal:11434
模型上下文长度: 32768
最大 token 上限: 4096
是否支持 Vision: 否
```

**这里是最容易卡住的地方**——Dify 跑在 Docker 里，`localhost` 指的是容器自己，不是宿主机：

| 环境 | 应填的 Base URL |
|---|---|
| macOS / Windows Docker Desktop | `http://host.docker.internal:11434` |
| Linux Docker | `http://172.17.0.1:11434`（docker0 网关）或宿主机内网 IP |
| Ollama 也在 Docker 且同一网络 | `http://ollama:11434`（用服务名） |
| Dify 源码本地运行（非容器） | `http://localhost:11434` |

Linux 下还需让 Ollama 监听所有网卡，否则容器连不上：

```bash
# systemd 环境
sudo systemctl edit ollama
# 加入：
# [Service]
# Environment="OLLAMA_HOST=0.0.0.0:11434"
sudo systemctl restart ollama
```

**第三步：设计对比测试**

用同一个应用、同一套提示词、同一批问题（≥8 条），只切换模型。问题要覆盖不同能力维度：

| 维度 | 示例问题 | 考察点 |
|---|---|---|
| 事实问答（带 RAG） | 「如何导出数据？」 | 能否老实用上下文 |
| 指令遵循 | 「用不超过 3 条列表回答」 | 是否守格式约束 |
| 中文表达 | 「解释什么是向量检索」 | 是否地道、有无翻译腔 |
| 拒答能力 | 知识库外的问题 | 会不会硬编 |
| 结构化输出 | 「以 JSON 返回」 | 格式是否可解析 |
| 长上下文 | 塞入 5 段资料再提问 | 是否遗漏中间内容 |

**记录表**

```text
| 问题 | 云端-质量 | 云端-首字延迟 | 云端-总耗时 | 本地-质量 | 本地-首字 | 本地-总耗时 |
|------|-----------|---------------|-------------|-----------|-----------|-------------|
| Q1   | 5/5       | 0.8s          | 2.1s        | 4/5       | 1.5s      | 6.3s        |
| Q2   | 5/5       | 0.7s          | 1.9s        | 3/5       | 1.4s      | 5.8s        |
```

耗时可以在「日志与标注」里看每条消息的详情，也可以直接掐表估。

**典型结论（7B 本地模型 vs 云端主流模型）**

| 维度 | 云端（如 gpt-4o-mini） | 本地 qwen2.5:7b |
|---|---|---|
| 回答质量 | 明显更强，尤其是多步推理 | 简单问答够用，复杂推理明显吃力 |
| 指令遵循 | 稳定守格式 | 偶尔跑偏，需要更啰嗦的提示词 |
| 结构化输出 | JSON 基本可靠 | 常带多余解释，需要加「只输出 JSON」 |
| Function Calling | 原生支持 | 7B 支持不稳，Agent 场景建议换 ReAct 或更大模型 |
| 响应速度 | 取决于网络，通常 1–3s | 取决于显卡；有 GPU 时快，纯 CPU 会很慢（10s+） |
| 成本 | 按 token 计费，量大时可观 | 一次性硬件成本，边际成本近零 |
| 数据安全 | 数据出网 | **完全不出内网** |
| 可用性 | 依赖外网与服务商 | 断网可用，但要自己保运维 |

**怎么选默认模型——不是二选一，而是分场景配**

正文提到 Dify 允许混搭，实践中最常见的是这样：

```yaml
# 系统模型设置（设置 → 模型供应商 → 系统模型设置）
系统推理模型: 云端模型        # 面向用户的主力，质量优先
Embedding 模型: bge-large-zh（本地）  # 调用量最大，本地跑省钱
Rerank 模型: bge-reranker-v2-m3（本地）
语音转文本: 按需
```

理由：**Embedding 是调用量最大、单次最简单的环节**，建一次知识库可能要跑几千次 embedding，放本地能省下最多的钱，而且质量差距很小。生成环节最考验模型能力，交给云端。

再按应用分别配：

- 面向客户的对话应用 → 云端强模型
- 内部工具、批量摘要、日志分类 → 本地模型（量大、容错高）
- 涉及敏感数据（合同、人事、医疗）→ **必须本地**，这是合规要求不是性能选择

**常见排错**

| 报错 | 原因 | 解决 |
|---|---|---|
| `Connection refused` | 容器访问 localhost | 换 `host.docker.internal` 或宿主机 IP |
| `model not found` | 模型名与 `ollama list` 不一致 | 名称含 tag，如 `qwen2.5:7b` 不能写成 `qwen2.5` |
| 本地模型响应极慢 | 没用上 GPU，在跑 CPU 推理 | `ollama ps` 看是否加载到 GPU；显存不足会回落 CPU |
| 云端 401 | Key 错误或额度耗尽 | 检查 Key 与账单 |
| 云端超时 | 网络不通 | 配代理，或改用国内服务商 |
| 切换模型后知识库检索失效 | 误改了 Embedding 模型 | **Embedding 模型一旦更换，已建的知识库必须重新索引**，因为向量维度和语义空间都变了 |

最后一条尤其重要，很多人在这里踩坑：**生成模型可以随便切，Embedding 模型不能随便切**。
</Answer>
</Callout>

## 小结

- Dify 统一管理 LLM / Embedding / Rerank 三类模型
- OpenAI 走 API Key；Azure 适合合规；本地 Ollama/vLLM 保数据不出网
- 密钥优先用环境变量；本地模型注意显存
- 应用内可随时切换模型做对比；下一步发布与 API 集成 →
